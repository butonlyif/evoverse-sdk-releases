Catalog Materials and How to Get Them

Applicable version: v1.0.0　Audience: every user who receives the Customer Package

What this page covers

The EvoVerse SDK's boards, reference designs, and IP materials are not distributed with the installation package. They live in the official Catalog release repository and are synced to your machine after you install the extension—no GitHub account is required. This page explains what the Catalog contains and how to sync; individual board specifications and datasheets are not expanded here—they are provided with the materials after you sync.

What the Catalog contains

Material category Description
Board definitions Core-module board data (used by natural-language project creation, pinout, and constraint generation)
Carriers and expansions Carrier board definitions and expansion interface information
Reference-design Jackets Complete reference projects you can create in one click (with specification and implementation notes)
Demo projects Sample projects for each board
IP materials IP cores and accompanying documentation distributed with the Catalog
Board documents Per-board specifications, datasheets, and reference-design notes (delivered locally with the sync)

Which boards, Jackets, and IP are currently offered is determined by the actual Catalog content after syncing; it is not statically enumerated in the delivery package.

How to get access

  1. Open the "Board Catalog" view on the left of Trae / VS Code and click refresh, or run the command EvoVerse: Sync Catalog.
  2. The sync pulls from the official public release repository (evoverse-catalog-release) by default—no GitHub account and no repository invitation are needed. When GitHub is unreachable (network errors), the sync automatically retries from the Gitee domestic mirror carrying the identical release; content and digest checks are unchanged, and the receipt records which repository actually served it.
  3. After the sync completes, the Welcome page and the Trae natural-language project flow can see every board, demo, and IP.

To use a self-hosted mirror or a private repository instead, override the repository URL with evoverse sync --repository <URL> or the EVOVERSE_CATALOG_REPOSITORY environment variable (priority: --repository > environment variable > default public repository; the Gitee fallback applies only to the default public repository—explicit overrides fail as-is). If a cache left by an older version still points to the previous address, re-running Sync rebuilds it automatically—no manual cleanup required.

Where the materials land after syncing

Materials install under the catalog/ directory of evoverse.home (default ~/evoverse-sdk):

  • catalog/boards/<board>/ — board data and the documents maintained alongside the board (specification, datasheet, reference-design notes)
  • Each sync writes the receipt catalog-sync-receipt.json, recording catalog_version and commit, so you can verify exactly what this round delivered

Run evoverse catalog status --json to see the current catalogVersion, commit, and treeDigest. The workspace pointer file .evoverse/catalog.json records the trusted material root (catalogRoot) and is refreshed on every sync.

Offline use (when the network is unreachable)

When the network is restricted or materials are delivered offline, online sync can be skipped entirely:

  1. Obtain the full catalog directory (with catalog.yaml, boards/, ips/) from EvoVerse operations.
  2. Copy it as the catalog/ directory under evoverse.home (default ~/evoverse-sdk).
  3. Reopen the window (or refresh the Board Catalog view). The SDK recognizes the directory automatically: status shows Catalog <version> (local) and boards, demos and IPs are all usable.

Customer-built material directories are supported the same way: include a catalog.yaml (evoverse import-local creates a minimal one on import).

Offline directories coexist with later online syncs: official entries overwrite same-path twins, customer-built material is never deleted.

The source field of evoverse catalog status --json tells them apart: local (offline/self-built, no official attestation) vs official.

Common statuses and issues

Symptom Explanation and handling
CATALOG_NOT_INSTALLED Not yet synced; this is expected. Follow the steps above and run Sync; offline environments see the Offline use section above
Sync failure (network) Fix the network and retry; the installed version is unaffected. The default public repository needs no GitHub authentication
A new version fails to sync but the local version is healthy A failed sync does not affect the existing local Catalog (only official entries are overwritten; local content is untouched); after checking the network, simply run EvoVerse: Sync Catalog again
The local catalog directory is corrupted Run EvoVerse: Sync Catalog again to rebuild it
Material updates After operations publishes a new Catalog, just Sync again; reinstalling the extension is unnecessary

Design notes

Keeping the materials out of the installation package is a deliberate decoupling design: the Catalog version evolves independently from the extension version, and syncing fetches the latest materials (with a treeDigest integrity gate). The Catalog syncs from the official public release repository by default with no GitHub account (switching automatically to the Gitee domestic mirror when GitHub is unreachable over the network); to use a self-hosted mirror or private repository, override it with --repository or the EVOVERSE_CATALOG_REPOSITORY environment variable. Board documents and board data evolve at the same version in the same repository, so the documents sync with the materials instead of being statically shipped in the package.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
