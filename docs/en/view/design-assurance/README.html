Design Assurance Rules and Evidence

EvoVerse Design Assurance

A zero-dependency, vendor-neutral Design Assurance engine: it runs deterministic rules and protocol-contract checks over RTL projects and produces reproducible JSON reports through a single evidence/exception mechanism.

  • Code: sdk/design-assurance/ (pure Python 3 standard library, no third-party dependencies)
  • Contract: the JSON Schemas under sdk/design-assurance/schema/ are the language-neutral public contract
  • Tests: python -m unittest discover -s sdk/design-assurance/tests -v

Status semantics: three states, not two

status Meaning
pass Every enabled rule passes or is covered by a valid exception
fail At least one structurally falsifiable violation exists
incomplete Behavioral properties (unverified) without evidence exist

Missing evidence is unverified, not pass. Temporal properties (such as handshake payload stability) cannot be proven by structural scanning; property-run evidence must be submitted. Without evidence, the report status is incomplete—it never passes silently.

Rule packs

Rule pack Contents
rtl-baseline@1 18 deterministic RTL baseline rules: 9 structural (latch, combinational loop, combinational blocking assignment, width truncation, derived clock, case completeness, reset polarity, default_nettype, multiple drivers) + 9 domain (synchronous reset release, reset to a known value, CDC synchronization property, CDC minimum stages, no bit-by-bit CDC bus synchronization, FSM default recovery, handshake payload stability, FIFO overflow protection, FIFO underflow protection)
amba.axis@1 AXI4-Stream contract: 6 static rules (binding validation, signal presence, signal direction, TDATA/TKEEP widths, sideband widths) + 5 behavioral rules (valid-stable, payload-stable, handshake = deadlock detection requiring at least one completed beat, reset-valid, beat-fields), plus directly bindable SVA assertion/cover assets
custom@1 User-defined regex rules (added via the rule manager, stored in assurance-rules.json)—declarative lint: full-text re.finditer over each source file; every match is reported as a violation (with line number). No built-in rules

Rule management (Rule Manager)

All rule switches are centralized in one global configuration file: <EVOVERSE_HOME>/assurance-rules.json (contract in sdk/design-assurance/schema/rule-config.schema.json). It applies to every assurance check (the CLI / MCP / the rule-management UI all read the same file).

{
  "version": 1,
  "enabled": true,
  "packs": { "rtl-baseline@1": true, "amba.axis@1": false },
  "disabledRules": ["rtl.comb.blocking"],
  "customRules": [
    {
      "id": "myteam.no-tabs",
      "description": "tabs are not allowed in RTL sources",
      "severity": "warning",
      "pattern": "\t"
    }
  ]
}
Field Semantics
enabled Master switch. false skips every rule—fail-closed: the report emits an engine.no-rule-packs unverified entry and status incomplete; it never impersonates pass
packs Per-rule-pack switch; absent means enabled
disabledRules Per-rule disabling (finer-grained than disabling a whole pack)
customRules User-defined regex rules, registered as the custom@1 pack and toggled by packs["custom@1"]

Custom-rule constraints: id must match ^[a-z][a-z0-9.-]*$ and must not collide with an entry in disabledRules; severity ∈ {error,warning,info}; pattern must be a compilable Python regex. Invalid configurations are rejected by the engine (CLI exit 64)—never silently downgraded.

UI: Welcome → Assure → Rule Manager

The evoverse.assuranceRules command (the Assure card on the Welcome page) opens the rule-management panel:

  • Master switch + per-pack switches + per-rule switches (with severity badges and rule descriptions)
  • Adding custom rules (id / severity / description / pattern, with client-side pre-validation) and deleting them
  • Save writes assurance-rules.json and reads it back through engine validation—errors the engine rejects (such as an invalid regex) are echoed with the engine's own error message; Reset restores the all-enabled default in one click
  • The configuration file path is shown in the panel header

Relationship to request-level disabledRules

The request JSON's disabledRules (see request.schema.json) is a per-run, temporary disable; the global configuration is merged into the request at the CLI/MCP entry point via apply_rule_config (global disables ∪ request disables). Inside the engine, the two are treated identically.

Requests (Assurance Request)

A request is a JSON document; the contract is sdk/design-assurance/schema/request.schema.json. Copyable template:

{
  "projectRoot": ".",
  "sources": ["rtl/axis_source.sv"],
  "rulePacks": ["amba.axis@1"],
  "interfaces": [
    {
      "id": "m_axis",
      "protocol": "amba.axis",
      "role": "master",
      "module": "axis_source",
      "clock": "clk_i",
      "reset": "rst_n_i",
      "resetPolarity": "active-low",
      "signals": {
        "tvalid": "m_axis_tvalid_o",
        "tready": "m_axis_tready_i",
        "tdata": "m_axis_tdata_o",
        "tlast": "m_axis_tlast_o",
        "tkeep": "m_axis_tkeep_o"
      },
      "widths": { "tdata": 32, "tkeep": 4 }
    }
  ],
  "evidence": [
    {
      "id": "sim-pass-1",
      "kind": "property-run",
      "status": "pass",
      "executor": "evoverse-sim",
      "executorVersion": "1.0.0",
      "artifact": "sim/m_axis.log",
      "propertyId": "evoverse_axis_m_axis_payload_stable"
    }
  ],
  "exceptions": [
    {
      "ruleId": "rtl.cdc.min-stages",
      "scope": { "module": "slow_sync" },
      "reason": "single-flop is acceptable for this debounce path",
      "expiresOn": "2026-12-31"
    }
  ]
}

Key points:

  • sources must be relative paths inside projectRoot; escaping the root is forbidden
  • interfaces binds protocol signals to module port names explicitly—the engine never guesses from port names
  • Property naming: evoverse_axis_<interface id sanitized>_<suffix> (for example evoverse_axis_m_axis_valid_stable)

Exception expiry forms

Every exception must provide exactly one expiry form, preventing exceptions from becoming permanent waivers:

  • expiresOn: an ISO date (YYYY-MM-DD); it lapses automatically once expired
  • untilRulePack: for example "rtl-baseline@2"; it lapses automatically when the rule pack is upgraded

An exception must carry an exact scope (exactly one of file / module / interface; wildcards forbidden) and a reason.

Evidence

  • status: pass | fail | error
  • kind must be a lowercase *-run form such as property-run / lint-run; only property-run can close a behavioral property
  • A pass evidence clears the corresponding unverified behavioral rule; a fail evidence escalates the behavioral rule to a violation, referencing executor / artifact / counterexample
  • No evidence at all → unverified, report incomplete
  • Scoping: a propertyId that is a rule id (such as rtl.handshake.payload-stable) applies only when the whole project has exactly one candidate module; in multi-module projects, qualify per module with propertyId=<rule id>@<module name>—one piece of evidence cannot close several modules at once
  • If interfaces is declared but the corresponding protocol pack (such as amba.axis@1) is not enabled, the report emits an engine.uncovered-interface unverified entry (fail-closed); it never passes silently

CLI

evoverse assurance check <project>
    [--request FILE] [--config FILE] [--format text|json]
    [--include-testbench] [--include-glob PATTERN] [--exclude-glob PATTERN]
evoverse assurance rules [--config FILE] [--format text|json]
  • When --request is omitted, check looks for <project>/.evoverse/assurance.json and then falls back to auto-discovering .v/.sv/.vh/.svh sources + rtl-baseline@1
  • --config defaults to <EVOVERSE_HOME>/assurance-rules.json (read only if present; absence means all rules enabled)
  • rules prints the rule catalog (all packs + each rule's switch state/severity/description; custom rules additionally include pattern)—the data source for the rule-management UI; --format text is the human-readable form
  • JSON goes to stdout only; diagnostics go to stderr only

Skipping testbenches during auto-discovery (default)

rtl-baseline@1 analyzes only the synthesizable subset; testbenches (initial/$task/#delay/@event) are out of scope. Auto-discovery skips testbench-style files per a default list:

Skipped form Description
Subtrees sim/, testbench/, tb/
Base names tb_*.*, *_tb.*, sim_*, test_*

Skipping happens only at the source-collection layer; the engine itself can still analyze those files. --include-testbench re-enables them; --include-glob PATTERN keeps only matching files (implicitly disabling the default testbench skip); --exclude-glob PATTERN stacks additional exclusions on top of the default list. The scanner skips whole initial ... end blocks as testbench material (recorded as info, never counted as unverified).

Exit-code contract

Exit code Meaning
0 pass (or normal output from the rules subcommand)
1 fail
2 incomplete
64 invalid request / usage (malformed request, missing project directory, no source files, invalid rule configuration)
70 engine failure (an internal engine exception; it never crashes silently)

Examples:

# Check a project (reads the global rule switches)
sdk/cli/evoverse assurance check my-project --request my-project/assurance.json --format json

# View the rule catalog and switch states
sdk/cli/evoverse assurance rules --format text

# Check with a specific configuration file (leaves the global config untouched)
sdk/cli/evoverse assurance check my-project --config team-rules.json

MCP

The MCP tool assurance_check is a thin adapter over the CLI (it duplicates no engine logic):

  • Inputs: project (required), request (optional), include_testbench (optional, default false), include_glob (optional, array of fnmatch patterns), exclude_glob (optional, array of fnmatch patterns); the format is fixed to JSON
  • Exit codes 1 (fail) and 2 (incomplete) still return the full JSON report; only 64/70 map to an MCP error
  • The testbench skip rules are identical to the CLI's --include-testbench / --include-glob / --exclude-glob
  • The legacy tool check_rtl_code_style keeps its original fields (violations / fileCount / totalLines / severity summary), adapting to the shared engine internally via legacy_style_report; unverified is never exposed as a violation

Reports

Reports are deterministic: the same request yields the same digest. Top-level fields: status / engineVersion / rulePacks / timestamp / digest / projectRoot / sourceCount / summary (errors/warnings/infos/unverified) / violations / unverified / exceptions / evidence. The contract is schema/report.schema.json.

Architectural position

Design Assurance is the executable home (single source of truth) of the design-principle rules: rules, evidence, and exceptions are all defined and adjudicated here; the Adapter and Catalog responsibilities are unchanged. See sdk/docs/SDK-ARCHITECTURE-VISION.md for details.

The legacy "code check" command in the editor and the MCP check_rtl_code_style are compatibility entry points only and no longer own rule implementations. Before vibe-coding generation, the rule-pack/config/interface digests are bound and the candidate RTL runs static Assurance first; the executable behavioral properties from incomplete enter the Test IR, and once Icarus, Questa, or Video Sim has produced qualified property evidence, this engine adjudicates them again. Functional simulation and Assurance must both be PASS before a parent module unlocks.

Video IP compliance

Video IP does not depend on the template-based generation entry. Once the frozen specification declares the evoverse.video@1 contract, Design Assurance independently validates the register interface, the port-group ordering, and the TJ180 BRAM line-buffer budget; with resource inputs missing, the report is incomplete—a pass is never inferred.

Dynamic properties (payload stability, AXIS handshake liveness) are permitted to be unverified in the test layer—by design they must be closed with simulation evidence (property-run).

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
