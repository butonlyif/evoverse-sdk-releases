Efinity Debugger Reference

Efinity Debugger Reference

Version: v1.0 | Based on Efinity 2026.1 (HLP-EFN-DBG-v2.0)

1. Debugger Overview

Efinity Debugger is a JTAG-based FPGA hardware debugging tool that provides two perspectives:

  • Profile Editor Perspective: the interface for manually configuring debug cores
  • Debug Perspective: the interface for observing probe signal values at runtime

The Debugger contains two kinds of debug cores: - Virtual I/O (VIO): supports probe inputs and outputs, emulating virtual IO - Logic Analyzer (LA): samples and captures internal signal waveforms

Minimum frequency requirement: the minimum operating frequency of a debug core is twice the JTAG TCK frequency.

Source: C:\Efinity\2026.1\debugger\doc\topics\hlp-dbg-intro.html

2. Debug Workflow

  1. Create a debug profile (VIO and/or LA cores)
  2. Generate the debug design file and add it to the project
  3. Compile
  4. Program the FPGA
  5. Run the Debugger GUI to observe probe values

3. Debug Profile JSON Format

A Debug Profile is a JSON file that defines the debug core configuration. Key structure:

{
    "debug_cores": [
        {
            "name": "vio0",
            "type": "vio",
            "uuid": "b60ce617846c46eb85bdb96be34cc1b0",
            "probes": [
                {"name": "counter", "width": 29, "init": null},
                {"name": "vio_reverse", "width": 1, "init": "0x0"}
            ]
        },
        {
            "name": "la0",
            "type": "la",
            "uuid": "55ccee6a763c4221a397cfa01e4fa0b2",
            "probes": [
                {"name": "counter", "width": 29, "probe_type": 1}
            ],
            "data_depth": 1024,
            "trigin_en": false,
            "trigout_en": false,
            "capture_control": false,
            "input_pipeline": 1,
            "auto_inserted": false
        }
    ],
    "session": {"debug_widget": [], "wizard": {}},
    "jtag_user": "USER1"
}

Key fields: | Field | Description | |-------|-------------| | debug_cores | Array of debug cores; may contain multiple VIO and LA cores | | type | Core type: "vio" or "la" | | uuid | 128-bit unique identifier, used for JTAG routing | | probes[].probe_type | LA probe type: 1 = Data and Trigger | | data_depth | LA buffer depth (uses on-chip RAM) | | trigin_en / trigout_en | Trigger input/output enable | | capture_control | Capture control enable (consumes more resources) | | auto_inserted | Whether generated automatically by the Debug Wizard | | jtag_user | JTAG USER TAP: "USER1" or "USER2" |

Source: C:\Efinity\2026.1\examples\helloworld-dbg_GOLDEN\dbg_manual.json

4. VIO Debug Core

Purpose: drive internal signals (output probes) and observe internal signals (input probes) during debugging.

Parameters: | Parameter | Description | |-----------|-------------| | NUM_PROBE_IN | Number of input probes (signals read from the FPGA) | | NUM_PROBE_OUT | Number of output probes (signals driven into the FPGA) | | PROBE_INn_WIDTH | Width of the n-th input probe | | PROBE_OUTn_WIDTH | Width of the n-th output probe | | UUID | 128-bit unique identifier | | Data depth | 4096 |

Probe types: - Probe Inputs (probe_in): read signal values from the design - Probe Outputs (probe_out): write signal values into the design (an initial value init can be set)

Source: C:\Efinity\2026.1\debugger\doc\topics\dbg-vio.html

5. LA Debug Core

Purpose: capture timing waveforms of internal signals, like a logic analyzer.

Parameters: | Parameter | Description | |-----------|-------------| | Buffer Depth | Buffer depth (4K, 8K, 16K, etc.), uses on-chip RAM | | input_pipeline | Number of input pipeline stages (0-2) | | Capture Control | When enabled, the capture mode can be switched in Capture Setup in the Debug Perspective | | Trigger Enable | Supports triggers to start/stop capture |

Probe types (probe_type): | Value | Type | Description | |-------|------|-------------| | 1 | Data and Trigger | Data + trigger | | 2 | Data Only | Data only | | 3 | Trigger Only | Trigger only |

Capture modes: - Immediately: start capturing immediately after the bitstream is downloaded - Wait for Trigger: start capturing after the trigger condition is met

Source: C:\Efinity\2026.1\debugger\doc\topics\dbg-la.html

6. Debug Wizard

Purpose: provides an automated flow for adding Logic Analyzers. Suited to multi-level, complex designs.

Workflow: 1. Launch the Debug Wizard 2. Choose the buffer depth (affects RAM usage) 3. Optionally enable Capture Control 4. Choose the JTAG User TAP (USER1/USER2) 5. Choose the signal source: Elaborated Netlist or Post-Map netlist 6. Select signals and add them with the arrows (regex filtering supported) 7. Specify each signal's probe type (Data+Trigger / Data Only / Trigger Only) 8. Click Next; the wizard generates and connects the cores automatically 9. Turn on Enable Auto Instantiation 10. Click Finish

Generated files: | File | Description | |------|-------------| | debug_profile.wizard.json | The debug profile created by the wizard | | debug_TEMPLATE.v | Debug template (contains the module instantiation) | | debug_top.v | RTL logic of the debug cores |

Notes: - Requires the JTAG_USER1 or JTAG_USER2 resource; if that resource is occupied by the Debugger, other JTAG functions cannot be used - Signals whose clock domain is "Undefined" have no clock driver in the post-map netlist; add an LA core for them manually

Source: C:\Efinity\2026.1\debugger\doc\topics\dbg-wizard.html

7. mark_debug Synthesis Attribute

Purpose: mark signals in RTL that need debugging; the synthesis tool automatically generates a debug profile containing those signals.

Verilog usage:

(* mark_debug = "true" *) wire [7:0] debug_signal;
// or
(* mark_debug = "1" *) reg debug_reg;

VHDL usage:

attribute mark_debug : string;
attribute mark_debug of debug_signal : signal is "true";

Synthesis options: - Enable: efx_map --enable-mark-debug (or turn on the synthesis option in the GUI) - After synthesis completes, debug_profile.mark_debug.json is generated - This profile can be imported into the Debug Wizard

Source: C:\Efinity\2026.1\debugger\doc\topics\dbg-mark-debug.html

8. Debugger Auto Instantiation

Project XML configuration (<efx:debugger> section):

<efx:debugger>
    <efx:profile name="profile_path"/>
    <efx:auto_instantiation name=""/>
    <efx:work_dir name="work_directory"/>
</efx:debugger>

Parameters: | Parameter | Description | |-----------|-------------| | profile | Path of the debug profile JSON file | | auto_instantiation | Whether auto-instantiation is enabled | | work_dir | Working directory of the debug cores |

In the GUI: Project Editor → Debugger tab → Debugger Auto Instantiation toggle

CLI trigger conditions (verified against efx_run.py sources, 2026.1): before efx_run --flow compile schedules run_debugger_auto_instantation, two silent checks run (check_and_set_auto_dbg_mark_dbg):

  1. The file pointed to by the XML profile parameter must actually exist (os.path.isfile, relative to CWD = project root) — if it does not, the debug flow is silently skipped as a whole, with no warning in the log, and the compile still "succeeds"
  2. The mark_debug auto-generation flow (--mark_debug mode) activates only when the profile value is exactly equal to outflow/debug_profile.mark_debug.json (string match against args.output_dir + "/debug_profile.mark_debug.json"; a relative path must be used); in that case efx_run_dbg.py uses DbgWizard.gen_debug_v_from_profile to automatically generate the debug core RTL from the mark_debug profile produced by synthesis

Correct minimal XML configuration (mark_debug flow):

<efx:debugger>
    <efx:param name="profile" value="outflow/debug_profile.mark_debug.json" value_type="e_string"/>
    <efx:param name="auto_instantiation" value="on" value_type="e_bool"/>
    <efx:param name="work_dir" value="work_dbg" value_type="e_string"/>
</efx:debugger>

Verification date: 2026-08-16 (ws-e1-sys: profile mistakenly pointing to a non-existent path → compile silently skipped debug, work_dbg/ not generated; fixed after pointing it to the outflow path)

The first-compile pitfall (measured in the 2026-08-16 debug_flow_test): starting a compile with auto=on + profile=outflow/debug_profile.mark_debug.json while the profile file does not exist yet makes the whole compile crash with exit 1 (not a silent skip) — An exception occurred: No such file: outflow\<design>.elab.vdb. Mechanism: - efx_run.py:1249-1251: the map step appends --opt write-premap-module=<design>.elab.vdb to write out the elab library only if args.debug_profile was already set when the flow started (i.e. the profile file existed at that time) - efx_run_dbg.py:291-292: the mark_debug (pre-map) profile must read outflow/<design>.elab.vdb for the VDB merge - Yet in the same map run, enable-mark-debug generates the mark_debug profile and triggers the debug step → the step crashes because it cannot find elab.vdb

The correct two-compile order (must be followed): build #1 with auto=off (here enable-mark-debug collects signals and generates the profile JSON, no debug step) → build #2 with auto=on (the profile already exists when the flow starts → map writes elab.vdb → the efx_run_dbg merge succeeds). The tool side (SDK adapter preview validation + SDK saveBuildOptions) has been tightened accordingly: auto=on requires the profile file to exist beforehand.

Source: C:\Efinity\2026.1\scripts\efx_run.py:129-145 (check_and_set_auto_dbg_mark_dbg), efx_run.py:1650-1702 (run_debugger_auto_instantation), efx_run.py:1249-1251 (write-premap-module condition), efx_run_dbg.py:291-292 (elab.vdb dependency)

11. Concurrent Debugging

  • Multiple debug windows can be open at the same time, each connected to a different JTAG USER TAP interface
  • Requires a Hardware Server connection
  • Open multiple windows via Tools → Open Debugger or by clicking the Debugger icon repeatedly

12. RTL Structure of Auto-Generated Debug Cores

Taking helloworld-dbg_GOLDEN\dbg_manual_top.v as the example:

module dbg_manual_edb_top (
    // JTAG boundary scan ports
    input  bscan_CAPTURE, bscan_DRCK, bscan_RESET, bscan_RUNTEST,
    input  bscan_SEL, bscan_SHIFT, bscan_TCK, bscan_TDI, bscan_TMS,
    input  bscan_UPDATE, output bscan_TDO,
    // VIO clock and probes
    input  vio0_clk, input [28:0] vio0_counter,
    input [3:0] vio0_raddr, input [5:0] vio0_led,
    output vio0_vio_reverse, output vio0_vio_mux_sel,
    output [3:0] vio0_vio_maddr,
    // LA clock and probes
    input  la0_clk, input [28:0] la0_counter,
    input [3:0] la0_raddr, input [5:0] la0_led
);
    // Debug Hub (JTAG bus converter)
    // edb_vio_top instantiation
    // edb_la_top instantiation
endmodule

Structural hierarchy:

debug_top.v
├── Debug Hub (JTAG → internal bus)
├── VIO Core (edb_vio_top)
└── LA Core (edb_la_top)

14. Disabling Debug Cores

Via the GUI: 1. Open the Project Editor 2. Click the Debugger tab 3. Turn off the Debugger Auto Instantiation option 4. Click OK 5. Recompile

Note: disabling does not delete the debug profile on disk; it can be re-enabled at any time.
