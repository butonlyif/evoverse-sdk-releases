0. Location corrections and reading guide

0.1 Three important corrections (read these first)

When consulting Efinity DesignAPI material, the following three locations are easy to get wrong; this document corrects them per the actual source:

Correction 1: the real DesignAPI lives in pt\bin\api_service\design.py, not design\db.py.

  • api_service\design.py L71 defines class DesignAPI — the facade class users call directly, ~2810 lines, containing all public methods such as create_*_gpio / set_property / assign_pkg_pin / import_design.
  • design\db.py (pt\bin\design\db.py) L64 defines class PeriDesign(db_item.PeriDesignItem) — an internal data container, the in-memory database holding GPIO/PLL/IOBank objects; it exposes no operational semantics. DesignAPI holds it via from design.db import PeriDesign (design.py L31).
  • There is also an intermediate orchestration layer, IntDesignAPI in api_service\internal\int_design.py (load L140 / create L316 / save L391 / create_block L758 / check_design L978, etc.); most of DesignAPI's lifecycle methods are a thin wrapper over it.

Correction 2: the peri.xml writer DesignWriterXml is in pt\bin\design\service.py (L3476) — not in api_service\design\service.py (that path does not exist), and not in a writer directory.

  • There is no design subpackage under pt\bin\api_service\ — api_service\design.py is a single-file module, not a package.
  • The top of pt\bin\design\service.py defines class DesignService (L540) and class DesignWriterXml (L3476); the former orchestrates peri.xml loading/saving, the latter is the real XML writer.

Correction 3: there is exactly one peri.xml writer, and peri.xml itself is a "project source file", not a "build artifact".

  • Every unified build (efx_run --flow compile) loads the persisted <design>.peri.xml and replays the ISF files referenced by the project XML onto it (see Chapter 3). peri.xml must therefore be version-controlled with the project, and no build path may delete it before a build.
  • Its root element and namespace are efxpt:design_db / http://www.efinixinc.com/peri_design_db (service.py L3506, L3521-3526) — a different schema from the project XML's enf_proj namespace (http://www.efinixinc.com/enf_proj); see xml-project-schema.md.

0.3 Relationship to ISF / peri.xml

  • ISF is Python API source: the content of a .isf file is line after line of design.xxx(...) calls, executed line by line via exec() by isf_importer.py (L236, L289). This is the root of "an ISF syntax error → the whole import aborts immediately" (Python's SyntaxError cannot be recovered line by line; see the exception matrix in 4.3).
  • peri.xml is the XML serialization of the object database: every object/property/pin assignment produced by ISF execution ends up in the PeriDesign container, which DesignWriterXml serializes into <design>.peri.xml.
  • Replay safety: every build re-executes ISF onto the existing peri.xml, so an ISF referenced by the project XML may contain only idempotent commands (set_property / assign_pkg_pin / assign_resource / set_device_property / set_iobank_voltage); create_* is a one-shot bootstrap that may run only once, while peri.xml does not exist — the ISF command set has no delete/clear, and repeated create_* raises "already exists"-type errors. The full statement of this contract is in isf-syntax-reference.md and in hard-constraint rule §15.

1.2 Object handle model

The first parameter of most DesignAPI methods is inst, of type BlockInstanceType = Union[str, int] (L68):

  • Pass a str: look up by instance name (e.g. "ddr0", "my_pll").
  • Pass an int: look up by internal object_id.
  • IOBank / SEU / RU / EXT_FLASH / CLKMUX are special: they are not ordinary blocks but device-setting singletons. __get_object_id (L2681) maps such names to device-setting objects (L2695-2713), which is why set_device_property("TL", "VOLTAGE", "3.3", "IOBANK") can use the bank name directly as inst.

1.3 The block_type system

create_block(name, block_type, ...) and the block_type parameter of property methods use the following block types (they appear across the design.py method signatures and docstrings):

block_type Purpose Related hard IP
GPIO plain GPIO / bus GPIO (creating via create_block is rejected, L196-197) —
PLL phase-locked loop PLL
OSC on-chip oscillator OSC
LVDS_TX / LVDS_RX / LVDS_BIDIR LVDS differential LVDS
MIPI_TX_LANE / MIPI_RX_LANE MIPI lane MIPI
JTAG JTAG JTAG
DDR DDR controller DDR
PMA_DIRECT PMA direct (PCIe/high-speed serial) PMA
QUAD_PCIE PCIe Quad PCIe
CM Clock Morphing / clock management CM

GPIO connection types (conn_type, injected fixedly by the 14 create_*_gpio): GCLK (global clock), RCLK (regional clock), PLL_CLKIN (PLL reference clock input), PLL_EXTFB (PLL external feedback), MIPI_CLKIN (MIPI clock input), PCIE_PERSTN (PCIe reset), GCTRL (global control), clkout (clock output).

The device-setting types used by set_device_property / get_device_property / reset_device_settings (L576 docstring):

3. The nine-step efx_run_pt_unified.py flow in detail

3.1 Role and exit codes

pt\bin\efx_run_pt_unified.py (393 lines) is the orchestrator of the PT stage in the unified flow: locate/bootstrap peri.xml → replay ISF → design check → generate constraints and reports → export simulation/timing netlists. Exit-code definitions (L52-57):

OK = 0
ERROR = 1
WARNING_SKIP = 0   # returns 0 on skip so the GUI flow is not interrupted

Note that WARNING_SKIP equals OK at 0: skippable situations (unsupported family, internal test devices, etc.) do not count as failures — this is what keeps the efx_run --flow compile GUI flow from being interrupted by PT-side skippable cases.

Helper functions: - check_bitstream_enabled(device, family) (L60-74): calls efx_pgm --query_bitstreams (L66-67) to query whether the device has bitstream enabled. - sync_design_file_efxproject(design_file, project_file) (L77-107): after a project rename, syncs the peri.xml file name (writes the new file, deletes the old one; the source carries a tech-debt comment at L79-80).

4. The isf_importer execution model: why ISF is Python

Evidence: pt\bin\api_service\exim\isf_importer.py (435 lines).

4.1 Two import entry points

# L37
class DesignISFImporter:

    # L155

Imports from a .isf file (line-by-line mode). It creates a fresh, independent DesignAPI instance (L172-173); after the import it cleans up the module: setattr(self.isf_module, "design", None) (L182), del sys.modules[...] (L188); issue count > 0 → returns False (L191-194).

Imports from a command-object list (the netlist reverse-derivation path). It likewise creates DesignAPI(is_verbose=True) (L111) and _setup_design (L112), design = self.design_api (L114); executes each command with exec(code) (L120); when netlist_checksum is given, calls lock_property on the relevant properties (L121-122).

4.2 exec + design binding: why ISF is Python

Core of line-by-line mode, __import_line_code (L197):

  • reads the file as UTF-8 (L202);
  • design = self.design_api — the original source comment reads "Set design context for import, used by exec()" (L217);
  • skips blank lines and # comment lines (L227-228); with is_skip_resasg=True, skips lines prefixed with design.assign (L231-233);
  • executes line by line with exec(code) (L236).

Core of whole-file mode, __import_code (L272-304):

# L282
module = types.ModuleType(name)
# L287
setattr(module, "design", self.design_api)
# L289
exec(code, module.__dict__)

That is: the ISF file is executed as a Python module body inside a temporary module namespace, with the name design pre-bound to a DesignAPI instance. This is the direct evidence that ISF must be written as design.xxx(...) and is, at heart, Python source — any "home-grown XML constraint format" is a Python syntax error in Efinity's importer and will inevitably be rejected (the historical lesson is at the head of isf-syntax-reference.md).

4.3 Exception handling matrix (L240-267)

How per-line exec exceptions are routed decides "does an ISF error abort immediately, or is it booked and execution continues":

Exception Handling Consequence
PTException booked (__register_command_issue L351, severity=warning) continues to the next line
AttributeError booked + traceback printed continues to the next line
SyntaxError booked (__register_syntax_issue L370, severity=error) + break the whole import aborts immediately
TypeError break aborts immediately
UnicodeError break aborts immediately
other Exception __register_general_issue (L389) + break aborts immediately

Reading: - Property-level errors are recoverable (unknown property, already exists, and other PTExceptions) — booked as warnings and execution continues, so one bad ISF can produce multiple issues; - syntax-level errors are not recoverable (SyntaxError comes from the Python parser; there is no "next line" semantics to resume at) — immediate abort. This confirms, at the implementation level, the hard constraint "an ISF syntax error aborts the whole import immediately, with no partial processing".

4.4 Post-processing and design check

  • __do_post_processing (L414-421): after the import completes, it recalculates all PLL frequencies (L417-420), keeping the counters and frequency properties consistent.
  • __do_design_check (L424-431): calls APIPropertyChecker for a lightweight check.

5.2 write() structure (from L3484)

write(design, design_file) (L3484) builds the XML in memory with QXmlStreamWriter + QBuffer (L3492-3496) and then writes it to disk (L3711-3713):

  • root element efxpt:design_db (L3506), with attributes including name / device_def / version / db_version / last_change_date (L3507-3519);
  • the namespace declaration xmlns:efxpt="http://www.efinixinc.com/peri_design_db" (L3521-3526) — direct evidence that peri.xml and the project XML (enf_proj) belong to two different schemas;
  • the device_info section (L3528-3594): iobank (normal/advance variants, L3532-3538); ctrl/seu selected by the tx60_ctrl / tx125_ctrl device plug-ins (L3542-3565); clkmux by tx60 / tx180 / tx375 (L3567-3583); ext flash (L3585-3591);
  • the efxpt:partial_design element (with a source attribute, L3699-3703) records the partial-design migration origin.

5.3 Block write order (L3596-3697)

The source comment reads "Blocks must be written in correct order" (L3596). The fixed order:

GPIO → PLL → OSC → LVDS → MIPI → JTAG → DDR → H264 → MIPI lane
→ SPI flash → HyperRAM → PLL SSC → common quad → QUAD PCIe
→ Lane10G → Lane1G → RawSerdes → SOC → CM

The tool guarantees this order; hand-editing peri.xml into a different order, or forging a peri.xml by hand, is unsupported — peri.xml can only be produced by the PT tools (hard constraint §1).
