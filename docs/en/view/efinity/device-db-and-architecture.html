1. Device families and JTAG IDCODE tables

1.1 Data source and structure

The programmer-side device database of Efinity 2026.1 actually lives in the pgm\bin\ directory (not the pgm\ root — a common path misconception):

Evidence: C:\Efinity\2026.1\pgm\bin\device_db.xml

This XML is the data source the programmer uses to identify devices on the JTAG chain. Its core structure is one entry per device, with the key fields:

Field Meaning
name Device name (e.g. Ti60, Ti180, Tz175)
idcode JTAG IDCODE (32-bit hexadecimal)
family Family (Trion / Titanium / Topaz)
sec_disp_name Security display name (the canonical name referenced by security scripts)

The same physical device may have multiple entries: ES (Engineering Sample) and MP (Mass Production) have different IDCODEs; there are also internal variants such as test boards and MUT entries. Whichever IDCODE the JTAG chain identifies, that is the entry the programmer handles — an ES part must use the bitstream matching the ES entry.

1.5 ES vs MP: comparison with the official documentation

The official Titanium IDCODE document lists MP values only:

Evidence: C:\Efinity\2026.1\pgm\doc\topics\jtag-device-ids-ti.html (lines 175-260, three-column table of FPGA / Package / JTAG Device ID, document version HLP-EFN-PGM-v2.0)

Comparison item device_db.xml Official jtag-device-ids-ti.html
Ti60 0x00360A79 (ES) + 0x10660A79 (MP, entry named Ti60_MP) Only 0x10660A79 (annotated "All" packages)
ES variants Explicitly present (Ti60 ES, Ti135ES, etc.) ES values not listed
Purpose Programmer runtime identification Manual table lookup

Conclusion: if the part on hand is an ES die (e.g. Ti60 ES), JTAG reads back 0x00360A79 and the programmer handles it per the ES entry; the 0x10660A79 found in the official documentation is the mass-production value. Both are "correct", but the bitstreams are not interchangeable — see §3.3.

2.2 Die codenames and device mapping

arch data is named by die codename + geometry, mapping to marketing device names as follows (measured anchors):

Die data name Corresponding device Evidence clue
opx_218x322_b16_d10 Ti60 An _es variant directory exists, corresponding to the Ti60ES device
opx_268x484_b24_d12 Ti180 Flagship die
opx_333x642_b40_d20 Ti375 Largest Titanium die
opx_334x484 Ti240

Die codename families: oph / opu / opx / opy / ssn / tz. Naming pattern: <die>_<width>x<height>_b<bank count>_d<scale tier> (the b/d suffixes are visible on only some dies).

2.3 File format determination table

Every extension inside the arch directory is a tool-private format; the determination is based on the DLLs that load them:

Extension Format determination Evidence
.xdb libdevicedb.dll private container (not plain-text XML) loaded by C:\Efinity\2026.1\bin\libdevicedb.dll; opening in a text editor shows no plain-text structure
.zst / .delaym.zst Zstandard compression installation contains libzstd.dll
.blk / .btm / .clib Block/timing/cell library data consumed by libchipper.dll + libprotobuf.dll the two DLLs coexist under C:\Efinity\2026.1\bin\
.oc Speed grade (operating condition) files named C2/C3/I4 etc. under arch\oc\
.flrpln Floorplan data arch\flrpln\
.tmv2 pt_route timing model v2 arch\pt_route\, used only by new Titanium dies
.tenc / .pt_device Interface Designer-side device data accompanies the pt directory

2.4 Read-only rules (important)

The arch directory is tool-internal data: read it, never edit it. Reasons:

  1. Everything is a private binary/compressed format (§2.3) with no published schema; manual editing inevitably corrupts it;
  2. No build path of the SDK / adapter / scripts should write to, delete, or regenerate arch content — that falls under §7 "do not build workarounds around tool behavior";
  3. When device capabilities need to be queried, the correct entry points are the project XML (enf_proj.xsd, see Efinity XML Project File Schema Reference) and the ISF API (see Efinity ISF Syntax Reference), not the arch binaries.

The evidence boundary of the "I4/I4L deprecated" claim (presented as measured):

  • Workspace rule asserts: Ti35/Ti60 timing models I4/I4L are deprecated; C4 or C5 must be used.
  • Evidence inside the installation: contradictory — arch\oc\ still contains I4.oc / I4L.oc; yet Ti125's tmv2 contains no I4/I4L; and no C5 data exists anywhere in the tree.
  • Conclusion: "I4/I4L deprecated" cannot be directly confirmed by a single file inside the installation; only two hard measured facts can be stated: (a) the speed grade set of the new dies (Ti125 tmv2) does not include I4/I4L; (b) the old grade files remain in the oc directory (possibly just for old-project compatibility). For project selection follow the workspace rule (C4/C5); this volume does not extrapolate beyond the evidence.

3. Flash loader bitstream and IDCODE mapping

Evidence: measured directory listing of C:\Efinity\2026.1\pgm\fli\ (fli = flash loader images) Parameter details and ftdi_program.py usage are in Efinity Helper Tools and Scripts Reference; the programming procedure is in Efinity Programming and Flashing Guide. This volume only gives the IDCODE ↔ bitstream-name correspondence.

3.1 Bitstream naming rule

Flash loader bitstream file name format: u<IDCODE>[_<die>].bit, where <IDCODE> is the 8-digit hexadecimal of the corresponding device entry in the §1 tables (no 0x prefix).

3.2 Three-family bitstream inventory overview

Family directory .bit count Naming examples
pgm\fli\titanium\ 21 u10660A79.bit (Ti60 MP), u00680A79.bit (Ti180)
pgm\fli\topaz\ 14 named by Topaz IDCODE
pgm\fli\trion\ 11 with die suffix: u00210A79_t20.bit (T20/T13/T8 share an IDCODE; the die suffix distinguishes them)

Key points:

  1. Trion bitstreams must carry the _<die> suffix — because multiple Trion devices share the same IDCODE (§1.2), the loader picks the right die via the suffix;
  2. Titanium / Topaz bitstreams are plain u<IDCODE>.bit, no suffix.

3.3 Ti60ES special case: no flash loader bitstream

Evidence: the listing of C:\Efinity\2026.1\pgm\fli\titanium\ contains no u00360A79.bit (Ti60 ES's IDCODE); only u10660A79.bit (MP) exists.

The triple restriction on Ti60ES (compiled in this volume from various sources):

# Restriction Evidence
1 No flash loader bitstream (u00360A79.bit does not exist) measured in pgm\fli\titanium\
2 Excluded from security features (the AES/RSA signing scripts explicitly say "excluding Ti60ES devices") C:\Efinity\2026.1\security\bin\AddSecurityTitanium.py line 31
3 2.5V IO voltage standard not supported (mass-production parts only) workspace rule (rules-efinity-hard.md §3); no direct file evidence inside the installation

Engineering implication: an ES part can only do functional verification; it cannot be the target device of a secure mass-production programming scheme; production designs must switch to an MP part (IDCODE 0x10660A79).

Item Content Evidence line
Algorithms RSA-4096 signature + AES-256 (GCM) lines 112, 132-137
Key write location non-volatile OTP (one-time programmable) lines 42-44: keys are written to non-volatile OTP

Flow chain: GenKeyFileTitanium.py generates the keys → the keys are burned into the device OTP → AddSecurityTitanium.py GCM-encrypts + RSA-4096-signs the bitstream with the same key → after programming, the device verifies and decrypts using the OTP key at power-up.

4.5 Applicability red lines

  • The security features are Titanium only and explicitly exclude Ti60ES (AddSecurityTitanium.py line 31);
  • Topaz / Trion are outside these scripts' scope;
  • The pycryptodome environment is required; _efx_security_util.exe is a native tool shipped with the installation — do not replace or bypass it.

5. lpf.xsd erratum: the real peri_device_db

5.1 The common misconception

The file name of C:\Efinity\2026.1\pt\bin\schema\lpf.xsd contains "lpf", so it is easily mistaken for something related to LPF constraint files, SDC constraints, or peri.xml (efxpt:design_db). All wrong.

5.2 Measured facts

Evidence: C:\Efinity\2026.1\pt\bin\schema\lpf.xsd

Line Measured content Meaning
Line 2 targetNamespace="http://www.efinixinc.com/peri_device_db" The namespace is peri_device_db (the device database), not constraints, and not peri.xml's efxpt:design_db
Line 5 Prefix efxpt Shares the efxpt prefix with peri.xml, but the URI differs
Line 8 imports peri_util.xsd Depends on common types in the same schema directory

Root element structure: periphery → sequence / block_def (with bitsize, paramsize attributes) / instance.

5.3 Conclusion

Question Answer
What does lpf.xsd describe? The bit-level block definitions of the peri_device_db device database (the bit-width model of bank/IO blocks), consumed internally by PT
Is it related to SDC/LPF constraints? No. The only constraint formats are ISF and SDC (workspace rule §1)
Is it related to peri.xml? No direct relation. peri.xml's namespace is http://www.efinixinc.com/peri_design_db (design_db); lpf.xsd's is peri_device_db (device_db) — two different URIs
Where do the XSDs actually live? Project-format XSDs are in C:\Efinity\2026.1\bin\ (e.g. enf_proj.xsd); lpf.xsd is in C:\Efinity\2026.1\pt\bin\schema\ — two distinct schema directories; do not mix them
