Efinity File Formats: peri.xml

Efinity File Format Reference — <project>.peri.xml (the PT design library)

Applies to: Efinity 2026.1 (C:\Efinity\2026.1) Investigation date: 2026-09-25 Evidence method: every conclusion comes from a first-hand read of real files in the Efinity 2026.1 installation directory (XSD schemas, Python sources, official examples, the official HTML glossary); evidence paths are annotated item by item in the body. Contains no speculation and no external-source content.

Warning: this volume describes the internal design-library file format of the Efinity PT (Periphery Tool / Interface Designer). It is a project source file produced exclusively by the PT tool — never hand-write it. Hand-writing carries neither schema guarantees nor replay-semantics guarantees (see §1.4).

1. Position and lifecycle: a project source file, not a generated artifact

1.1 Official definition (glossary verbatim)

The official glossary defines <project>.peri.xml as follows (evidence: C:\Efinity\2026.1\doc\topics\gloss-peri.xml.html L168-197):

  • Title (L168): <project>.peri.xml
  • Filesystem location (L177-178): <project> (i.e. in the project root, sharing the project XML's name)
  • Created by (L181-183): "Interface Designer when you create an interface"
  • Design source? Yes (L185-186) — the only PT-related artifact the vendor marks as a design source (the SDC-and-reports volume §5 compared: report artifacts are all "Design source? No")
  • Content (L190-193, quoted verbatim):

"The Interface Designer creates this file when you create a new interface for your project. This file contains all of the settings that you specified in the Interface Designer for I/O banks, GPIO, LVDS, PLLs, MIPI, DDR, etc. You should not edit this file directly!"

Two key official conclusions: 1. Design source? Yes → peri.xml is a project source file, on par with .v, .sdc, and .isf: it must survive a build and must be placed under version control. 2. You should not edit this file directly! → the vendor explicitly forbids direct editing. All modifications must go through the Interface Designer (GUI) or ISF/DesignAPI (scripts).

1.2 The triple identity

peri.xml is three things at once; understanding any one of them must not drop the other two:

# Identity Meaning Evidence
① Project source file Holds every periphery setting you specify in the Interface Designer (IO banks, GPIO, PLL, MIPI, DDR, ...); together with the project XML it constitutes the project gloss-peri.xml.html L185-193
② Exclusive product of the PT tool Producible only by the PT tool / Interface Designer (the XSD schema is efxpt:design_db; the internal structure is complex and evolves across versions) §2, §3
③ The replay target of every unified build Every unified compile loads the persisted peri.xml and replays the ISFs referenced by the project XML onto it; hence ISFs must be replay-safe efx_run_pt_unified.py L180-184, L252; ISF volume §3

Project XML (.xml)
   │ references
   ▼

                              │

Corollary: every .v / .pbn / .isf derived from peri.xml is a generated artifact — deletable and regenerable; only the peri.xml itself is a source file — deleting it means losing the entire periphery design.

1.4 The bootstrap / replay two-phase contract (division of labor with ISFs)

The existence of peri.xml directly dictates how ISFs may be written (the full contract is in the ISF volume §3 and hard rule rules-efinity-hard.md §15; the essentials are restated here from the peri.xml perspective):

Phase Condition Commands allowed in the ISF Effect on peri.xml
bootstrap peri.xml does not exist yet (new project/new baseline) create-style commands such as create_*_gpio / create_block / create_pll_input_clock_gpio, plus set/assign style Creates instances and sets properties, persisting the first peri.xml
replay peri.xml already exists (every subsequent build) Only idempotent commands: set_property / assign_pkg_pin / assign_resource / set_device_property / set_iobank_voltage Re-sets properties on existing instances; create_* fails with GPIO/PLL ... exists because the instance already exists → the second compile fails
  • The ISF command set has no delete/clear — the PT native API raises on nonexistent instances, so there is no idempotent deletion that could be written into an ISF (do not try to invent one).
  • Hence the standard bootstrap ritual: temporarily enable create_ → compile once to generate the peri.xml → comment out create_ immediately** → the replay compile must PASS again in full (two consecutive PASSes count as acceptance).

2. Namespace and root element

2.1 The three-way namespace split

The XML world of Efinity PT is built from three targetNamespaces with clearly separated prefix conventions and responsibilities (evidence: the targetNamespace declarations at the head of each XSD, C:\Efinity\2026.1\pt\bin\schema\):

Namespace URI Conventional prefix Responsibility Representative files
http://www.efinixinc.com/peri_design_db efxpt Design library: the periphery instances in your project (GPIO/PLL/iobank...) peri_design_db.xsd + 24 design-class sub-schemas
http://www.efinixinc.com/peri_device_db (device library) Device library: factory data for the chip (die/package/timing model/bit-level block definitions) peri_device_db.xsd, lpf.xsd, die_definition.xsd, 9 files in total
http://www.efinixinc.com/peri_tool (tool types) Common simple types (non-empty strings, coordinate strings, etc.) peri_util.xsd

⚠️ peri.xml and the project XML (enf_proj namespace http://www.efinixinc.com/enf_proj) are completely different things — the project XML is written by the user/SDK, the peri.xml by PT; the two cooperate indirectly through the project XML's <efx:inter_file name="*.isf"> references.

2.2 Root element and its six attributes

The root element of a peri.xml is design_db (evidence: C:\Efinity\2026.1\pt\bin\schema\peri_design_db.xsd L36 <xs:element name="design_db" type="design_db_type"/>).

Root attribute definitions (peri_design_db.xsd L175-222):

Attribute Required Type Meaning Observed value in helloworld
@name ✅ string Design name = project name (matches the {design} of {design}.peri.xml) helloworld
@device_def ✅ string Device definition name (must match the project XML's device; triple-checked at load, see §1.3) Ti60F225
@version ❌ string Tool version that produced the file 2025.2.276
@db_version ❌ string Design-library schema version number, an 8-digit form such as 20252006 (not a dotted version) 20252006
@last_change_date ❌ string Last-modified time (a human-readable timestamp PT writes out) Wed Oct 29 10:27:16 2025
@location ❌ string File path (a location record written by PT) —

@db_version semantics: an 8-digit integer such as 20252006; it is the generation marker of PT's internal design_db format, and PT uses it to decide whether an old file needs migration. Never change it by hand — the value is tightly bound to the tool version.

2.3 A minimal fragment (structure illustration, not a hand-writing template)

The fragment below is excerpted from the official example (C:\Efinity\2026.1\examples\helloworld-unified\helloworld.peri.xml L1-4 + L105-108, showing the root element, an iobank, and empty containers) — for understanding the format only:

<?xml version="1.0" encoding="UTF-8"?>
<efxpt:design_db name="helloworld" device_def="Ti60F225" version="2025.2.276"
    db_version="20252006" last_change_date="Wed Oct 29 10:27:16 2025"
    xmlns:efxpt="http://www.efinixinc.com/peri_design_db"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <efxpt:iobank name="1A" iostd="1.8 V LVCMOS" is_dyn_voltage="false"/>
  <!-- ... the other 11 iobanks, see §6.2 ... -->
  <efxpt:osc_info/>
  <efxpt:lvds_info/>
  <efxpt:jtag_info/>
  <efxpt:mipi_dphy_info/>
</efxpt:design_db>

Key points: - All elements hang under the efxpt: prefix (declared on the root element as xmlns:efxpt="http://www.efinixinc.com/peri_design_db"). - Unused domains are still written out as empty containers (e.g. <efxpt:osc_info/>) — this is DesignWriterXml's fixed behavior and does not mean content is missing (see §5).

3. Schema structure map

3.1 The aggregation mechanism

All type definitions of a peri.xml are aggregated by peri_design_db.xsd (evidence: C:\Efinity\2026.1\pt\bin\schema\peri_design_db.xsd, 256 lines in total):

  • L3-4: targetNamespace="http://www.efinixinc.com/peri_design_db", the xmlns:efxpt prefix declaration;
  • 24 <xs:include> + 1 <xs:import> (the import pulls in peri_util.xsd from the peri_tool namespace);
  • Erratum: ext_flash_design.xsd is included twice, at L8 and L26 — the same file aggregated twice. XSD processors tolerate this (it is idempotent); it is a minor blemish in the official schema itself, and a custom validator should simply deduplicate.

4. Complete table of core domain attributes

This section lists XML attributes domain by domain: attribute name / type / meaning / example value. Types are taken from the XSD declarations; "meanings" follow the embedded <xs:documentation> verbatim (or a faithful translation). All source files live under C:\Efinity\2026.1\pt\bin\schema\.

4.1 The iobank domain (iobank_design.xsd, 75 lines)

iobank_config_type:

Attribute Required Type Meaning Example value
@name ✅ string IO bank name ("IO Bank name as per device") TL
@iostd ✅ string The IO standard set for this bank. XSD verbatim (L36-39): "IO Standard set for this IOBank. This is not just the voltage since the decision to display voltage was rather late in the game." — @iostd is the full IO standard (voltage + level family), not just the voltage "1.8 V LVCMOS" / "3.3 V LVCMOS"
@is_dyn_voltage ❌ bool Dynamic-voltage enable (introduced in PT-1225) false
@mode_sel_name ❌ string Bank mode-select signal name TL_MODE_SEL

Child element mode_sel_name (0..*): bank_name + value pairs recording the legal mode-select combinations.

ISF correspondence: design.set_iobank_voltage("TL", "3.3") actually writes @iostd (ISF volume §3). The SDK hard rules "MIPI banks must be 1.2 V" and "MIPI and LVDS never share a bank" ultimately land on this domain.

5. DesignWriterXml write-out logic

This section gives only a summary + pointers; the line-by-line dissection of the call chain (DesignAPI.save → IntDesignAPI.save → DesignService.save_design → DesignWriterXml.write, with the L3484→L3526→L3596-3713 line-level detail) is in the sibling volume Efinity DesignAPI Reference (docs/efinity/Efinity-DesignAPI方法参考.md), section 5 "DesignWriterXml write-out model"; the line-number evidence is consistent across the two volumes (C:\Efinity\2026.1\pt\bin\design\service.py).

5.1 When the peri.xml is written out

Scenario Trigger Evidence (service.py)
The user clicks save in the Interface Designer / DesignAPI.save() DesignService.save_design (L720-732) iterates and calls each block service's save_design service.py L3696-3697
During a unified compile (after ISF replay) After replay completes, the in-memory evolved design is written out as a whole tree the flow after efx_run_pt_unified.py L252

The final persistence action (service.py L3711-3713): open(design_file, mode='wb') — binary write, UTF-8 XML, full-file rewrite (not incremental).

5.2 The fixed write-out order of the 19 block classes

service.py L3596 carries the source comment # Blocks must be written in correct order. L3597-3695 then use 19 if/elif slots to fix the order in which block services append — i.e. the order the blocks appear in the XML:

①GPIO (GPIODesignService or GPIODesignServiceComplex, one of the two)
②PLL (a 5-variant if/elif chain: plain/complex/advanced, etc.)
③OSC (3 variants)         ④LVDS (3 variants)         ⑤MIPI (2 variants)
⑥JTAG                     ⑦DDR (2 variants)          ⑧H264
⑨MIPI DPHY (2 variants)   ⑩SPI Flash                 ⑪HyperRAM
⑫PLL SSC                  ⑬CommonQuad               ⑭QuadPCIe
⑮Lane10G                  ⑯Lane1G                    ⑰RawSerdes
⑱SOC                      ⑲CM (cm_v1)

Why the order matters: blocks reference each other (GPIO references iobanks; PLL outputs reference GPIOs), so the referenced side is written first. The tool writes in this order, and parsers/validators should read in this order too. After each block is written, save_design runs one by one (L3696-3697); L3699-3703 writes the partial_design element (a partial-design-mode marker, empty in normal projects).

5.3 Empty-container behavior

Even a completely unused domain is written out by DesignWriterXml as an empty container element (e.g. helloworld's <efxpt:osc_info/>, L105-108). This matches minOccurs=0 on every child of design_db_type (§3.3): an empty container ≠ a missing one — both are legal states; when diffing, do not treat an empty container as a "content change".

7. Confusable-format erratum: lpf.xsd is misnamed

7.1 The problem: the name lpf is highly misleading

The schema directory contains C:\Efinity\2026.1\pt\bin\schema\lpf.xsd (167 lines). The file name lpf immediately suggests "Logic Preference File" / "LPF constraint file" (a physical-constraint format used by some FPGA vendors), leading people to assume Efinity also has some LPF constraint format.

7.2 The fact: it is a device database in the peri_device_db namespace

First-hand evidence (lpf.xsd):

Line Content Conclusion
L2 targetNamespace="http://www.efinixinc.com/peri_device_db" Belongs to the device-library namespace, not peri_design_db (the design library); it has no aggregation relationship whatsoever with peri.xml (efxpt) — see the §3.2 list, where lpf.xsd does not appear
whole file Root element periphery (periphery_type: @device / @design / @checksum) Describes the periphery block data of a specific device — a checksummed database snapshot
— Child elements sequence / block_def (@name / @bitsize / @paramsize) / instance (@id / @type + parameter + binary value) Bit-level block definitions: each block's (block_def) width, parameter layout, and per-instance binary image
— The setting type of parameter_value is binary_string_type (pattern ([01])+) Parameter values are 01 bit strings
— parameter_int_type carries @min / @max / @endianness (little/big) / @format (binary/hex) Bit-encoding rules for integer parameters

7.3 Conclusion

Common misreading Fact
"lpf.xsd defines Efinity's LPF constraint file format" ❌ Efinity has no LPF constraint format; constraints come in exactly two kinds — ISF (for PT) and SDC (for pnr) (hard rules §1)
"peri.xml references lpf" ❌ lpf.xsd belongs to peri_device_db (device library) while peri.xml belongs to peri_design_db (design library); different namespaces, no include/import relationship (§2.1, §3.2)
"lpf is a variant of SDC" ❌ Nothing to do with SDC; SDC is consumed by efx_pnr, while lpf.xsd describes the bit-level block definitions inside the PT device database

Purpose: lpf.xsd serves PT's internal scenario of aligning/validating design-library data (peri.xml) against the device's factory bit-level definitions (block_def's bitsize/paramsize + instance binary values). SDK-level tooling never needs to parse it; any code that treats "lpf" as a constraint format is a bug misled by the file name.

For similar namespace errata, compare the DesignAPI volume's §0.1 "three errata" and the SDC volume's analysis of report-artifact namespaces.

8. Engineering rules and sibling-volume cross-references

8.1 peri.xml engineering rules (checklist)

  1. Never hand-write or hand-edit a peri.xml. The vendor's own words: "You should not edit this file directly!" (gloss-peri.xml.html L190-193). There are exactly two modification entry points: the Interface Designer (GUI) or ISF/DesignAPI (scripts).
  2. peri.xml is a project source file: place it under version control together with the ISFs; no build path (SDK / adapter / scripts) may delete it before a build — delete-and-regenerate is a workaround, not a fix (hard rules §15).
  3. Self-check gate: after every constraint change, first pass the ISF through cli/import_gpio.bat --dry-run, then run one replay compile to confirm the peri.xml loads cleanly (ISF volume §4; hard rules §16).
  4. Bootstrap is one-shot: create_* runs only once, while the peri.xml does not exist, and must be commented out afterwards (ISF volume §3; this volume §1.4).
  5. Do not write homegrown tools that parse/generate peri.xml: the format spans 24 sub-schemas and evolves with db_version (§3, @db_version §2.2); the correct approach is DesignAPI (the DesignAPI volume). The only legitimate programmatic surface is the DesignAPI read interface (e.g. for a workbench UI display).
  6. Notes for diffing: an empty container ≠ a content change (§5.3); @last_change_date changes on every save — ignore it in diffs.
  7. Triple device consistency: the peri.xml's @device_def must match the project XML's device information, or the unified flow errors out immediately at L224-230 (§1.3) — when copying another project as a template, switching the device is the first thing to do.
  8. SDC clock-name alignment: the PLL comp_output_clock/@name in a peri.xml is the RTL clock name, and the SDC create_clock must match it exactly (§6.7; SDC volume hard rule §7).
