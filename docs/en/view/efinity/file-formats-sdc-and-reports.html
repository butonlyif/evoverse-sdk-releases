2.2 Clock definition commands

create_clock

# Official syntax (constraint-create-clock.html L170-172)
create_clock -period <float> [-waveform {ris fall}] [-name <clock name>] [<targets>] [-add]
Point Description Evidence
-name with no target = virtual clock A clock that only defines a name without attaching to a port; the tool prints an info note; an accidental virtual clock is one of the 4 official common SDC mistakes constraint-create-clock.html L168-206; efn-sdc-mistakes.html L173-216
Multiple clock assignments on the same target are not supported Unless -add is added constraint-create-clock.html L168-206
Clock count affects runtime Official tip: STA/PNR runtime grows with the number of clocks constraint-create-clock.html L168-206
Minimal example C:\Efinity\2026.1\examples\helloworld-unified\helloworld.sdc is a single line in full: create_clock -period 10 -name clk [get_ports clk] that file, L1

create_generated_clock

# Full official parameter set (constraint-create-generated-clock.html L168-172)
create_generated_clock -source <pin/port> (-divide_by <n> | -multiply_by <n>)
    [-duty_cycle <float>] [-invert] [-master_clock <name>] [-phase <deg>]
    [-offset <float>] [-edges <list>] [-edge_shift <list>] [-add] <targets>

Key points: -source is mandatory; -divide_by / -multiply_by are mutually exclusive (pick one); -edges / -edge_shift describe the clock edge by edge. Evidence: constraint-create-generated-clock.html L168-212. The companion practice for the repository hard rule "PLLs must be created in the ISF; RTL only declares ports" is: when a PLL output clock name appears in the SDC, it must exactly match the PLL output name created in the ISF (an engineering rule, see §2.9).

2.7 Path selection: the -through option and Object Specifiers

-through is supported by five commands — set_bus_skew, set_false_path, set_max_delay, set_min_delay, set_multicycle_path. Officially supported usage (constraint-through-option.html L168-187):

set_false_path -through [get_pins <pin name1>]
set_false_path -through [get_pins {add*|CI}]
set_false_path -through [get_pins <pin1>] -through [get_pins <pin2>]
set_false_path -through [get_cells {add*}]
set_false_path -through [get_cells <cell1>] -through [get_cells <cell2>]

Not supported: mixing multiple get_* commands inside a single -through (constraint-through-option.html L181-186):

# ❌ explicitly unsupported by the official docs
set_false_path -through [[get_pins <pin1>] [get_pins <pin2>]]

2.8 Common SDC mistakes (the official 4)

Source: C:\Efinity\2026.1\doc\topics\efn-sdc-mistakes.html L173-216.

# Mistake type Official essentials What to do
1 Latches / combinational loops Incomplete if/case produces latches; Trion/Topaz/Titanium have no native latch support and emulate them with LUTs; timing graphs forbid loops, and the tool cuts the loop at an arbitrary point Fix the RTL (add default/else); do not mask it with constraints
2 Accidental virtual clocks -name given without a target → virtual clock; the tool prints an info note Use virtual clocks only for abstract references such as set_clock_groups/IO constraints; real clocks must attach to ports
3 Undefined clocks A nonexistent clock name is referenced create_clock first, with names exactly matching the RTL ports/PLL outputs
4 Wrong constraint order create_clock must precede set_input_delay/set_output_delay references to that clock Organize SDC scripts in the order clock definitions → clock groups → IO delays → exceptions

Tension with the repository rule, recorded as observed: the repository rule says "an empty <efx:inter_file name=""/> breaks the build", yet the official unified example itself carries an empty inter_file (helloworld.xml L15). Two possible reconciliations: the tool may treat the official example's empty tag as "unused" and ignore it, while the failure cases seen in this repository may be triggered by other field combinations. Recommended handling: project XML generators should not emit an empty inter_file tag at all (simply omit it) — this satisfies the repository rule without conflicting with the official example. This is an observation recorded here, not a settled conclusion.

4. tool_report.xsd — the tool XML report format

4.1 Schema structure

C:\Efinity\2026.1\bin\tool_report.xsd (30 lines in full) defines the XML report skeleton uniformly emitted by efx_run and the tools. Two levels:

tool_report  (root element, attributes: project, date)
└── group    (1..n, attribute: name)
    └── group_data  (0..n, attributes: name, value, info?, severity?)

4.2 Element/attribute table

Level Element Attributes Semantics Evidence (xsd lines)

Level 1 group name Report grouping (e.g. resources, clock domains, flow stages) same
Level 2 group_data name, value Key-value data points same
Level 2, optional group_data info, severity Additional notes and severity same
