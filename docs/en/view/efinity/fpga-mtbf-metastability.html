1. Metastability basics

1.1 Trigger conditions

When a D flip-flop's setup or hold time is violated, the output is neither 0 nor 1 — a metastable state.

"A metastable state occurs when the output of flip-flop is unknown. This occurs when setup or hold times are violated." — Source: [B4] Max Planck Institute Lesson 11

1.2 Physical mechanism (UBC [B3])

Inside the D flip-flop is a pair of cross-coupled inverters. Under normal conditions it stabilizes at 0 or 1. If the input changes exactly within the metastability window of the clock edge, the inverter pair may temporarily stabilize at an intermediate voltage, then decay exponentially back to 0 or 1:

V(t) = V_metastable + (V_final − V_metastable) · (1 − e^(−t/τ))

where τ = the flip-flop RC time constant.

1.3 Metastability propagation

The resolution time of metastability depends on the flip-flop's physical parameters + output capacitance + noise.

"When a register's setup or hold time is violated — which can happen when data changes close to a clock edge from a different domain — the output of the register can become undefined for an unpredictable period of time." — Source: [B10] Embedded Design CDC Part 1

Key facts: - Metastability is unavoidable (it is avoidable only when the two clocks have a fixed frequency ratio and fixed phase — impractical in real engineering) - Metastability is unpredictable (the resolution direction — 0 or 1 — cannot be guaranteed) - Metastability's probability decays exponentially with time — given enough time, it almost certainly resolves

Therefore: the job of a synchronizer is to give metastability time to resolve, not to prevent it from occurring.

2. The MTBF equation

2.1 The classic formula (UBC ELEX 7660 [B3])

MTBF = e^(T_s / C_2) / (C_1 · f_d · f_c)
Variable Meaning
T_s Setup slack time (obtained from timing analysis)
C_2 Flip-flop time constant (RC + gain)
C_1 Flip-flop "window" constant (the size of the window that captures metastability)
f_d Data toggle frequency (toggle rate)
f_c Sampling clock frequency

Source: [B3] UBC ELEX 7660 Lec 11 (excerpts were once kept in internal research notes; those temporary notes are not published with the repository)

2.2 Key property of the formula

"Since accurate estimation of MTBF requires knowing the propagation delay between flip-flops and the constants for the specific flip-flops used, MTBF calculations are typically done by timing analysis software. For example, Intel's TimeQuest STA can recognize CDC synchronizers (described below) and generate MTBF estimates." — Source: [B3] UBC ELEX 7660 Lec 11

Efinity currently provides no MTBF reporting tool (as of 2026.1 there is no report_mtbf command) — you must calculate by hand or refer to cross-vendor tools (Intel TimeQuest, Xilinx Vivado).

See §6 for details.

3. The variables in detail

3.1 T_s (setup slack time)

Definition: read from the timing analysis report — the setup slack of the synchronizer's second-stage FF (from the source clock to the destination clock).

Typical values: - 100 MHz system, source domain 50 MHz: T_s ≈ 20 ns (one destination period) - 100 MHz system, source domain 100 MHz: T_s ≈ 10 ns

3.2 C_2 (time constant)

Definition: the RC time constant with which the flip-flop decays from the metastable voltage to a valid logic level.

Typical values (Xilinx 7-series experience): - C_2 ≈ 10-50 ps (typically 20 ps)

Experimental measurement (UBC [B3] exercise):

"Exercise 1: A TimeQuest MTBF report says Under typical conditions, an increase of 100ps in available settling time will increase MTBF values by a factor of 10.8. What is C_2?"

Solution:

MTBF ∝ e^(T_s / C_2)
MTBF' / MTBF = 10.8 = e^(100ps / C_2)
ln(10.8) = 100ps / C_2
C_2 = 100ps / ln(10.8) = 100ps / 2.38 ≈ 42 ps

3.3 C_1 (window constant)

Definition: proportional to the flip-flop's "metastability window width" — the setup/hold edge-sensitive window.

Typical values (Xilinx 7-series experience): - C_1 ≈ 10⁻³ to 10⁻² (1/s)

3.4 f_d (data toggle frequency)

Definition: how many times per second the D input changes.

Typical values: - Asynchronous control signals (e.g., interrupts): f_d ≈ 1 kHz – 1 MHz - High-speed data streams: f_d ≈ 100 MHz – 1 GHz

3.5 f_c (sampling clock frequency)

Definition: the clock frequency of the synchronizer's second-stage FF.

4. The exponential MTBF-vs-slack relationship

4.1 The property of the formula

MTBF ∝ e^(T_s / C_2)

Increase slack → MTBF grows exponentially:

"Since MTBF increases exponentially with slack time (T_s), the most effective way to increase the MTBF is to increase the slack time." — Source: [B3] UBC ELEX 7660 Lec 11

4.2 Order-of-magnitude example (typical C_2 = 20 ps)

Slack T_s T_s / C_2 e^(T_s/C_2) MTBF improvement
100 ps 5 148 1× (baseline)
200 ps 10 22,026 148×
500 ps 25 7.2 × 10¹⁰ 4.9 × 10⁸ ×
1 ns 50 5.2 × 10²¹ 3.5 × 10¹⁹ ×

Conclusion: give the synchronizer one more destination period of slack (10 ns) and the MTBF reaches astronomical numbers.

4.3 The other key optimization

"The MTBF is also inversely proportional to product of the clock and data input toggle frequencies. Thus another way to increase the MTBF is to minimize the clock frequency and data toggle rates." — Source: [B3] UBC ELEX 7660 Lec 11

Reduce f_d · f_c: - Choose a low-frequency clock as the synchronizer destination domain (register the data in the high-frequency domain first, then pass it through a 2-FF sync into the low-frequency domain) - Stretch pulses at the data source first (e.g., 1 cycle → 4 cycles) to reduce f_d

5. MTBF target values

5.1 Application tiers

Application Target MTBF Design requirement
Ordinary consumer electronics ≥ 10⁹ years (1 billion years) 2-FF synchronizer + async_reg
Industrial control ≥ 10¹² years 2-FF synchronizer + async_reg + ample slack
Automotive AEC-Q100 ≥ 10¹⁵ years 3-FF synchronizer + multiple redundancies
Medical IEC 62304 ≥ 10¹⁸ years 3-FF + a complete fault tree analysis
Aerospace / nuclear control ≥ 10²⁰ years Multiple redundancies + self-checks

Source: Intel TimeQuest MTBF report (quoted by [B3] UBC) — "Typical MTBF is Greater than 1 Billion Year" is treated as the minimum consumer-grade requirement.

5.2 A simple calculation example

Assume a 100 MHz system with a 2-FF synchronizer: - T_s = 10 ns (one destination period of slack) - C_2 = 20 ps - C_1 = 10⁻³ (1/s) - f_d = 1 MHz - f_c = 100 MHz

MTBF = e^(10ns / 20ps) / (10⁻³ · 1MHz · 100MHz)
     = e^500 / (10⁻³ · 10¹⁴)
     = 1.4 × 10²¹⁷ / 10¹¹
     = 1.4 × 10²⁰⁶ seconds
     ≈ 4.4 × 10¹⁹⁸ years

Far beyond any reasonable target — hence a 2-FF synchronizer is usually sufficient.

6. Efinity MTBF tool support

6.1 Status in Efinity 2026.1

Efinity does not provide an explicit report_mtbf command (as of 2026.1). MTBF verification requires: 1. Calculating it yourself (using the formulas in §3) 2. Using cross-vendor STA tools (Intel TimeQuest / Xilinx Vivado) for reference MTBF data 3. Engaging third-party formal verification tools (the formal.org CDC module)

6.2 Indirect verification

For CDC paths, the Efinity STA report pt_timing.rpt does report setup slack — if the synchronizer has positive slack (typically > 0.5 ns), the MTBF can be estimated to far exceed consumer-grade requirements.

See 时序分析指南.md §3 for details.

6.3 Design-stage MTBF estimation script (Python)

# mtbf_calc.py — MTBF estimation tool (based on the UBC [B3] formula)
import math

def mtbf(T_s_ps, C_1, C_2_ps, f_d_Hz, f_c_Hz):
    """Calculate MTBF in years.

    Args:
        T_s_ps: Setup slack in picoseconds
        C_1: Aperture constant (1/s) - device-specific
        C_2_ps: Time constant in picoseconds - device-specific
        f_d_Hz: Data toggle rate (Hz)
        f_c_Hz: Clock frequency (Hz)
    """
    exp_arg = T_s_ps / C_2_ps
    mtbf_sec = math.exp(exp_arg) / (C_1 * f_d_Hz * f_c_Hz)
    SEC_PER_YEAR = 365.25 * 24 * 3600
    return mtbf_sec / SEC_PER_YEAR

# Typical Efinity Titanium FF (estimate from C_2 ≈ 20-50 ps)
# NOTE: Efinity does not publish FF constants — industrial typical values are used here
T_s_ps = 10_000       # 10 ns slack
C_1    = 1e-3         # aperture constant
C_2_ps = 40           # 40 ps time constant
f_d_Hz = 1e6          # 1 MHz data toggle
f_c_Hz = 100e6        # 100 MHz clock

years = mtbf(T_s_ps, C_1, C_2_ps, f_d_Hz, f_c_Hz)
print(f"Estimated MTBF: {years:.2e} years")
# Output: ~10^200+ years (consumer-grade target easily met)

Note: Efinity does not publish the C_1 / C_2 constants (unlike Xilinx / Intel) — the script is for order-of-magnitude estimation only; precise values require actual silicon measurements or equivalent-process data from Intel TimeQuest.

7. The Efinity 2-FF synchronizer (async_reg)

7.1 The async_reg attribute

Key synthesis attribute: marks registers as CDC synchronizers — synthesis is forbidden from merging / optimizing / duplicating these registers.

"To designate a register as a synchronizer, use the async_reg synthesis attribute. When async_reg is true, synthesis does not perform optimization to reduce, merge, or duplicate these registers." — Source: C:\Efinity\2026.1\doc\topics\tim-clk-relationships.html ([A3.3])

7.2 Complete RTL template

module cdc_sync_2ff #(
    parameter [0:0] INIT = 1'b0
) (
    input  wire dst_clk,
    input  wire dst_rst_n,
    input  wire async_in,
    output wire sync_out
);
    (* async_reg = "true" *)
    reg meta, settled;

    always @(posedge dst_clk or negedge dst_rst_n) begin
        if (!dst_rst_n) begin
            meta    <= INIT;
            settled <= INIT;
        end else begin
            meta    <= async_in;
            settled <= meta;
        end
    end

    assign sync_out = settled;
endmodule

Source: recommended template based on [A3.4] tim-clk-syncronizers.html

7.3 VHDL equivalent

library ieee;
use ieee.std_logic_1164.all;

entity cdc_sync_2ff is
    generic (INIT : std_logic := '0')
    port (
        dst_clk    : in  std_logic;
        dst_rst_n  : in  std_logic;
        async_in   : in  std_logic;
        sync_out   : out std_logic
    );
end entity;

architecture rtl of cdc_sync_2ff is
    attribute async_reg : boolean;
    signal meta, settled : std_logic;
begin
    attribute async_reg of meta, settled : signal is true;

    process(dst_clk, dst_rst_n)
    begin
        if dst_rst_n = '0' then
            meta    <= INIT;
            settled <= INIT;
        elsif rising_edge(dst_clk) then
            meta    <= async_in;
            settled <= meta;
        end if;
    end process;

    sync_out <= settled;
end architecture;

Source: [A1] Efinity Timing Closure User Guide §5 "Metastable Synchronizer Circuit"

8. The 3-FF synchronizer: when it is needed

8.1 Academic advice (formal.org [B9])

"The resolution time doubles and the MTBF improves exponentially — typically by many orders of magnitude. For most technologies and clock frequencies, two flip-flops provide MTBF measured in millions or billions of years, which is adequate for functional correctness. High-reliability designs occasionally use three flip-flops for an additional exponential improvement." — Source: [B9] formal.org Module 7

8.2 When to upgrade to 3-FF

Condition Recommendation
Ordinary consumer / industrial (target 10⁹ years) 2-FF + async_reg
Setup slack < 200 ps 3-FF
Destination clock ≥ 500 MHz 3-FF (short slack time)
Aerospace / medical 3-FF + self-checks
Known poor silicon metastability behavior 3-FF

8.3 Efinity 3-FF template

module cdc_sync_3ff #(
    parameter [0:0] INIT = 1'b0
) (
    input  wire dst_clk,
    input  wire dst_rst_n,
    input  wire async_in,
    output wire sync_out
);
    (* async_reg = "true" *)
    reg stage1, stage2, stage3;

    always @(posedge dst_clk or negedge dst_rst_n) begin
        if (!dst_rst_n) begin
            stage1 <= INIT;
            stage2 <= INIT;
            stage3 <= INIT;
        end else begin
            stage1 <= async_in;
            stage2 <= stage1;
            stage3 <= stage2;
        end
    end

    assign sync_out = stage3;
endmodule

9. Worked example: the Intel TimeQuest MTBF report

9.1 Report sample (quoted by UBC [B3])

Synchronizer Chain #1: Typical MTBF is Greater than 1 Billion Year
Chain Summary Statistics
Source Node   Typical MTBF (years)   Property
included in   Design MTBF            Yes
Greater than 1 Billion   Value

Source: [B3] UBC ELEX 7660 Lec 11 (TimeQuest report quotation)

9.2 Interpretation

  • Typical = typical silicon (typical process / voltage / temperature corner)
  • Greater than 1 Billion Year = the usual design target is met
  • Design MTBF = the combined value of the MTBF of all synchronizer chains in the design

9.3 Intel TimeQuest command

# Report MTBF in TimeQuest
report_mtbf
# Outputs something like the "Greater than 1 Billion Year" above

9.4 The Efinity alternative

Efinity does not support MTBF reports. Recommended practice: 1. Use Efinity report_timing to verify the synchronizer setup slack > 0 (preferably > 500 ps) 2. Use the §6.3 script to estimate the MTBF order of magnitude 3. For critical paths (medical / aerospace), use third-party formal verification (formal.org / JasperGold)

10. Design guidelines

10.1 Minimize the number of CDC crossings

Principle: avoid crossing domains whenever you can.

"To avoid CDC problems you should minimize clock domain crossings, use only commonly-accepted synchronization methods and ensure the MTBF calculated by CAD tools are appropriate for the application." — Source: [B3] UBC ELEX 7660 Lec 11

10.2 Use standard patterns

Principle: pick one of 2-FF / Gray code / handshake / async FIFO.

"Use only commonly-accepted synchronization methods." — Source: [B3] UBC ELEX 7660 Lec 11

See the pattern selection table in fpga-cdc-patterns.md §9.

10.3 async_reg is mandatory

Principle: every synchronizer FF must carry async_reg = "true".

"When async_reg is true, synthesis does not perform optimization to reduce, merge, or duplicate these registers." — Source: C:\Efinity\2026.1\doc\topics\tim-clk-relationships.html ([A3.3])

Counter-example (the synthesizer may optimize incorrectly):

// Wrong: two synchronizer FFs without async_reg
reg sync_ff1, sync_ff2;
always @(posedge dst_clk) sync_ff1 <= async_in;
always @(posedge dst_clk) sync_ff2 <= sync_ff1;
// Synthesis may: merge them into a single FF, or optimize away the second one → MTBF is lost

10.4 No combinational logic between synchronizer stages

Principle: there must be no combinational logic between synchronizer stages — otherwise the settling time T_s is insufficient.

// Wrong: combinational logic in between
always @(posedge dst_clk) sync_ff1 <= async_in;
always @(posedge dst_clk) sync_ff2 <= sync_ff1 & other_signal;  // Wrong!
// Correct:
always @(posedge dst_clk) sync_ff2 <= sync_ff1;

10.5 A reset synchronizer is mandatory

Principle: before an asynchronous reset is released, it must pass through a 2-FF synchronizer.

See the reset synchronizer template in fpga-cdc-patterns.md §8.2.

10.6 Beware over-short pulses

Principle: a crossing pulse width must be ≥ 1 destination period (see the DAC case in fpga-cdc-patterns.md §7).

Term Meaning
