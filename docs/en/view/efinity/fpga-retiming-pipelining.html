1. Why retiming is needed

The FPGA frequency handicap:

"Low clock frequencies are one of the drawbacks of the FPGA technology. According to [1], the clock frequency of FPGA designs increased only by 3.8× between 1999 and 2009. In the same time period, the CPU frequencies increased more than 9× from around 400 MHz to 3.6 GHz. For the 90 nm technology, compared to an ASIC, FPGA designs operate at 3 to 4× lower clock frequency." —— Source: [B6] University of Twente FPGA Pipelining Paper (Asghar et al.)

"Since the invention of the FPGA, the logic density has grown by a factor 10,000, whereas the maximum clock frequency has only increased by 100x." —— Source: [B6] Twente

FPGA vs ASIC quantified comparison:

"FPGAs incur 3–4× longer delays, 5–15× greater area usage, and 5–14× higher power consumption than ASICs." —— Source: Kuon & Rose 2007 (cited via [B5] arXiv 2510.26985)

Conclusion: on FPGAs you must actively apply retiming / pipelining to approach ASIC performance.

2. Retiming theory (Leiserson)

2.1 The classic definition (Leiserson 1983)

"The idea of automatic pipelining was first introduced by Leiserson et al. [8] with an approach called retiming. The retiming is an optimization technique, which attempts to replace the existing registers in a design to achieve certain optimization goals (e.g., reducing the delay of the critical path). This optimization can thus improve the throughput of a system while keeping the initial latency unchanged." —— Source: [B6] Twente (citing Leiserson 1983)

Core properties: - Leaves the combinational structure untouched—only register positions move - Preserves observable behavior—the circuit remains functionally equivalent - Keeps latency unchanged (the key difference from pipelining)

2.2 Mathematical description

Retiming label r(v): the retiming label of each node v = the number of registers moved to v's incoming edges.

A legal retiming:

r(v) ≥ 0                              (no negative delay)
r(v) − r(u) ≤ w(e) for each edge e    (retiming per edge must not exceed the original register count)

Key property (Leiserson): after retiming, the minimum clock period is Φ* = max over cycles C { (W(C) - w(C)) / |C| } + 1, where W(C) = the maximum delay around the cycle.

Engineering implication: retiming shortens the critical path by balancing delays across cycles.

2.3 A simple example (CSDN [B7]/[C1])

// Original design: 3 adders in series, all registers at the end
always @(posedge clk) begin
    temp1 <= a + b;
    temp2 <= temp1 + c;
    result <= temp2 + d;
end
// Critical path delay = (a+b) + (temp1+c) + (temp2+d) → too long

// After retiming: registers between each stage (balanced stages)
always @(posedge clk) begin
    temp1 <= a + b;
    temp2 <= temp1 + c;
    result <= temp2 + d;
end
// The synthesis tool automatically redistributes registers across the combinational logic

Source: [C1] CSDN FPGA optimization guide §"Retiming example"

3. C-Slow Retiming

3.1 Concept (Weaver et al., UC Berkeley)

"C-slow retiming is a process of automatically increasing the throughput of a design by enabling fine grained pipelining of problems with feedback loops... each design register is first replaced with c registers before retiming... The effect of c-slow retiming is to enable pipelining of the critical path, even in the presence of feedback loops." —— Source: [B6] Twente (citing Weaver et al., Iowa State)

3.2 Steps

  1. Replace every original FF with c FFs (c-slowing)
  2. Run Leiserson retiming on the c-slowed design
  3. The critical path can now be broken by c-slowing (even in the presence of feedback loops)

3.3 Engineering implications

  • Throughput improves c× (latency unchanged)
  • Area grows c× (FF count)
  • Fits: streaming / DSP / video pipelines

3.4 Efinity support

Efinity efx_map --seq_opt 1 + --retiming 2 (advanced) implicitly performs c-slow-like optimization (decided automatically during synthesis), but there is no explicit c-slow CLI parameter.

See optimization-guide.md §"Retiming".

4. Integrated Retiming + Placement

4.1 Singh & Brown FPGA 2002 (U Toronto)

"Retiming is a synchronous circuit transformation that can optimize the delay of a synchronous circuit by moving registers across combinational circuit elements. The combinational structure remains unchanged and the observable behavior of the circuit is identical to the original." "Our experiments show that the integration of retiming with placement results in 19% better clock periods in comparison to the application of retiming before the place and route steps." —— Source: [B6] Twente (citing Singh & Brown, FPGA 2002)

Key finding: optimizing retiming jointly with placement beats the serial "retiming → placement" flow by 19% on clock period.

4.2 Efinity implementation

Efinity integrates retiming into efx_pnr (the P&R stage); combined with synthesis --retiming 2 (advanced), it achieves joint retiming + placement optimization.

See optimization-guide.md §"P&R optimization".

5. Pipelining: Latency vs Throughput

5.1 The core trade-off

Scheme Latency Throughput
Not pipelined L 1/L (Hz)
N-stage pipeline L (latency grows by ~N cycles) 1/Tcycle (Hz) — a large improvement

5.2 Pipelining example (8-tap FIR)

// Not pipelined: combinational delay = 8 × (mul + add) → long critical path
module fir_8tap_comb (
    input  wire clk,
    input  wire [15:0] x_in,
    output reg  [31:0] y_out
);
    reg [15:0] x [7:0];
    wire [31:0] coef [7:0] = '{...};
    always @(posedge clk) x[0] <= x_in;
    always @(posedge clk) x[1] <= x[0];
    // ... 7 delay stages
    always @(posedge clk) y_out <=
        x[0]*coef[0] + x[1]*coef[1] + ... + x[7]*coef[7];
endmodule
// fMAX limited by the 8× mul-add chain → tens of MHz

// Pipelined: registers break every stage → fMAX approaches a single mul-add
module fir_8tap_pipe (
    input  wire clk,
    input  wire [15:0] x_in,
    output reg  [31:0] y_out
);
    reg [15:0] x [7:0];
    reg [31:0] acc [7:0];
    wire [31:0] coef [7:0] = '{...};
    integer i;
    always @(posedge clk) begin
        x[0] <= x_in;
        for (i = 1; i < 8; i = i + 1) x[i] <= x[i-1];
        acc[0] <= x[0] * coef[0];
        for (i = 1; i < 8; i = i + 1) acc[i] <= acc[i-1] + x[i] * coef[i];
        y_out <= acc[7];
    end
endmodule
// fMAX approaches a single mul-add → hundreds of MHz, throughput ×N

5.3 Choosing between latency and throughput

Application Choice
Control logic / state machines no pipelining (latency first)
FIR / FFT / signal processing deep pipeline (throughput first)
Video processing moderate pipeline (latency ≤ 1 frame)
Processor pipelines 5-20 stage pipeline (e.g., 5-stage RISC-V)

6. Efinity --retiming parameter

6.1 Three modes

Value Behavior Use case
0 disabled the RTL is already hand-pipelined
1 enabled — moves registers forward/backward across combinational logic to balance path delays before the default value
2 (default) advanced mode — more aggressive than mode 1, recommended for Titanium complex designs that need maximum fMAX

Source: C:\Efinity\2026.1\doc\topics\syn-retiming.html ([A3])

6.2 Official description (verbatim)

"The Efinity software includes an option for retiming. You enable it by setting the --retiming option to 1 in Project Editor > Synthesis tab. When this option is turned on, the software moves registers forward or backward to improve the design's performance." —— Source: C:\Efinity\2026.1\doc\pdf\efinity-synthesis.pdf §4 "Retiming" ([A2])

6.3 Limitations

It can only redistribute among existing registers and cannot create new registers. It suits combinational paths whose pipelines are not deep enough. —— Source: optimization-guide.md §1.2 (based on --help output)

6.4 CLI / GUI invocation

# CLI: efx_map
efx_map --retiming 2 --seq_opt 1 ...

# GUI: Project Editor → Synthesis tab → Retiming = 2

See toolchain-reference.md §"efx_map".

7. Efinity --infer-clk-enable

Purpose: converts gated clocks into clock enables—avoiding the skew/hold problems gated clocks bring.

"Infer Clock Enable Option ... Converts gated clock patterns to clock-enable logic, removing clock tree distortion." —— Source: C:\Efinity\2026.1\doc\topics\syn-options-infer-ce.html ([A3])

Benefits: - No gated clock network is created (avoids skew) - Keeps the global clock timing clean - Automatically inserts (* syn_preserve *) to preserve registers

7.1 Example

// Gated clock (automatically converted to CE during synthesis)
always @(posedge gated_clk)
    if (enable) reg_data <= reg_data_next;

// Equivalent after synthesis
always @(posedge sys_clk)
    if (enable) reg_data <= reg_data_next;

7.2 CLI parameter

efx_map --infer-clk-enable ...

See toolchain-reference.md.

8. Efinity --seq_opt

Purpose: synthesis optimization for sequential logic—optimizes state machines and register-to-register paths.

Value Effect
0 disabled
1 (default) enabled — optimizes the sequential-logic synthesis result
--seq-opt-sync-only optimizes only synchronous set/reset logic

Source: optimization-guide.md §1.3

Typical effects: - Automatically retimes synchronous set/reset chains - Optimizes state machine encoding (one-hot → binary, etc.) - Balances FSM registers against logic paths

9. Retiming vs Pipelining: which to use when

Scenario Recommendation Reason
Existing RTL close to fMAX --retiming 2 automatically balances the critical path
Deep combinational logic (≥8 LUTs) add RTL pipeline stages + --retiming 2 synthesis + RTL together
Heavy feedback loops rewrite RTL with c-slow + --retiming 2 c-slow explicitly breaks the loop
Latency must not change retiming only retiming preserves latency; pipelining adds it
Latency can grow pipelining higher performance ceiling
DSP-heavy designs RTL pipelining + --retiming 2 + --dsp-input-regs-packing multi-level optimization
State machines (FSM) --seq_opt 1 purpose-built for FSM optimization

9.1 Decision flow

START
│
├── How many LUT levels on the existing RTL critical path?
│   ├── ≤ 3 LUTs → defaults are fine, no optimization needed
│   ├── 4-6 LUTs → --retiming 2 (automatic retime)
│   └── > 6 LUTs → add RTL pipeline stages + --retiming 2
│
├── Does the design have feedback loops?
│   ├── No → retiming works automatically
│   └── Yes → rewrite RTL with c-slow (each FF replaced by c FFs)
│
├── Is latency constrained?
│   ├── Strictly → retiming only (latency untouched)
│   └── Flexible → retiming + pipelining
│
└── DSP block utilization?
    ├── High → --dsp-input-regs-packing + pipeline the RTL input registers
    └── Low → defaults are fine

10. Practical RTL examples

10.1 Adder chain retiming (CSDN [C1])

// ===== Original =====
module add_chain_orig (
    input  wire        clk,
    input  wire [15:0] a, b, c, d,
    output reg  [15:0] result
);
    reg [15:0] temp1, temp2;
    always @(posedge clk) begin
        temp1  <= a + b;
        temp2  <= temp1 + c;
        result <= temp2 + d;
    end
endmodule
// Critical path = (a+b) + (temp1+c) + (temp2+d) = 3 adders in series

// ===== After retiming (automatic in synthesis) =====
// The synthesizer inserts FFs between the adders:
//   stage1: temp1 <= a + b
//   stage2: temp2 <= temp1 + c
//   stage3: result <= temp2 + d
// Equivalent structure + latency grows by 2 cycles + fMAX approaches a single adder

10.2 C-slow FIR filter (Twente [B6])

// Original 4-tap FIR (feedback)
module fir_4tap_orig (
    input  wire        clk,
    input  wire [15:0] x,
    output reg  [31:0] y
);
    reg [15:0] d1, d2, d3;
    wire [31:0] coef [3:0] = '{16'h0001, 16'h0002, 16'h0003, 16'h0004};
    always @(posedge clk) begin
        d1 <= x;
        d2 <= d1;
        d3 <= d2;
        y  <= (d3 * coef[3]) + (d2 * coef[2]) + (d1 * coef[1]) + (x * coef[0]);
    end
endmodule

// ===== C-slowed (c=2, each FF → 2 FFs) =====
// Throughput ×2 (one new sample accepted every 2 cycles)
module fir_4tap_cslow2 (
    input  wire        clk,
    input  wire [15:0] x,
    output reg  [31:0] y0, y1
);
    reg [15:0] d1_0, d1_1, d2_0, d2_1, d3_0, d3_1;
    wire [31:0] coef [3:0] = '{16'h0001, 16'h0002, 16'h0003, 16'h0004};
    always @(posedge clk) begin
        // Interleaved input: x valid every other cycle
        d1_0 <= x;
        d1_1 <= d1_0;
        d2_0 <= d1_1;
        d2_1 <= d2_0;
        d3_0 <= d2_1;
        d3_1 <= d3_0;

        // Two parallel computation lanes
        y0 <= (d3_0 * coef[3]) + (d2_0 * coef[2]) + (d1_1 * coef[1]) + (d1_0 * coef[0]);
        y1 <= (d3_1 * coef[3]) + (d2_1 * coef[2]) + (d3_0 * coef[1]) + (d2_0 * coef[0]);
    end
endmodule

Source: based on the [B6] Twente c-slow retiming pattern

Appendix A — Key terminology

Term Meaning
Retiming moves register positions to shorten the critical path; latency preserved
Pipelining inserts registers between combinational logic to raise throughput; latency increases
C-Slow replaces each FF with c FFs so retiming can break feedback loops
fMAX maximum operating clock frequency
Critical Path the path with the worst slack
Latency input-to-output delay (in cycles)
Throughput data processed per unit time (samples/second)
