1. Why static timing analysis (STA)

STA (Static Timing Analysis): without any stimulus vectors, it traverses all timing paths in the design and computes worst-case delays. It is the standard approach for timing verification in ASICs and FPGAs.

vs DTA (Dynamic Timing Analysis):

"Dynamic Timing Analysis: Back-annotates the placement-and-routing delays into the gate-level netlist for simulation. Disadvantage: Cannot produce exhaustive test vectors, so some paths may have hidden timing issues. Static Timing Analysis: Uses exhaustive enumeration of all timing paths, computes propagation delays, checks setup and hold. No input vectors needed, exhausts all paths, fast runtime, low memory." —— Source: [B8] CSDN STA Deep Dive

"Two problems with either approach (Dynamic Timing): 1) Analysis was only as good as simulations – a problem was only found if exercised by the sim. 2) Logic simulations were 5-10 times slower." "Static Timing is more comprehensive. Calculate the delay for every possible logical path in the design. The worst case path determines the max freq." —— Source: [B2] UTEP EE5375 (MacDonald)

STA tool vendors (vendor-neutral): - Xilinx Vivado Timing Engine - Intel Quartus Prime TimeQuest - Synopsys PrimeTime / DC - Efinity integrated STA (based on PrimeTime, invoked automatically by efx_run.bat --flow compile)

Source: [B8] CSDN STA Deep Dive (tool list section)

"The introduction of Static Timing Analysis (STA) in the 1980s revolutionized digital design by enabling simulation-free timing verification." —— Source: [B5] arXiv 2510.26985 (Darvishi, 2020)

2. The four standard timing paths

# Path type Name Start End Efinity SDC constraint
1 Reg-Reg clock→clock register CLK register D create_clock + (multi-cycle/false path exceptions)
2 In-Reg input→register Input Port register D set_input_delay
3 Reg-Out register→output register CLK Output Port set_output_delay
4 In-Out input→output (purely combinational) Input Port Output Port set_input_delay + set_output_delay (+ set_max_delay)

Source: [B8] CSDN STA Deep Dive ("Four standard timing paths"); [B2] UTEP EE5375 (equivalent classification: "Clock-to-Setup / Clock-to-Pad / Pad-to-Setup / Pad-to-Pad")

Practical implications for Efinity: - Paths 1 + 2 + 3 need a complete SDC before STA is correct - Path 4 is often forgotten—if left unconstrained, the missing set_max_delay makes the P&R tool fall back to the most permissive default (mismatched with the functional frequency)

Source: [B7] CSDN timing analysis ("If you don't add constraints, the tool uses a very permissive default that only guarantees basic connectivity")

3. Setup Time (Tsu)

Definition: the minimum time that data (at the D pin) must remain stable before the active clock edge (the capture edge) arrives.

"The Setup time (t_su) is the time required for the input to be stable before a clock edge." —— Source: [B4] MPI Lesson 11 (Dr. Davide Cieri, Sep 2024)

Minimum clock period equation:

t_clk(min) = t_su + t_h + t_p

where t_p = data path delay (Tco + Tlogic + Tnet).

Source: [B4] MPI Lesson 11 ("Minimum clock period equation")

Setup timing equation (data must arrive before the requirement):

T_dataArrival + T_setupRequirement ≤ T_clockArrival

"Setup time (Tsetup) is the minimum duration that data must be stable before the clock's active edge to ensure correct capture by a flip-flop." —— Source: [B5] arXiv 2510.26985

A setup violation = data too slow (not ready for capture at the next capture edge).

Tsu magnitude (FPGA vs ASIC):

Process / device Tsu (ps) Th (ps)
7nm ASIC 45 35
Modern FPGA (Kintex UltraScale+ etc.) 180 120

"Experimental results show ASICs achieve superior timing—45ps setup and 35ps hold—while modern FPGAs remain competitive with 180ps setup and 120ps hold times." —— Source: [B5] arXiv 2510.26985

4. Hold Time (Th)

Definition: the minimum time that data (at the D pin) must remain stable after the active clock edge arrives.

"The Hold time (t_h) is the minimum amount of time required for the input to be stable after the clock edge." —— Source: [B4] MPI Lesson 11

Hold timing requirement: the data arrival time must be later than the hold requirement time.

"Hold requirement is the time after the edge that data should remain valid. ... Worst case is a shift register with no logic between flip-flops." —— Source: [B2] UTEP EE5375

A hold violation = data too fast (it overruns the previous data that the current clock edge is sampling).

Key engineering properties: - Hold violations are independent of clock frequency—a slower clock cannot fix a hold violation - Hold checks must be performed at the fastest PVT corner (fast process / low voltage / high temperature) - Hold violations cannot be fixed by lowering the frequency—buffer delay must be added

"Hold times violations are only possible due to the positive clock skew. Sinister problem. Fabricated chip cannot be fixed by slowing down the clock." —— Source: [B2] UTEP EE5375

5. Clock-to-Output Tco

Definition: the time from the clock edge (capturing the data) to a stable output at Q, mainly the time for data to transfer from the master latch to the slave latch output.

"Tco refers to the time from clock edge capturing data to stable output Q, mainly the time for data to transfer from master latch to slave latch output." —— Source: [B8] CSDN STA Deep Dive

Tco is included in the Data Arrival Time:

Data Arrival Time = T_clk_launch + Tcko + T_logic + T_net

In the Efinity timing report, Tco appears as the cell delay with model name = ff, for example:

Data Path
pin name             model name    delay (ns)
============================================
 src_reg|clk-to-q    ff            0.350
 ...

Source: C:\Efinity\2026.1\doc\topics\tim-synth-hi-fanout.html (timing report excerpt)

6. The Setup Slack formula

Slack = Data Required Time − Data Arrival Time
       = (Capture Clock Period − T_setup − T_uncertainty) − (Launch Edge + T_co + T_logic + T_net)

"Calculate the required arrival time (RAT) and the actual arrival time. The actual should be before the required. How much before is your slack." —— Source: [B2] UTEP EE5375

Interpretation: - Slack > 0: met (positive margin) - Slack = 0: marginal (any PVT variation causes a violation) - Slack < 0: violation (data arrives too late)

Generic setup fix directions (vendor-neutral, 5 classes):

  1. Logic restructuring — fewer logic levels / balanced levels / shared subexpressions
  2. Cell upsizing — higher-drive cells on the critical path
  3. Buffer / inverter insertion — break up long nets, reduce RC delay
  4. Retiming / pipelining — move registers across logic (see fpga-retiming-pipelining.md)
  5. Multi-Cycle Path (MCP) — only when the data rate is actually slower (see fpga-timing-exceptions-cookbook.md)

Source: cross-vendor synthesis — EcrioniX STA Tutorial + UTEP EE5375 + Intel AN 584 v21.3 §6

7. The Hold Slack formula

Slack = Data Arrival Time − Data Required Time
       = (Launch Edge + T_co_min + T_logic_min + T_net_min) − (Capture Clock + T_hold)

"Calculate the required arrival time (RAT) and the actual arrival time. The actual should be after the required. How much after is your positive slack." —— Source: [B2] UTEP EE5375

Interpretation: - Slack > 0: met - Slack < 0: violation (data too fast)

Generic hold fix directions:

  1. Buffer / delay cell insertion — add delay on the short path; never make the path faster
  2. Avoid direct FF-to-FF connections — put combinational logic between FFs to provide intrinsic delay

Source: cross-vendor synthesis — UTEP EE5375 + Intel AN 584 v21.3

"Fix Hold violation by inserting delay elements. NEVER speed up the path." —— Source: UTEP EE5375 ([B2]) + Intel AN 584 ([B1])

8. Clock Skew

Definition: the difference in arrival delay of the same clock at different registers.

"Skew is the difference in clock arrival time between any two flip-flops." —— Source: [B2] UTEP EE5375

How positive/negative skew affects setup/hold

Skew sign Effect on setup Effect on hold
Positive skew (capture later than launch) Helpful (widens the capture window) Harmful (hold violation risk ↑)
Negative skew (capture earlier than launch) Harmful (narrows the capture window) Helpful (mitigates hold risk)

Worked example (UTEP EE5375 [B2])

Positive skew — good for setup:

Launch = 1ns, Logic = 9ns, Setup = 1ns, Skew = -2ns, Period = 10ns
Setup Slack = +1 ns

Positive skew — bad for hold:

Launch = 1ns, Setup = 1ns, Skew = -3ns → Hold Slack = -1 ns (violation)

Key design implications: - A balanced clock tree (low skew) is the engineering goal that benefits both setup and hold - Efinity actively adjusts clock phases via beneficial skew (slack borrowing), lending slack from fast paths to slow ones

"Beneficial skew (sometimes called 'slack borrowing') is a process in which the software adjusts clocks to better close timing." "This option is only available for Titanium and Topaz FPGAs." —— Source: C:\Efinity\2026.1\doc\topics\tim-beneficial-skew.html ([A3.12])

9. Jitter / Uncertainty

Jitter = the time deviation of clock edges from their ideal positions (short-term noise) Uncertainty = extra timing margin the designer deliberately adds (covering jitter + margin + OCV)

Efinity SDC form

set_clock_uncertainty -to clk -setup 0.06

"How to Set Clock Uncertainty ... set_clock_uncertainty -to clk -setup 0.06" —— Source: C:\Efinity\2026.1\doc\pdf\efinity-timing-closure.pdf §5 "How to Set Clock Uncertainty" ([A1])

set_clock_uncertainty affects both setup and hold checks—typical values: - Setup: 100 MHz period → 60–100 ps - Hold: 5–20 ps (just to cover on-chip variation)

"The clock insertion delay is the time it takes for a clock signal to travel from the pad of a GPIO configured as a global clock (GCLK) through the global clock network to the destination register. This document calls it the 'base' clock insertion delay." —— Source: AN 042 v1.0 §A4.3 ([A4.3])

See fpga-clock-constraints-cookbook.md §6.

10. Logic delay vs routing delay

Logic delay (Tlogic): sum of the cell delays of combinational logic (LUT / MUX / adder / DSP) Routing delay (Tnet): signal propagation delay over the net (RC)

"Propagation delay is the time needed for a signal to travel from a source to a destination component. Sources of Propagation Delay: - Logic Delay: The delay introduced by the combinational logic (e.g., LUTs, multiplexers). - Routing Delay: The delay caused by the interconnects or wiring between logic elements." —— Source: [B4] MPI Lesson 11

"Every time a signal passes through a LUT, flip-flop, or routing switch, there is a small delay called logic delay. The signal traveling on the metal wire connecting these logic elements also produces delay, called routing delay or path delay. These two delays together constitute the total delay from point A to point B." —— Source: [B7] CSDN timing analysis

FPGA architecture implications: - In a LUT4 architecture (Efinity Trion), each LUT has only 4 inputs; deep combinational chains (≥3 LUTs with no register in between) easily trigger setup violations - LUT5/6 (Xilinx 7-series 6-LUT) occupies more area but packs more logic per level - On the global clock network, Efinity skew is usually <0.1 ns (see timing-analysis-guide.md §1.3)

Source: synthesis — [B6] Twente FPGA Pipelining Paper + timing-analysis-guide.md §1.3

11. Recovery / Removal

Recovery: the asynchronous reset de-assertion must occur a certain time before the clock edge, otherwise the register is not guaranteed to exit the reset state Removal: the asynchronous reset de-assertion must occur a certain time after the clock edge

"The rst_n reset assertion moment must be before recovery time; otherwise the register may not be in reset state. The de-assertion of rst_n must be after the removal time (for active-low reset)." —— Source: [B8] CSDN STA Deep Dive

Engineering implications: - An asynchronous reset must enter the clock domain through a reset synchronizer (2-FF) - Otherwise CDC + asynchronous reset paths may violate recovery/removal - Efinity runs STA checks on asynchronous reset paths by default; an explicit reset synchronizer + async_reg is recommended

See design-rules.md §"Reset design" and fpga-cdc-patterns.md §"Reset signal CDC".
