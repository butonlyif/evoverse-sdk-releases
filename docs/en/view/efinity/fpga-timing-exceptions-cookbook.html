1. set_false_path — cutting paths

Purpose: tells the STA tool not to check these paths (neither setup nor hold); typically used for: - Asynchronous clock domains (a CDC synchronizer is in place, but the synchronizer path is still checked and reported as a setup violation—false path skips it) - Static configuration registers (independent of the clock frequency) - Debug / JTAG / test paths - Reset signals (asynchronous resets do not participate in timing)

1.1 Complete Efinity syntax

# Unidirectional: cut clk1 → clk2
set_false_path -from clk1 -to clk2

# Bidirectional
set_false_path -from clk1 -to clk2
set_false_path -from clk2 -to clk1

# Cut paths to a port
set_false_path -from clk1 -to [get_ports testout]

# Pin-level
set_false_path -from [get_pins {u_fft/clk}] -to [get_pins {u_cpu/data_in[*]}]

Source: C:\Efinity\2026.1\doc\topics\tim-set-false-path.html ([A3.9])

"Provides examples of unidirectional/bidirectional false path constraints." —— Source: C:\Efinity\2026.1\doc\topics\tim-set-false-path.html ([A3.9])

1.2 Complete asynchronous reset example

# All asynchronous reset paths are false paths
set_false_path -from [get_ports arst_n]

1.3 The -through option (path passes through a specific pin)

# Cut all paths passing through a specific pin
set_false_path -through [get_pins {u_xbar/sel}]

See fpga-clock-constraints-cookbook.md §7.

2. set_clock_groups -exclusive — exclusive clocks

Purpose: marks a set of clocks as mutually exclusive (only one active at a time). The STA tool completely skips checks between these clock domains.

Source: C:\Efinity\2026.1\doc\topics\tim-add-clock-set-clock-groups.html ([A3.8])

2.1 Clock mux scenario

# Only clk_a or clk_b active at a time (selected by the sel register)
set_clock_groups -exclusive -group {clk_a clk_b}

# Three-way selection
set_clock_groups -exclusive -group {clk1 clk2} -group {clk3} -group {clk4}

2.2 Decision criteria

Preconditions for using -exclusive: - The clocks are hardware-exclusive (via a mux or clock gate) - No corner case exists where they actually run at the same time - If unsure, use -asynchronous (more conservative)

See fpga-cdc-patterns.md §6.1.

3. set_clock_groups -asynchronous — asynchronous clocks

Purpose: marks clock groups as completely independent (asynchronous clock domains). The STA tool completely skips the checks—this is the standard CDC practice.

Source: C:\Efinity\2026.1\doc\topics\tim-unrelated-clk.html ([A3.7])

3.1 Typical asynchronous scenarios

# sys_clk (100 MHz main system) vs ddr_ck (400 MHz DDR PHY)
set_clock_groups -asynchronous -group {sys_clk} -group {ddr_ck}

# Multiple asynchronous groups
set_clock_groups -asynchronous \
    -group {sys_clk vid_clk ddr_ck} \
    -group {adc_clk usb_clk}

3.2 Caveats

  • Must be paired with a CDC synchronizer (2-FF + async_reg)—set_clock_groups only tells the tool to skip the check; it does not eliminate metastability
  • Use 2-FF for single-bit signals; use a handshake or FIFO for multi-bit data

See the complete templates in fpga-cdc-patterns.md §3.

4. set_multicycle_path — multi-cycle path

Purpose: tells the STA tool that a path does not need to complete in a single cycle and may span multiple clock cycles.

"In a default single-cycle clock relationship, the two clocks are in phase and toggle together. The default setup and hold represent a one clock cycle capture window and is the same as setting a constraint of setup = 1 and hold = 0. The hold is checking one clock cycle before the capture clock edge. When you use the set_multicycle_path constraint, you are adjusting the capture window by shifting it, widening it, or both." —— Source: C:\Efinity\2026.1\doc\topics\tim-multicycle.html ([A3.1])

4.1 Default equivalence

# Default setup = 1, hold = 0 is equivalent to
set_multicycle_path -setup -from a -to b 1
set_multicycle_path -hold  -from a -to b 0

4.2 Typical multicycle 2 scenario

# CPU bus read/write: registers in the CPU clock domain, 2 cycles across to the peripheral clock domain
set_multicycle_path -setup -from [get_clocks cpu_clk] -to [get_clocks peri_clk] 2
set_multicycle_path -hold  -from [get_clocks cpu_clk] -to [get_clocks peri_clk] 1

Rule of thumb: setup N → hold N-1 (see §10.1).

Source: C:\Efinity\2026.1\doc\pdf\efinity-timing-closure.pdf §5 "set_multicycle_path" ([A1])

4.3 Slow clock domain to fast clock domain

# Source 50 MHz, destination 200 MHz → data valid only after 4 destination cycles
set_multicycle_path -setup -from [get_clocks slow_clk] -to [get_clocks fast_clk] 4
set_multicycle_path -hold  -from [get_clocks slow_clk] -to [get_clocks fast_clk] 3

See §10.

5. set_max_delay / set_min_delay — custom path constraints

Purpose: applies custom max/min delay constraints to specific paths (no clock identification needed).

5.1 When to use

  • Purely combinational paths (no clocked registers)—must use set_max_delay, not create_clock
  • Specific paths crossing multiple clock domains (more precise than a false path)
  • Module-boundary IO constraints (internal clock relationships irrelevant)

5.2 Complete example

# Impose a 10 ns cap on a cross-clock-domain path (tighter than a single-cycle constraint, but still satisfiable)
set_max_delay -from [get_pins {u_fft/clk}] -to [get_pins {u_cpu/D_reg[*]/D}] 10.0

# Purely combinational path
set_max_delay -from [get_ports data_in[*]] -to [get_ports data_out[*]] 8.0
set_min_delay -from [get_ports data_in[*]] -to [get_ports data_out[*]] 2.0

"set_max_delay / set_min_delay ... Used for combinational paths or specific inter-clock constraints." —— Source: C:\Efinity\2026.1\doc\topics\constraint_setmaxdelay-setmindelay.html ([A3])

6. Which one to use: a decision tree

START
│
├── Does the path need a timing check?
│   ├── No → set_false_path
│   └── Yes ↓
│
├── Is there a clock?
│   ├── No → set_max_delay / set_min_delay (purely combinational path)
│   └── Yes ↓
│
├── Does the path span multiple clock cycles?
│   ├── Yes → set_multicycle_path
│   └── No → default single-cycle constraint (no exception needed)
│
└── Multiple clock domains?
    ├── Exclusive clocks → set_clock_groups -exclusive
    ├── Asynchronous clocks → set_clock_groups -asynchronous (needs a CDC synchronizer)
    └── Same source / known phase → default checks are fine

8. Common pitfalls

8.1 Over-using false paths

Pitfall: marking all cross-domain paths as false paths, causing functional bugs.

"If you don't add constraints, the tool uses a very permissive default that only guarantees basic connectivity. The tool may route critical signals on slow channels, or use non-optimized placement, ultimately causing the design to fail to work." —— Source: [B7] CSDN timing analysis

Correct practice: - Only false-path genuinely false paths (asynchronous resets / static configuration / test) - For cross-domain data paths, use set_clock_groups -asynchronous + a CDC synchronizer - For cross-domain synchronous paths, use set_multicycle_path

8.2 Multicycle setup N but hold = 0 (wrong)

Pitfall: forgetting to also set hold, causing hold violations.

Correct practice: - setup N → hold N-1 (synchronous paths) - setup N → hold 0 (shift-only)

See §10.1.

8.3 set_false_path does not distinguish setup/hold

Pitfall: false path skips both the setup and hold checks—if you only need to skip setup, constrain hold explicitly with set_max_delay.

8.4 Mis-declared clock groups

Pitfall: using -exclusive when the two clocks may actually be active simultaneously (glitch), causing a race condition.

How to decide: - Different frequencies from the same PLL → do not use -exclusive - Outputs of different PLLs → -asynchronous - Multi-way mux selection → -exclusive (provided the mux output is glitch-free)

8.5 Multicycle path with the wrong clock direction

Pitfall: set_multicycle_path -from slow -to fast 4 when the data actually flows the other way.

Fix: verify the path direction with report_timing -from X -to Y.

9. Multicycle shifted capture windows

9.1 Basic concept

A multicycle path affects timing checks by adjusting the position of the capture window:

"When you use the set_multicycle_path constraint, you are adjusting the capture window by shifting it, widening it, or both." —— Source: C:\Efinity\2026.1\doc\topics\tim-multicycle.html ([A3.1])

Two classes of adjustment: 1. Shifted Capture Window (tim-multicycle-shift.html) — moves the window position only 2. Shifted and Widened Window (tim-multicycle-shift-widen.html) — shifts and widens the window at the same time

9.2 The shift formula

setup N → hold N - 1

Meaning: the hold check always starts one cycle before the setup window.

Source: C:\Efinity\2026.1\doc\topics\tim-multicycle-shift.html ([A3])

10. Fast/slow clock multicycle

10.1 Complete formulas

"Constraints between Fast and Slow Clocks" —— Source: C:\Efinity\2026.1\doc\topics\tim-multicycle-fast-slow.html ([A3])

Source clock Destination clock setup N hold formula hold value
Slow Fast N (destination cycles) N - 1 N - 1
Fast Slow N (source cycles) N - 1 N - 1
Same frequency Same frequency N N - 1 N - 1

10.2 Typical example: CPU → peripherals

# CPU 200 MHz (5 ns period) → peripherals 50 MHz (20 ns period)
# CPU data needs 4 CPU cycles to stabilize in the peripheral domain
set_multicycle_path -setup -from [get_clocks cpu_clk] -to [get_clocks peri_clk] 4
set_multicycle_path -hold  -from [get_clocks cpu_clk] -to [get_clocks peri_clk] 3

Interpretation: - Setup N=4: 4 destination cycles allowed (peri_clk 4 × 20 ns = 80 ns) - Hold N-1=3: data must stay stable through the previous 3 destination cycles (the old data must not clobber the new data)

10.3 Complex scenario with a 1:2 frequency ratio

# src 100 MHz → dst 50 MHz (2:1 ratio)
# Data needs 2 cycles to stabilize in the dst domain (→ setup N=2)
set_multicycle_path -setup -from [get_clocks src] -to [get_clocks dst] 2
set_multicycle_path -hold  -from [get_clocks src] -to [get_clocks dst] 1

Source: C:\Efinity\2026.1\doc\topics\tim-multicycle-fast-slow.html ([A3])

10.4 Verification

report_timing -from [get_clocks cpu_clk] -to [get_clocks peri_clk] -path_type full -max_paths 5
# Confirm the "captured by" behavior is as expected
