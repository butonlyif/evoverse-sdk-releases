Efinity Hard IP: DDR Reference

Efinity Hard IP Reference — DDR

Applicable version: Efinity 2026.1 (verified against the installation at C:\Efinity\2026.1) Investigation date: 2026-09-25 Evidence source: Every property name, legal value, and dependency relationship in this document was verified line by line against the Python source code inside the Efinity 2026.1 installation directory; each entry is annotated with file:line. Unless noted otherwise, the source root is C:\Efinity\2026.1\pt\bin\ (abbreviated below as pt\bin\). Companion documents in this series: Efinity ISF Syntax Reference (isf-syntax-reference.md), Efinity File Formats — peri.xml (file-formats-peri-xml.md), Efinity DesignAPI Method Reference (designapi-reference.md), Efinity Hard IP Reference — PLL and OSC (hard-ip-pll-osc.md), Efinity Hard IP — LVDS/MIPI/JTAG Interface Reference (hard-ip-interfaces-jtag.md)

1. Overview and positioning

The DDR hard IP is the hard memory-controller block (Hard Memory Controller + PHY) in Efinity devices, configured through the Interface Designer (PT) and instantiated at compile time by the unified build. The 2026.1 source has two generations of Prop classes; build_ddr_prop selects automatically by device (pt\bin\api_service\property\ddr_prop.py:204-225):

Generation Prop class DB block_type ISF exporter Memory types covered
Basic DDRProp (ddr_prop.py:56) ddr DDRISFBuilder (pt\bin\api_service\exim\isf_exporter.py:2553) DDR3, LPDDR2, LPDDR3
Advanced DDRAdvProp (ddr_prop.py:1360, inherits DDRProp) adv_ddr DDRAdvISFBuilder (isf_exporter.py:2683) LPDDR4, LPDDR4x, etc.

Selection logic (ddr_prop.py:215-225): if the device database supports ddr → basic; if it supports adv_ddr → advanced.

API block_type string: "DDR" (pt\bin\api_service\common\object_db.py:51 API_BLOCK_TYPE, :130 otype2str_map).

This volume has the largest property count of the three: 88 PropIds in the basic version plus 153 in the advanced version, over half of them AXI port properties; §4.5/§7.3 list them one by one, as requested.

2. The creation trio

design.create_block("ddr_inst1", "DDR")                          # 1. Create the block
design.set_property("ddr_inst1", "MEMORY_TYPE", "DDR3", "DDR")   # 2. Set properties one by one (4th argument "DDR")
design.assign_resource("ddr_inst1", "<DDR资源名>", "DDR")         # 3. Assign the DDR hard resource (device-dependent)
  • The legal block_type string list: object_db.py:35-59; create_block raises PTBlkCreateException for unsupported types (pt\bin\api_service\design.py:229-231).
  • create_* is a one-time bootstrap: it must be commented out after the bootstrap compile (AGENTS.md §15; the ISF has no delete command).
  • There is no DDR ISF sample in the official examples (a full search of the 2026.1 examples finds no "DDR" block instance); the §8 example in this document is constructed from the property tables. After constructing it, always self-check with cli/import_gpio.bat --peri <工程>.peri.xml --input <文件>.isf --dry-run (rules-efinity-hard.md §1).

3. Preset-family dedicated APIs (the recommended entry point for DDR configuration)

DDR is the only generic block in the whole toolchain with a preset mechanism (get_all_preset_info accepts only DDR and PMA_DIRECT, design.py:2067). Recommended flow: lay down a preset first, then override individual items.

3.1 API signatures (pt\bin\api_service\design.py)

Method Signature/line Description
get_all_preset_info design.get_all_preset_info(name: str, block_type: str = "DDR") -> List[Tuple[str, str]] (design.py:2059) Lists every preset available for the device as (preset name, description) tuples; only "DDR"/"PMA_DIRECT" are legal for block_type (:2067)
set_preset design.set_preset(...) (design.py:2088) Applies a preset; under the hood it writes the "PRESET" property (:2101)
get_preset design.get_preset(...) (design.py:2105) Reads the current preset name

3.2 The preset five-tuple

The preset data of set_preset is a five-tuple; candidates come from DDRPresetService (ddr_prop.py:818-831 _set_preset; the service object is initialized at :187):

Element Property Meaning
1 MEMORY_TYPE Memory type (DDR3 / LPDDR2 / LPDDR3 / LPDDR4 / LPDDR4x)
2 DQ_WIDTH Controller data width (ctrl_width)
3 MEMORY_WIDTH DRAM device width (dram_width)
4 MEMORY_DENSITY DRAM density (dram_density)
5 MEMORY_SPEED Speed bin / frequency (speedbin)

After a preset is applied, the tool bulk-fills the timing parameters and related values with the preset's defaults for that memory type; individual items can then be overridden with set_property.

5.2 LPDDR2 / LPDDR3 (ddr_api_options.py:38-64 / :66-92)

  • LPDDR2: CL uses the combined RL=x/WL=y format (RL=3/WL=1 … RL=8/WL=4); FPGA_ITERM only 120/OFF; MEM_OTERM levels 120, 34.3, 40, 48, 60, 80.
  • LPDDR3: same family structure as LPDDR2; see ddr_api_options.py:66-92 for the exact levels.
  • LPDDR4/LPDDR4x have no static map: ddr_api_options.py ends at L92; LPDDR4 legal values are provided at run time by the device database (dynamic getattr; a missing map means an empty table). Before configuring LPDDR4, confirm device support with get_all_preset_info, then follow the preset.

6. Property ↔ memory-type dependency matrix (ddr_prop.py:651-760)

Check this before setting properties — setting a type-specific property on an unsupported memory type is rejected by the dependency graph or silently ignored:

Property group DDR3 LPDDR2 LPDDR3 LPDDR4/4x
PRECHARGE_PD, ASR, CL, CWL, RTT_WR, MEM_OTERM, SRT ✅ exclusive — — —
RTT_NOM ✅ — ✅ —
DQ_ODT — — ✅ exclusive —
RL/WL — ✅ ✅ —
BL ✅ ✅ — ✅

Other structural dependencies:

  • CONTROL_TYPE decides control-pin visibility (reset / calib / seq / I2C pins, ddr_prop.py:651-760).
  • TARGET0_EN / TARGET1_EN decide whether the corresponding AXI0_* / AXI1_* pin properties take effect (same source).
  • ISF export dependency order: memory_type → physical_rank → axi0_enabled → axi1_enabled; the exporter emits commands in this order (ddr_prop.py:2360-2374). This explains why MEMORY_TYPE must be set first.

# ...complete the remaining AXI0_* signals one by one per the §4.5 table

# --- Resource assignment ---
design.assign_resource("ddr_inst1", "<DDR资源名>", "DDR")   # the resource name follows the device package; look it up in the device database

LPDDR4 (advanced version) differences: the block is still created with create_block("x","DDR") (the API layer only has "DDR"); the properties switch to the DDRAdvProp names from §7 (e.g. TRPAB/TRPPB replace TRP, and the AXI channels split into AXI0_ARADDR_BUS/AXI0_AWADDR_BUS).

9. Common errors and troubleshooting

Symptom Root cause Fix
set_property reports a nonexistent property Basic/advanced property mixing (e.g. TRP set on an LPDDR4 project, or TCCDMW on DDR3) Confirm the device generation first (ddr vs. adv_ddr); check the §4/§7 property tables
Property value rejected MEMORY_TYPE not set first, so the legal-value map is not loaded (getattr returns an empty dict) MEMORY_TYPE must be the first property set (ISF export order puts memory_type first, ddr_prop.py:2360-2374)
LPDDR4 levels cannot be found LPDDR4 has no static legal-value map; they come dynamically from the device database Follow get_all_preset_info + the GUI; do not hard-code LPDDR4 levels
Abnormal timing values FLOATs are formatted to 3 decimal places; integer properties (ROW_WIDTH etc.) use INT validation Give timings within the §5 ranges; DDRPresenter formatting rules at ddr_prop.py:1082-1094
AXI0_CLK_INOUT_PIN not found The historical name of the 2022.1 spelling bug 2026.1 auto-corrects it to AXI0_CLK_INPUT_PIN (ddr_prop.py:198-202); write INPUT in new code
AXI pins set but not taking effect TARGET0_EN/TARGET1_EN not set to 1 Enable the port first, then set the pins (dependency graph :651-760)
RESET/I2C/SEQ pin errors as unrelated CONTROL_TYPE mode and pin combination mismatch Check §6: control_type decides reset/calib/seq pin visibility
Second compile fails with DDR ... exists A replayed ISF still contains create_block Comment out create_* (AGENTS.md §15)
Individual parameters lost after applying a preset The preset overwrote hand-edited values Fixed order: set_preset first, then set_property overrides
Gate delay changed but no effect GDELAY_OVERRIDE_EN not enabled Set it to 1 first; note the DB values are 'Yes'/'No' (:1052-1164)
