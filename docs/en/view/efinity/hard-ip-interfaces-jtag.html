Key findings:

  1. None of the three families has a dedicated public creation method (same as PLL and DDR) — the public surface is only the generic trio create_block + set_property + assign_resource.
  2. JTAG is the only interface hard IP with an official ISF sample (helloworld-dbg_MULTI_USERS); LVDS and MIPI have no sample anywhere in examples\*.isf → the LVDS/MIPI ISF templates in this volume are constructed from the property tables and must pass the cli/import_gpio.bat --dry-run self-check before use (same treatment as in Efinity Hard IP Reference — DDR).
  3. All three families are subject to the §9 bank-voltage rules: an LVDS bank is forced to 3.3 V, MIPI DPHY requires a 1.2 V bank, and the two cannot coexist in one bank.

1.1 The block_type naming-inversion trap (important)

The two MIPI DPHY-related strings in object_db.py point in opposite naming directions and are extremely easy to get wrong:

What you want Correct block_type string Evidence
Lane-level soft DPHY (discrete lanes, replaces pixel-level MIPI) "MIPI_TX_LANE" / "MIPI_RX_LANE" object_db.py:121-122 (internal names mipi_dphy_tx/rx → MIPI_TX_LANE/MIPI_RX_LANE)
The hard DPHY whole-block IP (complete PHY including PLL/SSC) "MIPI_DPHY_TX" / "MIPI_DPHY_RX" object_db.py:126-127 (internal names mipi_hard_dphy_tx/rx → MIPI_DPHY_TX/MIPI_DPHY_RX)

Mnemonic: a string containing LANE is the lane-level soft DPHY; only a string containing DPHY is the hard DPHY. If you get it wrong, PT parses against the other property set, and the symptoms are rejected properties or behavior that does not match.

1.2 ISF support whitelist

supp_block in isf_exporter.py lists the block types that can enter an ISF (:149-173):

  • Basic: GPIO, PLL, IOBANK, JTAG (:149)
  • Pixel-level MIPI: MIPI_TX, MIPI_RX (:156-157)
  • Hard DPHY: MIPI_DPHY_TX, MIPI_DPHY_RX (:160-161)
  • Lane-level DPHY + LVDS: MIPI_RX_LANE, MIPI_TX_LANE, LVDS_RX, LVDS_TX, LVDS_BIDIR (:164-168)

2. The creation trio

The ISF configuration of every interface hard IP consists of three commands (BlockISFBuilder CommandType, isf_exporter.py:1252-1258; string mapping cmd2str_map :1260-1264):

# 1) Create the instance — one-time bootstrap (allowed only while peri.xml does not exist)
design.create_block("<实例名>", "<BLOCK_TYPE>", [create 额外参数])

# 2) Set properties — idempotent, replayable
design.set_property("<实例名>", "<PROP_NAME>", "<值>", "<BLOCK_TYPE>")

# 3) Assign hardware resources — idempotent, replayable
design.assign_resource("<实例名>", "<RESOURCE>", "<BLOCK_TYPE>")

Key points:

  • The 4th argument of set_property must be the exact block_type string (generic implementation isf_exporter.py:1379-1425).
  • The builder emits assign_resource only when the instance's device (RESOURCE) is non-empty (build_resasg_command, isf_exporter.py:1427-1449) — for JTAG, RESOURCE is JTAG_USER1/JTAG_USER2.
  • Replay-safety contract (Efinity ISF Syntax Reference and hard constraint §15): create_* is a one-time bootstrap; the resident ISF referenced by the project allows only idempotent commands such as set_property / assign_resource / set_iobank_voltage. Comment out the create_* lines immediately after the bootstrap compile generates <design>.peri.xml. See Efinity File Formats — peri.xml for details.
  • LVDS create commands carry extra keyword arguments (emitted by the builder per generation): legacy TX emits tx_mode="<api_mode>" (gen_extra_create_parameter, isf_exporter.py:2225-2235), legacy RX emits rx_conn_type="<api_mode>" (:2334-2344); lane-level DPHY TX emits mode="CLOCK_LANE" or mode="DATA_LANE" by mode (MIPIDPhyTxISFBuilder :1764-1767).

3. JTAG hard IP

JTAG provides boundary scan / a user debug channel after FPGA configuration. It is the only hard IP of the three interface families with an official ISF sample; the property tables and template in this section can be copied verbatim.

3.1 Complete property table

Every entry in jtag_prop_map of jtag_prop.py (:67-79) has no default value (PropData(..., None)) — all properties must be set explicitly. As for legal values, get_valid_option returns an empty set (:230-233), i.e. the ISF layer performs no static enum validation on values; the values are dictated by how PT uses them internally (pin-name conventions below).

DRCK string Pin name (<实例名>_DRCK) — DRCK (Drck clock) pin same as above

4. LVDS hard IP

4.1 Generation mechanism

LVDS comes in three generations selected by design.lvds_type; the builder dispatches on it (isf_exporter.py:340-405; property classes dispatch per generation map, lvds_prop.py RX :355-360, TX :910-915):

Generation TX property class RX property class TX builder Notes
legacy (lvds) LVDSTxProp (:861) LVDSRxProp (:301) LVDSTxISFBuilder (:2167) Basic LVDS on older devices
Adv (adv_lvds) LVDSTxAdvProp (:1074) LVDSRxAdvProp (:468) LVDSTxAdvISFBuilder (:2381, db reads design.lvds_type :2390) The workhorse generation with the fullest property set
V3 (efx_lvds_v3) EfxLvdsV3TxProp (:1643) EfxLvdsV3RxProp (:1656) EfxLVDSTxV3ISFBuilder (:2488, only swaps in IntEfxLVDSV3API) Newer-generation devices

LVDSBidirAdvProp (lvds_prop.py:1369) is not an independent property set but an RX+TX combiner: build_lvds_prop assembles RX/TX properties for adv_lvds (:1411-1416) or efx_lvds_v3 (:1417-1422); is_rx_prop routes by whether the property name contains RX/TX (:1438-1451). 4.4 LVDS constraint rules (verified via check_properties)

  1. Non-NORMAL connection types require deserialization off: when RX_CONN_TYPE is GCLK/RCLK/PLL_CLKIN/PLL_EXTFB, RX_EN_DESER must be disabled, otherwise PT rejects it (lvds_prop.py:447-462, :636-649).
  2. DYNAMIC termination needs a pin: RX_TERM=DYNAMIC requires RX_TERM_PIN.
  3. See §9 for the TX/RX paired constraint: the bank containing LVDS is forced to 3.3 V LVTTL / LVCMOS.

9. Bank-voltage coexistence rules (the key LVDS / MIPI constraint)

Rule engine: IOBankChecker in pt\bin\common_device\iobank\iobank_rule.py hooks two rules at Design Check time (_build_rules :108-113):

  1. io_bank_rule_voltage_assignment (IOBankStandard, :126-151): per bank, verifies that each IO's voltage standard is in the bank's device-database support table — checker.reg.is_io_standard_valid(device_db, bank, standard) (:148-149); on failure it reports "I/O Voltage ... is not supported for the bank" (:150-151). Which voltages a bank supports is defined by the device db; the rule only performs the mechanical check.
  2. io_bank_rule_lvds (IOBankLVDS, :155-195): if any LVDS instance exists in a bank, the bank's IO standard must equal LVDS_IO_STANDARD = "3.3 V LVTTL / LVCMOS" (:36); otherwise it reports "I/O Voltage has to be set to ... when LVDS is used" (:193-194). The set of LVDS banks is maintained by set_lvds_bank_map (:61-106).

Coexistence conclusions derived from this (practical constraints, consistent with the existing hard constraints):

  • A MIPI DPHY bank must be 1.2 V — the exact value is defined by the device-db support table (iobank_rule.py only performs the mechanical check; the :48 comment notes that MIPI DPHY follows the same voltage rule).
  • An LVDS bank is forced to 3.3 V (rule 2 above, hard-coded in source at :36).
  • A bank cannot simultaneously satisfy "1.2 V only" and "must be 3.3 V" → MIPI and LVDS cannot coexist in one bank. The first symptom of a violation is usually an io_bank_rule_voltage_assignment error.
  • Declare bank voltages in the ISF with design.set_iobank_voltage("<bank>", "<voltage>") (idempotent, replay-safe); every IO in the same bank must use an IO standard compatible with that voltage.

Debug procedure: on an io_bank_rule_voltage_assignment error, follow four steps — check the bank's voltage declaration → list the IO standards of every instance in the bank → compare against the device-db support table → split MIPI and LVDS into different banks.
