Efinity Hard IP: PLL and OSC Reference

Efinity Hard IP Reference — PLL and OSC

Applicable version: Efinity 2026.1 (verified against the installation at C:\Efinity\2026.1) Investigation date: 2026-09-25 Evidence source: Every property name, legal value, and default behavior in this document was verified line by line against the Python source code inside the Efinity 2026.1 installation directory; each entry is annotated with file:line. Unless noted otherwise, the source root is C:\Efinity\2026.1\pt\bin\ (abbreviated below as pt\bin\). Companion documents in this series: Efinity ISF Syntax Reference (isf-syntax-reference.md), Efinity File Formats — peri.xml (file-formats-peri-xml.md), Efinity DesignAPI Method Reference (designapi-reference.md), Efinity Hard IP Reference — DDR (hard-ip-ddr.md), Efinity Hard IP — LVDS/MIPI/JTAG Interface Reference (hard-ip-interfaces-jtag.md)

1. Overview and positioning

PLL and OSC are the two on-chip clock-source hard IPs in Efinity devices:

Hard IP Role Creation API block_type string
PLL Phase-locked loop: multiplies/divides/phase-shifts the reference clock into multiple output clocks create_block("name", "PLL") "PLL"
OSC On-chip oscillator: generates a low-frequency clock without any external clock create_block("name", "OSC") "OSC"

Hard constraint (consistent with rules-efinity-hard.md §4): the PLL must be created in the ISF (design.create_block("name", "PLL")) and must not be instantiated in RTL; RTL only declares the pll_clk_out / pll_locked ports. Note that create_* is a one-time bootstrap (see §7 and AGENTS.md §15).

1.1 The six PLL generations (important)

In the 2026.1 source code the PLL is not a single class but an inheritance chain of six generations. When design.create_block("x", "PLL") runs, the tool automatically selects the Prop class for the device model; property writes use the unified uppercase property names, but the available properties and legal values differ per generation:

Generation Prop class (property authority) DB block_type (ISF export layer) Typical device families
v1 simple PLL PLLProp (pt\bin\api_service\property\pll_prop.py:49) pll Trion (T4/T8/T13/T20 series)
v2 advanced PLL PLLAdvProp (pll_prop.py:599, inherits PLLProp) adv_pll Titanium (TiTi60/Ti375, Tz170, etc.)
v3 five-output PLL PLLCompProp (pll_prop.py:1152, inherits PLLAdvProp) comp_pll newer Titanium
v4 PLLV4Prop (pll_prop.py:1674, inherits PLLCompProp) (reuses the v3 path) —
EfxFpll V1 EfxFpllV1Prop (pll_prop.py:1786, inherits PLLV4Prop) efx_fpll_v1 —
EfxFpll V2 EfxFpllV2Prop (pll_prop.py:1990, inherits EfxFpllV1Prop) efx_fpll_v2 newest devices such as Ti125

Inheritance-chain evidence: pll_prop.py:599 class PLLAdvProp(PLLProp), :1152 class PLLCompProp(PLLAdvProp), :1674 class PLLV4Prop(PLLCompProp), :1786 class EfxFpllV1Prop(PLLV4Prop), :1990 class EfxFpllV2Prop(EfxFpllV1Prop).

Each generation has its own legal-value table (api_options) and its own ISF exporter (isf_exporter.py):

  • Legal-value import evidence (pll_prop.py:40-45): pll_api_options → v1_api_ops_map, pll_adv_api_options → v2_api_ops_map, pll_comp_api_options → v3_api_ops_map, pll_v4_api_options → v4_api_ops_map, fpll_v1_api_options, fpll_v2_api_options.
  • ISF exporter chain (pt\bin\api_service\exim\isf_exporter.py): PLLISFBuilder (:1476, db_block_type pll) → PLLAdvISFBuilder (:1495, adv_pll) → PLLCompISFBuilder (:1507, comp_pll) → PLLV3ComplexISFBuilder (:1518, efx_pll_v3_comp) → EfxFpllV1ISFBuilder (:1529, efx_fpll_v1) → EfxFpllV2ISFBuilder (:1540, efx_fpll_v2).
  • There are also a separate PLL_SSC spread-spectrum clock block (block_type "PLL_SSC", PLLSSCISFBuilder at isf_exporter.py:1953, property class pll_ssc_prop.py) and a CM clock block (CMISFBuilder :1452, db_block_type cm_v1); neither is expanded here — see §6.4.

Writing discipline: every "legal value" in this document is annotated with the applicable generation. Mixing legal values across generations is the number-one source of PLL configuration errors.

2. The creation trio

Hard IPs have no dedicated creation method; everything goes through the generic trio (the DesignAPI implementation lives in pt\bin\api_service\design.py, create_block signature at :192):

design.create_block("pll_inst1", "PLL")                      # 1. Create the block (block_type must be "PLL")
design.set_property("pll_inst1", "REFCLK_FREQ", "25.0", "PLL")  # 2. Set properties one by one (the 4th argument must be "PLL")
design.assign_resource("pll_inst1", "PLL_TL0", "PLL")        # 3. Assign the PLL hard resource (3rd argument is the resource name, 4th is "PLL")

Key points (all verified):

  1. block_type strings: use "PLL" for PLL and "OSC" for OSC. The legal-value list is at pt\bin\api_service\common\object_db.py:35-59 (API_BLOCK_TYPE Literal list: GPIO, JTAG, PLL, OSC, MIPI_TX, MIPI_RX, ..., DDR, PLL_SSC, ...); the enum→string mapping otype2str_map is at object_db.py:109-140. Passing an unsupported string raises PTBlkCreateException (design.py:229-231, which checks is_block_supported).
  2. The reference-clock pin GPIO is created separately: an external reference clock needs a design.create_pll_input_clock_gpio("pll_refclk") call (official ISF example: C:\Efinity\2026.1\examples\helloworld-unified\Ti60F225_kit_manual.isf:15), followed by design.assign_pkg_pin("pll_refclk", "B2") to bind the package pin (same file :45).
  3. The 4th argument of set_property (block_type) is mandatory: non-GPIO blocks such as JTAG/PLL/OSC must explicitly pass "PLL"/"OSC".
  4. create_* is a one-time bootstrap: create_block / create_pll_input_clock_gpio may run only once, while the project's peri.xml does not yet exist; every unified build replays the ISF referenced by the project XML onto the persisted peri.xml, and a replayed ISF that still contains create_* fails with ... exists. After the bootstrap compile, the create_* lines must be commented out (AGENTS.md §15, rules-efinity-hard.md §15).

3.3 Output clocks (CLKOUT0–CLKOUT4)

Each output channel has three switch properties plus two frequency properties:

Property pattern Type Legal values Description Evidence
CLKOUTn_EN (n=0–4) BOOL "0"/"1" Enables output n. Do not set other CLKOUTn_* properties on a disabled output channel pll_prop.py:76-80 (EN), :81-85 (PIN), :86-90 (DIV)
CLKOUTn_PIN Pin name (STR) Default "" RTL-side signal name of this output clock pll_prop.py:81-85
CLKOUTn_DIV INT v1: powers of two only [2,4,8,16,32,64,128,256]; v2: any integer 1–256; v3/f1: 1–128 Output divider pll_api_options.py:4-6 (v1 OptionValidator); pll_adv_api_options.py:5,7,9 (v2 RangeValidator(1,256)); pll_comp_api_options.py (v3 1–128)
CLKOUTn_FREQ Read-only — (computed and back-filled by the tool) Output frequency (MHz), computed by calc_pll_clock pll_prop.py:91-95

Important clarification (tool-side evidence): the rule "PLL output dividers support only powers of two" holds only for the v1 simple PLL (the OptionValidator([2,4,...,256]) at api_options\pll_api_options.py:4-6). For the v2 advanced PLL (Titanium etc.), clkout0/1/2_div is a RangeValidator(1,256) (api_options\pll_adv_api_options.py:5-9) — any integer is legal. In the official example C:\Efinity\2026.1\examples\helloworld-unified\Ti60F225_kit_manual.isf:26, Ti60 configures CLKOUT0_DIV="110", and Ti60F225_kit.isf:101 uses CLKOUT0_DIV="27" — neither is a power of two, and both compile directly. Treat this constraint according to the actual device generation in your project.

From v3 on, the 4th/5th output channels are supported: CLKOUT3_EN/PIN/DIV/FREQ/PHASE, CLKOUT4_* (pll_prop.py PropId definitions, :92-98 region); from v4 on, CLKOUT3/4 connection types support GCLK/RCLK (PLLV4Presenter, pll_prop.py:1773-1783).

Precise statement of the 45°-step conclusion: the static phase legal values of the v2 advanced PLL are indeed 45° steps (and the 2026.1 v2 table does not include 315); the v3 five-output PLL offers continuous 0–360 levels. 6. Dedicated APIs (the clock-calculator family)

All of them live in the DesignAPI (pt\bin\api_service\design.py, class DesignAPI starting at :71).

6.1 calc_pll_clock — back-calculate frequencies after manual configuration

design.calc_pll_clock(inst) -> Dict[str, str]   # design.py:1989
  • Prerequisite: configure M/N/O and every CLKOUTn_DIV yourself first.
  • Returns: a property map of the VCO frequency, PLL frequency, and each enabled output frequency (internally via PLLProp.get_frequency_property, design.py:2019).
  • Raises PTBlkEditException if the instance does not exist (design.py:2003-2004).

6.2 auto_calc_pll_clock — automatic solve for target frequencies (recommended)

design.auto_calc_pll_clock(inst,
                           target_freq: Dict[str, str],   # target frequencies (MHz) and phases (degrees)
                           apply_optimal: bool = True,    # True = write the best solution back into the PLL counters
                           result_len: Optional[int] = None  # number of solutions returned, default 5; 0 = all
                          ) -> List[Dict]                  # design.py:2219
  • The key names of target_freq depend on the PLL generation, determined by the calculator parameter mapping (pt\bin\api_service\property\pll_cal_prop.py):
  • Simple PLL (PLLCalcPresenter): inputs include M/N/O/REFCLK_FREQ/CLKOUTn_FREQ/CLKOUTn_PHASE/CLKOUTn_EN/CLKOUTn_DIV etc.; results include VCO_FREQ/CLKOUTn_DIV/...;
  • Five-output PLL (PLLCompCalcPresenter): adds the PHASE_SETTING (psv0–4) parameter;
  • EfxFpllV2 (EfxFpllV2CalcPresenter): adds the inputs FEEDBACK_CM_CLKOUT/FEEDBACK_CM_PHASE/FEEDBACK_CM_FREQ and the results FEEDBACK_CM_DIV/PHASE_SETTING.
  • target_freq=None raises immediately (design.py:2242-2244).
  • Typical usage:
results = design.auto_calc_pll_clock("pll_inst1", {"CLKOUT0_FREQ": "100"})
best = results[0]                      # list of candidate solutions sorted by accuracy
design.set_property("pll_inst1", "M", str(best["M"]), "PLL")
design.set_property("pll_inst1", "N", str(best["N"]), "PLL")
design.set_property("pll_inst1", "O", str(best["O"]), "PLL")
design.set_property("pll_inst1", "CLKOUT0_DIV", str(best["CLKOUT0_DIV"]), "PLL")

8. Common errors and troubleshooting

Symptom Root cause Fix
PTBlkCreateException: block type ... is not supported block_type misspelled (e.g. pll/PLLV2) Only strings from the API_BLOCK_TYPE list are accepted (object_db.py:35-59); for PLL it is always "PLL"
Second compile fails with PLL pll_inst1 ... exists A replayed ISF still contains create_block/create_pll_input_clock_gpio Comment out create_* right after the bootstrap compile (AGENTS.md §15; the ISF has no delete command — do not attempt an "idempotent delete")
set_property rejects a value Cross-generation mixing of legal values (most often CLKOUT0_DIV=110 on v1, or PHASE=315 on v2) Check the device generation against the §4 quick reference; v1 div is powers of two only, v2 phase has no 315
Computed frequencies are all wrong REFCLK_FREQ does not match the actual input; or the counters were changed after computing Re-run calc_pll_clock after changing M/N/O/DIV; or switch to auto_calc_pll_clock
Unknown instance exception Instance name not created or misspelled; or a PLL calculator was called on a non-PLL instance Both design.py:2001-2004 and :2237-2240 validate the object type first
BYPASS/PWDN property errors The 2026.1 DesignAPI has no such properties (refuted, see §3.9) Delete the line; configure the corresponding feature in the GUI
Debating the case of CLKOUT0_CONN_TYPE in the ISF Dual track: API uppercase (GCLK) / DB lowercase (gclk) Copy the DB value from the official ISF; both work when a script writes through the DesignAPI
Bank resource conflict (PLL_TL0 already occupied) PLL resource slots are unique Switch assign_resource to a free resource name; see the device datasheet for the PLL resource count per bank
OSC output has no clock FREQ set on a simple OSC (the property exists only on adv/hposc) The simple OSC has only CLKOUT_PIN (osc_prop.py:34-40); the frequency is fixed by the device
