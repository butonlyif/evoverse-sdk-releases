2. ftdi_program.py — the native JTAG/SPI programming script

2.1 Actual location and invocation entry

The actual path is pgm\bin\efx_pgm\ftdi_program.py (not pgm\ftdi_program.py under the installation root), main class FtdiProgram, with parse_cmdline() at the bottom of the module (pgm\bin\efx_pgm\ftdi_program.py:3148) + main() (same file :3341).

The official command-line entry is pgm\bin\ftdi_pgm.bat:

:: ftdi_pgm.bat:7-8 (read from the actual file)
set PYTHONPATH=%EFINITY_HOME%/debugger/bin;%EFINITY_HOME%/pgm/bin
"python3.bat" pgm\bin\efx_pgm\ftdi_program.py %*

Two key points (evidence pgm\bin\ftdi_pgm.bat:7-8):

  1. PYTHONPATH injects debugger\bin (providing the efx_dbg package) and pgm\bin (providing the efx_pgm package) — ftdi_program.py imports both (ftdi_program.py:147-171, including efx_dbg.jcf/jtag/jtag_chain_detector, efx_pgm.jtag2SpiDriver, etc.).
  2. The bat invokes the script via the relative path pgm\bin\efx_pgm\ftdi_program.py, so pgm\bin\ftdi_pgm.bat must be run from the %EFINITY_HOME% root (or cd /d %EFINITY_HOME% first).

The underlying dependencies are pyftdi (MPSSE/JTAG-SPI) and pyspiflash; the docstring (ftdi_program.py:1-116) gives the ADBUS pin mapping for the FTDI C232HM-DDHSL-0 cable (SCLK=ADBUS0 … CDONE=ADBUS5) plus driver installation notes (udev rules on Linux, zadig to replace the FTDI driver on Windows). On Linux, also watch the udev permissions.

Default clock frequencies and the verify method are set in FtdiProgram.__init__ (ftdi_program.py:193-219):

Item Default Evidence
jtag_program_freq 3 MHz (3E6) around ftdi_program.py:219 (__init__)
spi_direct_program_freq 3 MHz (3E6) same
spi_flash_program_freq 6 MHz (6E6) same
verify_method onchipx2 ftdi_program.py:219

2.2 The eight programming modes

-m/--mode has 8 legal values (from parse_cmdline() at ftdi_program.py:3148, the choices list). Dispatch inside main() (ftdi_program.py:3341-3379):

mode (default passive) Function dispatched by main() Semantics Input file format
passive spi_direct_program The FPGA is unconfigured; the SPI flash bus is wired straight to the host, which writes the flash directly .hex
active spi_flash_program The FPGA is configured and running; the SPI flash is written through the FPGA-side bridge .hex
jtag jtag_program JTAG downloads the bitstream straight to the FPGA (no flash write) .bit
jtag_chain jtag_program(chain=True) Multi-device JTAG chain; -n/--num selects the Nth chip on the chain .bit
erase_flash spi_erase_flash Erases the SPI flash (combine with --address / --num_bytes) no input file
read_flash spi_read_flash Reads flash contents into -o/--output_file no input file
jtag_bridge jtag2spi Accesses the SPI flash via the JTAG-Bridge (the §5 flash loader is preloaded into the FPGA first) .hex
jtag_bridge_x8 jtag2spi_x8 Same as jtag_bridge, 8-bit-wide bus variant .hex

Mode-file compatibility is enforced by check_mode_file_compatibility() (ftdi_program.py:3130-3145):

  • jtag / jtag_chain accept only .bit;
  • passive / active / jtag_bridge / jtag_bridge_x8 accept only .hex (SPI flash programming uses the hex format exported by the Efinity GUI).

The sub-operations of the jtag_bridge family are controlled by --jtag_bridge_mode; jtag2spi() dispatches on six values (ftdi_program.py:1696-1737): read / erase / write / erase_and_write / all_no_erase / all (all and all_no_erase verify per --verify_method after programming).

2.4 Exit codes

At the end of main(), success and failure call sys.exit(0) / sys.exit(1) respectively (ftdi_program.py:3341-3379). Scripts/CI can judge the programming result from this.

2.5 Invocation examples for the eight modes

All examples below are run from the %EFINITY_HOME% root (for the reason, see §2.1 point 2). Query the device URL with --list_usb first; the examples use ftdi:// as a placeholder:

:: 1. passive: FPGA unconfigured, write .hex to the SPI flash directly
pgm\bin\ftdi_pgm.bat -m passive -u ftdi:// design.hex

:: 2. active: FPGA already running, program the flash through the FPGA bridge
pgm\bin\ftdi_pgm.bat -m active -u ftdi:// design.hex

:: 3. jtag: download .bit to the FPGA over JTAG (with a JCF)
pgm\bin\ftdi_pgm.bat -m jtag -u ftdi:// -x debug.jcf design.bit

:: 4. jtag_chain: multi-chip chain, select the 2nd chip
pgm\bin\ftdi_pgm.bat -m jtag_chain -u ftdi:// -n 2 design.bit

:: 5. erase_flash: erase the whole chip (--address/--num_bytes can limit the range)
pgm\bin\ftdi_pgm.bat -m erase_flash -u ftdi://

:: 6. read_flash: read the flash back into a file
pgm\bin\ftdi_pgm.bat -m read_flash -u ftdi:// -o flash_dump.hex

:: 7. jtag_bridge: write the flash via the JTAG-Bridge (preloads the fli loader first, see §5)
pgm\bin\ftdi_pgm.bat -m jtag_bridge -u ftdi:// --jtag_bridge_mode erase_and_write design.hex

:: 8. jtag_bridge_x8: 8-bit-wide JTAG-Bridge variant
pgm\bin\ftdi_pgm.bat -m jtag_bridge_x8 -u ftdi:// design.hex

SDK/adapter-side automation: the program flow of scripts\efx_run.py imports efx_pgm.ftdi_program directly and calls FtdiProgram (the run_program() from scripts\efx_run.py:1718), sharing the same code path as the command line.

  • Entry script: pgm\flashshell\flashshell.py, built on the cmd2 framework; get_all_plugins() scans the exts\ directory for all BaseExt subclasses and registers commands automatically (read from flashshell.py).

5. Flash loader bitstreams (pgm\fli) and the device_db IDCODE mapping

5.1 Purpose and naming rules

pgm\fli\ is split into three device-family subdirectories (trion\ 11, topaz\ 14, titanium\ 21 — 46 .bit files in total). These are the bridge bitstreams (flash loaders) preloaded into the FPGA when programming the flash over the JTAG-Bridge: ftdi_program.py -m jtag_bridge[_x8] (§2.2) first downloads the matching loader into the FPGA, and the FPGA then bridges access to the SPI flash.

Naming rule: u<IDCODE lowercase hex>[_t<model/speed grade>].bit

  • u + the IDCODE without the 0x prefix, matching <idcode value="0x…"> in pgm\bin\device_db.xml verbatim (e.g. u006C0A79 ↔ 0x006C0A79).
  • _tXX suffix: distinguishes multiple models/speed grades sharing one die (e.g. T35/T20 same die → u00240A79_t35 and u00240A79_t20).
  • _tXXqYYY: includes a package variant (e.g. u00210A79_t8q144, u00210A79_t20q144 are q144 package variants).
  • Special cases u00000000_t8/t4: small T8/T4 devices use an all-zero placeholder IDCODE in device_db (device_db.xml:41-42, original comment "this is obviously invalid").

5.2 device_db.xml structure

pgm\bin\device_db.xml is organized by <die name="…">; each die carries <idcode>, <family>, <option_register> (bitstream option register layout and sync words), and <scan_chain> (CDONE/NSTATUS/CBUS and other status bit addresses). Example (device_db.xml:125-126): <die name="T35/T20"> <idcode value="0x00240A79"/> <family value="Trion"/>. The whole database has 48 die entries (lines 16-882).

5.4 When they are used

Only -m jtag_bridge / -m jtag_bridge_x8 need an fli loader (load the loader first, then reach the flash through the bridge); -m passive / -m active access the flash directly or through the already-configured FPGA, and -m jtag / jtag_chain only download the SRAM bitstream — none of them consume fli.

  1. Loads four local C extension libraries (:15-26, picking bin\*.dll / lib\*.so per platform):

  2. Thin wrapper forwarding + collection-command overloading:
  3. :199-347 forwards every top-level command in one line into the C namespaces: timing:: (read_sdc/write_sdc/report_), sdc_get_cmds:: (get_cells/get_ports/all_), sdc_constr_cmds:: (create_clock/set_*). The comment is explicit: "wrappers must stay thin; all checks happen on the C side" (:189-195).
  4. :349-434 overloads lappend/lassign/lsort/lindex/linsert/llength/lrange/lreplace/lreverse/lsearch/lset/foreach via rename + interp alias so they support "object groups" (collection objects), and provides foreach_in_collection. This means that in these shells, when iterating timing objects, the standard Tcl list commands have been replaced with object-aware versions — do not rely on the original semantics of the overloaded commands when writing your own STA Tcl scripts.

7.3 The efx_map package (synthesis front-end shell)

  • pkgIndex.tcl:18: package ifneeded EfxShell 1.0 → pkgLoad sources EfxPkg.tcl then EfxTclShellInit.tcl in turn (:12-16); EfxPkg.tcl is a bare shell that only does package provide EfxShell 1.0 (:1-3).
  • EfxTclShellInit.tcl:
  • :9 package require cmdline (depends on tcllib\cmdline);
  • :21-49 sets the efx_va [id]> interactive prompt and runs the shell initialization;
  • :53-162 forwards the Verific/VeriApps object API (get_libs/get_attribute/get_instances/get_ports/get_port_direction, etc., landing in the va:: namespace);
  • :164-262 synthesis front-end commands: read_verilog, read_binary_netlist, map -design -lib-name, write_verilog/write_binary, fm_verify (formal verification; accepts .v/.vbd/netlist inputs);
  • :265-396 flow options: set_option_value/set_private_option_value and their parameterized wrappers set_option (root/efx-verilog/include-dir/output-dir/work-dir/num_ram_4k/num_mult16/insert-ios/max-bit-blast-mem-size, etc.) and set_private_option (efx_root/debug/assert_mode/merge_cascaded_muxes).

7.4 How efx_sta consumes these packages

Two consumption paths (both verified live):

  1. Standalone STA: bin\efx_sta.exe --help (captured 2026-09-25) gives the full usage — --prj <xml> opens a project; -t/--tclsh [script] "Open the specified project, load the design, then start a Tcl session" (interactive without an argument, or runs the given script). This embedded Tcl interpreter loads the tcl_packages packages at startup (the 4 DLLs and the command wrappers of efinity_init.tcl take effect here).
  2. Compile-flow embedded STA (the sta_tclsh flow): the flow list of scripts\efx_run.py:184 includes sta_tclsh; -t/--tcl_script names the script (:194); run_pnr(args, run_sta_tclsh=True) (:1273) appends --sta_tclsh to the pnr command line and passes the user's Tcl script via --sta_tclsh_script <file> (:1326-1330) — i.e. after pnr finishes place-and-route, the same Tcl/STA environment opens directly on the result database.

Extension point: user-defined STA Tcl scripts can use every timing/SDC command of §7.2 plus the object-group iteration facilities; the typical skeleton is efx_run -t my_sta.tcl --prj xxx.xml --flow sta_tclsh (or interactive exploration in an efx_sta -t session). SDC command semantics: see toolchain-reference.md and design-rules.md.

8. debugger\bin\efx_dbg overview

debugger\bin\efx_dbg\ is the Python engine of the Efinity debugger (39 modules), pulled into PYTHONPATH by pgm\bin\ftdi_pgm.bat (§2.1), so the programming scripts and the debugger share the same JTAG foundation. Core modules (sampled 2026-09-25):

Module Responsibility (evidence)
rtl_gen.py Debug soft-core RTL generator. Entries DbgTopGenerator.gen_veri_top_str / gen_veri_template_str; adding a generator class named {Type}Generator is auto-discovered by get_generator_cls and matched against the spec's type field (docstring :12-33); spec types are defined in efx_dbg.define (CoreSpec/LogicNSpec/VioSpec, :43-44)
jtag.py The JTAG API entry point: the singleton JtagManager provides all JTAG access (the TAP is a Trion hard IP; the soft cores live in the fabric); {Vio\|LogicN}Controller implements each debug core's communication protocol (docstring :10-16)
flash.py Flash operations: built on pyftdi.spi + spiflash.serialflash; reuses efx_pgm.efinix_flash / get_flashdb_json / header_processor (imports :23-40), sharing the flash database with the programmer
openocd_manager.py OpenOCD subprocess lifecycle management (subprocess/multiprocessing/socket, efx_pgm.usb_resolver.UsbResolver, :42-49)
jcf.xsd The XML Schema of the JCF (debug configuration file), located at debugger\bin\efx_dbg\xmlschema\jcf.xsd (found via Glob); the corresponding parser is jcf.py:JcfParser (referenced at flash.py:30)
