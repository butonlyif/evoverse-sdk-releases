1. IP Manager Overview

Efinity IP Manager is the interactive wizard tool built into the Efinity IDE for customizing, validating, and generating Efinix soft IP cores.

Core features:

Feature Entry point Description
IP Catalog Toolbar button / Tools → Open IP Catalog Browse all 47 IP components (see §3)
IP Configuration Select an IP in the Catalog → Next Wizard-style parameter configuration, deliverable selection, review, and generation
IP Editor / IP Manager main window Tools → IP Manager Manage generated IPs, import third-party IPs, package IPs

IP Manager validates parameter legality (VALIDATE_PARAMS) and can attach an Example Design and/or Testbench targeting Efinix development boards when generating.

4. The dual IP system: soft IP (ipm) and hard IP (pt) go through completely different channels

In Efinity 2026.1 the word "IP" covers two different things with completely different configuration channels; mixing them up is a common source of errors.

4.1 Comparison table

Dimension Soft IP (the IP Manager system) Hard IP (the PT / Interface Designer system)
Representatives efx_soc, efx_dma, efx_tsemac, efx_fifo_2, efx_bram, efx_uart, the efx_csi2 protocol layer, and all 47 entries of §3 PLL, DDR (ddr-memtest class), LVDS, the MIPI D-PHY pin layer, the JTAG hard core, OSC
Description format IPXACT 1685-2014 (ipm/ip_component.xml) PT tool-internal data + the ISF Python API
Configuration entry IP Manager GUI / IPMDesignAPI Interface Designer (GUI) or hand-written ISF
Parameter storage project ip/<module>/settings.json <design>.peri.xml (the efxpt:design_db namespace)
Registration project XML <efx:ip_info> (native GUI flow) or <efx:design_file> (EvoVerse flow, see §7.3) project XML <efx:isf_file> referencing the ISF; the ISF replays into peri.xml
Artifacts variant RTL (.v/.sv) + instantiation template hard block definitions inside peri.xml, netlist auto-instantiated during synthesis
create semantics create_ip can be run repeatedly (generates a new instance directory) ISF design.create_* is a one-shot bootstrap (see §4.3)

4.2 Decision rules

Given a requirement, first ask "is it a hardened macro cell":

  1. Hardened macro cells (blocks physically present on silicon: PLL, DDR hard controller, LVDS, MIPI D-PHY, JTAG, OSC, the PCIe hard core) → go through the ISF/peri.xml channel; it is not possible to create them in IP Manager. Note the MIPI layering: the D-PHY pin/register layer is hard IP (ISF), while the CSI-2/DSI protocol layer is soft IP (the 12 components of the §3 mipi group).
  2. Pure RTL soft IPs (in the §3 list) → go through the IP Manager channel (GUI or IPMDesignAPI).
  3. Edge cases: the JTAG hard core itself is on the PT channel; efx_jtag (JTAG user interface) and efx_jtag2spi_flash (spiOverJtag) are soft IPs sitting on top of the JTAG hard core and go through IP Manager.
  4. The two IP classes finally converge in the same compile: the soft-IP variant RTL enters the efx_map source scan, and the hard block definitions enter PT/place-and-route via peri.xml.

Source: C:\Efinity\2026.1\ipm\ip\ component list vs $EFINITY_HOME PT tool documentation; the EvoVerse dual-channel practice is in awesomsdk\products\efinity-adapter\extension\src\capabilities\ip.ts

4.3 Relationship to the ISF bootstrap contract

The one-shot semantics of ISF's create_* commands (comment them out after bootstrapping, keep only replay-safe set/assign commands) are governed by the rules-efinity-hard.md §15 contract; peri.xml is a project source file and must survive builds. The IP Manager channel never touches peri.xml — IPMDesignAPI.generate_ip does auto-locate peri.xml, but only so the generator is aware of the project context; it writes nothing into it.

Source: C:\Efinity\2026.1\ipm\bin\ipm_api_service\design.py (generate_ip implementation); AGENTS.md §15

7.2 Registration in the native Efinity GUI flow

In the native flow, Efinity writes into the project XML automatically:

<efx:ip_info>
    <efx:ip path="ip/<module_name>/settings.json"/>
</efx:ip_info>

When efx_run/efx_map parses this entry, it converts it into a source scan of the ip/<module_name>/ directory (--dir semantics), bringing the generated variant RTL into the compile.

7.3 The verified EvoVerse flow decision: do not write <efx:ip>, register a design_file instead

When EvoVerse generates a project it deliberately does not write the <efx:ip> entry; instead it registers the generated IP RTL as a <efx:design_file>. Verified reasons (comments at awesomsdk\products\efinity-adapter\extension\src\capabilities\ip.ts publishGeneratedIp L73-108):

  1. <efx:ip path="ip/<m>/settings.json"> is converted by efx_run into a whole-directory --dir ip/<m> source scan, which compiles twice against the already-registered design_file entries and reports VERI-1206 (duplicate module definition);
  2. Under ip_src_file semantics, the resolution lands on the IP root directory and fails to find SoC-netlist-class artifacts.

So EvoVerse registers only design_file. Implementation details (publishGeneratedIp):

  • A new design_file entry must be inserted before <efx:top_vhdl_arch> (element-order constraint of enf_proj.xsd);
  • ip.ts has a built-in vlnv validation regex: ^[A-Za-z0-9_.-]+(?:[:/][A-Za-z0-9_.-]+){2,3}$ (validateIpIdentity).

10. OOC (Out-of-Context) Synthesis

OOC synthesis lets an IP be synthesized independently of the top-level design into a standalone netlist, integrated as a black box during top-level P&R. Benefits: shorter top-level synthesis time; an IP parameter change only requires re-synthesizing that IP; enables team parallelism.

Configured in the project XML via <efx:ooc_info>; element order is in xml-project-schema.md.

Source: xml-project-schema.md (ooc_info element); C:\Efinity\2026.1\bin\enf_proj.xsd

11. IP Parameter Management

11.1 settings.json

Each IP instance's parameters live in the project's ip/<instance>/settings.json. Uses: restore parameters when regenerating; track configuration changes in version control; reuse configurations across projects. The EvoVerse flow uses the same native settings.json (§7.4).

11.2 Pickle cache and log events

IP Manager serializes component metadata with Python pickle (component.pickle, graph.pickle). Common events in efxIP.log:

Log event Level Meaning

14.1 Division of responsibilities

Stage File Key functions/locations

IPM result parsing same file parseIpmResult (extracts the JSON result from IPM output)

14.3 peri.xml protection when adding an IP

The evoverse ip add flow (adapter side):

  1. beginIpTransaction backs up the current peri.xml and the project ip/ directory;
  2. invokes IPMDesignAPI to generate the IP;
  3. runs the DesignAPI DRC after generation;
  4. if IPM, result parsing, or the post DRC fails → rollbackIpTransaction restores the original library, preventing a half-finished state from reaching the compile.

This is consistent with the peri.xml survival contract of AGENTS.md §15: peri.xml is a project source file, and no failure path may leave a corrupted version behind.

14.4 Decision record: why <efx:ip> is not written

See §7.3. Key points: avoid duplicate compilation between the --dir directory scan and design_file (VERI-1206); avoid ip_src_file resolution landing in the wrong place. This decision is an EvoVerse empirical finding and must be followed when writing project XML.

Source: original comment at ip.ts L100-106; first-hand read of sdk\cli\evoverse _build_native_project_xml (2026-09-25)

15. Troubleshooting

15.1 IP generation failures

Symptom Cause Fix
Module Name is empty No module name entered Enter a name in the IP Configuration Module Name box
Pickle cache corrupted pickle file damaged Delete that IP's component.pickle/graph.pickle; reopening IP Manager rebuilds them automatically
PermissionError pickle held by another Efinity process Close the other Efinity instances and retry (efxIP.log has recorded instances)
Device/family mismatch Project device differs from the IP cache target PICKLE_LOAD-ERROR log shows details; it is a normal fallback — wait for the full load to finish
Duplicate module definition (VERI-1206) An EvoVerse project mistakenly wrote <efx:ip> or was registered twice manually Register via design_file only, per §7.3; delete the extra <efx:ip> entries
Manually added <module_name>.sv reported as duplicate The IP file is already managed by the tool Remove the manually added entry (§6.3)

15.2 Parameter validation failures

A VALIDATE_PARAMS failure usually means an illegal parameter combination: check parameter value ranges and inter-parameter dependencies (e.g. efx_pll_cfg Multi-config mode requires a valid RAM Hex file, and the PLL Instance Name must match the Interface Designer block name).

15.3 Localization techniques

  1. First check the last *-BEGIN and the first *-ERROR in C:\Efinity\2026.1\ipm\log\efxIP.log;
  2. In the EvoVerse flow, also check the adapter's transaction log (whether rollbackIpTransaction ran after beginIpTransaction);
  3. For name-related issues, first cross-check the IPXACT name and moduleName against the §3.3 trap table.
