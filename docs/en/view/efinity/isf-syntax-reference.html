One-sentence conclusion (remember this first): An ISF is Python source code executed line by line by exec(), with the execution context binding the design variable to an Efinity DesignAPI instance. It has exactly two legal usages: the one-shot bootstrap (containing create_*) and the replay-safe form (set/assign only). The project XML may reference only replay-safe ISF files.

1. What an ISF really is: Python API source executed by exec()

1.1 Execution model

Every line of an ISF file is extracted and handed to Python exec() for execution:

Step Evidence
Line-by-line exec(code) isf_importer.py:236
Before execution, design = self.design_api is injected (binding the DesignAPI instance) isf_importer.py:217
The module-mode execution path injects the same: setattr(module, "design", self.design_api) isf_importer.py:287
Lines written by the exporter likewise start with design. (design_api_handle="design") isf_exporter.py:94

Therefore, what you can write in an ISF is exactly the Python method calls exposed by DesignAPI (the complete set in Chapter 2), plus whatever comments and blank lines the Python language itself permits. There is no "ISF-specific syntax" — the so-called ISF syntax is simply the textual serialization format of DesignAPI method signatures.

1.2 Pre-filtering rules

Before exec, the importer pre-screens every line (isf_importer.py):

Rule Behavior Evidence
Blank line or full-line # comment Skipped, not executed isf_importer.py:227 (code == "" or code.startswith("#"))
When --skip-resasg is enabled, lines starting with design.assign Skipped (used when consuming .auto_asg.isf to take only the properties, not the assignments) isf_importer.py:231-233
All other lines Handed to exec() isf_importer.py:236

Corollary: comments must be written as Python comments (#); trailing comments are legal Python and execute as such. But to stay consistent with exporter output (see §5.5), use only full-line comments.

1.3 Error severity and abort behavior (what decides how far "one bad line" wrecks the file)

The importer classifies exceptions by type (isf_importer.py):

Exception Level Continues with subsequent lines? Evidence
PTException (Efinity semantic error, e.g. instance does not exist) warning yes importer exception branch
AttributeError (method name does not exist → typo) error yes importer exception branch
SyntaxError / UnicodeError / TypeError / other Exception fatal no — break, aborts the entire import importer exception branch

Key semantics: import_isf returns False whenever the issue registry is non-empty (even if every issue is warning-level) (around isf_importer.py:191). In other words —

warning ≠ pass. A single issue of any kind fails the import, and the unified flow aborts immediately (§7.2).

Post-processing follows the import: PLL frequencies are recalculated and the APIPropertyChecker design check runs (isf_importer.py:414-431); issues found there also count toward the registry.

1.4 ISF is not XML, and not a pin table

Format What it is Consumer
.isf (ISF) Python API source: design.create_input_gpio(...) etc. efx_run_pt_unified.py / DesignAPI.import_design()
<design>.peri.xml A project source file (database) in the efxpt:design_db namespace; can only be produced by the Efinity PT tools PT tools / GUI
3-column GPIO .csv A pin list only; goes through the ImportGPIODesign backend (the same one as the GUI wizard) import_gpio_cli.py:154

Never write XML such as <efx:gpio> into a .isf file; never hand-write <design>.peri.xml (the namespace is efxpt:design_db, the schema is peri_design_db.xsd, as the header of the official helloworld.peri.xml proves). Historically the SDK once produced a 46 KB <EFX_PERI_INTERFACE> XML named *.peri.isf, which the ISF importer rejected outright with "invalid syntax" — that lesson is now enshrined as a mandatory self-check (§6).

1.5 ISF vs. peri.xml (the prerequisite for understanding replay)

In the unified flow:

  1. <design>.peri.xml is the persisted project source file (all official unified samples ship one); it is loaded at build time;
  2. every .isf referenced by the project XML is replayed (imported) onto this existing database;
  3. design_api.save() writes the merged result back to peri.xml (efx_run_pt_unified.py:281).

So every ISF command runs under the assumption "the database already exists" — this is the root of the replay-safety contract in §3.

2. DesignAPI method reference (the complete ISF command set)

All methods are defined in C:\Efinity\2026.1\pt\bin\api_service\design.py; line numbers refer to that file.

2.1 Category overview

Category Methods Idempotent / replayable ISF serialization

Property family set_property / set_device_property / set_gpio_unused_state / set_mode_sel_name / lock_property ✅ replayable ✅ (lock_property is serialized too)
Resources and pins assign_resource / assign_pkg_pin ✅ replayable ✅

2.2 Creation family (one-shot bootstrap)

2.2.1 create_block

# design.py:192
def create_block(self, name: str, block_type: str, **kwargs)
  • Common block_type values: PLL, OSC, DDR, LVDS_RX, LVDS_TX, MIPI_RX, MIPI_TX, JTAG, SPI_FLASH, etc. (the full legal set is in the exporter support table, §5.2).
  • kwargs supports creation-time parameters: mode / conn_type / tx_mode / rx_conn_type (signature at design.py:192).
  • Serialization format (isf_command.py:102-108):
design.create_block("pll_inst1","PLL")
design.create_block("inst","TYPE",mode="X")     # with kwargs

Bus determination rule (design.py:1088-1091, shown for create_input_gpio; the other creates are isomorphic):

# msb == lsb → scalar GPIO; msb != lsb → GPIO bus (gpio_bus)
if msb == lsb:
    gpio = ...
else:
    gpio_bus = ...

Serialization format (isf_command.py:45-48):

design.create_input_gpio("rstn")            # scalar
design.create_input_gpio("data_in", 3, 0)   # bus, msb=3, lsb=0

Pitfall: never re-create plain GPIO (RTL top-level ports) in the ISF. Under the unified flow the synthesis tool infers GPIO from RTL ports automatically; re-creating the same-named instance in the ISF triggers already exists on replay (§3.4, §8.2). The ISF create_ family exists only for hard IP and its dedicated GPIO* (PLL/DDR/LVDS/OSC/MIPI and PLL_CLKIN-style inputs).

2.3 Property family (replayable)

set_property (design.py:507)

def set_property(self, inst, prop_name: Union[str, Dict[str, str]], prop_value=None, block_type: str="GPIO")
  • The four-argument form is the only shape used in ISF serialization: the serializer always emits 4 positional arguments (isf_command.py:147):
design.set_property("pll_inst1","REFCLK_FREQ","25.0","PLL")
design.set_property("reverse","PULL_OPTION","WEAK_PULLUP")     # block_type defaults to GPIO when omitted
  • ⚠️ The set_property docstring warns explicitly: do not use it for resources or pins — that is the job of assign_resource / assign_pkg_pin (docstring at design.py:507).
  • prop_name may be passed as a dict for batch setting (a Python-call-level capability; textual ISF is one property per line).
  • The from_str parsing regex only allows spaces and square brackets in prop_value: [\w\s\.\[\]]* (isf_command.py:130) — values containing commas/quotes cannot be expressed in textual ISF.

set_device_property (design.py:559)

def set_device_property(self, inst: str, prop_name, prop_value=None, devset_type: str="IOBANK")

The device-level setting entry point. The legal devset_type set has exactly 5 values (int_device_setting.py:79-108, decided by is_setting_supported):

devset_type Supported when
IOBANK always supported
SEU Tesseract family only
RU the device has ctrl_reg
EXT_FLASH the device has ext_flash_reg
CLKMUX Tesseract only (source comment: Trion clkmux has no configuration)

set_iobank_voltage (design.py:639)

def set_iobank_voltage(self, bank_name: Union[str, Dict[str, str]], voltage=None)

It is pure syntactic sugar for set_device_property(bank, "VOLTAGE", volt, "IOBANK") (implementation at design.py:639) — hence naturally idempotent and replayable:

design.set_iobank_voltage("TL","3.3")

Hard constraints (violation → Design Check io_bank_rule_voltage_assignment): all IOs in a bank must share one voltage standard; a MIPI bank must be 1.2V and must not share a bank with LVDS; within an HSIO bank, at least one pair of unassigned IOs must be left between GPIO/LVDS/MIPI as isolation; Ti60ES does not support 2.5V.

set_gpio_unused_state (design.py:1360)

Global unused-pin level setting. Serialization (isf_command.py:92):

design.set_gpio_unused_state("value")

set_mode_sel_name (design.py:754)

def set_mode_sel_name(self, bank_name, value, bonded_bank=None)

Sets a bank's mode_sel name; bonded_bank handles the bank mapping for non-fully-bonded packages. Per-IO voltage standards (iostd) and mode_sel_name both end up on the efxpt:iobank element of peri.xml (as helloworld.peri.xml proves).

lock_property (design.py:1936)

def lock_property(self, inst, prop, value, btype, checksum)

Registers a property into netlist_config (locked by the periphery-netlist checksum). Note: when inst is unknown it silently returns None without raising an error (implementation at design.py:1936) — a lock line with a wrong instance name will not fail immediately; when debugging, always confirm the instance exists first. Serialization (isf_command.py:175):

design.lock_property("inst","PROP","VALUE","TYPE","checksum")

2.4 Resources and pins (replayable)

assign_resource (design.py:790)

def assign_resource(self, inst, res_name, block_type="GPIO", override=True)

Places an instance onto a concrete hard resource (e.g. PLL → PLL_TL0). Serialization is always 3 positional arguments (isf_command.py:156):

design.assign_resource("pll_inst1","PLL_TL0","PLL")

assign_pkg_pin (design.py:837)

def assign_pkg_pin(self, inst, pin_name, override=True)

Pin assignment. Bus members are written in the "bus[N]" form. Serialization is always 2 positional arguments (isf_command.py:164):

design.assign_pkg_pin("rstn","J13")
design.assign_pkg_pin("led[0]","K14")

Always assign GPIO pins with assign_pkg_pin, not assign_resource — the exporter's pin channel for GPIO is exactly assign_pkg_pin (isf_exporter.py:837-853).

Query family (read-only, no ISF serialization)

Method Line Purpose
is_resource_used 865 whether a resource is already taken
is_pkg_pin_used 890 whether a pin is already taken
get_resource 904 an instance's current resource
get_pkg_pin 928 an instance's current pin
get_bonded_bank 723 bonded bank lookup

These methods have no serialized counterpart in ISF and contribute nothing to replay — do not write them into an ISF.

2.5 Deletion family (API-only, no ISF serialization — this is the evidence that "ISF has no delete")

Method Line Notes
delete_block 255 API-level block deletion
delete_gpio 302 API-level GPIO deletion
reset_device_settings 2404 clears device settings
clear_design 2423 clears the design

These deletion capabilities exist in the API, but none of isf_exporter.py's 46 classes (§5) nor any command class in isf_command.py can serialize them into ISF text. Conclusion: the ISF command set has no delete/clear, and inventing one is not allowed. The only legitimate way to clear the database is to delete peri.xml and bootstrap again (a decision owned by the tool/project lifecycle; scripts must never delete peri.xml on their own).

3. The replay-safety contract (the primary acceptance criterion for ISF in this repository)

3.1 Why this contract exists

The fixed behavior of a unified build: load the persisted <design>.peri.xml → import one by one every ISF referenced by the project XML → save() writes back. Every compile replays (§1.5, efx_run_pt_unified.py). Hence every command in an ISF must be re-executable against a database where "the instances already exist".

3.2 Idempotent command allowlist

An ISF referenced by a project may contain only these commands (repeated execution changes nothing):

Command Idempotence basis
design.set_property(...) property overwrite, design.py:507
design.assign_pkg_pin(...) re-assignment with override=True, design.py:837
design.assign_resource(...) re-assignment with override=True, design.py:790
design.set_device_property(...) device setting overwrite, design.py:559
design.set_iobank_voltage(...) sugar over set_device_property, design.py:639
design.set_gpio_unused_state(...) / set_mode_sel_name(...) overwrite-style, design.py:1360 / 754

lock_property is also registration-style (design.py:1936), but it is normally generated by the tool during the partial-design flow; hand-written ISF does not need it.

3.3 One-shot bootstrap: create_*

create_block and all create_*_gpio carry "create instance" semantics (isf_command.py:177-181 — is_creation_command identifies creation commands by exactly these). Replaying them onto a peri.xml that already contains the same-named instance → already exists. Therefore:

  • create_* may run only once, while peri.xml does not yet exist (or right after a deliberate rebuild);
  • afterwards they must be removed (commented out) from any ISF that will be replayed.

3.4 The already exists failure chain (why the second compile always fails)

When an ISF containing create_* is replayed, the underlying duplicate check throws at:

Throw site File:line
database item duplicate check pt\bin\design\db_item.py:792
design export/import layer pt\bin\design\design_export_import.py:2015
service layer pt\bin\design\service.py:635

The error looks like GPIO/PLL ... exists. It is a PTException (warning-level, execution continues), but as §1.3 showed — any issue fails the import, and the unified flow aborts at once. The symptom is "first compile PASS, second compile always fails".

3.5 The project-side contract (three SDK iron rules)

  1. The project XML references only replay-safe ISF files (the official samples do exactly this: §4.4).
  2. No build path (SDK / adapter / script) may delete <design>.peri.xml — it is a project source file; deleting and regenerating it is a workaround, not a fix.
  3. ISF and peri.xml go into version control together; every ISF change must pass the import_gpio.bat --dry-run self-check (§6).

4.5 The bootstrap ritual (the SDK standard bootstrapping procedure)

Fixed steps for a new project / new baseline (based on §3 + §4):

  1. Write all set_property / assign_* lines, and temporarily enable the create_* lines;
  2. compile once (PT generates <design>.peri.xml) → immediately comment out every create_*, with a one-line side note (when it was enabled);
  3. the replay compile must PASS again — only the "bootstrap + replay" double PASS counts as ISF acceptance;
  4. commit peri.xml together with the ISF.

The authoritative template source is always "copy and adapt": $EFINITY_HOME/examples/ and the bitstream-verified baseline demos in the catalog — never invent from scratch.

5. ISFBuilder export rules (peri.xml → ISF auto-export)

This chapter answers "what rules the tool follows when exporting peri.xml into ISF". Source: C:\Efinity\2026.1\pt\bin\api_service\exim\isf_exporter.py (46 classes).

5.1 Exporter architecture

  • Top-level DesignISFExporter (isf_exporter.py:94), line handle design_api_handle="design" — every exported line starts with design.;
  • one ISFBuilder subclass per block type, converting that type's instances into a command-line sequence;
  • line text is generated by the format_str() of each command class in isf_command.py (§5.8).

5.2 Supported block types (build_supported_block_type, isf_exporter.py:143-217)

Always supported Device-dependent (appended per device)
GPIO / PLL / IOBANK / JTAG OSC, MIPI_*, LVDS_*, SEU, RU, HYPERRAM, SPI_FLASH, DDR, PLL_SSC, EXT_FLASH, CLKMUX (Tesseract only), SOC, QUAD_PCIE, 10GBASE_KR, SGMII, PMA_DIRECT, CM

Compared with the 5 device-setting types of §2.3 (int_device_setting.py:79-108): IOBANK is always present; SEU/RU/EXT_FLASH/CLKMUX appear per device capability.

5.3 Builder output order (build_block_builder_list, isf_exporter.py:218-235)

The section order of the exported text = the builder registration order:

gpio → cm → pll → osc → jtag → mipi_dphy_rx → mipi_dphy_tx
→ lvds_rx → lvds_tx → lvds_bidir → mipi_hard_dphy_tx → mipi_hard_dphy_rx
→ hyper_ram → spi_flash → ddr → mipi_rx → mipi_tx → pll_ssc
→ soc → pcie → lane10g → lane1g → raw_serdes

5.4 The six PLL builder variants

The PLL builder selects among six variants by device family (isf_exporter.py:299-326) — different Titanium/Trion generations have different PLL property sets, so the PLL set_property lists in official samples must not be copied across families.

6. The self-check flow: import_gpio.bat --dry-run

6.1 Tool chain

sdk\cli\import_gpio.bat (environment setup)
  └─ python sdk\cli\import_gpio_cli.py (arguments and exit-code management)
       ├─ .isf → DesignAPI.import_design(<path>, gen_issue_csv=True)   # import_gpio_cli.py:104
       └─ .csv → ImportGPIODesign backend (same as the GUI wizard)     # import_gpio_cli.py:154

import_gpio.bat is responsible for: locating EFINITY_HOME (default C:\Efinity\2026.1), setting PYTHONHOME / EFXPT_HOME, exiting with exit 3 when Python is not found, and forwarding all arguments while returning the real exit code via exit /b %errorlevel%. It explicitly declares "This file is NOT a parser" — judgment is delegated entirely to Efinity's own DesignAPI.

6.2 Usage

# Dry run: parse and import, produce the report, do not write back peri.xml
sdk\cli\import_gpio.bat --peri <project>.peri.xml --input <file>.isf --dry-run

6.3 Exit-code semantics (import_gpio_cli.py)

Exit code Meaning Action
0 import OK, no issues pass
1 import error (issues present, including warning-level) must fix
2 warnings only, requires --force (CSV path only) manual confirmation
3 environment/infrastructure error (missing Python, etc.) fix the environment

Echoing §1.3: on the .isf path, a non-empty issue_reg is already a failure (exit 1); warnings cannot be "tolerated through".

6.4 Write-back behavior

  • --dry-run: parse and report only, no write-back to peri.xml (import_gpio_cli.py:243-245);
  • non-dry-run: before writing back, a backup is saved as <name>.bak_pre_import (import_gpio_cli.py:216-217).

6.5 CI requirements (mandatory)

  • Every constraints/*.isf must pass --dry-run (exit 0) before commit;
  • CI runs automatically on every constraints/*.isf change;
  • but --dry-run only validates syntax and import legality; it cannot replace the "bootstrap + replay double PASS" replay verification of §4.5 (a dry run cannot uncover the timing precondition behind already exists — it does not simulate a full build).

7.2 Semantics of {design}.unified.isf

  • Content: the current periphery netlist (the GPIO/PLL etc. inferred from RTL by the synthesizer) deserialized into ISF commands, wrapped in setup_partial_design / finish_partial_design;
  • Effect: it first deletes the same-named instances already present from the netlist (partial design), then rebuilds them from the netlist — this is the mechanism behind "RTL ports automatically enter the interface database";
  • it is a tool-generated artifact, placed at the head of the import queue; never edit it by hand.

7.3 Semantics of {design}.auto_asg.isf

  • Content: the planning output of auto_assign_resource (auto assignments not yet persisted into peri.xml), expressed as design.set_property / design.assign_* lines;
  • Consumption: later imports may skip its design.assign* lines with --skip-resasg (isf_importer.py:231-233);
  • it is likewise a tool-generated artifact.

7.4 <design>.peri.xml

  • Namespace efxpt:design_db (schema peri_design_db.xsd, see the header listing in §4.4);
  • project source file: it must survive the build and be version-controlled; only the Efinity PT tools/GUI can produce it;
  • hand-editing has neither schema guarantees nor replay semantics — always express intent through ISF.

8. Known pitfalls (revised per new evidence)

8.1 Writing ISF as XML / inventing tags → "invalid syntax"

ISF is Python API source. XML such as <efx:gpio> or <EFX_PERI_INTERFACE> inside a .isf is parsed as Python; the first line raises SyntaxError → the whole file aborts (§1.3). Historical lesson: a 46 KB XML renamed .peri.isf was rejected by the importer on the spot, and the defect lay dormant for months undetected — because nothing ever actually imported it. The countermeasure is the mandatory self-check in §6.

8.2 Replaying an ISF containing create_* → GPIO/PLL ... exists; the second compile always fails

Mechanism chain: create semantics + replay on every build (§3.1) → duplicate check failure (db_item.py:792, design_export_import.py:2015, service.py:635) → PTException (warning-level, continues) → a non-empty issue registry fails the import (§1.3) → unified flow aborts. Countermeasure: the §4.5 bootstrap ritual (comment out create_* right after bootstrapping; the replay compile must PASS again).

8.3 Setting resources or pins with set_property

The set_property docstring forbids it explicitly (design.py:507). Resources and pins have dedicated channels, assign_resource / assign_pkg_pin; properties sent through the wrong channel may be overwritten by Design Check or later assignments.

8.4 Bus vs. scalar confusion

  • msb == lsb means scalar; anything else is a bus (design.py:1088-1091);
  • a bus GPIO is created with create_output_gpio("led", 5, 0) — never split it into per-bit create_output_gpio("led[0]", 0, 0) calls;
  • pin assignments for members use the "led[N]" form: design.assign_pkg_pin("led[0]","K14") (listing in §4.3);
  • at the textual serialization level: a scalar create line has no msb/lsb; a bus create line carries two numbers (§5.8).

8.5 ISF instance names not matching RTL port names

In the unified flow, GPIO instance names come from RTL top-level ports (rebuilt via .unified.isf, §7.2). When the names used in set/assign do not match the port names, set_property attaches to a wrong or invalid object, and lock_property even returns None silently (design.py:1936) — the error may stay hidden until Design Check.

8.6 "A warning-level issue is still a failure"

PTException is warning-level in the importer and execution continues, but import_isf looks only at the issue count (§1.3). Never treat an import whose log shows warnings as a success; the exit code / flow status is the only yardstick.

8.7 create_regional_control_gpio does not exist

The exporter map has the gpio_reg_ctrl entry commented out (isf_exporter.py:695-712); the API was never provided. Writing it = AttributeError (error-level issue, §1.3) → import failure.

8.8 Textual ISF has limited value expressiveness

from_str allows only letters/digits/underscores/whitespace/dots/brackets in prop_value (isf_command.py:130). Complex values containing commas or quotes cannot be expressed as a text line; empty-string values are legal (in the §4.2 listing, LOCKED_PIN","","PLL").

8.9 Hand-writing / hand-editing .peri.xml

efxpt:design_db is a tool-private database that only the PT tools/GUI can produce (§7.4). Any build path that deletes or regenerates peri.xml is an illegitimate workaround; the three SDK iron rules are in §3.5.

8.10 Bank voltage vs. IO standard matching (kept from the old edition; Ti180 field evidence)

  • All IOs in one bank must share the same voltage standard; the bank voltage is declared with design.set_iobank_voltage("TL","3.3") (§2.3);
  • a MIPI bank must be 1.2V, and MIPI and LVDS cannot share a bank (different voltage requirements) → violations raise io_bank_rule_voltage_assignment;
  • inside an HSIO bank, at least one pair of unassigned IOs must be left between GPIO/LVDS/MIPI as isolation;
  • Ti60ES (engineering sample) does not support 2.5V; only production parts do;
  • verified baseline: the bank voltage declarations in the Ti180 catalog project XML (opx_333x642_b40_d20_tj180a484s.xml) are consistent with the rules above.

8.11 A PLL can only be created in the ISF (pair with the §4.2 template)

The RTL declares only ports (pll_clk_out / pll_locked); the PLL instance and all its parameters are expressed through ISF create_block("pll_inst1","PLL") + set_property, with the resource via assign_resource("pll_inst1","PLL_TL0","PLL"). PLL output dividers can only be powers of two, and phase moves in 45° steps (see optimization-guide.md).
