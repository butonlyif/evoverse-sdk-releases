Efinity On-Chip Debug Guide

Efinity On-Chip Debug Guide

Version: v1.0　Applies to SDK: v1.0.0 (Efinity Adapter) Last updated: 2026-09-30

The Debug tab of the Efinity Adapter provides a closed-loop on-chip debug flow without opening the Efinity GUI: mark signals → compile twice → program → scan the device → configure trigger conditions → capture waveforms. The whole flow bridges the official Efinity debug API through evoverse_dbg.py, and the results are delivered as VCD waveform files.

1. Two Core Concepts

Concept Full name Role
LA (logic analyzer) Logic Analyzer Like an oscilloscope inside the FPGA: it continuously records signal values on the sample clock, and when the trigger condition is met, exports the entire history of the waveform as a VCD. Use it to answer "how does a signal change over time".
VIO (virtual I/O) Virtual I/O Virtual switches / indicators that do not consume board pins: output probes can be written at runtime to drive internal FPGA signals, and input probes can read current values in real time. Use it to "flip something by hand and watch the reaction".

The mark_debug flow uses LA by default (sampled recording per signal); VIO cores must be defined manually in the debug configuration file, or generated with AI assistance.

3. The Complete Flow (Seven Steps)

The top of the Debug tab shows the same flow guide. Every step can also be delegated directly to AI (see §5).

Step 1 · Mark signals

In the RTL editor, select a signal name (pattern, data_valid, etc.), right-click → Add Signal to Efinity Debug. The command writes a synthesis attribute before the declaration:

(* mark_debug = "true" *) wire [7:0] pattern;
  • Running it again on the same signal reports that it already exists; Remove Signal from Efinity Debug undoes the mark (keeping other synthesis attributes such as keep).
  • Writing (* mark_debug = "true" *) by hand has the same effect — the right-click command is just an automated edit.
  • The context menu requires: selected text present + file extension .v/.sv/.vh/.svh.
  • Prepare Selection for Efinity Debug = mark, then jump straight to the Debug tab.

Step 2 · First compile (generates the debug configuration file)

Click Build. The synthesizer (the enable-mark-debug option) collects all marked signals and generates the debug configuration in outflow/debug_profile.mark_debug.json: it contains the probe list, bit widths, sample clock, and the default sample depth.

Why a first compile is mandatory: auto-instantiation of the debug cores requires the configuration file to already exist before the compile starts (an Efinity mechanism, see Efinity Debugger Reference §8). Enabling auto-instantiation on the very first compile crashes the build (elab.vdb missing). The Adapter already front-loads a validation that blocks this usage.

Step 3 · Enable debug (Debug tab · 1 · Debug Configuration)

  • Check Auto Instantiation; the configuration file path auto-fills to outflow/debug_profile.mark_debug.json. You can "Preview Configuration Changes" first, then "Apply".
  • Sample depth (default 1024): the number of samples one LA buffer capture records; larger values consume more BRAM. Changes take effect after a recompile.
  • Sample clock: auto-detected from the synthesis result (the clock domain the probes belong to); read-only display.

Step 4 · Second compile (compiles the debug cores into hardware)

Click Build again. When the compile finishes, the Debug tab profile status should show ✓ debug cores compiled, and the work_dbg/ directory contains the debug core RTL.

Step 5 · Program and scan the device

Debug tab 2 · Program downloads the bitstream; 3 · Scan Device scans the FTDI/JTAG chain and confirms the number of debug cores in hardware. The probe table now shows the marked signals.

Step 6 · Configure trigger conditions and capture

4 · Debug Probes, one signal per row:

Column Meaning
Compare condition equal to / not equal to / < / <= / > / >=; 1-bit signals additionally offer no trigger (this signal does not participate)
Match value The comparison target, e.g. 0xA5
Mask All 1s by default (all bits participate); bits set to 0 are ignored

5 · Capture: - Conditional trigger capture: on click, the conditions in the table are collected and sent to hardware; recording starts only when all conditions are simultaneously met, and on completion the VCD is exported and opened automatically. - Immediate capture: skips the conditions and records the current state right away — use it first when checking "is this signal changing at all".

Multiple signal conditions are ANDed: the trigger fires only when all signal conditions hold simultaneously.

Step 7 · Wrap up (debug version management)

  • Clean debug traces: one click back to the no-debug baseline — removes all (* mark_debug *) attributes, resets the debug configuration (auto-instantiation=off, profile=NONE), and deletes the debug configuration file and the work_dbg/ directory. A confirmation dialog appears; debug cores already in a programmed bitstream disappear only after a recompile.
  • Branch clean baseline: copies the project to a new folder and cleans the copy's debug traces while the original debug-enabled project is left untouched — ideal for "keep one debug-enabled version and start fresh to test something else".

5. AI-Assisted Path

The Debug tab only handles status viewing, trigger configuration, and capture; editing RTL, changing configuration, and running compiles can all be driven directly in a Trae conversation using natural language, for example:

"Add debug marks to pattern and data_valid, change the sample depth to 4096, then compile and program."

"Clean all debug traces from this project, then branch off a clean copy named blink_test."

The AI edits RTL/the project XML directly and invokes the SDK compile commands; hazardous operations (VIO writes, applying configuration) still go through the command channel with confirmation.

8. FAQ

Symptom Cause and handling
Compile crashes, log contains No such file: ...elab.vdb Auto-instantiation was enabled on the very first compile. Follow the correct order: compile once without auto-instantiation to generate the configuration file, then enable it and compile a second time. The Adapter already blocks this; when you hit it, redo in the prompted order.
No Add Signal entry in the context menu No text selected, or the file is not .v/.sv/.vh/.svh. Select the signal name in the editor first.
Debug tab state is stale It refreshes automatically after compile/apply; if the project was not ready when it opened, reopen the Debug tab.
Probe table is empty The device has not been scanned, or the bitstream contains no debug cores (check whether the profile status is ✓ and the second compile has completed).
Sample depth change had no effect The depth is baked into hardware at compile time; after changing it, recompile and reprogram.
Stuck waiting after trigger The condition never becomes true. Use "Immediate Capture" first to confirm the signal is changing, then relax the condition or change the mask.
Want to restore a clean project Use "Clean Debug Traces"; to keep the debug version at the same time, use "Branch Clean Baseline".

For the underlying mechanisms (the elab.vdb dependency behind the two compiles, XML debugger block fields, the profile JSON format), see the Efinity Debugger Reference.
