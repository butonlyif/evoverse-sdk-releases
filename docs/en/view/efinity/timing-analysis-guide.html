1. Timing analysis fundamentals

1.1 Core terminology

Term Meaning
Setup Time The minimum time data must be stable before the clock edge arrives. A violation = data too slow
Hold Time The minimum time data must remain stable after the clock edge arrives. A violation = data too fast
Slack Timing margin. Positive = met, negative = violation. Equals Required Time − Arrival Time
WNS (Worst Negative Slack) The worst negative slack; the slack value of the most severe violation in the entire design
TNS (Total Negative Slack) The sum of slack over all violating paths; reflects the total amount of violation
Tlogic Combinational logic delay (sum of cell delays: LUTs, MUXes, adders, etc.)
Tnet Routing delay (signal propagation delay over the net)
Tclk_skew clock skew (difference in arrival delay of the same clock at different registers)
Critical Path the timing path with the smallest (worst) slack; the primary target for optimization

1.2 The timing path model

Launch register CK→Q → [Tlogic] → [Tnet] → capture register D pin
                                                ↑
                                             Setup/Hold window

Data Arrival Time = Tclk_launch + Tcko + Tlogic + Tnet
Data Required Time = Tclk_capture + Tperiod − Tsetup − Tuncertainty

Slack = Required Time − Arrival Time
  • setup slack < 0: data arrives too late to be sampled by the next clock edge
  • hold slack < 0: data arrives too early and overruns the previous data being sampled at the current clock edge

1.3 How the Efinix architecture affects timing

  • LUT4 architecture: each LUT implements only a 4-input function; deep logic chains (≥3 LUTs with no register in between) are prone to setup violations
  • Quantum-architecture IO blocks: provide dedicated input/output registers that consume no core logic and add less delay
  • Global clock network: Efinix uses global clock spines; clock skew is usually very small (<0.1 ns)
  • Built-in DSP/RAM registers: the output registers of these hard blocks are "free"; leaving them unused creates long combinational paths

2. Writing SDC constraints

2.1 Basic constraint template

# ========== Clock definitions ==========
create_clock -period 10.0 -name sys_clk  [get_ports clk_i]
create_clock -period 6.734 -name video_clk [get_ports video_clk_i]

# ========== Asynchronous clock domains ==========
set_clock_groups -asynchronous \
    -group [get_clocks sys_clk] \
    -group [get_clocks video_clk]

# ========== Generated clocks (PLL outputs) ==========
# If the PLL is configured in the Interface Designer, Efinity derives it automatically
# Manual case:
create_generated_clock -name pll_clk_200m \
    -source [get_ports clk_i] -multiply_by 4 \
    [get_pins PLL_inst/clk_out]

# ========== I/O delays ==========
# Input: external device clock-to-out + board trace = 3ns max
set_input_delay -clock sys_clk -max 3.0 [get_ports {data_in[*]}]
set_input_delay -clock sys_clk -min 1.5 [get_ports {data_in[*]}]

# Output: board trace + external device setup = 2.5ns max
set_output_delay -clock sys_clk -max 2.5 [get_ports {data_out[*]}]
set_output_delay -clock sys_clk -min 1.0 [get_ports {data_out[*]}]

# ========== False paths (only after confirming asynchrony) ==========
# Do NOT put a false_path over the entire CDC path!
# Correct approach: set_clock_groups cuts off inter-clock-domain analysis,
# then add a false_path only on the first two stages of the synchronizer (where data is uncertain)
set_false_path -from [get_cells sync_ff_reg[0]] -to [get_cells sync_ff_reg[1]]

2.2 Common mistakes

Mistake Consequence Correct practice
Forgetting set_clock_groups -asynchronous The tool tries to satisfy synchronous relationships between asynchronous clocks, and placement gets disrupted Add it as soon as asynchrony is confirmed
A set_false_path covering the entire CDC Masks real violations and may hide signals that lack synchronizers Cover only the synchronizer itself
Using 0 for all I/O delays The tool does not know the external conditions and may misallocate critical resources to unimportant I/O Provide reasonable conservative values
A wrong clock period The tool optimizes for the wrong frequency → recompile Verify with an oscilloscope / the device datasheet
Multiple create_clock on the same port The later definition overrides the earlier one Define each clock port only once

2.3 Where to place the SDC

<project>/
  constraints/
    top.sdc          ← main constraint file, referenced in the Efinity project XML

Before every build, the EvoVerse SDK automatically checks whether the SDC file exists. If it is missing, a warning is raised.

3. Interpreting the Build Report

3.1 How to trigger

After opening an EvoVerse project in VS Code:

  • Command Palette → EvoVerse: Build (or the keyboard shortcut)
  • Or call build_project in the MCP Server

When the compile finishes, if "evoverse.build.autoOpenReport": true is set, the Build Report opens automatically.

3.2 Report panel tabs

The Build Report contains the following tabs:

Tab Content
Overview Compile overview: device, top module, elapsed time, timing status (All Met / N violations)
Resources Resource-usage pie charts: LUT, FF, RAM, DSP, PLL utilization
Timing WNS/TNS/violating-path counts grouped by clock domain, one entry per domain
Critical Paths Hop-by-hop delay list for each violating path (sorted by slack)
Tcl Console Interactive STA queries
Optimization Build strategy optimization suggestions (generated by BuildStrategyAdvisor)

3.3 Quick assessment from Overview

  • All Met, utilization below 50%: the design closes timing comfortably; just watch resource efficiency
  • All Met, utilization 80%+: the design is stable, but future features may trigger violations
  • N violations, N ≤ 5: few paths; diagnose individual paths first
  • N violations, N ≥ 10 concentrated in one clock domain: possibly a systemic architecture problem (frequency too high? long-path pattern?)

3.4 Quick localization from the Timing tab

The Timing tab lists results by clock domain. Prioritize: 1. The clock domain with the most negative WNS 2. The clock domain with the largest TNS (greatest total violation) 3. The clock domain with the most violating paths (a systemic problem)

4. Timing diagnosis: automatic root-cause analysis

4.1 How to trigger

If the build finishes with violations, a notification appears:

Build completed with 3 timing violations (WNS = −1.2 ns). Run timing diagnosis?

Click "Diagnose Timing", or trigger it manually via Command Palette → EvoVerse: Diagnose Timing.

4.2 How the diagnosis engine works

CriticalPath[] → extractFeatures() → classify() → queryByCategory() → scoreFingerprint() → Diagnosis[]

Step 1: Feature extraction. For each violating path, compute: - Cell count and ratio (logicRatio) - Route count and ratio (netRatio) - Whether it crosses clock domains (crossClock) - Whether it starts at an IO port (startsAtPort) - Whether it passes through RAM/DSP (throughBlock)

Step 2: Classification. Match against 7 major categories in priority order:

Category Criterion Confidence
CDC start/end clock names differ 0.7
I/O startsAtPort or endsAtPort 0.8
Resource bottleneck passes through RAM or DSP 0.8–0.85
Long combinational logic ≥3 cells + logic ratio > 0.5 0.85
High fanout net ratio > 0.4 0.6
Clock architecture ≥3 violations in the same clock domain auto-escalated
Unknown none of the above conditions 0.3

Step 3: Knowledge base recall. Look up the 14 built-in knowledge base entries by category; each entry carries a fingerprint-matching score.

Step 4: Generate suggestions. Sort by match score and return the best root-cause diagnosis and fix.

4.3 The diagnosis result view

The diagnosis webview contains three tabs:

Tab Content
Diagnosis Root-cause analysis + fix suggestions (with example code) + evidence
Data path Mermaid path topology + delay flame graph + delay decomposition
Pipeline analysis Three-stage redundant pipeline-stage analysis report

The top-left corner lets you switch between violating paths (a slack-sorted dropdown selector).

The bottom-right corner has an "Ask LLM" button that sends the current path's diagnosis context + RTL snippet + SDC to an LLM for deeper analysis.

5. Data path analysis and visualization

5.1 DataPathTracer output

DataPathTracer reorganizes the hop sequence from a timing report into a structured data flow:

Hop sequence:
  cam_top/cap_reg[3]/CK→Q  ← launch register
  LUT4: cam_top/cap_next[3]  ← combinational logic
  NET: cap_next[3]           ← routing
  LUT4: cam_top/fifo_wr      ← combinational logic (cross-module!)
  NET: fifo_wr                ← routing
  u_fifo/wr_ptr[0]/SETUP     ← capture register

Structured as:

Inside module cam_top:
  register → logic(LUT4) → route → logic(LUT4) ───cross-module boundary──→ module u_fifo:
                                                                  route → register

5.2 Delay decomposition

Component Meaning Optimization direction
logicNs Combinational logic delay Reduce LUT levels; insert pipeline stages
routeNs Routing delay Check high fanout, duplicate logic, floorplan
registerNs Register CK→Q + setup Not optimizable (fixed by the process)
clockOverheadNs Clock overhead (skew + uncertainty) Reduce clock-uncertainty settings, or adjust the PLL

5.3 Mermaid topology

DataPathTracer automatically generates a Mermaid flow diagram showing the structure of the data path:

  • Green nodes: delay share < 12%
  • Yellow nodes: delay share 12%–25%
  • Red nodes: delay share ≥ 25% (bottleneck!)
  • Module boundaries are marked with dashed lines

6. Pipeline depth analysis: redundant pipeline-stage detection

6.1 Not a simple "find a register and remove it"

This is the most complex analysis module. Removing one register upsets the timing contract of the entire data path—companion control signals, counters, frame markers, and initialization sequences can all fall out of sync.

6.2 Three-stage analysis

Stage 1 (timing feasibility)  Stage 2 (signal dependencies)  Stage 3 (equivalence)
    ↓                      ↓                        ↓
findCandidateRegisters() → analyzeSignalDep()  → checkEquivalence()
    ↓                      ↓                        ↓
Candidate register list     Dependency report           Final recommendation
(slack estimate)           (7 checks)              (actionable? risk level)

Stage 1: Timing feasibility (pure number crunching)

Find two adjacent registers on the path (most commonly across a module boundary) and estimate the slack after removing one: - slack > 0 → continue the analysis - slack ≤ 0 → mark as "still violating after removal"; do not enter Stage 2

Stage 2: Signal dependency analysis (7 checks)

Check Logic
Handshake protocol Whether the candidate register sits in the same always block as valid/ready
Frame markers Whether last/sof/eof signals accompany it
Counters Whether frame/line counters can still align after the data latency changes
Feedback loops Whether removing one stage breaks closed-loop logic (e.g., an integrator)
Multiple consumers Whether the register output feeds more than one downstream module
Initialization timing Whether the reset/initialization sequence depends on the current latency in cycles
SVA Whether ##N delay assertions in simulation verification are affected

Stage 3: Equivalence

Generates a before/after timing-contract comparison and flags every inconsistency. When in doubt, stay conservative—mark it "requires manual confirmation" and provide no action button.

6.3 Hard constraints

  • Never suggest removing a single register alone: once companion signals are identified, the whole group must be handled together
  • All companion signals are flagged: even seemingly unrelated debug counters are checked
  • No action button when actionable = false: only the analysis conclusion is shown, awaiting human judgment

6.4 Simulation regression

After the pipeline analysis recommends RTL changes, equivalence must be verified. The EvoVerse SDK provides one-click simulation regression:

  • Command Palette → EvoVerse: Run Simulation Regression
  • Automatically runs iverilog / vvp to compare the outputs of the test vectors before and after the change
  • The diff report is embedded directly in the diagnosis webview

7. Build strategy optimization

7.1 BuildStrategyAdvisor

After each compile it automatically analyzes the BuildSummary and presents strategy suggestions in the Optimization tab of the Build Report. Each suggestion includes:

  • Trigger reason: cites concrete report data
  • Expected effect: quantified estimate
  • Risk level: low / medium / high
  • Action button (auto type only): one-click apply + rebuild

7.2 Strategy types

Strategy Trigger condition Type
AOE area optimization High resource utilization (≥80%) + relaxed timing auto
AOE off Low resource utilization (<60%) + tight timing auto
Retiming Uneven register distribution along paths manual
PNR Effort High WNS barely missing (−0.1 to −0.5 ns) auto
Seed Sweep Placement results fluctuate widely manual
DSP Packing Multipliers not mapped to DSP blocks manual
BRAM Output Register Violations on RAM read paths manual

7.3 AOE decision matrix

Resource utilization Timing status Recommendation
≥80% All Met Keep AOE on; area has the right priority
≥80% Violations Relax AOE: allow area growth in exchange for timing
<60% All Met Enable AOE: area can be optimized
<60% Violations Turn off AOE: with room to spare, timing comes first
60–80% Violations Depends on the specific resource bottleneck; prefer turning AOE off for the affected modules

9. Typical optimization flow

9.1 Standard workflow

Step 1: Write the SDC
  ↓
Step 2: Build (Ctrl+Shift+B or EvoVerse: Build)
  ↓
Step 3: Check Build Report → Timing tab
  ├─ All Met? → done ✓
  └─ Violations →
       ↓
Step 4: Diagnose timing (Diagnose Timing)
  ↓
Step 5: Review diagnosis suggestions
  ├─ Try low-risk tool options first (Optimization tab)
  │   · Effort Level High
  │   · Seed Sweep
  │   · Retiming → Rebuild → back to Step 2
  ↓
Step 6: If tool options are not enough → review RTL-level suggestions
  ├─ Long combinational chain → insert pipeline stages
  ├─ High fanout → (* max_fanout = N *)
  ├─ CDC → add a synchronizer + fix constraints
  ├─ I/O → configure IO register + IO delay
  └─ Resource bottleneck → enable RAM/DSP output registers
  ↓
Step 7: Edit RTL → Rebuild → back to Step 2
  ↓
Step 8 (advanced): if difficult paths remain
  ├─ Open the "Data path" tab → find the bottleneck hop
  ├─ Open the "Pipeline analysis" tab → check for redundant cross-module stages
  └─ "Ask LLM" → hand the full context to an LLM for analysis

9.2 Priority principles

  1. Constraints first, RTL second: SDC errors/omissions are the most common root cause
  2. Tool options first, manual edits second: Effort Level / Retiming are painless optimizations
  3. Local fixes first, architecture second: avoid lowering the frequency unless many paths violate broadly
  4. Slow paths first, fast paths second: setup violations > hold violations (hold is usually fixed automatically by the tool)

10. Common violation patterns and fixes

10.1 Pattern A: long combinational logic chain

Symptom: Tlogic share > 60%; 3+ consecutive LUTs/MUXes with no register in between

Root cause: compute-everything-in-one-statement code such as assign data_o = f(g(h(data_i)))

Fix:

// ❌ assign result = stage3(stage2(stage1(data_i)));
// ✅
reg [W-1:0] pipe1, pipe2;
always @(posedge clk) pipe1 <= stage1(data_i);
always @(posedge clk) pipe2 <= stage2(pipe1);
assign result = stage3(pipe2);

Cost: 2 extra cycles of latency

10.2 Pattern B: high fanout

Symptom: Tnet share > 40%; one signal drives hundreds of sinks

Fix:

(* max_fanout = 100 *) reg shared_enable;

10.3 Pattern C: CDC violation

Symptom: the path's start and end are in different clock domains

Fix:

# Step 1: cut off cross-clock-domain synchronous analysis
set_clock_groups -asynchronous \
    -group [get_clocks clk_a] \
    -group [get_clocks clk_b]

// Step 2: make sure a synchronizer exists
(* ASYNC_REG = "TRUE" *) reg [2:0] sync_ff;
always @(posedge clk_dst)
    sync_ff <= {sync_ff[1:0], src_signal};

10.4 Pattern D: I/O paths

Symptom: violations on paths through IO ports

Fix: 1. Add set_input_delay / set_output_delay 2. Tick the pin's "Register" option in the Interface Designer 3. In RTL: register inputs on the very first stage; make the final output stage a register

10.5 Pattern E: clock architecture problems

Symptom: ≥3 violations in the same clock domain; single-point optimization cannot converge

Fix: - Is the frequency too high? (For deep LUT4 logic on TJ180, a practical ceiling is roughly 100–150 MHz) - Consider using the PLL to lower this clock domain's frequency - Or split the data path: slow domain for control, fast domain for data processing

10.6 Pattern F: resource bottleneck

Symptom: violations on paths through BRAM/DSP

Fix:

// BRAM: enable the output register (it's free!)
(* ram_style = "block" *) reg [W-1:0] mem [0:D-1];
reg [W-1:0] mem_rd;
always @(posedge clk) begin
    if (wr_en) mem[wr_addr] <= wr_data;
    mem_rd <= mem[rd_addr];  // ← this register lives inside the BRAM and consumes no logic
end

// DSP: register inputs and outputs
(* use_dsp = "yes" *)
reg [17:0] a_r, b_r, p_r;
always @(posedge clk) begin
    a_r <= a; b_r <= b;  // input registers
    p_r <= a_r * b_r;     // output register
end

10.7 Redundant pipeline stages across modules

Symptom: two modules each register data at the interface

Module A: always @(posedge clk) data_o <= data_next;  // one pipeline stage
Module B: always @(posedge clk) data_r <= data_i;     // another pipeline stage

Fix: use pipeline depth analysis to determine whether one side's register can be removed (see Chapter 6)
