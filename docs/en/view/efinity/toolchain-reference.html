1. Toolchain overview and the unified flow pipeline

1.0 EvoVerse dual Python runtime domains

EvoVerse does not require customers to replace their system Python with the version bundled with Efinity, and never installs Python automatically:

  • The SDK's specification, Design Assurance, layered simulation orchestration, CLI, and MCP use the customer's system Python 3.11+. Before startup they actually import encodings, json, hashlib, and the verification engine; a version number alone does not count as usable.
  • Efinity Build, DesignAPI, IPM, and Debug are managed solely by the Efinity Adapter. For the selected installation, the Adapter first runs its bin\setup.bat, then uses the vendor interpreter chosen by that environment; the SDK never assembles version directories such as python311.
  • Both subprocesses strip the other side's leftover PYTHONHOME, PYTHONPATH, and Python PATH entries. A failing runtime domain is never silently taken over by the other Python.
  • Build, DesignAPI, IPM, and Debug report capabilities separately. For example, when native efx_run.bat --flow compile is available, a DesignAPI incompatibility does not block Build.

The Workbench Runtime domains panel reports interpreter and API probe results only. It does not mean simulation, a Questa license, native compilation, timing, or hardware validation has passed.

1.2 The unified flow pipeline (the seven do_ steps of the compile flow)

efx_run.py expands each flow into a set of boolean switches (build_cmdline_options first sets each to False at L265-298, then sets them per flow branch). compile (the default flow) expands to seven steps (L332-340):

elif re.match('^nosim$|^compile$', args.flow):     # efx_run.py L332
    args.use_prj_name = True
    args.do_map = True              # 1. Synthesis
    args.do_pt_generation = True    # 2. Interface Designer (PT)
    args.do_pnr = True              # 3. Place-and-route + STA
    args.do_pgm = True              # 4. Bitstream generation
    args.do_security = True         # 5. Security layer (survives only in --prj mode, see below)
    args.do_security_sc = True      # 6. Security layer SC (same)
    args.do_export_bitstream = True # 7. Export bitstream artifacts

Actual execution order inside run_flow() (L1991-2014, compile main line):

run_synthesis(map)                          # L1991
run_debugger_auto_instantation (optional)    # L1995, when debug_profile
run_pt('default')                           # L1996  ← after map, before pnr
run_pnr (may run run_early_phys_syn first)  # L2000-2003
run_pgm                                     # L2005
run_security / run_security_sc              # L2006-2007
run_export_bitstream                        # L2008

That is, map → PT(interface) → pnr → pgm → security → export_bitstream. Two key orchestration rules:

  • The two security steps survive only under --prj (project XML mode): at the end of build_cmdline_options, non-prj mode force-resets args.do_security = False; args.do_security_sc = False (L553-555).
  • debug_profile hijacks the PT step: under the compile/full flow, if a debug profile is given beyond --flow, then do_auto_instantiate_dbg=True, do_dbg_pt_generation=True, and plain do_pt_generation=False (L140-145) — the standard PT is replaced by "auto core insertion + dbg PT".

Source: C:\Efinity\2026.1\scripts\efx_run.py. The internals of the PT step (the nine-step DesignAPI orchestration inside efx_run_pt_unified.py) are not expanded in this volume; see Efinity DesignAPI Reference.

1.3 Exit code semantics

efx_run.py: binary exit code (__main__, L2130-2151):

Exit code Condition
0 run_flow returns True (and, in --prj mode, the project XML has been written back, update_project_file L2141-2142)
1 Any step fails: a subprocess exits non-zero (CalledProcessError, L2015-2021), a --timeout expiry (TimeoutExpired, L2022-2028), or any other Python exception (L2029-2032, L2144-2146)

Two notes: (1) inside run_flow, success = e (L2032) assigns the exception object to success, and __main__ then raises it as the final catch-all — so any exception ultimately converges to exit 1; (2) update_project_file (from L2046) merges this run's command-line opts back into the project XML after success — the project file is "a living document updated by the orchestrator".

efx_run_pt_unified.py: three-valued status code, but WARNING_SKIP and OK both map to 0 (sys.exit(ret), L393):

PTFlowRunnerStatusCode exit code Trigger
OK 0 PT completed normally
WARNING_SKIP 0 EFX_SKIP_PT is not '0' (L127-129), or the family is not trion/titanium/topaz (L138-140)
ERROR 1 device/family missing (L133-135, L142-145) or any exception (L390-392)

So from the caller's perspective a direct PT invocation has only two states, 0/1; "skipped" counts as success — one reason AGENTS.md §7 opposes stitching flows together with EFX_SKIP_PT: it silently turns "should have run but didn't" into green. The full semantics of the three-valued enum and the nine-step flow are in Efinity DesignAPI Reference.

1.4 Direct PT invocation and ISF self-checks (efx_run_pt_unified.py / import_gpio)

1.4.1 Blank PT baseline (direct invocation without --peri_scripts)

When efx_run_pt_unified.py is run without --peri_scripts, the import loop is empty and no ISF is executed; it directly produces a blank <project_name>.peri.xml containing only the device's default peripheral database:

# Run from the project root (design_dir defaults to the current directory)
python efx_run_pt_unified.py <design> <family> <device> --project_xml <project>.xml
# Output: <project_root>\<project_name>.peri.xml (blank baseline)

Key behaviors (source: C:\Efinity\2026.1\scripts\efx_run_pt_unified.py):

Behavior Evidence
peri_scripts defaults to an empty list; the import loop does not run L377-378 (if args.peri_scripts is None: d['peri_scripts'] = []); the import loop consumes this list
design_api.generate() is still called with an empty script list to produce the peripheral design PTFlowRunner main body
In project_xml mode peri.xml is always written to the project root (same directory as the project XML), not outflow proj_path / f"{proj_db.project_name}.peri.xml"
--output_dir defaults to <design_dir>/outflow; --work_dir defaults to work_pt argparse definition near L365

1.4.2 The "first import" semantics of the ISF dry-run self-check

The SDK's bundled sdk/cli/import_gpio.bat (→ import_gpio_cli.py) is a thin wrapper: load the peri.xml → call Efinity's official DesignAPI.import_design() (ISF path) / ImportGPIODesign (CSV path) → report issues; --dry-run only parses and reports, without writing back to the peri.xml.

Understand this: import operates on the peri.xml design library passed via --peri. assign_pkg_pin can only assign pins to GPIO instances that already exist in the peri.xml; when the instance does not exist, the import fails outright (observed error signature Unknown instance). The ISF's create_*_gpio calls are what create the instances first — therefore:

The self-check baseline must be a blank PT first import (the blank peri.xml of §1.4.1); never use a peri.xml that has already imported GPIOs. A dry-run against a library that already contains GPIOs will, because the instances already exist, produce results completely different from the real build flow (where PT, after synthesis, consumes the persisted peri.xml and replays the ISFs).

1.4.3 Standard CI fixed-baseline procedure

# 1. Blank PT produces the first-import baseline (see §1.4.1)
# 2. Dry-run the ISF under test; only exit 0 counts as valid
import_gpio.bat --peri <project>.peri.xml --input constraints\xxx.isf --dry-run

Repeat the two steps "blank PT → dry-run" on every constraints/*.isf change; the baseline must be freshly produced by the current toolchain on site — never reuse a hand-kept peri.xml or one left over from a historical build.

1.4.4 Output isolation for investigative runs

A direct PT invocation creates outflow/ and work_pt/ in the project directory. Investigative runs — troubleshooting, ISF validation — should explicitly point at isolated output directories:

python efx_run_pt_unified.py ... --output_dir <isolated_dir>\outflow --work_dir <isolated_dir>\work_pt

Note that --output_dir only isolates intermediate artifacts; peri.xml is always written to the project root (§1.4.1) and is never redirected by this parameter.

2.3 The pass-through option mechanism (--opt name=value)

The four *_opts parameters are all string lists with append nargs='+'; every element must be in name=value form. The orchestrator expands each group into --opt-prefixed arguments for the target tool:

Target Splicing code (efx_run.py) Form received by the target tool
efx_map L1245 [sys.argv.extend(['--opt'] + x) for x in args.map_opts] efx_map ... --opt mode=area --opt retiming=1
efx_pnr L1317 argv.extend(['--opt'] + x) efx_pnr ... --opt seed=42
efx_pgm L1370 [sys.argv.extend(['--opt'] + x) for x in args.pgm_opts] efx_pgm ... --opt bitstream_compression=off
PT L1448 for x in chain(*args.pt_opts) DesignAPI parameter dictionary

Three guardrails:

  1. option_exists() deduplication (L2037-2043): a ^option= regex checks whether the pass-through list already has an option with the same name, so automatically injected orchestrator options (such as root=, arch=, sdc_file=) never overwrite values the user passed explicitly (L693-701, L726-733).
  2. The name in name=value must be the registered name from the options XML (§8); CLI hyphenated-style variants are not accepted (for efx_map you pass retiming=2, not --retiming 2).
  3. Write-back to the project XML on success: after a successful --prj-mode build, update_project_file (from L2046) merges the opts back into the matching project XML sections (<param> under <synthesis> / <place_and_route> / <bitstream_generation>), so the GUI and the CLI share one parameter truth.

7.2 EFX_SKIP_PT

It appears only in efx_run_pt_unified.py (L127-129):

if os.getenv('EFX_SKIP_PT', '0') != '0':
    print("Skipping Interface Designer flow due to EFX_SKIP_PT environment variable")
    return PTFlowRunnerStatusCode.WARNING_SKIP
  • Semantics: set it to any value other than '0' (1, true, yes all work) and the entire PT step is skipped, with the exit code still 0 (§1.3, WARNING_SKIP = 0).
  • EvoVerse position: forbidden on production build paths (AGENTS.md §7, No Workaround Tools). It is an official debug backdoor for "the interface is frozen, I only want to rerun the backend", but its silent-success behavior lets configuration errors of the "PT should have run but didn't" kind (a missing peri.xml, <inter_file name=""/>) slip past compile checks and explode only at board-level validation. The root-cause fix is always to fix the project configuration, never to set this variable.
  • In a normal build it should be unset; CI may add an assertion that EFX_SKIP_PT is not defined.

8. Options XML ground truth and the XML-only determination method

8.1 Architectural differences among the three options XMLs

File namespace schema Entries (all / family-specific) Relationship to the project XML
bin\efx_map_options.xml enf_topt enf_topt.xsd 32 / Trion 2 + Titanium 5 Values written by the orchestrator into <synthesis>/<param> and read back
bin\efx_pnr_options.xml enf_topt enf_topt.xsd 5 / Titanium 1 + TitaniumX 1 Values written into <place_and_route>/<param> (the qp_options= merge mechanism, efx_run.py L813-840)
bin\efx_pgm_options.xml enf_proj (exception) enf_proj.xsd 15 / Titanium 3 Isomorphic to <bitstream_generation>/<param>, passed through directly

The option element structure is uniform across the three files:

<efx:option name="--mode" value="speed,area,cong,power,speed2,area2" default="speed" value_type="e_option"/>
  • Four value_type kinds: e_option (enumeration, value = comma-separated legal values), e_integer (value=min,max is a closed interval, e.g. --fanout-limit value="0,2000" = 0..2000; special case --seed value="1" a single value), e_bool (value = on,off), e_string (only --jtag_usercode).
  • options_group groups by family_name + device_name; a same-named option in a sub-group overrides the all-group default (the only instance: --active_capture_clk_edge all=posedge → Titanium=negedge).
  • Family-specific options are legal only for that family: passing a Titanium-group option to a Trion project is rejected by the tool.

8.2 How to determine XML-only options (without running --help)

The steps used to determine the "XML-only?" column of this document, reusable for future version upgrades:

  1. Read bin\efx_*_options.xml for all registered options (source of truth: name / default / legal values).
  2. The matching official CLI documentation page (DITA-generated; the body starts around L168, earlier lines are navigation boilerplate):
  3. doc\topics\cli-map-opts.html (Table 1 Synthesis Options, from L178)
  4. doc\topics\cli-pnr-opts.html (Table 1-5, L178-365)
  5. doc\topics\cli-pgm-opts.html (Table 1-3, L178-425)
  6. Present in XML but absent from the HTML tables → XML-only: not shown by --help, settable only via --opt name=value pass-through or a project XML param.
  7. Present in HTML but absent from XML → a CLI-inherent parameter (§3.3 / §4.2 / §5.2), generated automatically by the orchestrator or not stored in the project XML.

8.3 The two-layer validation split between efx_run.py and the options XMLs

  • Orchestration layer (efx_run.py parse_project_file): does existence checks and deduplication only (option_exists), never consumes value_type (read at L802-803 and discarded) — type legality is validated by the tool binaries themselves. This conclusion matches Efinity XML Project File Schema Reference.
  • Tool layer (efx_map/efx_pnr/efx_pgm): validates enumerations/ranges against the options XML; an illegal value errors out immediately (exit ≠ 0 → converged to exit 1 by efx_run).
  • Empty-name truth check: when elem.get('name') is falsy the orchestrator skips option generation (L726) — <efx:inter_file name=""/> generates no sync_file= and raises no "empty name" error; the error is deferred until pnr cannot find the interface file. This is the source-level evidence for AGENTS.md §7's "an empty <efx:inter_file> is a configuration bug".
