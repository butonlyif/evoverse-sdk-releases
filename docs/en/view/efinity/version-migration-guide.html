Efinity Version Migration

Efinity Version Migration Guide

Version: v1.0 | Based on Efinity 2026.1 | Last updated: 2026-07-30

This document collects every change point to watch when migrating from older Efinity releases to v2026.1, covering the toolchain, project XML, the Sapphire SoC, RTL coding, timing constraints, and other incompatible changes.

1. Version overview

1.1 How to check the current version

Method Command/path Description
Efinity splash screen shown at GUI startup Shows the version number and build date
Command line efx_run.bat --version Shows the efx_run version
Project XML in the project .xml, <project sw_version="..."> Records the Efinity version that created the project
Version file C:\Efinity\<version>\version.txt Contains the full version information

Source: Efinity UG v16.0/v16.2 and project XML practice.

1.2 Version compatibility warning

Important: after a new Efinity version opens a legacy project, the project file is updated with version-specific modeling information and is not backward compatible. If legacy build artifacts (synthesis/place-and-route outputs) are incompatible, the software prompts for a recompile.

Source: Efinity Software User Guide v16.0/v16.2, the "Using an Existing Project with a New Software Version" section.

3. Toolchain migration (GCC 8.3 → 13.4)

3.1 Change overview

Version GCC version Target architectures
Efinity ≤ v2025.2 GCC 8.3.0 (riscv64-unknown-elf-gcc) RV32IMAC / RV64IMAC
Efinity v2026.1 GCC 13.4.0 (riscv64-unknown-elf-gcc) RV32IMAC / RV64IMAC

3.2 Upgrade benefits

  • Improved C23 support
  • Better C++20/C++23 support
  • Support for more RISC-V ISA extensions

3.3 Incompatibility risks

  • BSP/firmware code: code that compiled under GCC 8.3 may need changes under GCC 13.4
  • Linker scripts: may need adapting to the new linker behavior
  • Compile options: some old compiler flags may be deprecated
  • Sapphire SoC: SoCs generated by v2026.1 must be used with the Efinity RISC-V Embedded Software IDE v2026.1

3.4 Rollback strategy

If you prefer not to upgrade the toolchain, you can keep using: - Efinity v2025.2 + Efinity RISC-V Embedded Software IDE v2025.2

Source: Efinix official documentation (https://www.efinixinc.com/docs-html/riscv-embedded-ide-ug/topics/riscv-embedded-software-ide-toolchain.html).

4. Sapphire SoC migration (v1 → v2)

4.1 Migration prerequisites

Sapphire SoC v2.0 was introduced in Efinity v2021.2 and cannot automatically migrate v1.x projects. Efinix officially recommends v2.0 for all new designs.

Source: Efinix official Sapphire RISC-V SoC User Guide v5.4, the "Migrating to the Sapphire RV32 SoC v2.0" section (https://www.efinixinc.com/docs-html/rv32-sapphire-ug/topics/riscv-sapphire-migrate-to-2.0.html).

4.2 Key v1 → v2 changes

Category v1.x v2.0
Timer peripheral Machine Timer CLINT Timer (the native CPU timer)
Device name definitions Old naming (soc.h) New naming + the compatibility.h bridge layer
Parameter names Partly different Updated parameter names
IP configuration wizard No FPU/MMU/Peripheral Clock options New: configurable Cache, FPU, MMU, Peripheral Clock
Debug configuration default_softTap only Supports Co-Debug and multiple JTAG configurations
AXI interface AXI3 only Supports both AXI3 and AXI4 (v2.0+)

4.3 Manual migration steps

  1. Create a new v2.0 project: use IP Manager to create a Sapphire SoC v2.0 and select the device part
  2. Reconfigure peripherals: enable the needed peripherals one by one in the IP configuration wizard (UART/SPI/I2C/GPIO, etc.)
  3. Re-attach APB/AXI slaves: reconnect custom peripherals in the RTL top level
  4. Adapt firmware code:
  5. Add #include "compatibility.h" and #include "bsp.h" at the top of application code
  6. Replace Machine Timer calls with CLINT Timer driver calls
  7. Recompile all firmware (with GCC 13.4)
  8. Replace the debug configuration: delete the old debug configuration and use the v2.0 one

4.4 v2.0 IP configuration reference (v1.x-compatible behavior)

Tab Option Recommended setting Notes
SOC Peripheral Clock DISABLE In v1.x, peripherals use the system clock
SOC FPU DISABLE Not supported in v1.x
SOC MMU DISABLE Not supported in v1.x
SOC Atomic Extension DISABLE Not supported in v1.x
Cache/Memory Data Cache Way 1 Fixed at 1 way in v1.0
Cache/Memory Data Cache Size 4 KB (v1.0) / 1–32 KB (v1.1) Match the original design
Cache/Memory I-Cache Way 1 Same as above
Cache/Memory I-Cache Size 4 KB (v1.0) / 1–32 KB (v1.1) Same as above

Source: Efinix official documentation (https://www.efinixinc.com/docs-html/rv32-sapphire-ug/topics/riscv-sapphire-migrate-to-2.0.html).

5. Project XML migration

5.1 Mandatory element order

Efinity 2026.1 enforces a strict order for the children of <efx:project> in the project XML:

device_info → design_info → interface_info → constraint_info → sim_info → misc_info → ooc_info → ip_info

Key points: - peri_file must sit inside <interface_info>, not <constraint_info> - ooc_info breaks some flow modes (when it carries content) - Wrong ordering can cause parse failures or abnormal behavior

Source: Efinity参考设计索引.md §M.2 and C:\Efinity\2026.1\bin\enf_proj.xsd.

5.2 Automatic XML upgrade behavior

  • When v2026.1 opens an older project XML, Efinity upgrades the XML schema automatically
  • The upgraded XML cannot be opened in older Efinity versions
  • Back up the original project directory before upgrading

Source: Efinity UG v16.0/v16.2.

5.3 Unified Flow notes

  • Unified Flow (unified_flow="true") remains supported in 2026.1
  • Legacy non-Unified-Flow projects need the (* syn_peri_port = 0 *) marker and can migrate to Unified Flow gradually

Source: Efinity参考设计索引.md §M.2.

6. Regenerating peri.xml

6.1 Version incompatibility

A peri.xml (the Interface Designer design database) can be incompatible across Efinity versions. Block type, property, preset, and resource names are tied to the device and the Efinity version.

Source: Efinity设计API集成.md, the "Version compatibility" section.

6.2 Regeneration strategy

When the peri.xml is incompatible after an Efinity upgrade:

  1. Delete the old peri.xml (after backing it up)
  2. Confirm the project XML correctly references the matching .peri.isf:
  3. Run the native Efinity efx_run --flow compile and let the native PT stage regenerate it
  4. Or open it in the Interface Designer, validate, and save
  5. Validate DRC: run evoverse design validate
  6. Confirm the build passes: run the full compile flow

Do not maintain an XML schema migrator in the SDK — the ISF is the source of truth.

Source: Efinity设计API集成.md, the "Version compatibility" section and the "TJ180 verified baseline" section.

6.3 The TJ180 verified case

A verified migration path (Efinity 2026.1): 1. Delete the old peri.xml 2. Rebuild from constraints/base.peri.isf 3. DesignAPI DRC passes (0 errors) 4. The full Synthesis → Interface → PNR → PGM flow PASSes

Source: Efinity设计API集成.md, the "TJ180 verified baseline" section.

8. RTL/synthesis migration

8.1 Timing model deprecation

The I4 / I4L timing models on Ti35/Ti60 devices are deprecated in Efinity 2026.1. Runtime emits a warning. Switch to a currently supported timing model.

Source: toolchain-reference.md §5.4.

8.2 Periphery inference vs instantiation

Mode Parameter Description
Inference mode --peri-syn-inference The synthesis tool infers peripheral primitives automatically
Instantiation mode --peri-syn-instantiation Peripheral primitives are instantiated manually
Unified Flow unified_flow="true" The recommended mode; unified management

Source: toolchain-reference.md §2.1, lines 107–108.

8.3 New synthesis options

Synthesis options added/updated in Efinity 2026.1 (verify against your old version by experiment); for the core parameters see toolchain-reference.md §2.

9. SDC/constraint migration

9.1 Timing model changes

  • After the I4/I4L timing models on Ti35/Ti60 were deprecated, the associated SDC constraints may need adjustment
  • The new devices (Ti125/Ti95) need new --operating_conditions settings

9.2 Unified SDC

  • 2026.1 continues to support unified SDC files (--unified_sdc_file)
  • The PT SDC generated by Interface Designer is included in the compile flow automatically

Source: toolchain-reference.md §3.2.

10. Build script migration (efx_run changes)

10.1 Core changes

Item Old behavior New behavior (2026.1)
Default device family Titanium Titanium
Default device Ti60F225 Ti60F225
Compile flow map → PT → pnr → pgm unchanged
Python API none efx_py support

10.2 The AOE script

The new efx_run_aoe.py automatically explores synthesis and placement options, replacing manual parameter trials.

10.3 Build command examples

# Standard compile (compatible with older versions)
efx_run.bat my_design

# Use a new device (must be specified)
efx_run.bat my_design --family Titanium -d Ti125F225

# Explore with AOE
efx_run_aoe.py my_design

Source: toolchain-reference.md §1.1–1.2 and the Efinity v2026.1 release notes.

11. Complete upgrade checklist

Before upgrading

  • [ ] Back up the whole project directory (including .xml, peri.xml, *.peri.isf, and sdc files)
  • [ ] Record the current Efinity version number
  • [ ] Check for deprecated Ruby/Jade/Opal SoCs in use
  • [ ] Check for I4/I4L timing models in use
  • [ ] Confirm IP dependency versions

During the upgrade

  • [ ] Install Efinity 2026.1 and the RISC-V Embedded Software IDE 2026.1
  • [ ] Open the project with v2026.1 → the XML schema upgrades automatically
  • [ ] Delete the old peri.xml → regenerate from the ISF
  • [ ] Check the child element order of <efx:project> (see §5.1)
  • [ ] If on Sapphire v1 → migrate to v2 manually per §4.3
  • [ ] Update the GCC toolchain (8.3 → 13.4) and recompile the firmware

After the upgrade

  • [ ] Run the Interface Designer DRC (evoverse design validate)
  • [ ] Run synthesis and review compile warnings
  • [ ] Run the full compile flow (Map → PT → PNR → PGM)
  • [ ] Check the timing report (confirm no new violations)
  • [ ] Reprogram the board and verify hardware functionality
  • [ ] Update the monthly development record (DAYLOG/<YYYY-MM>.md)

12. Rollback strategy

If you need to go back to an older Efinity:

  1. Keep the old installation: Efinity supports multiple versions side by side (installed into different directories)
  2. Use the backed-up project: never take a new-version project XML back to an old version — it has been auto-upgraded
  3. Restore the peri.xml: rebuild from the ISF (do not restore the old binary)
  4. Roll back the toolchain: use the old Efinity + the old RISC-V IDE (GCC 8.3)

Recommended multi-version layout:

C:\Efinity\
├── 2025.2\   (kept for existing stable projects)
└── 2026.1\   (the new version, for new projects and migration validation)
