1. Positioning, namespace, and layout rules

1.1 What the project file is

<project_name>.xml is the single entry file of an Efinity project: the GUI opening a project, efx_run --flow compile orchestrating a build, and the tool binaries (map/pnr/pgm) reading their configuration sections all start from it. It is defined by enf_proj.xsd, with targetNamespace:

xmlns:efx="http://www.efinixinc.com/enf_proj"

Evidence: c:\Efinity\2026.1\bin\enf_proj.xsd L1-L7; c:\Efinity\2026.1\scripts\efx_run_common.py L10 (EFX_PRJ_XML_NAMESPACES = {'efx': 'http://www.efinixinc.com/enf_proj'} — the orchestration scripts resolve by this prefix; a wrong namespace is equivalent to every efx: element not existing).

1.2 Hard layout rules (violation = failure)

Rule Description Evidence
The project XML lives in the project root Every official example does this; do not invent subdirectories such as efinity_project/ C:\Efinity\2026.1\examples\helloworld-unified\helloworld.xml sits in the example root
All relative paths resolve against the directory holding the XML file SDC, RTL, ISF, flist — all of them §1.3 of this document
The namespace must be exact Tools resolve by the prefix→URI mapping efx_run_common.py L10
Empty <efx:inter_file name=""> See the dedicated ruling in §13; generators must not emit it workspace hard rules §2 + official example L15

1.3 The relative-path resolution base

The EvoVerse-side validation logic matches Efinity tool behavior — referenced paths always resolve relative to the project XML's parent directory:

  • EvoVerse project-reference validation: c:\work\awesomsdk\sdk\cli\evoverse L1562-1570 (an os.path.exists check relative to the project_xml parent directory).
  • The XSD's file_type notes that name "must include relative path" (enf_proj.xsd L123-126).

Therefore, with the project XML in the root, <efx:sdc_file name="constraint/timing.sdc"/> points at <project_root>/constraint/timing.sdc.

2. Root element <efx:project>: attributes and child element order

2.1 Child element order (xs:sequence, strictly ordered)

The XSD defines the children as an xs:sequence (enf_proj.xsd L9-43); the order must not be shuffled. Occurrences:

# Element Occurrence Description
1 device_info 1 Device and timing model
2 design_info 1 Top-level module and source files
3 package_info 0..1 Pending deprecation (XSD comment "will be deprecated")
4 interface_info 0..1 Interface Designer (peri file)
5 constraint_info 1 SDC / inter / ISF constraints
6 isf_info 0..1 ISF scripts (the new location; unused by the official examples, see §6.4)
7 sim_info 0..1 Simulation
8 misc_info 0..1 Reserved section (unused by the official examples)
9 ooc_info 0..1 Out-of-Context compilation
10 ip_info 0..1 IP instances
11 synthesis 0..1 Synthesis options
12 place_and_route 0..1 Place-and-route options
13 bitstream_generation 0..1 Bitstream options
14 debugger 0..1 Debugger options
15 security 0..1 Encryption/signing

Order sensitivity, evidenced: <efx:design_file> must appear before top_vhdl_arch — the EvoVerse adapter's comments explicitly record that violating this order makes Efinity reject the project XML on the next native load (c:\work\awesomsdk\products\efinity-adapter\extension\src\capabilities\ip.ts L92-95).

2.2 Root element attribute table (enf_proj.xsd L44-59)

Attribute Required Default Semantics
name ✅ — Project name
description — empty Description
sw_version ✅ — The Efinity version that produced the project (official examples: 2025.2.276)
last_change — empty Last modifier
last_change_date — empty Retained backward-compatibility attribute
location — empty Project path
last_run_state — empty Enum pass/fail/crash/empty — GUI status display; does not affect compilation
last_run_flow — empty Name of the last-run flow
last_run_tool — empty Last-run tool
config_result_in_sync — empty GUI project/configuration sync marker
design_ood / place_ood / route_ood — empty Enum sync/new/change/empty — the GUI's "out-of-date" markers
last_run_timing — empty Enum core_only/unified_timing/unknown/empty

These last_run_* / *_ood attributes are GUI bookmarks: the tools write them back after a run. The EvoVerse generator simply pins neutral values such as last_run_state="pass" (sdk\cli\evoverse L1868-1954 does exactly that).

3. <efx:device_info> — device and timing model

Schema (enf_proj.xsd L63-85):

Child element Occurrence Default Type Semantics
family 1 Quantum non_empty_string Device family: Titanium / Trion / Quantum / Topaz
device 1 Q10 non_empty_string Specific part, e.g. Ti60F225, T120F576
timing_model 0..1 op1 string Timing model speed grade

Project XML ↔ peri.xml consistency: the unified PT stage validates that the project XML's device/timing_model matches the peri design database, and errors out on a mismatch (c:\Efinity\2026.1\scripts\efx_run_pt_unified.py L226-231). Switching devices must handle the peri.xml as well — changing only the project XML is not enough.

Workspace rule tie-in: the Ti35/Ti60 timing models I4/I4L are deprecated; use C4 or C5 (workspace hard rules §13). All three official examples use C4.

4. <efx:design_info> — top-level module and source files

4.1 Attributes (enf_proj.xsd L88-103)

Attribute Required Default Semantics
top_module ✅ — Synthesis top-level module name (→ map command line root=<name>)
top_vhdl_arch — empty VHDL top-level architecture name (→ arch=<name>)
unified_flow — false Whether the unified flow is enabled (the interface-designer-fused flow)
partition_interface_allowed_off_perimeter — true Partition interfaces allowed off the perimeter

⚠️ The XSD default of unified_flow is false (enf_proj.xsd L101). Omitting the attribute = the standard dual flow; for the unified flow you must write unified_flow="true" explicitly. The official helloworld-unified example writes it; helloworld-dbg/helloworld-ru do not (i.e. false).

4.2 Child element order and the two file element kinds

Inside design_info it is again an xs:sequence: all design_file entries first (0..N), then the optional top_vhdl_arch last. Every design_file must precede top_vhdl_arch (see the order-sensitivity evidence in §2.1).

4.3 <efx:design_file> — the three-state semantics of version (core)

Schema (enf_proj.xsd L123-136): name (required, includes the relative path), version (optional), library (optional, VHDL library name).

efx_run.py handles version in three states (c:\Efinity\2026.1\scripts\efx_run.py L703-715):

version value Parse result What the map binary actually receives
Omitted (attribute not written) Added to the extra_files list -v <file> (Verilog include semantics)
"na" Added to the flist list --flist <file> → map binary --f
Any other value (e.g. "v1.2") extra_files + a ,t:<version> suffix -v <file>,t:v1.2 (versioned compilation unit)

Evidence chain: efx_run.py L703-715 (the three-state dispatch); the second mapping from --flist to the map binary is at c:\Efinity\2026.1\scripts\efx_run_map.py L44, L144 (--flist → map --f).

Practical meaning:

<!-- Plain RTL source: write nothing -->
<efx:design_file name="rtl/top.v"/>

<!-- flist manifest: version="na"; the file content is other file paths, one per line -->
<efx:design_file name="src/files.f" version="na"/>

<!-- Versioned compilation unit (rare) -->
<efx:design_file name="rtl/legacy.v" version="1995"/>

5. <efx:interface_info> — Interface Designer files

Schema (enf_proj.xsd L106-113):

Child element Occurrence Semantics
peri_file 1 Interface Designer database file (<design>.peri.xml)
interface_script_file 0..N Interface scripts (synonymous with isf_file under constraint_info, see §6.4)

⚠️ The schema and the orchestration script disagree on the location (practical warning): the XSD defines peri_file in the interface_info section (enf_proj.xsd L110-111), but efx_run.py's parse_project_file actually reads peri_file from the constraint_info section (efx_run.py L983-990). Projects work because GUI-written projects are semantically compatible at both locations and because tools reading the XML themselves via --prj go through the projectdb layer (db.py L283 maps inter_file to interface_constraint_file; the peri is managed by the interface database system). Conclusion: copy the official examples' layout (never hand-write the peri file; it is produced by the PT tool) — do not invent a layout that is legal at only one of the two locations.

<design>.peri.xml itself is a project source file in the PT tool's efxpt:design_db namespace — not part of this document's enf_proj system; neither users nor the SDK should ever hand-write it (workspace hard rules §1, §15).

6. <efx:constraint_info> and <efx:isf_info> — constraint files

6.1 constraint_info children (enf_proj.xsd L152-183, ordered by xs:sequence)

# Element Occurrence Status Consumer
1 sdc_file 0..N valid efx_pnr (timing constraints)
2 unified_sdc_file 0..N valid unified timing analysis (efx_run_pnr.py L224-241: multiple unified SDCs form a filelist)
3 io_place_file 0..1 deprecated Legacy pin assignment (mapped to user_io_assignment)
4 core_place_file 0..1 deprecated Legacy core placement (mapped to fix_pins)
5 inter_file 0..1 valid → efx_pnr's sync_file (only when name is non-empty, see §13)
6 interface_script_file 0..N valid (old name) migrated to isf_file at load
7 isf_file 0..N valid input to PT's design_api.import_design()

6.2 The constraint → CLI mapping table in efx_run.py

The mapping dictionary in efx_run.py L720-733 (verbatim):

{'sdc_file': 'sdc_file',
 'unified_sdc_file': 'unified_sdc_file',
 'io_place_file': 'user_io_assignment',
 'core_place_file': 'fix_pins',
 'inter_file': 'sync_file'}

Key detail: L726 applies a truthiness check on elem.get('name') — entries whose name is an empty string or missing are silently skipped. This directly drives the ruling in §13.

6.3 How SDCs are consumed

  • The PNR wrapper efx_run_pnr.py L174 passes --prj <xml> straight to the efx_pnr binary, which reads the SDC list from the XML itself.
  • Under use_unified_timing, multiple SDCs form a filelist (efx_run_pnr.py L224-241).
  • Fallback when there is no sync_file: on Trion/Titanium/Topaz devices the wrapper automatically looks for .interface.csv as the sync file (efx_run_pnr.py L203-206).

6.4 The interface_script_file → isf_file synonymous migration

The project-database load layer migrates explicitly (c:\Efinity\2026.1\python311\Lib\site-packages\projectdb\db.py):

  • L283: interface_constraint_file = inter_file
  • L284: interface_script_file_list = isf_file
  • L731-737: interface_script_file elements are migrated to isf_file at load (source comment verbatim: "because of some genius define two element type for same information").

In practice: always write isf_file in new projects; the two are equivalent when reading old projects.

6.5 The relationship between isf_file and the unified PT (the replay mechanism)

Under the unified flow (c:\Efinity\2026.1\scripts\efx_run_pt_unified.py L233-267):

  1. Netlist interface extraction produces <design>.unified.isf, inserted at the head of the peri_scripts list;
  2. Each ISF in the list is executed via design_api.import_design(script); any single failure fails the whole run.

This is the toolchain root of workspace hard rule §15, "ISFs must be replay-safe (only set_property/assign_pkg_pin etc.; create_* only for the one-time bootstrap)": every unified build replays all ISFs referenced by the project XML onto the persisted peri.xml.

6.6 The evidenced rejection of empty <efx:isf_file name=""/>

The EvoVerse generator's comments record that an empty <efx:isf_file name=""/> entry makes PT reject projects that carry a peri.xml (c:\work\awesomsdk\sdk\cli\evoverse L1884-1887, comment verbatim: "an <efx:isf_file name=""/> entry makes PT reject projects that carry a peri.xml instead of an ISF"). Hence the generator omits the whole line when the isf file name is empty, instead of writing an empty value.

7. <efx:sim_info> / <efx:misc_info> / <efx:ooc_info>

7.1 sim_info (enf_proj.xsd L199-211)

Item Kind Default Description
top_module Attribute "sim" Simulation top (⚠️ older versions of this document miswrote it as a child element; it is an attribute)
pt_sim_top_module Attribute "ptsim" PT simulation top
sim_file Child element 0..N — Simulation source files; when present with a .v/.sv/.vhd suffix, efx_run.py converts them to --tb (efx_run.py L666-673)
defmacro Child element 0..N — Simulation macro definitions (→ verilog-macros=) 
<efx:sim_info top_module="tb_top" pt_sim_top_module="ptsim">
    <efx:sim_file name="sim/tb_top.v"/>
</efx:sim_info>

7.2 misc_info / ooc_info

  • misc_info (L213-219): a reserved section; none of the three official examples use it.
  • ooc_info (L221-243): Out-of-Context compilation configuration, used only by hierarchical compile flows; normal projects do not write it.

8. <efx:ip_info> — IP instances

8.1 Schema definition (enf_proj.xsd L245-263)

Under ip_info there are 0..N ip elements (ip_type):

Item Kind Required Default Semantics
instance_name Attribute ✅ — IP instance name
path Attribute ✅ — Points at the IP's settings.json (with path)
ooc Attribute — false Whether to compile Out-of-Context
ip_src_file Child element 0..N — — Additional IP source files (resolved relative to the IP root)
ip_postmap_module Child element 0..1 — — post-map replacement module name

8.2 A complete, valid example

<efx:ip_info>
    <efx:ip instance_name="ddr_ctrl" path="ip/ddr_ctrl/settings.json" ooc="false">
        <efx:ip_src_file name="ip/ddr_ctrl/synthesis/edn/ddr_ctrl_wrapper.v"/>
    </efx:ip>
</efx:ip_info>

8.3 What <efx:ip> really does at the orchestration layer (key insight)

efx_run.py L676-683: every <efx:ip path="ip/<m>/settings.json"> is converted into adding ip/<m> (the parent directory of settings.json) to source_dir → map command line --dir ip/<m> — i.e. a full source scan of that directory. --project_xml is also passed to the tool core, which consumes ip_src_file on its own (resolved relative to the IP root — resolution fails if the file does not exist under the IP root).

8.4 EvoVerse's evidenced decision: do not write <efx:ip>

Comments in c:\work\awesomsdk\products\efinity-adapter\extension\src\capabilities\ip.ts L100-106 (essentials):

  • efx_run turns every <efx:ip path="ip/<m>/settings.json"> into a --dir ip/<m> source scan;
  • this compiles the same file a second time when it is already a design_file → the VERI-1206 duplicate module error;
  • ip_src_file resolves relative to the IP root, but the SoC netlist does not exist under the IP root.

Therefore the EvoVerse adapter's publishGeneratedIp (ip.ts L73-108) registers the generated IP sources as design_file only, deliberately writing no <efx:ip_info>/<efx:ip>; selectGeneratedSources (L136-160) additionally filters out the sim/, testbench/, template/, devkit/, and source_<simulator>/ directories so that non-synthesis sources are not scanned into the project.

Conclusion: <efx:ip> is an element of the "IP-integration toolchain (IP-generator-managed)" world; flows where sources are managed by hand or by a generator stay more controllable with design_file.

9. Compile option sections: synthesis / place_and_route / bitstream_generation / debugger / security

The five sections share the same structure (the tool-section definitions in enf_proj.xsd): each holds 0..N <efx:param name="..." value="..."/> entries.

9.1 The generic <efx:param> structure

<efx:param name="param_name" value="param_value"/>
  • Both name and value are required strings; the interpretation of value belongs to each consuming layer (§10).
  • Each section's parameter set is defined by the GUI's option database (the tool_options global element, enf_proj.xsd L372-394); the XSD itself does not validate param names — a wrong param name raises no schema error, it is just silently ignored by the tool or reported as a nonexistent option.

9.2 synthesis (efx_run.py L738-795)

param → command line / behavior
work_dir work-dir=<dir>, and it is enforced (DEVINFRA-1142: work_dir from the XML takes precedence; CLI overrides are suppressed)
def_veri_version / def_vhdl_version veri_options=verilog_mode=<v> / vhdl_mode=<v> (e.g. verilog_2k)
include I=<path> (repeatable)
opt_mode syn_options=mode=<v> (e.g. speed/area)
peri-syn-instantiation / peri-syn-inference Dispatched only under the unified flow (un_flow); the official unified example uses 1
dynparam top-params=<k>=<v> (dispatched twice, once for map and once for syn)
defmacro verilog-macros=...

When unified_flow="true" and the CLI does not explicitly pass --un_flow, efx_run.py derives un_flow=True from the attribute (within L738-795).

9.3 place_and_route (efx_run.py L797-840 + efx_run_pnr.py L168-182)

The orchestrator handles only two kinds of param:

  1. work_dir → the PNR working directory;
  2. params prefixed with qp_options= (minus anneal_random_seed) → spliced into the vpr options.

The remaining pnr params are not translated to CLI by efx_run.py — efx_run_pnr.py L168-182 parses the XML pnr params only for the option_exists dedup check, then L174 passes --prj <xml> straight to the efx_pnr binary, and the binary parses the <efx:place_and_route> section itself. This is the "dual-channel" model (§11.2) in typical action: do not expect a pnr param added to the XML to necessarily show up on the command line.

Common pnr params (evidenced by the official examples): active_capture_clk_edge (Titanium must keep the default negedge), retiming, oscillator_clock_divider, beneficial_skew, etc.

9.4 bitstream_generation (efx_run.py L842-867)

param Behavior
mode / width The official examples contain both e_option and e_string spellings (§12 comparison table); both are read
cascade / cold_boot / randomize_iv_value / iv_value Ignored by the orchestrator (the binary reads them itself via --prj)
jtag_usercode Validated against the regex ^0x[a-fA-F0-9]{8}$; on mismatch it is forced to 0xFFFFFFFF and written back into the project XML (side effect: the XML is rewritten by the tool)
bitstream_compression / four_byte_addressing Valid params (the dbg example has compression=on; only some examples carry four_byte_addressing)

9.5 debugger (efx_run.py L962-981)

work_dir, auto_instantiation (on → True, controls automatic debug-core instantiation at build time), profile (NONE → empty string). The official dbg example carries a debug core configuration.

9.6 security (efx_run.py L877-960)

Bitstream encryption/signing: encrypt → --encrypt, sign → --sign, keypair → --keypair=, plus the sc_* family (secure chip); IV-type values must be 24 characters long (12 bytes of hex).

10. param_value_type in depth: XML value types and the consumption chain

10.1 The five enumerations (enf_proj.xsd L325-333)

<xs:simpleType name="param_value_type">
    <xs:restriction base="xs:string">
        <xs:enumeration value="e_string"/>
        <xs:enumeration value="e_bool"/>
        <xs:enumeration value="e_option"/>
        <xs:enumeration value="e_integer"/>
        <xs:enumeration value="e_noarg"/>
    </xs:restriction>
</xs:simpleType>
Enumeration Semantics Typical value in the XML
e_string Free-form string Any text (paths, names, numbers all fine)
e_bool Boolean on / off (not true/false!)
e_option Dropdown enumeration One of the predefined options (e.g. pgm mode=active as an e_option)
e_integer Integer Decimal integer string
e_noarg The "no-argument" switch Stored like e_bool as on/off; semantically "the option takes effect by existing, taking no value"

10.2 Examples of XML → command-line mapping

XML After consumption
<efx:param name="opt_mode" value="speed" value_type="e_option"/> syn_options=mode=speed (the value enters the option string as-is)
<efx:param name="auto_instantiation" value="on" value_type="e_bool"/> the orchestration layer reads on → Python True (efx_run.py L962-981)
<efx:param name="retiming" value="2" value_type="e_integer"/> read by the pnr core via --prj; the numeric value 2
an e_noarg-style switch (value=on) when the core reads the XML it treats it as "option on, no associated value"; the orchestration layer generates no valued parameter for it

10.3 Who actually consumes value_type? (an important clarification)

  • The Python orchestration layer essentially does not: in the whole of efx_run.py, value_type is read exactly once at L803 and never used. The orchestration layer just carries value around as a plain string.
  • The GUI rendering layer does: efinity_plugin/OptionSchema.py L29-49 (e_bool/e_noarg → boolean widgets, e_option → comma-separated enum dropdown), efinity_plugin/ProjectMeta.py L1111-1159 (e_bool/e_noarg serialize as 'on'/''), aoe/core/common.py L43-49 (the EFX_VT enum's historical lack of noarg), projectdb/defines.py L79-88 (ParameterType includes NOARG).
  • The tool binaries: when reading the XML themselves via --prj, they interpret values per their own section's parameter semantics.

Practical meaning: in a hand-written project XML, a wrong value_type usually does not fail the build (the orchestration layer ignores it) but breaks GUI display/editing behavior; boolean-semantic values must be on/off to be recognized reliably.

11.2 The "dual-channel" model: orchestrator CLI translation ≠ all parameter passing

efx_run.py has two parameter channels; understanding this explains what §9.3 observed:

  1. The CLI channel: the orchestrator parses the XML and translates some parameters into sub-tool command-line arguments (the §11.1 master table).
  2. The XML direct-read channel: the XML is passed as --prj <project.xml>, and each tool core parses the sections it cares about itself:
  3. Synthesis: with --prj, --project_xml is passed as well (efx_run.py L1200-1266);
  4. PNR: --prj <xml> passed straight through (efx_run.py L1273-1341 → efx_run_pnr.py L174);
  5. PT/unified: --un_flow + --peri_netlist, plus the project database is loaded to take interface_script_file_list and issue each as --peri_scripts (efx_run.py L1420-1495).

Corollary: a parameter written in the XML but not translated by the orchestrator can still take effect via the XML direct-read channel — "invisible on the command line" does not mean "not in effect"; conversely, to confirm a parameter's real effect, trust the tool reports/logs.

Within the same official package, value_type spellings are inconsistent (pgm mode/width) and active_capture_clk_edge takes both negedge and posedge — evidence that value_type does not participate in compile semantics (§10.3), while active_capture_clk_edge is a flow-dependent parameter (the SPI active configuration scenario requires negedge, workspace hard rules §13; the dbg example's posedge is for selecting the LA capture clock edge — a debug configuration, not an SPI configuration scenario).

13. [Evidence-tension ruling] The empty <efx:inter_file name=""/>

13.1 The conflict

  • Fact A (official examples): L15 of all three 2025.2.276 official project XMLs is <efx:inter_file name=""/>, and the root attribute reads last_run_state="pass" (the previous build passed).
  • Fact B (workspace rules): this repository's hard rules (rules-efinity-hard.md §2 / AGENTS.md §2) say "an empty <efx:inter_file name="" /> breaks the build" and require deletion on sight.

13.2 Further first-hand reads of both sides' evidence

Evidence Content Points to
efx_run.py L726 applies the elem.get('name') truthiness check to inter_file; an empty name is silently skipped The orchestration layer is harmless toward an empty inter_file
efx_run_pnr.py L203-206 with no sync_file, it falls back to auto-finding .interface.csv Empty/missing inter_file has a fallback on the PNR side
sdk\cli\evoverse L1884-1887 an empty <efx:isf_file name=""/> was observed making PT reject projects that carry a peri.xml (the same-family "empty-name reference" failure mode) The failure may occur at the PT/core layer rather than the orchestration layer
Official example sw_version 2025.2.276 (older than the 2026.1 tool) Room for a version-difference hypothesis

13.3 The ruling

  1. The two facts do not directly contradict: the orchestrator (efx_run.py) does skip an empty inter_file; but the full build chain also includes PT import_design, projectdb loading, and the efx_pnr core reading the XML directly — the failure may occur in those layers, or only in specific version combinations (the official examples passing with the 2025.2-era build does not make every version safe).
  2. The same-family failure mode is evidenced: an empty isf_file making PT reject the project is an EvoVerse-side tested conclusion; "empty-name reference elements are unsafe" is a reasonable cross-element generalization.
  3. Safe practice (this repository's enforcement position):
  4. Generators do not write <efx:inter_file> (XSD minOccurs=0; omission is fully legal) — EvoVerse's _build_native_project_xml emits no such element;
  5. When a legacy GUI project carries an empty inter_file and builds fine: no need to panic-delete, but it must be revalidated after every toolchain upgrade;
  6. Never "fix" an empty inter_file by filling in a junk non-empty value — that genuinely creates a broken sync_file reference;
  7. This repository's rules still follow the workspace hard rules: <efx:inter_file name=""/> is not allowed on generation paths.

16. Self-check list (before/after generating or modifying a project XML)

  • [ ] The namespace is exactly http://www.efinixinc.com/enf_proj (§1.1)
  • [ ] The project XML is in the project root; every relative reference exists relative to the XML's directory (§1.2, §1.3)
  • [ ] Child element order follows xs:sequence: device_info → design_info → … → constraint_info → …; all design_file before top_vhdl_arch (§2.1)
  • [ ] unified_flow="true" is written explicitly (default false) (§4.1)
  • [ ] The three-state semantics of design_file's version are used correctly: omitted = -v, na = --flist, other = versioned with ,t: (§4.3)
  • [ ] timing_model is not a deprecated value (use C4/C5 on Ti35/Ti60, not I4/I4L) (§3)
  • [ ] No <efx:inter_file name=""/>, no empty <efx:isf_file name=""/> (§13, §6.6)
  • [ ] ISFs are replay-safe (only idempotent set/assign commands; create_* only for the one-time bootstrap, then commented out) (§6.5)
  • [ ] peri.xml exists, was produced by PT, is under version control, and is deleted by no build path (§5)
  • [ ] Every clock port has a matching create_clock in the SDC, with clock names exactly matching the RTL/PLL outputs (§6.3, tied to the workspace SDC rules)
  • [ ] Prefer design_file for hand-managed IP integration; use <efx:ip> only when you understand the --dir scanning behavior (§8.3, §8.4)
  • [ ] jtag_usercode matches ^0x[a-fA-F0-9]{8}$ (otherwise it is rewritten) (§9.4)
  • [ ] Boolean params use on/off; value_type agrees with GUI semantics (§10)
