Specification-Driven Layered Simulation and Vibe Coding

Spec-Driven Layered Simulation and Vibe Coding

Applicable version: EvoVerse SDK v1.0.0

This flow makes the design specification the sole behavioral authority. Even for a small feature, establish and freeze the specification before any RTL is generated. Simulation code, oracles, test vectors, and models are never reverse-engineered from the RTL under test, which rules out "the code and the test are both wrong yet everything still shows PASS".

When you need a staged, reliable flow, start your specification or RTL design request with @evoverse; the SDK Agent first confirms the working mode: the reliable design flow or free-form development. Ordinary agent conversations stay in free-form development, with no automatic mode prompt. The product has exactly two working modes: choosing the reliable design flow commits you to stage-by-stage confirmation; choosing free-form development stays out of this flow entirely—direct editing and Builds are unaffected.

RTL design-rule verification is not a coding style check. It examines structure, clocks, resets, CDC, state machines, FIFOs, data integrity, and protocol contracts; dynamic obligations require simulation evidence, and incomplete is not PASS.

1. Specification layers and the right granularity

  • ModuleSpec: a single functional unit that can be understood and verified on its own. It may span multiple HDL files; "one module spec per RTL file" is not required.
  • SystemSpec: describes module composition, subsystem boundaries, system behavior, dependencies, and hard-IP contracts.
  • Verification units are split strictly along functional boundaries into module, subsystem, and system; simple glue logic is never mechanically fragmented into overly fine grains.

Recommended layout:

design/
  modules/<unit>/rtl/              # multi-file DUT
  modules/<unit>/sim/{tb,models,assertions,vectors}/
  subsystems/<unit>/rtl/
  subsystems/<unit>/sim/{tb,models,assertions,scenarios}/
  system/<unit>/rtl/
  system/<unit>/sim/{tb,models,assertions,scenarios}/
.evoverse/verification/             # Frozen specs, graphs, requests, evidence, and decisions; do not edit by hand

2. Staged sequence of the reliable design flow

  1. Pick the concrete board/carrier and discover the relevant demos, IP, constraints, and Efinity models; copy them into the run-local quarantine and generate an exact-byte baseline-manifest.json. Unmodified legacy RTL may be reused with its recorded rule debt, but any byte change voids the exemption; encrypted code is treated purely as an interface/model-contract black box.
  2. Confirm the simulation level (the user chooses; the level precedes the specification): once the reliable iteration is established and before spec.draft drafts the specification, the simulation level must be confirmed first—otherwise the control plane blocks drafting with SIMULATION_PROFILE_REQUIRED. The AI extracts structured risk facts from the user's requirements, the bill of materials, and the project topology (single clock, CDC, FIFO, backpressure, cross-line/cross-frame state, safety-related, and so on) and submits them as riskFacts to simulation.profile.select; the control plane computes the recommended level under fixed risk rules, and the AI must never fill in the recommendation field itself. The three preset levels:
Level Applies to Default blocking obligations Deferred to board test by default
FPGA_FUNCTIONAL Simple features with a single clock, clear boundaries, and easily observable outputs (counters, LED chasers, stopwatches, GPIO) Compile/elaborate, reset, 1–3 main-path scenarios, 1 critical boundary, and, when needed, 1 integration smoke run Full wraparound, coverage quotas, long regressions, button feel, display aesthetics, parameter fine-tuning
FPGA_INTEGRATION Protocols, buffering, cross-line/cross-frame state, shared resources (FIFO, AXI/streaming interfaces, windowed ISP, DMA) Everything at the functional level + handshake/backpressure/frame boundaries, width/saturation/truncation, FIFO overflow protection, CDC, integration regression Exhaustive input combinations, exhaustive subjective image-quality sweeps
HIGH_ASSURANCE High-speed complex protocols, memory control, irreversible control, safety-related All obligations of the frozen specification (including recovery scenarios and coverage closure) No automatic deferrals; subjective tuning may still be deferred explicitly

You may accept the recommendation, go higher or lower, or use CUSTOM to partition blocking/deferred obligations explicitly; choosing below the recommended minimum requires acceptedRisks to be recorded. The level is bound to the design iteration: the specification is written to the selected level's budget (the number of scenarios is controlled at the source), specification revisions within the same iteration do not change the level, and changing the level requires a new design iteration. When the budget is exceeded (for example, FPGA_FUNCTIONAL allows at most 3 core blocking scenarios, 1 critical boundary, and 1 integration smoke run), the control plane demands explicit reconfirmation of the overrun—silently trimming or expanding the verification scope is not allowed. Stopwatch example: under FPGA_FUNCTIONAL, only reset display, start/stop hold, one 00:00.99 → 00:01.00 boundary, and one scan-rotation smoke run are required; the full 59:59.99 wraparound, all-digit coverage, 1000 property activations, and narrow glitch injection are deferred by default. ISP example: functional-level coverage suffices for black-level offset, while Bayer interpolation/window filtering/video-stream integration fall into the integration level on structural facts, and HDR/3A/safety imaging are recommended at the high-assurance level—grading follows risk, not hardcoded application names. 3. Extract readable facts from the archived materials, then combine them with the customer's requirements to draft the specification within the selected level's budget and complete the automated review; never reverse-derive a behavioral specification from legacy RTL—when ambiguity appears, generate options for the customer to choose from instead of guessing. 4. Freeze the specification and record its semantic digest; code generation is forbidden while the spec is unfrozen or the digest is stale. 5. Issue to the agent only the leaf functional units that are READY in the DAG; a response may modify only the declared rtl/ root. 6. Generate and qualify testbenches, oracles, assertions, vectors, and models automatically. A failure in compilation, interface binding, forward references, mutation detection, boundary/relational checks, watchdog, event integrity, or model compatibility is recorded as TEST_ASSET_FAIL and is never attributed to the DUT. 7. Static Design Assurance violations are recorded directly as DESIGN_RULE_FAIL; executable dynamic properties are compiled into the Test IR and re-adjudicated by simulation evidence. A "PASS" in an ordinary log does not count as evidence. 8. A subsystem's dependencies unlock only after both functional simulation and Design Assurance PASS for it; the system unlocks only after its subsystems PASS. The flow never generates every level first and backfills the tests later. A simulation pass is level-limited (FPGA_FUNCTIONAL_PASS / FPGA_INTEGRATION_PASS / HIGH_ASSURANCE_PASS; DEFERRED_RISKS_ACCEPTED is attached when deferred risks were accepted), and deferred items never produce a pseudo-PASS; NATIVE_BUILD_PENDING / BOARD_VALIDATION_REQUIRED and simulation status are always reported separately—a functional-level simulation pass does not mean a native build or hardware pass. 9. Modifying a module automatically invalidates that node and its downstream nodes; unrelated upstream nodes stay valid. Only change-promote can write the official tree; external tooling or manual edits become UNVERIFIED_EXTERNAL_CHANGE. 10. Before the customer confirms readiness for Build, BuildEligibility is read to summarize every node, dynamic obligation, registered asset, and final receipt. If anything does not match, the reliable flow advises against moving to the next stage; the customer may still explicitly exit to free-form development, and ordinary Builds are unaffected.

3. Status semantics

Status Meaning
PASS Frozen specification, qualified assets, complete coverage, and certified evidence are all satisfied
DESIGN_RULE_FAIL Design Assurance static or dynamic property evidence proves a design-rule violation
DUT_FAIL Qualified test evidence shows the DUT disagrees with the specification
TEST_ASSET_FAIL Qualification of simulation code or of oracles/vectors failed
SIMULATOR_ERROR A simulator or infrastructure failure; not attributed to the DUT
ORACLE_BLOCKED / MODEL_BLOCKED The customer must choose an oracle or model direction
TIMEOUT_OR_DEADLOCK Timeout attribution is not unique; a choice or additional evidence is required
INSUFFICIENT_EVIDENCE Insufficient coverage, missing evidence, or tampered evidence
WAIVED_PASS An explicit, scope-limited, unexpired customer waiver exists; not a full PASS

Results obtained with an ASSUMPTION_MODEL may only be stated as "passes under the approved assumption model", never as unconditional system compliance.

4. Customer choices and re-freezing

Whenever interface width, latency, register mapping, architectural boundaries, hard-IP models, or oracle direction are ambiguous, the system presents a finite set of options together with the recommendation rationale, the risks, the affected nodes, and the invalidation scope. The customer can only pick from the presented options; choice records are append-only evidence. If a choice changes the specification, the affected specifications must be re-reviewed and re-frozen before generation can continue.

Neither simulation nor the DUT may silently modify the specification, oracles, tests, thresholds, models, or historical evidence. Automatic repair is capped at three attempts, each allowing exactly one assumption plus a DUT-only patch; on failure, a byte-level rollback follows.

5. Efinity hard IP

Hard-IP simulation must first identify instances and configuration digests from the project XML, the ISF, peri.xml, and IP configuration, then proceed under the following trust tiers:

  • VENDOR_MODEL: a vendor model whose configuration matches and that is available.
  • QUALIFIED_BEHAVIOR_MODEL: when no executable vendor model exists, a behavioral model qualified through contract testing.
  • ASSUMPTION_MODEL: usable only with explicit customer approval; conclusions must carry qualifying language.

When a model is missing or its version or configuration does not match, the status is MODEL_BLOCKED; hollow or constant models must never fake a system PASS. For native Efinity commands and model facts, the Efinity generic simulation flow is authoritative.

6. Testbench authoring checklist

From case 2026-09-16-led-chaser-t20f256: all 3 first-round FAILs were testbench defects (false FAILs); the DUT had none.

  • Reset-initial-value checks must sample on the synchronous release edge (posedge rst_n). When the DUT uses an asynchronous reset with synchronous release (a 3-stage synchronizer chain), the internal reset release lags the removal of the external rst_n_i by 2–3 cycles; checking "the initial value was untouched during reset" against a fixed cycle count misaligns with the release edge and produces false FAILs.
  • The judgment semantics of coverage counters must align verbatim with the coverage-item definition. For example, the coverage item "switch between adjacent gears" cannot be implemented as "two consecutive period counts are equal"—if each gear has a distinct period, that condition is always false and the coverage point is unreachable. Re-read the coverage-item definition before implementing it and verify every comparison operator word for word.
  • When a testbench FAIL appears, attribute it first (testbench defect or DUT defect) before changing anything; snapshot the FAIL log before re-running, and do not capture vvp output with a bare > redirection (see the agent-rules harness rules).

7. Entry points

The control plane holds 25 actions in total (spec.draft, simulation.profile.select, candidate.deliver, verification.simulate, build.native, hardware.program, hardware.validate, candidate.promote, contract.qualify, and more), all owned by the server-side control plane. The CLI and MCP are two entry points into the same control plane.

The CLI uses the evoverse verification subcommands (six subcommands: project-status / project-next / project-execute / state / facts / reconcile):

evoverse verification project-status --project <project> --json
evoverse verification project-next --project <project> --json
evoverse verification project-execute --project <project> --input <request.json> --json
evoverse verification state --project <project> --json
evoverse verification facts --project <project> --json
evoverse verification reconcile --project <project>

The --input (a JSON file) or --input-json (inline JSON) of project-execute carries the exact service payload: an action name plus its arguments. state / facts / reconcile consume the local journal and the baseline tree directly—they are read-only or converge local state, and never trigger service actions.

MCP exposes 11 tools in total: project_status / project_next / project_execute correspond one-to-one with the CLI subcommands, plus evoverse_health and 7 rk3588_* environment and project tools. There are no standalone verification_* MCP tools; verification evidence is carried by the receipts of actions such as verification.simulate.

The IDE's Welcome page and the Workbench Control show the same status and customer decisions; the recommended action returned by project_next is the only executable action at any given moment.

Tooling prerequisite: install system Python 3.11+ yourself; the SDK neither installs it automatically nor borrows Efinity's older Python. Specifications, Design Assurance, simulation orchestration, the CLI, and MCP use the system Python; Efinity Build, DesignAPI, IPM, and Debug are invoked by the Adapter with the vendor interpreter inside the selected installation's setup.bat environment, and the two run domains inherit neither each other's PYTHONHOME, PYTHONPATH, nor PATH.

The Workbench shows availability separately for System Python, Build, DesignAPI, IPM, and Debug. A passing run-domain probe only means the interpreter/API can start: ordinary RTL/Video Sim runs can use Icarus Verilog, but vendor-model simulation with Efinity hard IP still requires a matching Efinity installation and an available Questa/ModelSim license. And a simulation pass still does not imply a native Efinity build, timing closure, or hardware validation pass.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
