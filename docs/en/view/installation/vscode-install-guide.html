VS Code Installation Differences

EvoVerse SDK: Visual Studio Code — From a Bare Machine to Full-Feature Use

Applicable version: v1.0.0　Updated: 2026-09-30 Goal: starting from a computer with no development environment installed, get to RTL editing, rules and constraints, simulation, Efinity builds, timing diagnosis, programming, the MCP Agent, AI chat, and optional RISC-V software debugging.

1. First pin down the scope of “full functionality”

In this guide, full functionality covers:

  • The EvoVerse Workbench, Catalog, project creation, and health checks;
  • Verilog/SystemVerilog editing, RTL coding rules, and Agent workflows;
  • Icarus Verilog functional simulation and VCD waveform viewing;
  • Efinity synthesis, place-and-route (PNR), bitstream generation, resource reports, and timing reports;
  • Timing Diagnosis, Build AI, and the multi-turn Conversation Runtime;
  • Programming Efinix FPGAs over USB/JTAG;
  • VS Code Chat querying the Catalog, creating projects, and checking RTL/SDC through the EvoVerse MCP;
  • Optional Sapphire/RISC-V software compilation, flashing, and GDB debugging.

1.1 Recommended operating systems

To get all of the capabilities above, use one of the following:

  • Windows 10/11, 64-bit: the first choice for customer desktop environments;
  • Ubuntu 20.04 or later;
  • RHEL 8.8 or later.

macOS can run VS Code, EvoVerse, MCP, AI, and Icarus simulation, but it cannot serve as a complete Efinity build/programming workstation as defined in this guide. For Efinity's current official installation requirements and USB driver steps, see the Efinity Software Installation User Guide.

1.2 Recommended hardware configuration

Item Bare minimum to launch Recommended full-feature customer workstation
CPU 64-bit dual-core 8 cores or more
Memory VS Code 1 GB; ~8 GB for the Efinity design flow 16 GB; 32 GB recommended for larger designs
Disk 10 GB of free space 30 GB or more of free SSD space
USB 1 free USB port 2 or more; avoid unpowered hubs
Network Optional for offline installation Required for the first download of VS Code, Efinity, extensions, models, and toolchains

For VS Code's own official minimum requirements, see VS Code Requirements. For Efinity memory and system requirements, defer to the official documentation of the version you install.

2. Hardware preparation

At minimum, prepare:

  1. An EvoVerse/Efinix FPGA core module — for example ws-e1 in the Catalog;
  2. A carrier board matching the core module, or a customer-built board;
  3. A power supply that matches the board specification; never guess voltage and polarity from connector shape alone;
  4. A USB cable that carries data; charge-only cables cannot be used for JTAG/serial;
  5. An on-board FTDI debug interface, or a compatible FT2232H/FT4232H JTAG module;
  6. For serial logs, an on-board USB-UART or a standalone 3.3 V USB-UART adapter;
  7. For sensors, MIPI, display, or networking, the corresponding Jackets, cables, and peripherals.

Before connecting anything, read the board specification in the Catalog (available after installation):

${EVOVERSE_HOME}/catalog/boards/<board-id>/<board-id>.md
${EVOVERSE_HOME}/catalog/boards/<board-id>/docs/
${EVOVERSE_HOME}/catalog/boards/<board-id>/carriers/

Never connect a custom board while I/O voltage, JTAG levels, or power direction are unknown. Efinix officially notes that development boards typically use an FT232H, FT2232H, or FT4232H; for a custom board, the board schematic remains authoritative.

3. Install the base software

3.1 Install Visual Studio Code

  1. Download the Stable 64-bit build from the official VS Code download page.
  2. On Windows, the User Installer is recommended; during installation, check “Add to PATH” and the Explorer “Open with Code” option.
  3. Launch VS Code and run:
code --version

If the terminal cannot find code, reopen the terminal or reinstall with the PATH option enabled.

3.2 Install Python 3.11+

The EvoVerse CLI and MCP Server use only the Python standard library; no pip install of other packages is required.

Windows:

  1. Install 64-bit Python 3.11 or newer from python.org;
  2. Check Add Python to PATH;
  3. Verify:
py -3 --version
python --version

Linux:

python3 --version

The output must show 3.10 or newer. Customers installing from the VSIX do not need Node.js or npm; those are only used to build the extension from source.

3.3 Install Efinity

  1. Get the Efinity installer that matches your target device and license from the Efinix Support Center;
  2. Follow that version's installation guide to complete the installation and license configuration;
  3. On Windows, install the Microsoft Visual C++ 2022 x64 Runtime; some IP Managers (for example Sapphire SoC) additionally require 64-bit Java 8 or 11;
  4. On Linux, install the GUI libraries and Java per the official requirements and make sure Java is on the PATH;
  5. Note the Efinity root directory, for example:
Windows: C:\Efinity\2026.1
Linux:   /opt/efinity/2026.1

Verify that the root directory contains:

bin/setup.bat             # Windows
bin/setup.sh              # Linux
bin/efx_run.bat or efx_run.py
bin/efinity.exe or bin/efinity

Every time EvoVerse runs a tool it sets up the child-process environment using Efinity's setup script, so permanent changes to the system PATH are normally not required.

3.4 Install the FPGA USB/JTAG drivers

Windows: use Zadig or the designated driver per the target board's user manual and the Efinity installation guide. Do not blindly replace every interface of a composite FTDI device; first confirm which interface the board documentation requires.

Linux: disconnect the board, then run:

sudo <EFINITY_HOME>/bin/install_usb_driver.sh
sudo udevadm control --reload-rules
sudo udevadm trigger

Reconnect the board. For Efinity's official USB driver instructions, see the “Installing USB Drivers” section of its installation guide.

3.5 Install Icarus Verilog

Full simulation functionality requires iverilog and vvp.

Prebuilt binaries are available for Windows; on Linux, for example:

sudo apt update
sudo apt install iverilog

Verify:

iverilog -V
vvp -V

3.6 Optional: the RISC-V software toolchain

Only needed when you use the Sapphire/RISC-V SoC:

  • xPack GNU RISC-V Embedded GCC;
  • GDB;
  • The board support package (BSP) generated by Efinity;
  • The VS Code Cortex-Debug extension;
  • The board's debugger/OpenOCD configuration.

You can run EvoVerse: Download & Install RISC-V Toolchain, or install manually and then set evoverse.riscvToolchainPath.

4. Install the VS Code extensions

4.1 Required

  1. EvoVerse SDK: install the delivered evoverse-sdk-0.9.0.vsix.

A Chat Agent is not a hard dependency of the EvoVerse VSIX. The VS Code native Chat Agent is recommended; if you only use the openai-compatible Provider of the EvoVerse built-in Runtime, you do not need GitHub Copilot.

Use only the VS Code native Chat Agent to write files and run terminal commands, so that multiple agents never auto-modify the same workspace concurrently.

To install the VSIX:

code --install-extension D:\packages\evoverse-sdk-0.9.0.vsix

You can also use Extensions → ... → Install from VSIX....

4.2 Install per feature

Extension Purpose Declared as an EvoVerse dependency
GitHub Copilot VS Code native Chat Agent, VS Code MCP, and vscode-lm No; install and sign in when using the native Chat Agent
VaporView Opens VCD waveforms produced by simulation Yes
Cortex-Debug RISC-V/MCU GDB debugging Yes
Verilog/SystemVerilog language plugin Syntax highlighting, navigation, and lint No; choose per your license and team standards

For agent conversations, MCP tool calls, and project rules, use the VS Code native Chat Agent. Without GitHub Copilot installed, the built-in EvoVerse Timing Diagnosis/Build AI still works through the OpenAI-compatible Provider described in section 10.3.

Offline environments require an administrator to prepare the dependency-extension VSIX files in advance. If the Marketplace is unreachable, the main EvoVerse VSIX cannot necessarily download dependency extensions on the customer's behalf.

5. Initialize EvoVerse

  1. Reload VS Code;
  2. Run EvoVerse: Set Up (re-run bootstrap);
  3. Choose Yes, set up;
  4. Confirm that Output → EvoVerse SDK shows:
EVOVERSE_HOME ready
Vendored CLI + MCP server
Seeded catalog
CLI works

After initialization, the main directories are:

~/evoverse-sdk/                 Catalog, projects, CLI, MCP Server, and shared rule assets
~/evoverse-sdk/cli/             EvoVerse CLI
~/evoverse-sdk/mcp-server/      MCP Server

Standard VS Code never creates or writes ~/.trae.

6. Configure VS Code settings

Open Settings, search for evoverse, or fill in your user settings.json:

{
  "evoverse.home": "D:\\EvoVerse",
  "evoverse.pythonPath": "C:\\Users\\<user>\\AppData\\Local\\Programs\\Python\\Python312\\python.exe",
  "evoverse.efinityPath": "C:\\Efinity\\2026.1",
  "evoverse.simulator": "iverilog",
  "evoverse.iverilogPath": "C:\\iverilog\\bin",
  "evoverse.buildMode": "cli",
  "evoverse.build.parallelJobs": 4,
  "evoverse.build.autoOpenReport": true,
  "evoverse.program.defaultMode": "jtag"
}

Linux example:

{
  "evoverse.home": "/home/<user>/evoverse-sdk",
  "evoverse.pythonPath": "/usr/bin/python3",
  "evoverse.efinityPath": "/opt/efinity/2026.1",
  "evoverse.simulator": "iverilog",
  "evoverse.iverilogPath": "/usr/bin",
  "evoverse.buildMode": "cli"
}

Replace the paths with the real ones on the customer machine. evoverse.iverilogPath must point directly at the directory that contains iverilog and vvp.

To use QuestaSim:

{
  "evoverse.simulator": "questa",
  "evoverse.questaPath": "C:\\questasim64_2024.1\\win64"
}

evoverse.questaPath must directly contain vlib, vlog, and vsim. This setting only affects the ordinary EvoVerse: Simulate; Video Sim keeps using its own built-in Icarus automation.

7. Environment variables

7.1 Recommended principles

Prefer evoverse.* settings; set system environment variables only when the CLI, MCP, or an enterprise deployment needs paths shared across processes.

Variable Required? Purpose
EVOVERSE_HOME Recommended for MCP Root of the Catalog and projects
EVOVERSE_CLI Recommended for MCP Absolute path of the EvoVerse CLI
PYTHONUTF8=1 Recommended for Windows MCP Keeps JSON/logs UTF-8 for both Chinese and English
EFINITY_HOME Usually no need to set permanently Efinity root; the extension builds the child-process environment from the setting
PATH As needed Lets terminals find Python, Icarus, Java, and the RISC-V GCC directly

Example for the current user in Windows PowerShell:

[Environment]::SetEnvironmentVariable('EVOVERSE_HOME', "$HOME\evoverse-sdk", 'User')
[Environment]::SetEnvironmentVariable('PYTHONUTF8', '1', 'User')

Linux shell example:

export EVOVERSE_HOME="$HOME/evoverse-sdk"
export PYTHONUTF8=1

If you write these into a shell profile, reopen VS Code after the change so the MCP child process inherits the new environment.

8. Configure the EvoVerse MCP in VS Code

8.0 Automatic registration (recommended)

Since v0.9.0, running EvoVerse: Set Up automatically merges servers.evoverse into the VS Code user-level mcp.json (on Windows, %APPDATA%\Code\User\mcp.json; it automatically backs up mcp.json.evoverse.bak before writing, and existing entries for other servers are left untouched). Reload VS Code and confirm with MCP: List Servers — no manual JSON editing required.

If automatic registration does not take effect (for example, an enterprise policy locks the configuration directory), merge manually per 8.1/8.2.

8.1 Windows user-level configuration (manual fallback)

First confirm Python and the file paths (note: the CLI and MCP Server are actually installed under ~/evoverse-sdk/):

py -3 --version
Test-Path "$HOME\evoverse-sdk\mcp-server\server.py"
Test-Path "$HOME\evoverse-sdk\cli\evoverse"

Merge the following into the mcp.json opened by MCP: Open User Configuration:

{
  "servers": {
    "evoverse": {
      "command": "py",
      "args": [
        "-3",
        "C:\\Users\\<user>\\evoverse-sdk\\mcp-server\\server.py"
      ],
      "env": {
        "EVOVERSE_HOME": "C:\\Users\\<user>\\evoverse-sdk",
        "EVOVERSE_CLI": "C:\\Users\\<user>\\evoverse-sdk\\cli\\evoverse",
        "PYTHONUTF8": "1"
      }
    }
  }
}

If the machine has no py launcher, set command to the absolute path of python.exe and remove -3 from args.

8.2 Linux user-level configuration

{
  "servers": {
    "evoverse": {
      "command": "/usr/bin/python3",
      "args": [
        "/home/<user>/evoverse-sdk/mcp-server/server.py"
      ],
      "env": {
        "EVOVERSE_HOME": "/home/<user>/evoverse-sdk",
        "EVOVERSE_CLI": "/home/<user>/evoverse-sdk/cli/evoverse",
        "PYTHONUTF8": "1"
      }
    }
  }
}

8.3 User-level or workspace-level

  • User-level: the server is available in every workspace — a good fit for a dedicated development workstation;
  • Workspace-level: saved as <project>/.vscode/mcp.json — good for team sharing, but never commit customer usernames or absolute paths;
  • Remote/SSH/WSL: the MCP runs in the environment where the configuration lives; you must use remote paths and the remote Python.

On first launch, check the configuration and accept the VS Code MCP Trust dialog. Then run MCP: List Servers:

  1. The evoverse server shows as Running;
  2. The tools list shows list_boards, validate_manifest, check_rtl_code_style, and so on;
  3. In Chat Agent mode, ask: “Use the EvoVerse tools to list the available boards”;
  4. If MCP reports errors, inspect the logs via MCP: List Servers → evoverse → Show Output.

Never write a model API key into mcp.json.

8.4 Recommended setup: use the EvoVerse MCP in the VS Code native Chat Agent

After completing 8.1 or 8.2, run MCP: List Servers in VS Code and confirm that evoverse is running with its tool list visible. Then open native Chat, switch to Agent mode, and allow it to use the EvoVerse MCP tools.

With that configured, run the following acceptance question in the VS Code native Chat Agent:

Use EvoVerse's list_boards tool to list the available boards, and state that the result comes from the tool rather than model memory.

If the native Chat Agent can see list_boards, validate_manifest, and check_rtl_code_style, you can ask questions about your project and invoke EvoVerse tools. The customer should still approve the first tool call or terminal command; do not enable unrestricted auto-approval.

9. Install project rules, RTL coding rules, and workflows

This step is mandatory for a full-featured VS Code installation, not an optional nicety.

9.1 Create an EvoVerse project

Describe the new or take-over target in natural language in Chat; the Agent shows the current action via the project_next envelope of Workbench Control and executes after you confirm. When the project is created, VS Code instructions are generated from the following authoritative rule assets:

~/evoverse-sdk/agent-rules/rules.md
~/evoverse-sdk/agent-rules/rules-rtl-style.md

This generates .github/copilot-instructions.md and .github/instructions/rtl.instructions.md. The former carries the general engineering workflow; the latter carries the full RTL, CDC, reset, Efinity-format, and verification rules. On both Trae and VS Code, the generated content comes from the SDK's host-independent authoritative agent-rules/ sources — it does not depend on .trae or the deprecated CLAUDE.md. VS Code officially supports .github/copilot-instructions.md, a root AGENTS.md, and .github/instructions/*.instructions.md; see Use custom instructions in VS Code.

9.2 Existing projects

Build the VS Code instructions from the shared rule assets produced by initialization:

Windows:

New-Item -ItemType Directory -Force ".github\instructions" | Out-Null
Copy-Item "$HOME\evoverse-sdk\agent-rules\rules.md" ".github\copilot-instructions.md"
$header = "---`nname: EvoVerse RTL rules`ndescription: Mandatory RTL, CDC, reset and verification rules`napplyTo: `"**/*.{v,sv,vh,sdc}`"`n---`n`n"
$header + (Get-Content "$HOME\evoverse-sdk\agent-rules\rules-rtl-style.md" -Raw) | Set-Content ".github\instructions\rtl.instructions.md" -Encoding utf8

Linux:

mkdir -p .github/instructions
cp "$HOME/evoverse-sdk/agent-rules/rules.md" .github/copilot-instructions.md
printf '%s\n' '---' 'name: EvoVerse RTL rules' 'description: Mandatory RTL, CDC, reset and verification rules' 'applyTo: "**/*.{v,sv,vh,sdc}"' '---' '' > .github/instructions/rtl.instructions.md
cat "$HOME/evoverse-sdk/agent-rules/rules-rtl-style.md" >> .github/instructions/rtl.instructions.md

The generated .github/copilot-instructions.md comes from the authoritative general rules; do not create or maintain a CLAUDE.md as well. Its key approval boundaries include:

# EvoVerse project instructions

- Before changing RTL, inspect `evoverse-project.md`, constraints and relevant board/IP manifests.
- Follow the naming, reset, CDC, handshake, synthesis and timing rules in the RTL instruction file.
- Run RTL style checks and simulation before build.
- Do not claim timing closure without a successful Efinity build and timing report.
- Do not program hardware or apply an optimization candidate without explicit user approval.

Teams may also let other agents read the root AGENTS.md, but do not duplicate and maintain full rule sets that contradict each other; the authoritative sources are always agent-rules/rules.md and agent-rules/rules-rtl-style.md in the SDK repository, and project files are generated by the CLI in the matching host format.

9.3 Verify the native Chat Agent's project rules

The VS Code native Chat Agent uses .github/copilot-instructions.md and .github/instructions/*.instructions.md from the project. EvoVerse generates these files automatically for new projects; for existing projects, create them per section 9.2:

.github/copilot-instructions.md
.github/instructions/rtl.instructions.md

The authoritative sources of the two files, after initialization, are respectively:

~/evoverse-sdk/agent-rules/rules.md
~/evoverse-sdk/agent-rules/rules-rtl-style.md

Do not copy rules from the deprecated CLAUDE.md. Open Customizations/Diagnostics in VS Code Chat and confirm that both the general rules and the dedicated RTL rules are loaded.

9.4 Recommended dedicated RTL instructions

Create .github/instructions/rtl.instructions.md:

---
name: EvoVerse RTL rules
description: Mandatory RTL, CDC, reset and verification rules
applyTo: "**/*.{v,sv,vh,sdc}"
---

Before proposing or editing RTL:
1. identify clock/reset domains and interface latency;
2. preserve explicit port connections and the project's naming rules;
3. treat CDC and constraints as deterministic verification items;
4. run `EvoVerse: Check This File's RTL Code Style` and the relevant simulation;
5. never treat model output as proof of functional or timing correctness.

Confirm in VS Code Settings:

{
  "chat.useAgentsMdFile": true,
  "chat.instructionsFilesLocations": {
    ".github/instructions": true
  }
}

Open Customizations/Diagnostics in Chat and confirm that copilot-instructions.md and the RTL instruction are loaded. Custom instructions influence Chat/Agent behavior but are not guaranteed to influence verbatim inline completion in the editor, so the EvoVerse deterministic checks must still be run in the end.

10. Configure the model

10.1 How the two Q&A entry points relate

Both the VS Code native Chat Agent and the EvoVerse built-in Conversation Runtime can answer project questions, but they are currently two independent sessions:

Entry point Model configuration Source of EvoVerse tools Shared session history?
VS Code native Chat Agent VS Code Chat model picker EvoVerse MCP configured in VS Code No
EvoVerse Timing Diagnosis / Build AI evoverse.model.* Extension-internal context and toolchain No

The VS Code native Chat Agent cannot act directly as evoverse.model.provider. If you want both entry points to use the same host model, select the target model in native Chat and configure the EvoVerse built-in Runtime as vscode-lm; the built-in Runtime can also use openai-compatible on its own. Credentials belong in each side's secure storage and must not be shared through project files.

10.2 VS Code host models

This fits customers who already use GitHub Copilot / the VS Code Language Model API and whose required model already appears in the VS Code model picker. Configuration steps:

  1. Install and sign in to GitHub Copilot;
  2. Confirm in VS Code Chat that the target model is available and complete the authorization the model provider requires;
  3. Set evoverse.model.provider to vscode-lm in user Settings;
  4. Run EvoVerse: Select AI Model and pick from the models the host actually returns; the command saves the exact Model ID;
  5. Reload the VS Code window, or wait for the configuration to refresh automatically.

You can also set it manually:

{
  "evoverse.model.provider": "vscode-lm",
  "evoverse.model.modelId": "<exact model id exposed by VS Code>"
}

EvoVerse never silently picks the first model in the list. If you do not know the exact ID, first check the available models in the host model picker, or use the OpenAI-compatible Provider.

The model list here is determined by your VS Code/Copilot account, license, region, and current service. Only models actually exposed by the VS Code Language Model API appear in the vscode-lm list.

10.3 OpenAI-compatible Provider

This fits customers who bring their own OpenAI, DeepSeek, Zhipu, MiniMax, or corporate model-gateway API key. The current implementation calls the standard POST <baseUrl>/chat/completions and requires the service to support the OpenAI Chat Completions format; tool calling and structured output further depend on how compatible the specific model is.

Configuration steps:

  1. Obtain the API key, Base URL, and exact Model ID from your model provider;
  2. Fill the following three values into user Settings;
  3. Run EvoVerse: Set OpenAI-compatible API Key to store the key in VS Code SecretStorage;
  4. Run Developer: Reload Window;
  5. On the first question, review the outgoing-size prompt and choose Send.
{
  "evoverse.model.provider": "openai-compatible",
  "evoverse.model.modelId": "<endpoint-model-id>",
  "evoverse.model.baseUrl": "https://<provider-host>/v1/",
  "evoverse.model.allowLocalHttp": false
}

Run EvoVerse: Set OpenAI-compatible API Key and enter the key. The key is stored in VS Code SecretStorage — do not put it into settings, MCP, prompts, or the project repository. Before any remote request, EvoVerse shows the message count and character size and asks for confirmation.

A local development endpoint can use HTTP only when the address is a localhost/loopback address and evoverse.model.allowLocalHttp is explicitly enabled.

Examples of common services (model names must follow the list actually enabled for the customer account):

Service evoverse.model.baseUrl Example evoverse.model.modelId Notes
OpenAI API https://api.openai.com/v1/ OpenAI model IDs actually available to the account Uses an OpenAI API key; not the same as automatically reusing a Codex subscription
DeepSeek https://api.deepseek.com/v1/ deepseek-chat Uses a DeepSeek API key
Zhipu BigModel https://open.bigmodel.cn/api/paas/v4/ GLM model IDs actually available to the account Zhipu offers an OpenAI-compatible API; coding plans may use a dedicated endpoint
MiniMax https://api.minimaxi.com/v1/ MiniMax model IDs actually available to the account MiniMax offers an OpenAI-compatible API
Corporate aggregation gateway The HTTPS /v1/ or compatible root URL provided by the company Model IDs published by the gateway Can forward models such as Claude, but Chat Completions compatibility must be confirmed

The built-in Runtime currently has no native Anthropic Messages API Provider. There are two workable routes to Claude: select a Claude model actually exposed by VS Code under vscode-lm, or use a gateway with OpenAI-compatible Chat Completions offered by your company, OpenRouter, or similar. Do not paste an Anthropic-native Base URL directly into this section's configuration.

10.4 Verify Timing Diagnosis and Build AI

After configuring either Provider, verify in this order:

  1. Open an EvoVerse project that has already built successfully and contains a timing report;
  2. Run Toolchain: Diagnose Timing Violations;
  3. On the Timing Diagnose page, click Ask AI; confirm that the send-confirmation dialog appears and that the analysis streams back once you approve;
  4. Ask one follow-up question in the input box and confirm that the Conversation Runtime keeps the multi-turn context of this entry point;
  5. Open the Build Report, click Ask AI Agent, and confirm you receive an answer with a build summary;
  6. Check whether the answer cites WNS/TNS, clock domains, or critical paths from the current report. Model suggestions are for analysis only and cannot replace actual simulation, CDC checks, and the Efinity timing report.

If it fails, check Output → EvoVerse SDK first, then verify: the Provider name, the Model ID, whether the Base URL already contains chat/completions, API key permissions, account balance, and any corporate proxy. Put only the API root path in baseUrl; EvoVerse appends chat/completions itself.

11. First project and step-by-step acceptance

Do not jump straight to programming the board. Work in order and continue only after each step passes.

11.1 Basics and the Catalog

  1. Open the EvoVerse Activity Bar;
  2. Confirm that ws-e1 appears in the Board Catalog;
  3. Run EvoVerse: Show Knowledge Base;
  4. Describe a minimal project goal in Chat, confirm the project_next envelope, and create the project;
  5. Confirm the project contains evoverse-project.md, .github/copilot-instructions.md, and .github/instructions/rtl.instructions.md.

11.2 Rules and MCP

  1. Open an RTL file;
  2. Run Toolchain: Check This File's Code Style;
  3. In VS Code Chat's Customizations/Diagnostics, confirm the rule files are loaded;
  4. Run MCP: List Servers and confirm evoverse is Running;
  5. Have the Agent call list_boards; the result must come from the actual Catalog, not from model memory.

11.3 Simulation

  1. The project contains a testbench;
  2. Run EvoVerse: Simulate;
  3. iverilog and vvp report success in Output;
  4. When a VCD is produced, open it with VaporView and check the clock, reset, and output behavior.

11.4 Efinity build and timing

  1. Run Toolchain: Project Health Check;
  2. Fix any missing SDC, device, or source-file issues;
  3. Run Toolchain: Build (Full Flow);
  4. In the Build Report, confirm that Resources, I/O/Clock, Timing, and Critical Paths are readable;
  5. Run Toolchain: Diagnose Timing Violations;
  6. Treat AI suggestions as hypotheses only; WNS/TNS, CDC, simulation, and build results are the verification evidence.

11.5 Programming

  1. While the board is powered off, confirm jumpers, voltages, JTAG, and boot mode;
  2. Connect power and the USB data cable;
  3. In the Efinity Programmer, first confirm the target device enumerates;
  4. Return to VS Code and run Toolchain: Program FPGA;
  5. If you see “no FTDI device”, check the data cable, drivers, permissions, hubs, and board power.

11.6 Optional RISC-V

  1. Configure the Sapphire SoC IP and sync it from Efinity;
  2. Run Software: Sync BSP from SoC IP;
  3. Run Software: Build App;
  4. Run Software: Program FPGA;
  5. After confirming the Cortex-Debug, GDB, and debugger paths, run Software: Debug App.

12. Troubleshooting

Symptom Check
Set Up cannot find Python Set evoverse.pythonPath to the interpreter's absolute path, reload the window, and rerun Set Up
MCP exits immediately on start Check command, server.py, EVOVERSE_HOME, and JSON escaping; open the MCP Output
MCP has a server but no tools Restart the server, confirm the running server.py is the one extracted from the VSIX, and check Python stderr
Chat ignores the RTL rules Check .github/copilot-instructions.md, the RTL instruction, Customizations/Diagnostics, and the applyTo glob
Build cannot find Efinity Check that evoverse.efinityPath points at the installation root rather than bin, and that the setup script exists
IP Manager fails to start Check the 64-bit Java version, PATH, and the Efinity version requirements
Simulation cannot find executables Check evoverse.simulator and point the matching path directly at the directory containing iverilog/vvp or vlib/vlog/vsim
