03 Generate IP and Controlled RTL

Stage 03 · Generate RTL and Deliver Candidates (Three Rounds of Increments)

The specification and the level-decision mechanics are ready. This stage builds the full SD card -> DDR frame buffer -> MIPI CSI-2 TX chain through three rounds of increments. Every round follows the same loop: intent.create declares the increment → simulation.profile.select decides the level → spec.draft drafts the delta specification → the candidate is generated → candidate.deliver freezes it → verification.simulate takes evidence independently → candidate.promote promotes it. The new baseline produced by each promotion becomes the parent baseline of the next round.

Candidate semantics (the core of reliable design): the Agent never writes into the official RTL directory directly. candidate.deliver only freezes the candidate and runs Design Assurance — the baseline stays untouched; only after the simulation PASSes and promotion eligibility is satisfied does candidate.promote merge the candidate with the parent baseline and install the result as the new baseline. Everything generated ultimately serves the display chain on the TJ180A484S.

Two rules that run through all three rounds:

  1. Parent baseline snapshot: intent.create snapshots this round's parent-baseline assets into IntentRecord.baseBaselineFiles (round one = the Stage0 initial baseline; rounds two and three = the previous round's promoted baseline). The delta-specification comparison, candidate validation, and the promotion merge all anchor on this snapshot.
  2. expectedRevision is a concurrency hint: the control plane always appends facts at the latest revision; a revision conflict at submission only yields a reconciliation action, never an overwrite. It is a collaboration hint, not a security boundary — the real boundaries are the receipts and the eligibility checks.

The loop, drawn out. Every round walks through it; a FAIL does not discard the candidate — fix it, re-freeze, and re-simulate:

What Trae does for you

  1. project_status confirms the Stage0 baseline is ready; project_next confirms intent.create is available and shows its inputSchema.
  2. Submits intent.create: the control plane snapshots this round's parent baseline (the Stage0 initial baseline for round one) into IntentRecord.baseBaselineFiles; the receipt shows this list — it is the anchor for the later "reuse / added / modified" bookkeeping.
  3. simulation.profile.select decides in two phases: the server recommends a level from the riskFacts, you confirm the choice; below the recommendation, each acceptedRisk is recorded individually. The level binds to this iteration — not inherited, not spilled over.
  4. spec.draft drafts and freezes the delta specification: it describes only this round's increment and its top-level connections to the parent baseline, with reused items annotated against the baseBaselineFiles snapshot.
  5. Invokes /evoverse-rtl to generate the candidate RTL and testbenches into candidate-area paths per the specification, following the RTL coding rules (async-reset sync-release, CDC synchronizers, no divided clocks, default values in combinational blocks).
  6. With the candidate ready, submits candidate.deliver (files or a staging directory via filesRoot, origin=generated): the control plane freezes the candidate, runs Design Assurance, and records the candidate summary — the baseline stays untouched; verification.simulate takes evidence on the frozen candidate independently at the selected level, and incomplete is never treated as PASS.
  7. After the simulation PASSes and eligibility is satisfied, submits candidate.promote: the control plane merges the candidate with the parent baseline and installs the new baseline; the promotion receipt records the new baseline summary — it is the next round's parent baseline.
  8. Re-runs project_status after every action, reporting the new revision and evidence-area changes; repeats steps 2–7 for the DDR buffering and CSI-2 output rounds.

What you need to confirm

  • No generation before the specification is frozen: if /evoverse-rtl finds ambiguity in interfaces, widths, clock domains, or Oracles, it stops at the specification decisions — that is a normal guard; go back to Stage 02 to settle them, do not bypass it.
  • Stop if the parent baseline does not match: every round's intent.create snapshot receipt must match the parent baseline you believe in — round one is the Stage0 initial baseline, rounds two and three are the previous round's promoted baseline. A mismatch means an unreconciled advance happened; stop and sort it out instead of continuing on the wrong baseline.
  • acceptedRisks is an explicit decision: whenever simulation.profile.select goes below the recommended level, each risk must be confirmed by you individually; downgrading is not saving money — it writes "what was not verified" into the ledger.
  • One changed line means re-delivery and re-simulation: simulation evidence binds to the frozen candidate's digest; after candidate.deliver the candidate is immutable, and any change means a new round of delivery and simulation.
  • An expectedRevision conflict is not an incident: it is just a concurrency hint; on conflict the control plane offers a reconciliation action; do not "play it safe" by teaching the Agent to rely on a stale revision.

Pass criteria

  • All 12 receipts of the three rounds are visible in project_status: per round, one each for intent.create, candidate.deliver, verification.simulate, and candidate.promote.
  • The three rounds' baseBaselineFiles snapshots are individually inspectable: Stage0 initial baseline → SD-promoted baseline → DDR-promoted baseline — the parent-baseline chain is complete.
  • The current baseline contains the full SD card -> DDR frame buffer -> MIPI CSI-2 TX chain of modules, with every round's candidate bound to a specification fingerprint and independent simulation evidence.
  • No candidate whose simulation did not PASS appears in the current baseline; incomplete was never treated as PASS.
  • The generated RTL and testbenches pass eligibility review: a broken testbench, an ambiguous Oracle, or insufficient coverage never yields a PASS.
  • With the three promotions done, the project is only the integration stage (Stage 05) away from the native efx_run --flow compile build.

When done, continue to Stage 04: Sapphire firmware.
