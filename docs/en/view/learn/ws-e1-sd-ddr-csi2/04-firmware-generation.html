04 Sapphire Firmware

Stage 04 · Sapphire Firmware

EvoVerse SDK v1.0.1 · 2026-11-28

The RISC-V core inside the SoC needs firmware before it can run. This stage generates the software project and the BSP in the Sapphire bare-metal environment, feeds the software candidate into the same control plane, and spells out the handover boundary of the hardware/software contract.

The SD card -> DDR frame buffer -> MIPI CSI-2 TX chain runs on the TJ180A484S, and the firmware schedules SD card initialization, FAT reads, and frame-buffer filling. It compiles for the Sapphire SoC, but its evidence enters the control plane just like RTL evidence: a successful compile is only SW_BUILT, not functional correctness.

The evidence boundary of the firmware looks like this — after SW_BUILT every step switches to a different class of evidence, and none can stand in for another:

flowchart TD
    A["All three module contracts pass<br>specification fingerprint stays valid"] --> B["Create the bare-metal project under soc/<br>startup code / linker script / BSP"]
    B --> C["Build the software<br>keep the full log"]
    C --> D{"Artifacts verifiable?"}
    D -->|yes| E["SW_BUILT<br>ELF / BSP digests registered"]
    D -->|no| C
    E --> F["Register the software candidate<br>bind hardware-software-contract"]
    F --> G["On-board functional verification waits for Stage 06<br>until then the state is INTEGRATION_PENDING_HARDWARE"]

What you say to Trae

The hardware side is done, so let's do the firmware: create the Sapphire bare-metal project under soc/,
implement the main loop for SD card initialization and frame-buffer filling, and generate the matching BSP.
Once it compiles, register the software candidate in the project too, and write down its interface contract with the hardware.
Every requirement that can be tested on the host needs a concrete test method.

What Trae does for you

  1. Confirms that the contract evidence of all three modules is complete and the specification fingerprint is still valid (it depends on the converged hardware baseline), and reads the hardware-software contract.
  2. Creates the bare-metal software project under soc/: startup code, linker script, BSP headers, and the register map (taken from the register section of the frozen specification, never from an intermediate draft).
  3. Regenerates the BSP after hardware configuration changes (clocks, address map) so that the BSP and the bitstream stay derived from the same source.
  4. Builds the software and keeps the full log; marks as SW_BUILT only the ELF/BSP artifacts that were actually produced and can be verified.
  5. Registers the software candidate, tags it with the software partition, and the control plane records its contract binding to the hardware candidate.
  6. States the boundary of its reporting plainly: on-board functional verification waits for the hardware evidence of Stage 06; until then it will not write any "should work" as PASS.

What you need to confirm

  • The hardware bitstream, the BSP, and the software must all come from the same project configuration; do not mix in a BSP from another revision.
  • Every mandatory software requirement has an executable test method: a host-level unit test or a board-level scenario, one of the two — "a human had a look" is not acceptable.
  • Ownership handover is clean: the hardware side provides the register map and interrupt contract (OWN_P1) and the software side consumes it; a change on either side goes back through candidate delivery.
  • Without hardware, this stage stops at SW_BUILT, and the on-board verification stays at INTEGRATION_PENDING_HARDWARE in the control-plane state.

If Things Don't Go Smoothly

Symptom How to handle it
The firmware build reports errors First have Trae distinguish a BSP/hardware-configuration mismatch from an application-code problem — the two need different fixes, so do not guess them together.
It compiles, but you are unsure the behavior is right A successful compile is only SW_BUILT, not functional correctness; on-board verification waits for Stage 06 — do not wave it through verbally.
No Sapphire toolchain on this machine Have Trae report the gap honestly; do not let it download a toolchain of unknown provenance on its own.

Pass criteria

  • The software candidate receipt is visible in the control-plane state, and the ELF and BSP digests are registered.
  • Both sides of the hardware/software contract (register map, address map, interrupts) reference the same revision.
  • The build log is kept in full, and the two classes of state — SW_BUILT and functional verification — are not conflated.
  • Together with the RTL candidates, the firmware completes the input set for the later efx_run --flow compile and the on-board verification.

When done, continue to Stage 05: SDK integration.
