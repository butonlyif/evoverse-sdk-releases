05 SDK Integration

Stage 05 · SDK Integration

With the baselines from the three promoted increments and the firmware in place, this stage aligns them with the Efinity project files (XML / ISF / SDC): inspect the project contract, synchronize design sources, and verify design consistency. Every change goes through "preview → confirm → apply".

The project contract defines the correspondence between the project structure the control plane sees and the project files the Efinity toolchain sees. In this step, the pins, clocks, and bank voltages of SD card -> DDR frame buffer -> MIPI CSI-2 TX land on the physical constraints of the TJ180A484S.

The three classes of verification are separated here: a PASS from verification.simulate proves only that the candidate behaves correctly in the simulation scenarios of the selected level; it proves neither that the native build converges nor that the board actually runs — the latter two are evidenced by stage 06's build.native and hardware.validate respectively.

Every check in this stage revolves around the project contract, with one goal: make the three views point at the same set of files:

    C["Efinity project XML<br>design source list"] --- B

What you say to Trae

Run an integration check on this project: first show me the project contract and
confirm that the top-level module, the design source list, the ISF/SDC constraints,
and the project XML are consistent; then synchronize the design sources into the
Efinity project and run design verification. Organize every inconsistency you find
into a preview list for my confirmation, and apply the changes only after I confirm.
After synchronization completes, read project_status again and show the new revision.

What Trae does for you

  1. project_status reads the current Baseline and asset inventory and presents the project contract: top-level module, design files, constraint files, device TJ180A484S.
  2. Checks the correspondence between design sources and the project XML: whether newly added candidate RTL has entered the source list, and whether removed files are still referenced by the XML.
  3. Synchronizes design sources into the Efinity project (adding <efx:design_file> entries, updating flist references) and shows you a full preview before syncing.
  4. Runs design verification: pin assignments, bank voltages, and clock definitions are compared item by item against the physical section of the specification; the MIPI bank must be 1.2 V, must not share a bank with LVDS, and the PLL must be created in the ISF.
  5. Applies the confirmed changes and reports the revision change with a fresh project_status.
  6. Any verification failure is reported as-is — the integration stage fixes only "project files out of sync with the candidate"; it never silently edits your RTL.

What you need to confirm

  • Every entry in the preview list: the sync tool touches only what is necessary; no "cosmetic touch-ups" to ISF/SDC.
  • Pin strategy: changing functionality must not change pins; new functionality picks free pins from the board pinout, with the same bank voltage.
  • The project XML is never hand-edited: structural changes go through the sync capability, avoiding hand-written mistakes such as an empty <efx:inter_file>.
  • Entries in the verification report that conflict with the physical section of the specification: either fix the project files, or go back to stage 02 and revise the specification — the two sides must not talk past each other.

Pass criteria

  • The three views of the project contract agree: control-plane assets, the Efinity project XML, and the ISF/SDC constraints all point to the same set of files.
  • Design verification has zero conflicts, or every remaining conflict has an explicitly recorded decision.
  • SDC provides a create_clock for every clock port, and asynchronous domains declare set_clock_groups -asynchronous.
  • The project satisfies every input condition of efx_run --flow compile: the source list is complete, constraints are legal, and the device and speed grade are correct.

When done, continue to Stage 06: Build and Hardware Verification.
