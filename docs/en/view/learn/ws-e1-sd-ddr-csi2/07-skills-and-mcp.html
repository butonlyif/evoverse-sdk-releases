07 Skills and MCP

Stage 07 · Skills and MCP Tools Quick Reference

Having walked through all seven stages, step back and survey every interface this path used: 11 public MCP tools, 25 control-plane actions, and 6 built-in Skills. Every step you took toward SD card -> DDR frame buffer -> MIPI CSI-2 TX on the TJ180A484S corresponds to a row in one of these tables and one piece of evidence.

What you say to Trae

Based on the design-package, intent and candidate receipts, simulation evidence,
build reports, and (if any) hardware validation receipts left by this project,
do a pre-delivery review. Walk through the seven stages — initialization, materials,
specification, candidates and simulation, firmware, integration, build and hardware —
and for each stage explain which control-plane action or Skill was used, what
evidence was left behind, and which boundaries remain unverified.
Explain in language a customer can understand; do not just list tool names.

What Trae does for you

  1. Uses project_status to summarize every fact under the current revision: Baseline, intents, candidates, evidence area.
  2. Maps each stage's action receipts to their evidence files one by one and flags the incomplete or not-executed items.
  3. Explains, using the quick-reference tables below, the relationship between "the stages you saw" and "the underlying interfaces", without regenerating any code.
  4. Offers next-step options: keep optimizing, open a new intent, or head into the stage 08 directory cleanup with the evidence chain in hand.

What you need to confirm

  • Every stage's conclusion is backed by a receipt or a file; "never done" and "never verified" are not written up as "passed".
  • You can state what question each of the 11 public MCP tools answers: the 3 control-plane tools handle status, next actions, and execution; evoverse_health handles health; the remaining 7 rk3588_* tools handle the RK3588 environment and project builds.
  • Ordinary agent conversation can explain and organize, but it cannot substitute for the receipts of candidate.deliver and verification.simulate.

Pass criteria

  • Without looking at the docs, you can recite the full path from materials to efx_run --flow compile build evidence.
  • You can point to where each action receipt sits in the project_status output.
  • You can tell which stage the project is currently at and what actions are allowed next — the answer from project_next, not a guess.

Quick reference: public MCP tools (11)

Tool Question it answers
project_status What state is the project in right now? (revision, Baseline, intents, candidates, evidence)
project_next What actions are allowed now? (action list + each action's inputSchema and blockedReasons)
project_execute Execute the chosen action (actionId + expectedRevision + inputs)
evoverse_health Are the SDK and the toolchain healthy and usable
rk3588_environment_status Read-only health check of the RK3588 environment: how far the toolchain and BSP are installed
rk3588_environment_prepare Prepare the RK3588 environment and return an inspectionToken for later checks
rk3588_environment_deploy Deploy the RK3588 toolchain / BSP (authorized via acceptedLicenses)
rk3588_project_generate Controlled generation of an RK3588 project (produces PROFILE_READY)
rk3588_project_preflight Read-only preflight qualification check before building
rk3588_project_build Four-stage build: uboot → kernel → rootfs → package
rk3588_project_status Read the build report at .evoverse/output/build-report.json

Other capabilities (JTAG observation, DesignAPI / IP management, project-contract checks, and so on) are provided by the extensions' provider tool surfaces, invoked through Skills and natural language; they are not part of the model-visible public MCP surface.
