08 Tidy Up and Deliver the Project

Stage 08 · Directory Cleanup and Delivery

Once the display link is verified, do not let scratch drafts, candidate files, and reports litter the project root. This chapter has Trae generate a cleanup preview first, execute only after you confirm each entry, and finally re-run one efx_run --flow compile to prove the project is still deliverable.

The goal of cleanup is to make it easy for the next engineer to find files — not to rewrite a project that already works. The frozen specification package (design-package/), the baselines formed by the three promoted increments (including each round's candidate.promote receipt), the delivered candidates, and all evidence receipts are protected files — they are the evidence chain of this SD card -> DDR frame buffer -> MIPI CSI-2 TX link on the TJ180A484S, and they take no part in the cleanup.

The cleanup runs in the order shown below — preview first, confirmation-driven, closed out by a re-build:

flowchart TD
    A["Generate cleanup preview<br>reports/project-cleanup-preview.md"] --> B["You confirm each entry<br>uncertain items marked as needing a decision"]
    B --> C["Execute only confirmed entries<br>fix reference paths along the way"]
    C --> D{"Project XML and<br>script paths still valid?"}
    D -->|Yes| E["build.native re-build<br>efx_run --flow compile"]
    D -->|No| F["Stop at the problem<br>roll back unconfirmed actions"]
    E --> G["Report: reorganized / protected /<br>references updated / re-build result"]

What you say to Trae

The project is finished — help me tidy up the directory. Generate a cleanup preview first, look-only, no moves:
list which files you suggest moving, which are protected and must not be touched, which references need updating after a move,
and which ones you are unsure about and need my decision. After I confirm, execute only the confirmed entries,
and finally rebuild once to prove the tidied project is still deliverable.

What Trae does for you

  1. Reads the project contract, the material ledger, the candidate.deliver and candidate.promote receipts, and the Efinity project files, and builds a "file ownership and references" inventory.
  2. The preview stage produces only a report (such as reports/project-cleanup-preview.md) and modifies no project file.
  3. Only after you confirm does it reorganize the files allowed to move, correcting the confirmed relative paths along the way.
  4. After reorganizing, it records one native efx_run --flow compile via build.native: a broken path or a build failure stops at the problem — it never copies reference-project files to paper over it.
  5. Every step respects the project contract: the project XML is never hand-edited; reference fixes go through the sync capability.

What you need to confirm

  • Every file suggested for moving was generated or is maintained by this project itself, and the inventory lists where it is referenced.
  • Third-party IP under IP/, Efinity artifacts, the frozen design-package/, the project XML, constraints, and baseline files are all on the protected list.
  • "Delete" applies only to the temp files you explicitly approved; anything that cannot be judged stays as-is and is listed as needing a decision.
  • After cleanup the project XML still references the correct RTL, constraints, IP, and software inputs, and the re-build report comes from the post-cleanup directory state.

If Things Don't Go Smoothly

Symptom How to handle it
The preview contains entries you are unsure about Mark all of them "needs my decision" — moving less beats moving more; the benefit of tidying is tiny next to the cost of touching a protected file by mistake.
The re-build fails Have Trae keep the failure report and roll back the unconfirmed actions, returning the directory to its pre-cleanup state, instead of patching onward.
It suggests touching the project XML or third-party IP Refuse. They are on the protected list; reference fixes go only through the sync capability — no "renaming things so the directory looks tidier".

Red lines for natural-language prompts

This chapter may only touch the RTL / simulation / software / reports / helper scripts generated by this project itself. The following phrasings push the agent past the protected list and break the project contract:

Don't say this Why it's dangerous Say this instead
"Clean up the temp directories" It doesn't distinguish "temp files" from "protected files" — the frozen specification package, IP artifacts, and the project XML can all be treated as "temp" "First mark in the preview which files are this project's temp files; leave everything not listed untouched"
"This file is no longer used, delete it" "No longer used" is a subjective judgment; the agent can easily mistake a baseline file for a temp file "Provide a receipt or path evidence that it is temporary, then delete"
"Archive the candidate-area files into reports/" Candidates and baselines are governed by the control plane: candidate.deliver freezes and candidate.promote promotes, and the receipts already record their digests; manual archiving pollutes reports "Leave candidate-area files as they are after delivery; no archiving needed"
"Rename the project XML so the directory looks tidier" The project XML is a protected file; renaming it leaves the Adapter unable to find the project "Do not rename or delete the project XML; just state the current situation in the confirmation report"

Pass criteria

  • reports/project-cleanup-preview.md records the preview, the scope you confirmed, the actual changes, and the items left unhandled.
  • The directory clearly separates design-package/, rtl/, sim/, constraints/, software/, reports/, and the helper scripts, with third-party IP and Efinity artifacts untouched by mistake.
  • The re-run efx_run --flow compile succeeds, and the report comes from the post-cleanup directory state; on failure, the report is kept and unconfirmed actions are rolled back, rather than claiming the project is still deliverable.
  • The final delivery notes can say where the materials, the frozen specification, the baselines formed by the three promotions, and the build/hardware evidence each live.
