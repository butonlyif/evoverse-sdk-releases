WS-E1 SD to CSI-2 Overview

WS-E1 SD to CSI-2 Project Tutorial (Complex Single FPGA)

EvoVerse SDK v1.0.1 · 2026-11-26

Applicable version: v1.0.1　Target device: TJ180A484S (Titanium Ti60, C4 timing model)　Default host: Trae

This tutorial teaches exactly one intent: build an SD card -> DDR frame buffer -> MIPI CSI-2 TX display chain on TJ180A484S. A complex single FPGA does not mean the customer must decompose it into a dozen steps; the Agent splits one intent into module slices, lets each module converge independently against its own contract, and finally composes them in a single on-chip composition.

One red line first: never copy the target sd-ddr-csi2 project's RTL, constraints, or project files as the baseline of a new project. The target project is used only for material analysis and conclusion comparison; what you need is a project backed by your own specification, your own candidate RTL, and your own evidence chain.

One intent, three decisions

The whole journey asks you to make three decisions; the control plane advances everything else continuously:

  1. Confirm the plan and executable specification — the Agent first proposes the module split (sd_host, frame_buffer_writer, csi2_tx plus clock/reset), each module's ModuleSpec and interface contract, the simulation level, and acceptance scenarios. After one confirmation the specification is frozen; generation will not interrupt you module by module.
  2. Confirm high-cost work or device writes when needed — only programming, deployment, or expensive builds require explicit authorization; read-only checks, generation, simulation, and low-cost builds do not interrupt you.
  3. Review the evidence boundary and accept — at technical completion, review the evidence summary and not-run levels; give the acceptance receipt after confirmation. Technical completion is not acceptance.

Module split and interface contracts

One intent splits into three module slices, each converging independently before they are composed into one chain:

Module Responsibility Interface contract Independent evidence
sd_host SD card initialization, command/data handshake Emits a valid/ready sample stream to frame_buffer_writer; width and cadence are fixed by ModuleSpec Simulation of protocol scenarios, timeout, and retry policy
frame_buffer_writer Writes samples into the DDR frame buffer and manages write-side backpressure Read-side ownership handoff, write address generation, full/empty semantics Simulation of backpressure, boundary addresses, and read-back consistency
csi2_tx Reads from the frame buffer and emits CSI-2 TX timing Line/field sync, lane count, pixel cadence Simulation of output timing and protocol scenarios

Interface contracts come before implementation: each module's ModuleSpec states ports, widths, clock domains, reset semantics, and the acceptance oracle; modules handshake only through contracts instead of "deciding the wiring later at the top". That is what lets modules be generated, simulated, and repaired independently.

On-chip composition: after all three modules pass their contracts and simulations, the Agent connects them together with the read-only DDR wrapper and the CSI-2 TX hard IP at the TJ180A484S top level in one composition pass, then runs the full-chain integration check. Composition is not a fourth step the customer must memorize; it is what the Agent performs in the "Integrate & Realize" stage.

How the background advances

The five background stages only explain the system; they are not an action list you must memorize:

  1. Intent — turn your natural-language goal into a managed intent and snapshot the current baseline.
  2. Plan & Approve — propose the module split, module contracts, simulation level, and acceptance scenarios, then wait for your single confirmation.
  3. Generate & Converge — generate candidates and run Design Assurance and independent simulation for each module in parallel; a failure affects only that module.
  4. Integrate & Realize — on-chip composition, project contract checks, native build, and programming.
  5. Accept — summarize the evidence boundary and wait for your accept or reject receipt.

Terminal states

BUILT (build artifacts exist) → PACKAGED (packaged) → PROGRAMMED (written to the device) → HARDWARE_VERIFIED (observed on the board) → SYSTEM_VERIFIED (complete system-level evidence) → READY_FOR_ACCEPTANCE (technically complete) → ACCEPTED (customer acceptance receipt); levels not actually executed stay NOT_RUN. A simulation PASS is not a passing build, a passing build is not successful programming, and successful programming is not board validation. Without hardware, hardware and system-level evidence stay NOT_RUN.

Failure recovery

A simulation FAIL is evidence, not an incident: a delivered candidate is frozen and immutable, so a fix must regenerate the candidate and rerun simulation; the baseline is not polluted by one failure, and other modules' existing evidence does not become invalid. If the failure exposes a contract ambiguity (for example, "how many times should SD initialization retry after timeout" is undefined), the Agent returns to the specification decision instead of privately adding logic in RTL.

Specification upgrade

A specification upgrade invalidates only the affected evidence. For example, changing the DDR buffer depth from 2 lines to 4 lines:

  • The specification and simulation evidence of frame_buffer_writer become invalid and must be regenerated and resimulated;
  • The contracts of sd_host and csi2_tx are unchanged, so their existing evidence remains valid;
  • The full-chain composition evidence must be rerun once because the top-level wiring and buffering behavior changed.

The correct approach is therefore to rerun only the affected nodes, not to start the whole tutorial over; one specification upgrade does not void an unrelated module's PASS.

Before you start

Walk through environment preparation once, about 10 minutes total:

  1. Install the three VSIXes (same version 1.0.1): evoverse-sdk, evoverse-efinity-adapter, evoverse-rk3588-adapter. In the Extensions view choose "Install from VSIX…" one by one; see the Trae installation guide.
  2. Restart the IDE so all three extensions activate.
  3. First-run setup: after restart, the "Set up EvoVerse SDK?" dialog asks you to confirm the workspace location (default ~/evoverse-sdk).
  4. The Welcome page opens automatically. Click Sync Catalog to synchronize the board catalog and wait for completion—the ws-e1 / ws-e1-base board selection later comes from this catalog.
  5. Open an empty directory as the project root and describe the intent in Chat: Trae: type @evoverse and then the goal; VS Code: describe the same goal directly in native Chat Agent mode without @evoverse, after confirming EvoVerse MCP is Running. Workbench (Project Control dropdown, command evoverse.selectDesignFlow) is a graphical entry, but it does not continue the Agent conversation for you.

Then confirm two more things:

  • Efinity 2026.1+ is available; functional simulation needs Icarus Verilog (or QuestaSim).
  • A WS-E1 core module (TJ180A484S) plus carrier board is preferable; without hardware you can still complete every stage up to the build, and the hardware verification stage will honestly mark itself as not executed.

What you will get

  • One managed project: project identity, frozen specification, candidates, and evidence are all traceable in the control-plane state.
  • An evidence chain from module contracts to hardware: every step either has a PASS receipt or is explicitly marked incomplete / fail—incomplete is never treated as PASS.
  • The final bitstream comes from the native Efinity unified flow efx_run --flow compile; the MIPI CSI-2 output is verified with a real receiver or an on-chip debug core.

What to do when something goes wrong

The prompts in this tutorial deliberately state only intent, without control-plane action names or flow steps—advancing the flow, choosing actions, and checking receipts is the Agent's job. The "What you say to Trae" sections in the following chapters remain the Trae mainline; in VS Code, send the same prompt directly to the native Agent and drop the leading @evoverse. Generation and simulation are stochastic; when things do not go smoothly, follow three principles:

  1. State the goal, not the flow. Describe what you want ("write the SD card data into DDR"), not command steps. If the Agent's approach differs from the mechanism described in the tutorial, ask "how do you plan to advance", listen to its explanation, and then decide.
  2. When it takes long, ask for progress; do not rush or restart. Generation, simulation, and native builds are minute-to-tens-of-minutes tasks; stacking new instructions midway only disrupts the cadence. If it feels slow, ask "where are we and what is left" instead of resending the prompt.
  3. When the result is unexpected, state the expectation first, then the problem. Make clear "what I expected and what I actually saw", and let the Agent return to the matching evidence or specification and rerun the flow.
