FPGA + RK3588 System-Intent Tutorial (WS-E2 Dual-Chip)

FPGA + RK3588 System-Intent Tutorial (WS-E2 Dual-Chip)

EvoVerse SDK v1.0.1 · 2026-11-28

Applicable version: v1.0.1　Target devices: TJ180A484S (Titanium Ti60) + RK3588J　Default host: Trae

This tutorial covers exactly one system intent: run an application on WS-E2 that necessarily requires the FPGA and the RK3588 to work together — the FPGA owns real-time capture and pixel preprocessing, while the RK3588 runs the Linux user-space application plus networking and storage. A system intent is not two single-chip tutorials pasted together: you allocate functions to the two chips first, freeze one interface contract, then implement each side, and finally perform system-level composition.

The journey still has only three user decision points: confirm the plan and the executable specification (including the chip allocation), approve high-cost actions or device writes when needed, and review the evidence boundary before final acceptance.

1. One system intent: functions first, chips second

State the system goal in a single sentence of natural language, and do not start by dictating "which code goes on the FPGA and which on the RK3588":

I want to build a dual-chip video path on WS-E2: the FPGA captures raw camera data and performs demosaicing and scaling, and the RK3588 runs a Linux application that receives the processed frames, overlays a UI, and streams them over the network. Start by proposing a functional breakdown and a chip allocation: for each function, state the responsibility, the data volume, the real-time requirement, and candidate board-to-board interfaces. Act only after I confirm.

What the Agent must return is a function inventory, not a file inventory: capture, preprocessing, frame buffering, display/streaming, and control-plane configuration. The granularity of a function is set by "can it be verified independently", not by the directory structure.

2. Chip allocation and interface contract (the first decision point)

Assign responsibilities to the two chips function by function, with reasons. A typical allocation looks like the table below; your actual targets and Catalog materials take precedence:

Function Chip Responsibility Independent evidence
Camera capture and pixel preprocessing FPGA Real-time pipeline, deterministic latency, hard CSI-2 / DDR interfaces Timing simulation + on-chip composition
Frame buffering and display/streaming RK3588 Linux drivers, user-space application, networking, and storage Kernel/user-space build + boot checks
Control-plane configuration Both sides FPGA register map, RK3588 device tree, and driver binding Interface-contract consistency check
Board-to-board data channel Both sides Select PCIe, MIPI, RGMII, or GPIO under bandwidth, latency, and pin constraints Link self-test and error counters

Responsibilities must be mutually exclusive: one function cannot be "partly done on both sides as a favor", or system-level evidence becomes impossible to attribute.

The interface contract precedes implementation. Freeze at least these fields:

  • direction and topology (who initiates, who responds, point-to-point versus a shared bus);
  • data format (bit width, byte order, alignment, packing);
  • bandwidth and clock domains (peak/average, cross-domain synchronization);
  • latency and buffering (maximum allowed latency, queue depth, full/empty semantics);
  • error handling (timeouts, retries, error counters, and the reporting path);
  • versioning and compatibility (the contract carries a revision, and any change on either side yields a new revision).

The chip allocation and the interface contract together form the plan decision. Once you confirm them at this decision point, the specification is frozen; generation will not interrupt you again with another "choose the implementation approach" round.

3. Parallel implementation on both chips

After the allocation is confirmed, the FPGA side and the RK3588 side can proceed in parallel: each side has its own project, specification, build chain, and evidence, and neither blocks the other.

  • The FPGA side converges along the WS-E1 module-slice path (a complex single-chip route: ModuleSpec, interface contracts, independent simulation, on-chip composition).
  • The RK3588 side converges along the WS-E2 atomic path (one intent, plan/specification confirmation, continuous generation, and the four-stage build).

Build details on each side belong to that side's Adapter: the Adapter reference is authoritative for the exact commands and parameters, and this document deliberately does not restate vendor-native commands, so that no second source of truth is created. You only need to review the evidence summary when each side reaches technical completion.

4. CHIP composition and SYSTEM composition

The two terms are not interchangeable:

  • CHIP composition: within a single chip, merge several sub-modules or sub-intents into one deliverable result — for example, the FPGA side composing capture, preprocessing, and DDR write-back into one complete pipeline.
  • SYSTEM composition: across the two chips, merge the respective CHIP results, the interface contract, and the system-level interconnection into system evidence.

System composition checks whether "the assembled whole still holds": whether the interface-contract revision matches on both sides, whether bandwidth and latency requirements are met, whether control-plane registers line up with the device tree, and whether the error-reporting path is closed. It never repairs either implementation, and it never promotes two independent PASS results into a system PASS on its own.

5. Terminal evidence states

BUILT (artifacts exist) → PACKAGED (packaged) → PROGRAMMED (written to the device) → HARDWARE_VERIFIED (observed on the board) → SYSTEM_VERIFIED (complete system-level evidence) → READY_FOR_ACCEPTANCE (technically complete) → ACCEPTED (customer acceptance receipt); levels not actually executed remain NOT_RUN.

  • BUILD_READY on both sides does not mean the system runs, and certainly does not mean SYSTEM_VERIFIED;
  • READY_FOR_ACCEPTANCE only means technically complete and is not ACCEPTED;
  • at technical completion you may review the evidence summary and issue an acceptance receipt, or reject it and send the problem back to the specification.

6. Partial failure: one side ready, the system still not ready

The most common state in a system journey is partial failure: the FPGA side is already BUILD_READY while the RK3588 side is still building; or one side is PROGRAMMED while the other has not been powered on yet; or both sides run but the board-to-board link error counter keeps climbing.

The correct report in all of these cases is: the system is still not ready. Completed chip evidence is retained, but its boundary is not extrapolated. Never substitute "the FPGA compiled cleanly" for a system-level conclusion, and never record a single-side PASS as SYSTEM_VERIFIED.

System acceptance prompt:

Accept the current dual-chip system intent. Read the CHIP evidence and the system composition record on each side separately, and list each side's terminal evidence state, interface-contract revision, not-run levels, and blocking reasons. If only one side is complete, state explicitly that the system is still not ready and which item is missing; do not report SYSTEM_VERIFIED.

7. Failure recovery and specification upgrades

Failure recovery touches only the failing side:

Diagnose the current system failure. Analyze only the evidence for this system composition and for the failing side, and classify the problem as exactly one of four classes: FPGA implementation, RK3588 implementation, interface-contract ambiguity, or unverified hardware. Give the root cause and a minimal fix first, and change nothing until I confirm; do not create scripts or wrappers that bypass the vendor-native chain.

A specification upgrade invalidates only the affected evidence. Take changing the board-to-board channel from RGMII to PCIe:

  • the interface-contract revision changes, and link-related evidence on both sides becomes invalid;
  • FPGA pixel-pipeline evidence that does not use that channel remains valid;
  • system composition must be rerun, because the connectivity and bandwidth assumptions changed.

Conversely, when only the RK3588-side user-space application logic changes, FPGA-side evidence must not be invalidated. The right move is to rerun only the affected nodes, not to restart the entire system journey from scratch.

8. Current capability boundary

  • Implemented: the three decision points, CHIP composition, SYSTEM composition, and the evidence hierarchy that separates "generation ≠ compilation ≠ packaging ≠ flashing ≠ hardware verification ≠ system verification ≠ acceptance".
  • Planned: fully automatic dual-chip parallel orchestration under a single system intent. If your version does not yet expose a system-level entry point, drive each chip separately and trigger system composition once both sides reach technical completion.
  • Remains NOT_RUN: on-board PCIe/MIPI/RGMII link validation, cross-chip timing bring-up, long-duration stability, and system-level hardware evidence. Without hardware, all of these are written as NOT_RUN, and must never be replaced by documentation, package structure, or a single-side PASS.

9. Completion checklist

  • [ ] The system intent was stated in one sentence, rather than starting with code ownership
  • [ ] The functional breakdown is independently verifiable, without over-splitting for form's sake
  • [ ] Chip allocation and responsibilities are mutually exclusive, and confirmed by the user
  • [ ] Interface contract frozen: direction, format, bandwidth/clock, latency/buffering, error handling, revision
  • [ ] Both chip implementations proceeded in parallel without blocking each other
  • [ ] The FPGA side completed CHIP composition, and the RK3588 side completed its own build evidence
  • [ ] System composition ran and left a record
  • [ ] Partial failure was reported honestly as "the system is still not ready"
  • [ ] Technical completion (READY_FOR_ACCEPTANCE) and ACCEPTED are kept distinct
  • [ ] Hardware and system-level evidence that was not actually executed remains NOT_RUN
