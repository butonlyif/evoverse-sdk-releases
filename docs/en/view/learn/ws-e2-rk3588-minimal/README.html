WS-E2 RK3588J Minimal-System Natural-Language Tutorial

WS-E2 RK3588J Minimal-System Natural-Language Tutorial

EvoVerse SDK v1.0.1 · 2026-11-26

This tutorial is a single atomic journey: one intent takes you from installing EvoVerse all the way to a WS-E2 RK3588J project containing U-Boot, a Linux kernel, a device tree, a minimal rootfs, and a firmware package. Apart from installing the VSIXes, Docker Desktop, and similar tools, every operation is generated and executed through natural language.

An atomic intent is not split by default. The WS-E2 minimal system is itself a deliverable unit; there is no need to carve it into sub-intents, sub-modules, or a string of small-step confirmations just to make the process look complete. Splitting happens only when an intent is genuinely too complex to converge in one pass.

The whole journey has just three decision points for the user:

  1. Confirm the plan and the executable specification;
  2. approve licenses, material deployment, high-cost actions, or device writes when they apply;
  3. review the evidence boundary and give final acceptance.

The five background stages (Intent → Plan & Approve → Generate & Converge → Integrate & Realize → Accept) exist to explain the system; you do not need to memorize an action-by-action list.

This tutorial closes the software build loop. Flashing, boot, DDR/eMMC stress testing, and FPGA↔RK3588 on-board interface validation remain hardware verification: NOT_RUN. BUILD_READY is not hardware verification.

Every section gives you a natural-language prompt you can copy verbatim. Whenever a license, a material choice, or a risk needs confirmation, the Agent must stop and wait for your explicit approval.

0. Install the three VSIXes and prepare Docker

This is the only part of the tutorial that requires manual work:

  1. Windows 10/11 x64 with at least 9 GiB of free space on the target disk;
  2. Trae CN or a compatible VS Code host;
  3. in the Extensions view, choose "Install from VSIX…" and install evoverse-sdk-1.0.1.vsix, evoverse-efinity-adapter-1.0.1.vsix, and evoverse-rk3588-adapter-1.0.1.vsix in that order;
  4. restart the IDE;
  5. install and start Docker Desktop, and confirm it is running Linux containers;
  6. stage the two .evopkg offline packages supplied by EvoVerse; do not extract, rename, or re-compress them.

Natural-language prompt 1: installation and preparation self-check

Check whether the current EvoVerse SDK, Efinity Adapter, and RK3588 Adapter are installed and activated correctly, and check the Docker CLI, the Docker daemon, and Linux-container mode. Then sync the EvoVerse Catalog (the default public repository, no GitHub account required) and confirm that the ws-e2 board, the rk3588j-evm carrier, and the RK3588 minimal-system materials are available. Run read-only checks only; do not modify the project. If a tool is missing, tell me exactly what I need to install by hand.

The answer should mention ws-e2, rk3588j-evm, BSP b8f5dda5, toolchain 2026.09, and the names of both offline packages. Tool installation is your job; never let the Agent download installers from unknown sources. The board and demo inventory is governed by the Catalog declarations: the BSP id and toolchain version quoted here are a snapshot from the time of writing, and if the sync result differs, the Catalog wins.

1. Environment and materials (the second decision point, on demand)

This section belongs to the second decision point and appears only when you need to deploy offline materials, accept a license, or pay for a high-cost action. If the environment is already READY or you are working with online materials, skip straight to Section 2.

Natural-language prompt 2: check the RK3588 development environment

Check the RK3588 development environment. Use the Adapter's environment health-check capability to inspect Docker, disk space, the WS-E2 BSP, the toolchain offline packages, installation receipts, and the identity of installed files. Explain PACKAGE_REQUIRED, REPAIRABLE, USER_ACTION_REQUIRED, or READY, and give only the next step that is legal right now.

Corresponding MCP capability: rk3588_environment_status (read-only; it creates no installation receipts and no staging directory). The first run typically returns PACKAGE_REQUIRED, meaning offline materials are needed.

License and high-cost confirmation (on demand, not mandatory for every user)

Copy the two original evopkg files into the fixed directory <EVOVERSE_HOME>\downloads\rk3588\ (EVOVERSE_HOME defaults to %USERPROFILE%\evoverse-sdk), then:

Re-inspect the two RK3588 offline packages and verify the Catalog declarations, byte counts, outer SHA-256, inner manifest, and per-file checksums. On success, show me the license terms and the estimated disk usage, and deploy only after I have explicitly confirmed. When deployment finishes, re-run the full health check, and report success only if the final state is READY.

Corresponding MCP capability: first call rk3588_environment_prepare to obtain a one-time inspectionToken, then call rk3588_environment_deploy with acceptedLicenses: true. The token is valid only for the bytes present at inspection time; if the package contents change, you must re-inspect, and replaying a stale token is rejected.

After reading the licenses, reply explicitly: "I accept the license terms in the offline packages and confirm deployment." If deployment is cancelled or fails, the directories, receipts, and images added by this run must be rolled back; images that existed before deployment are not deleted. Importing the Docker image, rebuilding the BSP Git tree, and per-file verification can add up to ten-plus minutes; keep the Agent waiting meanwhile and do not stack new instructions on top. It re-runs the full health check when the run ends, and only READY counts as success.

2. One intent: the WS-E2 RK3588J minimal system

Open an empty directory as the project directory and describe the goal in one sentence. Project identity comes from the current Catalog, BSP qualification, and generation chain; you never hand-assemble a Profile.

Natural-language prompt 3: create the WS-E2 RK3588J minimal system

Create an EvoVerse project named ws-e2-rk3588j-minimal in the current empty directory. Select the ws-e2 board, the rk3588j-evm carrier, and the rk3588 development target. Generate a minimal Linux system from the current Catalog and the offline environment that is already READY; eMMC boot, UART2 logging, and a Buildroot minimal rootfs are recommended. Do not hand-assemble a Profile, and do not guess the loader, partitions, DDR, or DTS; identity must come from the current Catalog, BSP qualification, and generation chain. Show me the recommended and alternative choices before generating, and wait for my confirmation.

The Agent should state that the core module already integrates the PMIC, LPDDR4X, eMMC, and the reference clock, and that this is still not an on-board validation conclusion.

Corresponding MCP capability: rk3588_project_generate (the target only accepts the ws-e2 / rk3588j-evm / minimal-linux combination, and the project directory must be an absolute path; on success the project is PROFILE_READY, which does not mean it can be built). A single atomic intent produces no integration record, so the lifecycle reuses COMPLETED directly.

3. Confirm the plan and executable specification (the first decision point)

Before generation, pin the plan down as an executable specification: BSP and toolchain identity, boot medium, serial console, rootfs, loader, partition table, and the source of the DTS. The specification is an upgrade gate: any later requirement change must go through it and trigger a rerun, and must not be bypassed with hard-coded values.

Natural-language prompt 4: confirm the plan and specification

I confirm the recommended plan: pin the current BSP and toolchain identities, eMMC boot, UART2 logging, and a Buildroot minimal rootfs. Complete the controlled generation but do not build. Check file ownership in the generation manifest and confirm that regenerating will not overwrite customer content under applications.

Expect a generated Profile, DTS/DTSI, generation manifest, customer application directory, and output-directory skeleton. The correct state at this point is PROFILE_READY; it must not be passed off as BUILD_READY.

4. Continuous generation, preflight, and build

Once the specification is confirmed, you do not need to send a prompt per step. Have the Agent run preflight and the four-stage build back to back; the Adapter's native chain owns the details, and you only need to watch the outcome.

Natural-language prompt 5: run preflight and the four-stage build back to back

Run the following against the current RK3588 project in one go: first preflight — re-qualify the BSP and check the root commit, the four submodules, the loader, the partition table, the container digest, the toolchain, the DTS manifest, the output directory, and the four-stage capabilities; then use the RK3588 Adapter to build U-Boot, kernel/DTB, rootfs, and package in that order. For every stage report the exit code, the artifacts that stage must produce, the SHA-256 values, and diagnostics; stop on any stage failure and never pass old artifacts off as success. If preflight finds a blocker, give me the stable error code, the evidence, and a minimal repair suggestion, and do not modify BSP sources automatically. When the run finishes, recompute the Build Identity and readiness.

Corresponding MCP capability: rk3588_project_preflight (read-only qualification checks, 300-second timeout) and rk3588_project_build (headless builds accept only the complete four-stage order uboot → kernel → rootfs → package; partial stages are rejected).

Common preflight blockers:

  • BSP_BINDING_REQUIRED: rebind using the materials currently deployed;
  • BSP_SOURCE_DIRTY: back up and restore the declared version; do not bypass it;
  • BSP_QUALIFICATION_STALE: re-verify the current identity; an old PASS cannot be inherited.

Each stage's commands, exit codes, and SHA-256 evidence are recorded together in .evoverse/output/build-report.json under the project directory; that file is authoritative for the final state, and the chat reply is only its summary. The four-stage build is a long task — on an average machine, half an hour or more is common. Keep the Agent waiting while it runs and do not stack new tasks on top of it.

5. Evidence review and acceptance (the third decision point)

Natural-language prompt 6: accept the evidence

Accept the current WS-E2 RK3588J minimal system. Read the build-report, build-manifest, the four-stage receipts, and the firmware package; do not settle for checking that the files exist. Present a table of stage statuses, artifact digests, and the Build Identity, judge whether the result is BUILD_READY, and list every NOT_RUN item separately.

Corresponding MCP capability: rk3588_project_status (reads .evoverse/output/build-report.json plus the readiness summary; read-only — it neither reruns the build nor refreshes evidence).

Acceptance requires: all four stages belong to the current Build Identity, the error diagnostics count is zero, the firmware package contains U-Boot/Image/DTB/rootfs, and the project state is BUILD_READY; state hardware verification: NOT_RUN explicitly. Flashing, boot, and on-board interfaces all fall under HARDWARE_VERIFIED and cannot be claimed on the strength of BUILD_READY.

6. Failure recovery and specification upgrades

Failure recovery always stays on the native chain: start by reading the logs, receipts, diagnostics, and Profile of the current runId, and classify the problem into one of five classes — environment, material binding, BSP qualification, native tool error, or unverified hardware. Do not build scripts, wrappers, or environment-variable hacks that bypass the native toolchain.

Diagnose the current RK3588 operation failure. Analyze only the evidence belonging to this runId and do not inherit an old PASS. Give the root cause and a minimal fix first, and change nothing until I confirm.

A specification upgrade is another controlled action: for example, switching the boot medium from eMMC to SD, or replacing the Buildroot minimal rootfs with a larger package set. Update the plan and the executable specification first, then regenerate and rerun preflight and the four-stage build. Only evidence for the affected nodes is invalidated; unaffected historical artifacts may be kept, but they must not be counted as new evidence.

7. Choosing the next step

Prepare for flashing without executing it

Based on the current WS-E2 Profile and firmware evidence, give me a pre-flash checklist covering only loader, partitions, device identification, backup, and rollback requirements. Do not flash, and keep the hardware state at NOT_RUN.

Add FPGA co-processing

Plan a WS-E2 FPGA + RK3588 system journey without modifying the existing RK3588 BUILD_READY baseline: allocate functions to chips, freeze the interface contract, let both chips proceed in parallel, and finish with chip-level and system-level composition. Do not treat the board-to-board connector as an independent source of truth, and do not run hardware verification.

Start the on-board application

Plan the first AArch64 user-space application on top of the current minimal rootfs. Put the application code in the customer directory, explain cross-compilation, packaging, and runtime dependencies, and do not modify the managed BSP or generated files.

8. Completion checklist

  • [ ] Three VSIXes installed and activated
  • [ ] Docker Linux containers available
  • [ ] ws-e2 / rk3588j-evm present in the Catalog
  • [ ] Environment reaches READY on demand (online materials can skip material deployment entirely)
  • [ ] The goal was described in a single natural-language intent, without forced splitting for procedural completeness
  • [ ] Plan and executable specification confirmed before generation
  • [ ] Profile, DTS, and generation-manifest origins are explicit
  • [ ] Preflight and the four-stage build ran back to back with complete evidence
  • [ ] Project is BUILD_READY, and it is stated that this is not hardware verification
  • [ ] Flashing, boot, and on-board interface validation remain NOT_RUN
