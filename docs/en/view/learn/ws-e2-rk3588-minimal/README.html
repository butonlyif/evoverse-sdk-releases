WS-E2 RK3588J Minimal-System Natural-Language Tutorial

This tutorial starts from installing EvoVerse and ends with a WS-E2 RK3588J project containing U-Boot, a Linux kernel, a device tree, a minimal rootfs, and a firmware package. Apart from installing the VSIXes, Docker Desktop, and similar tools, every operation is generated and executed through natural language.

This tutorial completes the software build loop. Flashing, boot, DDR/eMMC stress testing, and FPGA↔RK3588 on-board interface validation remain hardware verification: NOT_RUN.

flowchart LR
  A[Install three VSIXes + Docker] --> B[Catalog + environment READY]
  B --> C[Create project via natural language]
  C --> D[PROFILE_READY]
  D --> E[Preflight]
  E --> F[Four-stage build]
  F --> G[BUILD_READY]
  G --> H[Firmware + receipts + logs]
  H --> I[Hardware verification: NOT_RUN]

Every section provides a ready-to-copy natural-language prompt. Whenever a license, a material choice, or a risk boundary is involved, the Agent must wait for your confirmation.

0. Prerequisites

  • Windows 10/11 x64 with at least 9 GiB of free space on the target disk;
  • Trae CN or a compatible VS Code host;
  • Docker Desktop running Linux containers;
  • the three EvoVerse VSIXes;
  • the two .evopkg offline packages provided by EvoVerse.

Do not extract, rename, or re-compress the .evopkg files.

1. Install the three VSIXes

This is the one tool-installation step that must be done by hand:

  1. In the Extensions view choose "Install from VSIX…";
  2. install evoverse-sdk-1.0.0.vsix;
  3. install evoverse-efinity-adapter-1.0.0.vsix;
  4. install evoverse-rk3588-adapter-1.0.0.vsix;
  5. restart the IDE;
  6. install and start Docker Desktop, and confirm it uses Linux containers.

Natural-language prompt 1: verify the installation

Check whether the EvoVerse SDK, the Efinity Adapter, and the RK3588 Adapter are correctly installed and activated, and check the Docker CLI, the Docker daemon, and Linux-container mode. Read-only checks only — do not modify the project. If anything is missing, tell me exactly what I need to install by hand.

Tool installation must be done by you; do not let the Agent download installers from unknown sources.

2. Sync the Catalog and confirm WS-E2

Natural-language prompt 2: sync board materials

Sync the EvoVerse Catalog (default public repository, no GitHub account required), then check whether the ws-e2 board, the rk3588j-evm carrier, and the RK3588 minimal-system materials are available. Report the Catalog version, the development target, the offline-package declarations, and the evidence boundary. Do not create a project.

The answer should mention ws-e2, rk3588j-evm, BSP b8f5dda5, toolchain 2026.09, and the two offline-package file names. If the Catalog is unavailable, fix the sync first — never fabricate materials from memory.

The concrete board, carrier, and demo lists are governed by the Catalog declarations: the BSP id and toolchain version written in this section are a snapshot from the time of writing and may change after a Catalog update. If the sync result disagrees with this section, the Catalog wins — have the Agent report the difference honestly instead of forcing the tutorial's old values.

3. Check the RK3588 development environment

Natural-language prompt 3: environment health check

Check the RK3588 development environment. Use the Adapter's environment health-check capability to inspect Docker, disk space, the WS-E2 BSP, the toolchain offline packages, installation receipts, and the identity of installed files. Explain PACKAGE_REQUIRED, REPAIRABLE, USER_ACTION_REQUIRED, or READY, and give only the currently legal next step.

The corresponding MCP capability: rk3588_environment_status (read-only; produces no installation receipts or staging directories).

The first run usually returns PACKAGE_REQUIRED, meaning offline materials are needed.

4. Obtain and deploy the two offline packages

Obtain from EvoVerse:

  • rk3588-toolchain-2026.09.evopkg
  • ws-e2-rk3588-bsp-b8f5dda5.evopkg

The two offline packages live in the fixed directory <EVOVERSE_HOME>\downloads\rk3588\ (EVOVERSE_HOME defaults to %USERPROFILE%\evoverse-sdk). Prompt 4 has the Agent open exactly this directory: copy the two original evopkg files in, then run prompt 5.

Natural-language prompt 4: open the inbox

Open the fixed RK3588 offline-package directory; do not start deploying. I will copy the two original evopkg files provided by EvoVerse into it. After opening, tell me the full path.

After copying both files:

Natural-language prompt 5: verify and deploy

Re-inspect the two RK3588 offline packages: verify the Catalog declarations, byte counts, outer SHA-256, inner manifest, and per-file checksums. On success, show me the license confirmation content and the estimated disk usage, and wait for my explicit confirmation before deploying in one shot. Afterwards you must re-run the full health check; only report success if the final state is READY.

The corresponding MCP capability: first call rk3588_environment_prepare to obtain a one-time inspectionToken, then call rk3588_environment_deploy with acceptedLicenses: true. The token is valid only for the bytes inspected at that moment; if the package contents change, re-inspection is mandatory — replaying an old token is rejected.

After reading the licenses, reply explicitly: "I accept the license terms in the offline packages and confirm deployment." If the deployment is cancelled or fails, the directories, receipts, and images added by this run are rolled back; images that existed before the deployment are not deleted.

Deployment is not a second-scale operation: importing the Docker image, rebuilding the BSP Git tree, and the per-file verification together can easily take ten-plus minutes. While deployment runs, keep the Agent waiting and do not send new instructions; it will re-run the full health check when finished, and only READY counts as success — "it looks like it is moving" midway is not evidence of success.

5. Confirm the environment is READY

Natural-language prompt 6: explain the environment evidence

Check the RK3588 development environment again and explain the READY evidence item by item: Catalog package identity, inner manifest, installation receipt, per-file and extra-file checks, BSP qualification, Docker image digest, and minimum Adapter version. Finish by stating explicitly what remains unverified.

The correct boundary here is an environment that is READY, while the current project is not yet BUILD_READY and flashing and hardware verification remain NOT_RUN.

6. Create the WS-E2 RK3588J minimal system

Open an empty directory as the project directory.

Natural-language prompt 7: create the project

Create an EvoVerse project named ws-e2-rk3588j-minimal in the current empty directory. Choose the ws-e2 board, the rk3588j-evm carrier, and the rk3588 development target. Generate a minimal Linux system based on the current Catalog and the offline environment that is already READY; recommend eMMC boot, UART2 logging, and a Buildroot minimal rootfs. Do not hand-assemble a Profile; do not guess loaders, partitions, DDR, or DTS — identities must come from the current Catalog, BSP qualification, and the generation chain. Show me the recommended and alternative choices and wait for my confirmation before generating.

The Agent should point out: the core module already includes the PMIC, LPDDR4X, eMMC, and the reference clock; this is still not an on-board validation conclusion.

Natural-language prompt 8: confirm the recommendation

I confirm the recommended plan: pin the current BSP and toolchain identities, eMMC boot, UART2 logging, Buildroot minimal rootfs. Complete the controlled generation, but do not build. Check the file ownership in the generation manifest and confirm that regeneration will not overwrite customer content under applications.

Expect a generated Profile, DTS/DTSI, a generation manifest, a customer application directory, and the output-directory skeleton. At this point the state may be PROFILE_READY, but it must not be passed off as BUILD_READY.

The corresponding MCP capability: rk3588_project_generate (targets allow only the ws-e2 / rk3588j-evm / minimal-linux combination, and the project directory must be an absolute path; on success the project is PROFILE_READY, which does not mean buildable).

7. Run the project preflight

Natural-language prompt 9: preflight

Run preflight on the current RK3588 project. Re-qualify the BSP: check the root commit, the four submodules, the loader, the partition table, the container digest, the toolchain, the DTS manifest, the output directory, and the four-stage capabilities. Do not modify BSP sources automatically; if anything blocks, give a stable error code, the evidence, and a minimal repair suggestion.

  • BSP_BINDING_REQUIRED: rebind with the currently deployed materials;
  • BSP_SOURCE_DIRTY: back up and restore the declared version — no bypassing;
  • BSP_QUALIFICATION_STALE: re-verify the current identity; an old PASS cannot be inherited.

The corresponding MCP capability: rk3588_project_preflight (read-only qualification checks, 300-second timeout; any repair action must be confirmed by the user and executed separately — it never happens automatically alongside preflight).

8. Complete the four-stage build via natural language

Natural-language prompt 10: build

Build the current project with the RK3588 Adapter, executing U-Boot, kernel/DTB, rootfs, and package in order. Report the exit code, the required artifacts of each run, SHA-256s, and diagnostics for every stage; stop on any stage failure and never pass old artifacts off as success. When finished, recompute the Build Identity and readiness.

Stage Expected artifacts
U-Boot uboot.img
Kernel Image, rk3588j-evoverse.dtb
Rootfs rootfs.ext2
Package ws-e2-rk3588j-minimal-firmware.tar.gz

The corresponding MCP capability: rk3588_project_build (headless builds accept only the complete four-stage order uboot → kernel → rootfs → package, not partial stages). Each stage's commands, exit codes, and SHA-256 evidence are attributed to .evoverse/output/build-report.json in the project directory; that file is the authority for the final state, and chat replies are only its summary.

The four-stage build is a long task; on an average machine, half an hour or more is common. While it builds, keep the Agent waiting and do not stack new tasks on top; if any stage fails, it stops and hands you diagnostics — it never passes old artifacts off as success. When you see a failure, have it explain the root cause first, then decide whether to re-run or to fix.

9. Accept the minimal system

Natural-language prompt 11: acceptance evidence

Accept the current WS-E2 RK3588J minimal system. Read the build-report, build-manifest, four-stage receipts, and the firmware package — do not just check that files exist. Present a table of stage statuses, artifact digests, and the Build Identity, judge whether it is BUILD_READY, and list all NOT_RUN items separately.

Acceptance requires: all four stages belong to the current Build Identity, zero error diagnostics, the firmware package contains U-Boot/Image/DTB/rootfs, the project state is BUILD_READY, and hardware verification: NOT_RUN is stated explicitly.

The corresponding MCP capability: rk3588_project_status (reads .evoverse/output/build-report.json and the readiness summary; read-only, never re-runs the build or refreshes evidence).

10. What to do next

Prepare for flashing, but do not flash yet

Based on the current WS-E2 Profile and firmware evidence, give me a pre-flash checklist: loader, partitions, device identification, backup, and rollback requirements. Do not flash, and keep hardware status NOT_RUN.

Add FPGA co-design

Plan a WS-E2 FPGA + RK3588 system project without modifying the existing RK3588 BUILD_READY baseline. Read the final device mapping and the interface contract, and recommend PCIe, MIPI, RGMII, or GPIO; do not treat board-to-board connectors as an independent source of truth, and do not run hardware verification.

Start an on-board application

Plan the first AArch64 user-space application on top of the current minimal rootfs. Application code goes in the customer directory; explain cross-compilation, packaging, and runtime dependencies, and do not modify the managed BSP or generated files.

11. Troubleshooting prompt

Diagnose the current RK3588 operation failure. Read the logs, receipts, diagnostics, and Profile for this runId, and analyze only this run's evidence. Distinguish five problem classes: environment, material binding, BSP qualification, native-tool errors, and unverified hardware. Do not inherit an old PASS, and do not create scripts that bypass the native toolchain; give the root cause and a minimal fix first, and wait for my confirmation before changing anything.

12. Completion checklist

  • [ ] Three VSIXes installed and activated
  • [ ] Docker Linux containers available
  • [ ] ws-e2 / rk3588j-evm present in the Catalog
  • [ ] Environment is READY
  • [ ] Generation completed with the "create WS-E2 RK3588J minimal system" natural-language prompt
  • [ ] Profile, DTS, and generation manifest have clear origins
  • [ ] Preflight passed
  • [ ] Four-stage build evidence complete
  • [ ] Project is BUILD_READY
  • [ ] Flashing and hardware verification remain NOT_RUN
