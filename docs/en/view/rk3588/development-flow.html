RK3588 Development Flow Guide

RK3588 Development Flow Guide

Version: v1.0.0　Updated: 2026-09-25
Current baseline: WS-E2 / RK3588J / BSP b8f5dda5 / toolchain 2026.09

This document describes the environment deployment, project generation, and minimal-system build chain that EvoVerse actually supports today. For your first hands-on run, go straight to the WS-E2 RK3588J Minimal System natural-language tutorial.

1. Four States That Must Not Be Confused

flowchart LR
  A[Install the three VSIXes] --> B[Sync the Catalog]
  B --> C[Deploy the two offline packages]
  C --> D[Environment READY]
  D --> E[Generate and bind a project]
  E --> F[PROFILE_READY]
  F --> G[Preflight + four-stage build]
  G --> H[Project BUILD_READY]
  H --> I[Flash and hardware verification NOT_RUN]
  • Environment READY: Docker, the pinned toolchain, the WS-E2 BSP, receipts, and per-file identities all passed their checks.
  • Project PROFILE_READY: the project skeleton has been generated, but binding or preflight has not fully closed yet.
  • Project BUILD_READY: U-Boot, kernel/DTB, rootfs, and package all succeeded under the same Build Identity.
  • Hardware NOT_RUN: flashing, boot, DDR/eMMC, and board-level interface verification have not been performed yet.

Environment deployment never searches for or rewrites arbitrary customer projects, and an environment READY does not imply a project BUILD_READY.

2. What Is Delivered

The Three VSIXes

VSIX Responsibility
evoverse-sdk-1.0.0.vsix SDK Shell, Catalog, natural-language tooling, and system orchestration
evoverse-efinity-adapter-1.0.0.vsix Efinity capabilities for the WS-E2 FPGA side
evoverse-rk3588-adapter-1.0.0.vsix RK3588 environment health checks, project preflight, builds, and evidence presentation

The Two Offline Packages

Large BSPs do not go into Git or the customer installation package. From EvoVerse you obtain the two offline packages rk3588-toolchain-2026.09.evopkg and ws-e2-rk3588-bsp-b8f5dda5.evopkg. The authoritative byte counts and SHA-256 values are in the "The Two Files to Obtain" table of the RK3588 Offline Environment Deployment Guide.

The Catalog also locks the internal manifest, the minimum Adapter version, board bindings, and the licensing policy. The hard deployment threshold is 8,300,000,000 bytes; keep at least 9 GiB free.

3. Setting Up the Environment

  1. Install the three VSIXes and Docker Desktop, and switch to Linux containers.
  2. Sync the Catalog (EvoVerse: Sync Catalog — the default public repository needs no GitHub account).
  3. Run the Adapter environment health check.
  4. Place the two offline packages in <EVOVERSE_HOME>/downloads/rk3588/, or select them one by one.
  5. The Adapter verifies the outer size/SHA, the internal manifest, and the per-file checksums, then issues a one-time inspection token.
  6. The user explicitly accepts the licenses, then runs the one-click deployment.
  7. The Adapter rebuilds the BSP Git tree, imports the Docker image, runs BSP qualification, writes per-file receipts, and runs the health check again.

Default locations: the BSP in <EVOVERSE_HOME>/bsp/ws-e2/b8f5dda5/, the toolchain material in <EVOVERSE_HOME>/toolchains/rk3588/2026.09/, and the receipts in <EVOVERSE_HOME>/receipts/rk3588/.

Deployment is transactional: on cancel or failure, the directories, receipts, and newly imported images from that run are rolled back; images that existed before the deployment are never deleted. A partial installation is reused only after its complete file closure, BSP qualification, or Docker image identity passes again.

4. WS-E2 Minimal System Recommendation

The curated WS-E2 material confirms that the core module carries the RK3588J, PMIC, power sequencing, LPDDR4X, eMMC, and a 24 MHz reference clock; the carrier provides the serial and USB OTG paths needed for a minimal boot. The current recommendation:

  • the Rockchip Linux 6.1-series BSP;
  • eMMC boot with UART2 carrying the first boot log;
  • a Buildroot minimal rootfs;
  • close the minimal SoC boot first, then add the FPGA↔RK3588 interfaces.

This is an engineering recommendation, not a validated-on-hardware conclusion. DDR parameters, loaders, partition tables, and DTS must come from the current Catalog/BSP identity; never reuse them across boards on the grounds that they are "also RK3588".

5. Generating a Project in Natural Language

The user simply picks WS-E2, rk3588j-evm, the target rk3588, and the project directory in natural language. The Agent drives the SDK's board project generation chain — users never hand-write a Profile or DTS.

Generated outputs include:

  • evoverse-rk3588-profile.json: board, BSP, container, toolchain, loader, partitions, and the four-stage commands;
  • .evoverse/board/*.dts / *.dtsi: board-level candidates managed by the generation manifest;
  • .evoverse/rk3588-generation-manifest.json: generation inputs and file ownership;
  • applications/: the customer code area, preserved on regeneration;
  • output/: build reports, receipts, logs, and firmware.

When material is incomplete, the project stays PROFILE_READY and returns BSP_BINDING_REQUIRED; a template state must never be passed off as buildable.

6. Preflight and the Four-Stage Build

flowchart TD
  P[Preflight] -->|identity matches| U[U-Boot]
  P -->|mismatch| X[Blocked, with the corrective action stated]
  U --> K[Kernel + DTB]
  K --> R[Buildroot rootfs]
  R --> F[Firmware package]
  F --> E[Receipts + Build Identity]
  E --> B[BUILD_READY]

Preflight re-checks the BSP Git status, the pinned commit, submodules, loader/partition SHAs, the container digest, the toolchain, and the DTS manifest. If tracked files have changed, it returns BSP_SOURCE_DIRTY or BSP_QUALIFICATION_STALE; a historical PASS is never inherited.

Stage Key artifacts
U-Boot uboot.img
Kernel Image, rk3588j-evoverse.dtb
Rootfs rootfs.ext2
Package ws-e2-rk3588j-minimal-firmware.tar.gz

A success verdict requires the exit codes, the run's required artifacts, the artifact SHA-256s, and the six-field Build Identity to all agree at once. A real tool error is never downgraded to success just because older artifacts exist.

7. Evidence and Boundaries

All build evidence lives under .evoverse/output/ in the project directory:

  • .evoverse/output/build-report.json: overall success, readiness, and diagnostics — the single authority for the final state;
  • .evoverse/output/build-manifest.json: stage commands, exit codes, and artifact digests;
  • .evoverse/output/logs/: native command output;
  • the firmware archive: a software build artifact, not proof of flashing or booting.

Stage states in chat replies are only summaries of that evidence; if the two ever disagree, build-report.json wins.

A historical WS-E2 baseline did complete a real four-stage build and reached BUILD_READY, but it does not substitute for the preflight and the fresh build of a customer's current project.

8. FPGA + RK3588 Follow-Up Expansion

Once the minimal system is done, you can create a system target that binds the FPGA evidence, the RK3588 BUILD_READY evidence, and one shared interface contract. Board-to-board connectors are not an independent source of design truth; the system consumes the final device/pin mapping and the PCIe, MIPI, RGMII, or GPIO interface contracts.

9. Common Blockers

Status Correct handling
PACKAGE_REQUIRED Obtain the two offline packages at their declared versions
PACKAGE_DIGEST_MISMATCH Replace the original package; do not modify the Catalog or receipts
USER_ACTION_REQUIRED Resolve Docker, disk space, or conflicting directories, then re-check
BSP_BINDING_REQUIRED Regenerate/rebind the project against the currently deployed material
BSP_SOURCE_DIRTY Back up and restore the declared version; never bypass qualification
PROFILE_READY Continue completing the binding and run preflight
BUILD_READY Proceed to flashing-plan confirmation; hardware remains NOT_RUN
