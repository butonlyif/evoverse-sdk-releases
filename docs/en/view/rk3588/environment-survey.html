1. RK3588 Overview

1.1 Chip Positioning

The Rockchip RK3588 is a high-performance ARM SoC from Rockchip Electronics, positioned for high-end IoT, smart cockpits, edge computing, and AIoT. It combines a heterogeneous 4× Cortex-A76 + 4× Cortex-A55 CPU architecture with an 8nm process; actual frequencies, media capabilities, and available interfaces remain subject to the silicon variant, package, board design, and BSP.

1.2 Key Features

Category Specification Notes
CPU 4x Cortex-A76 + 4x Cortex-A55 ARM big.LITTLE architecture; big cores up to 2.4GHz
GPU Mali-G610 MP4 OpenGL ES 1.1/2.0/3.2, Vulkan 1.2 support
NPU 6TOPS INT4/INT8/INT16/FP16 support; strong compute
VPU 8K@30fps codec H.265/H.264/VP9/AV1 support
ISP Up to 48MP Dual ISP channels
Memory LPDDR4/LPDDR4X/LPDDR5 Up to 32GB
Storage eMMC 5.1, UFS 2.1, PCIe 3.0, SATA 3.0 Multiple storage interfaces
Interfaces USB 3.0, USB 2.0, PCIe, HDMI 2.1, MIPI-CSI/DSI Rich peripheral interfaces
Process 8nm FinFET Low power, high performance

1.3 Application Scenarios

  • Smart cockpit: IVI, digital instrument clusters, HUD
  • Edge computing: AI inference, machine vision
  • Smart home: smart speakers, smart displays
  • Industrial control: industrial tablets, machine vision
  • ARM development boards: evaluation boards for developers (e.g., Rockchip EVB, third-party boards)

The RK3588 uses the ARM64 (AArch64) architecture and requires a cross-compilation toolchain:

GCC AArch64 The mainstream choice, GCC 10+ apt install gcc-aarch64-linux-gnu

Typical toolchain prefix: aarch64-linux-gnu-

4. Common Development Scenarios

4.1 Linux Development

4.1.1 Kernel Driver Development

# 1. 获取内核源码
cd kernel-6.1
make ARCH=arm64 rockchip_linux_defconfig
make ARCH=arm64 menuconfig  # 配置内核选项

# 2. 编写驱动 (示例: hello_world.c)
cat > drivers/misc/hello_rk3588.c << 'EOF'
#include <linux/module.h>
#include <linux/kernel.h>

static int __init hello_init(void) {
    pr_info("Hello RK3588!\n");
    return 0;
}

static void __exit hello_exit(void) {
    pr_info("Goodbye RK3588!\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("Developer");
MODULE_DESCRIPTION("Hello RK3588 Driver");
EOF

# 3. 编译模块
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- M=drivers/misc modules

7. macOS Special Notes

7.1 Environment Limitations

macOS developers should note these limitations:

  1. Cross-compilation toolchain: Homebrew's ARM toolchains may be incomplete; prefer Docker or a Linux VM
  2. USB drivers: Install the Silicon Labs VCP driver to recognize serial ports
  3. Flashing tools: Rockchip Flash Tool ships only for Windows/Linux; use rkdeveloptool on macOS

8. In-Depth Findings and Engineering Baseline

8.1 The Most Important Findings

  1. The RK3588 is not a self-contained "generic target" you can build in isolation. The real build target is SoC + package/memory topology + PMIC + storage + carrier + BSP release. Boards that are all "RK3588" — EVB, Rock 5, Firefly, and so on — can differ in DDR initialization, U-Boot defconfig, DTS, partition table, and flashing loader.
  2. A BSP is a version closure, not a parts list. U-Boot + rkbin/DDR blob + TF-A/OP-TEE + Kernel + DT + Rootfs + packaging tools must be locked as the vendor-validated combination. Bumping just the kernel or U-Boot to "a newer version" is not a reproducible recipe.
  3. Separate development from deployment. Compile inside a pinned Linux container/VM; serial, ADB/SSH, and flashing may run on the host. The Linux VM behind macOS Docker Desktop does not pass Maskrom USB through by default — flash from a native Linux/Windows workstation or a verified USB-forwarding setup.
  4. Do board bring-up before automation. The Adapter's first supported target must be one specific board and one specific BSP version; bootable firmware cannot be derived straight from a SoC datasheet.

8.2 Recommended Reproducible-Environment Contract

Every build must produce a build-manifest.json recording at least:

{
  "boardProfile": "vendor-board-revision",
  "bspManifestCommit": "<sha>",
  "components": {"uboot": "<sha>", "kernel": "<sha>", "rkbin": "<sha>"},
  "toolchain": {"triple": "aarch64-linux-gnu", "version": "<exact>", "sha256": "<sha256>"},
  "containerImage": "<registry/image@sha256:digest>",
  "configHashes": {"uboot": "<sha256>", "kernel": "<sha256>", "rootfs": "<sha256>"},
  "sourceDateEpoch": 0
}

Recommended host baseline: Linux x86_64, at least 250 GB of reserved disk (more for Android builds), at least 16 GB RAM (32 GB recommended for large parallel builds), with Git LFS and repo available. Follow the BSP release note for exact sizes. Container images must be pinned by digest; mount sources, the download cache, and output directories as separate volumes so artifacts survive container removal.

8.3 Three Corrected Workflows

Workflow Input Output Scope
Full BSP build Vendor manifest, board profile, pinned container Flashable images and manifest Release/CI; most trustworthy
Kernel/DT incremental .config, DTS, Module.symvers from the same BSP Image, DTB, modules Driver development; ABI consistency is mandatory
Application/NPU sysroot, cross toolchain, RKNN compatibility matrix ELFs/packages, .rknn, validation reports Leaves the boot chain untouched; fastest iteration

8.4 Flashing Safety Gates

  • Before any write, record the USB VID/PID, chip information, device mode, board profile, and target storage medium; refuse auto-selection when multiple devices are attached.
  • Loaders must come from the current board/BSP; reusing one just because it is "RK3588" is forbidden — mismatched DDR parameters can cause download failures or instability.
  • Never treat the example 0x4000 as a generic partition address. Offset units, GPT/parameter layout, and image types must be stated explicitly by the profile.
  • By default, read and save the GPT/parameter first; erasing, writing the bootloader, and writing whole-disk images are high-risk operations that require explicit confirmation.
  • After writing, at least verify the image hash/readback, key serial boot stages, kernel version, DT model/compatible, and rootfs version.

8.5 Acceptance Checklist

The environment survey counts as complete only when all of this evidence exists: two consecutive successful builds from the same clean checkout; traceable artifacts and configurations; passing cold boot, warm reboot, and power-loss boot; a full BootROM→loader→U-Boot→Kernel→userspace log retained on serial; PCIe, GMAC, MIPI, and GPIO each verified against the board schematic and runtime probing; and NPU records covering Toolkit2, model format, runtime, and driver versions, with accuracy/performance regression on fixed inputs.

8.6 Source Trustworthiness and Open Items

Priority order: board BSP release note/manifest and schematic > Rockchip chip documentation and official repositories > Linux kernel documentation > community board material. Public material cannot replace controlled datasheets/TRMs, board schematics, or the actual BSP.

Until the first target board is chosen, the following remain "to be confirmed": exact PCIe/Combo PHY muxing, MIPI DPHY routing, GPIO availability, debug UART baud rate, partition layout, loader files, DT node labels, kernel branch, and RKNN compatibility combinations. The EvoVerse Adapter must take these as profile inputs, never hard-code them.
