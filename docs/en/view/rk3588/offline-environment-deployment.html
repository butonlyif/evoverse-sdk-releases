RK3588 Offline Environment Deployment Guide

RK3588 Offline Environment Deployment Guide

This guide applies to the RK3588J development environment for WS-E2. The SDK never auto-downloads large BSPs from the public internet or file-hosting services; obtain the two locked offline packages from EvoVerse first, and let the RK3588 Adapter handle verification, deployment, and qualification.

The Two Files to Obtain

File Download size Post-install purpose SHA-256
rk3588-toolchain-2026.09.evopkg 256,584,627 bytes (about 244.7 MiB) Ubuntu 22.04 / AArch64 GNU cross-compilation Docker image d05eaff178a72f6764e75f52418ee3e642a74cb15ca182c93a03cdc005fc28f2
ws-e2-rk3588-bsp-b8f5dda5.evopkg 344,225,733 bytes (about 328.3 MiB) kernel, U-Boot, rkbin, Buildroot, and WS-E2 inputs at pinned commits b3107d7bfeabc1fc29bf013bbc980d3d6b883d7ce4e5ef97881b42d2fc43f118

The rebuilt BSP is expected to occupy about 4.03 GiB; the toolchain image expands to about 685 MiB. The Catalog's hard deployment threshold is 8,300,000,000 bytes; allow for logs and subsequent builds and keep at least 9 GiB free on the target disk.

Before You Deploy

  1. Install and start Docker Desktop, and switch to Linux containers.
  2. Confirm the SDK has synced the latest private Catalog.
  3. Confirm the target disk has enough free space.
  4. Do not extract, rename, or recompress .evopkg files.

By default EVOVERSE_HOME is %USERPROFILE%\evoverse-sdk. If you changed it in the SDK settings, every path below follows the configured value.

Recommended Procedure: Drop into the Fixed Directory, Then One-Click Deploy

  1. In the RK3588 Workbench Overview, click "Open offline package directory".
  2. Copy both .evopkg files to:

text <EVOVERSE_HOME>\downloads\rk3588\

  1. Click "Check environment". Only after both packages pass every check — file names, sizes, outer SHA-256, internal manifest, and per-file checksums — does the UI offer a deployment token bound to that check.
  2. Read the license notice and check the license confirmation box.
  3. Click "One-click deploy", and do not close the IDE or Docker Desktop during deployment.
  4. Wait until the Overview shows READY, then move on to Build.

To abort, use the cancel action of the current run; the Adapter cancels unpacking/deployment under the same run ID and rolls back the installation directories, receipts, and Docker images created by that run. Images that already existed before the deployment are not removed.

You can also click "Select offline packages" and pick the two files individually. Selecting files does not install anything; deployment becomes possible only after both packages pass the same controlled check.

What the Adapter Actually Does

flowchart LR
  A[Two offline packages] --> B[Size and outer SHA-256]
  B --> C[Manifest and per-file checksums]
  C --> D[Unpack into a staging directory]
  D --> E[Docker load and image ID check]
  D --> F[Rebuild the BSP from a Git bundle]
  F --> G[root/submodule/loader/partition-table/toolchain qualification]
  E --> H[Atomic install and receipts]
  G --> H
  H --> I[Environment READY]
  I --> J[Project preflight / build]
  J --> K[Hardware verification still NOT_RUN]

The BSP package stores a controlled Git bundle rather than a .git directory. Deployment rebuilds a real Git repository, restores the pinned root commit and the four submodules, then invokes the SDK's existing BSP qualification gate. If qualification fails, staged results are never passed off as an official installation.

Installation Results

Content Default location
BSP <EVOVERSE_HOME>\bsp\ws-e2\b8f5dda5\
Toolchain archive <EVOVERSE_HOME>\toolchains\rk3588\2026.09\
Installation receipts <EVOVERSE_HOME>\receipts\rk3588\
Temporary staging area <EVOVERSE_HOME>\staging\rk3588\

Do not edit the installation receipts by hand. If an installed directory and its receipts disagree, the health check reports REPAIRABLE or USER_ACTION_REQUIRED and never silently overwrites unknown content.

What the Statuses Mean

  • PACKAGE_REQUIRED: one or both offline packages are missing.
  • REPAIRABLE: the packages were found and the environment can be repaired through controlled deployment.
  • USER_ACTION_REQUIRED: the user must resolve Docker, disk space, package corruption, or an existing-directory conflict.
  • READY: environment identity and installation receipts passed; this does not mean any project has been built.
  • BUILD_READY: the current project passed its own preflight and is ready for a controlled build.
  • NOT_RUN: flashing or board-level hardware verification has not been performed yet.

FAQ

PACKAGE_DIGEST_MISMATCH is reported

The file is not the original package declared by the Catalog, or it was corrupted during copying. Delete the copy and obtain it again from EvoVerse; do not modify the Catalog JSON or the verification receipts.

Docker CLI exists but the daemon is unavailable

Start Docker Desktop, wait for the engine to be ready, confirm you are on Linux containers, then click "Check environment" again.

An existing installation directory does not match

The tool never overwrites a directory of unknown origin. Back up that directory and its receipts first, have the project owner decide whether to restore the old version or move the conflicting directory away, then redeploy.

Can I take only the BSP and skip the toolchain?

No. The reproducible WS-E2 environment binds the BSP and the toolchain image together; a deployment token is never issued when either package is missing.

Can I flash directly once the environment is READY?

No. You still need to generate/confirm the project Profile, run preflight and Build, and complete the firmware, flashing-method, and board-level verification. Environment health only answers "are the development material and tools the declared versions".

One-click deployment never searches for or rewrites the Profile of any customer project. After the environment reaches READY, the user must still explicitly choose the target project; the project generation/binding chain then writes the BSP, container, loader, and partition identities, and only that project's own preflight can yield BUILD_READY.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
