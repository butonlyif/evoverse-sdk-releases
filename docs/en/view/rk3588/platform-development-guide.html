RK3588 Platform Development Guide

RK3588 Platform Development Guide

EvoVerse SDK v1.0.1 · 2026-11-26

Applies to EvoVerse SDK v1.0.1. Current boundary: software qualification can finish without a board. Flash, boot, target execution, and NPU performance require real hardware.

1. What customers receive

Customers consume a signed Platform Development Release; they do not clone or receive the Platform development repository. One platform-manifest.json binds:

  • the flashable update.img firmware;
  • a sysroot derived from the same root filesystem;
  • the App Builder used by Windows with Docker;
  • an optional Model Builder for AI projects;
  • Developer Runtime, SBOM, licenses, and source-compliance material;
  • separate software, boot, and hardware qualification states.

.evoverse/platform-lock.json pins the platform version and descriptor digest. Reopening the project reuses that lock; another version never replaces it silently.

2. Online Workbench path

  1. Install the SDK and RK3588 Adapter, then synchronize the Catalog.
  2. Create or open a project whose Catalog module/carrier identity matches the target.
  3. Select Prepare Platform on the RK3588 Workbench Platform Development card.
  4. Review the version, download size, licenses, and qualification state, then approve the download.
  5. Without a board, prepare only sysroot + App Builder; add Model Builder for an AI project. Firmware may be pre-downloaded but is not flashed.
  6. Select Build Application and, for AI projects, Convert Model.
  7. When hardware is available, select Flash/Update Board, verify board identity, and then Deploy and Run.
  8. Use View Evidence to distinguish software, flash, boot, target execution, and NPU performance facts.

Downloads use a content-addressed cache and recheck size and SHA-256. A cache hit never proves that a board was flashed or booted.

3. Development without a board

No-board development is supported. Customers can complete release resolution and locking, AArch64 cross-compilation, ELF/loader/dependency/RPATH checks, ONNX inspection, quantization, RKNN conversion, host-simulator comparison, and static Application Package verification.

The valid endpoint is WAITING_FOR_BOARD. Board discovery, flash, boot, target deployment, target execution, NPU execution, and hardware performance remain NOT_RUN / NO_BOARD.

4. Manual and offline path

Online channels, enterprise mirrors, and offline media must carry the same signed manifest and identical asset digests.

  1. Obtain the complete Release directory from an approved channel; do not copy only update.img.
  2. Transfer the manifest, signature, SHA256SUMS, required assets, SBOM, and licenses.
  3. Verify the signature with the release verification tool, then verify every asset's SHA-256 and size on the destination Windows host.
  4. Import verified assets into the SDK content-addressed cache, or place the descriptor at .evoverse/platform-descriptor.json and run Prepare Platform. Do not edit the descriptor to substitute local paths.
  5. If Docker is unavailable, use SSH native build after the board arrives. The device Developer Runtime must match the project lock.

Manual flashing must use the board-specific instructions shipped with the Release. Recheck module, carrier, board revision, firmware digest, and qualification state first. UNQUALIFIED_NO_BOOT permits download and project preparation; it is not a production-qualified image.

5. AI model workflow

Model Builder performs ONNX inspection, quantization, ONNX-to-RKNN conversion, and host simulation. App Builder compiles the AArch64 application against RKNN Runtime/MPP/RGA. The same Platform manifest binds Toolkit, Runtime, driver ABI, and target NPU compatibility.

A host-simulator pass is not a real-NPU pass. Accuracy, performance, memory, temperature, and stability require separate evidence from a real RK3588 board.

6. Common blockers

  • PLATFORM_DESCRIPTOR_UNREADABLE: the descriptor is absent, unreadable, or invalid JSON.
  • PLATFORM_UPGRADE_CONFIRMATION_REQUIRED: the project is pinned to another release; review and explicitly approve an upgrade.
  • PLATFORM_MATERIALS_MISSING: cached assets are incomplete; prepare again or re-import the offline release.
  • WAITING_FOR_BOARD: software work is complete and awaits hardware; this is not a failure.
  • UNQUALIFIED_NO_BOOT: the firmware has no real boot qualification and must not be reported as flash/boot PASS.

7. What customers do not need

Customers do not need the private Platform repository, internal CI/CD, credentials, unpublished BSP branches, or lab automation. Source obligations for Linux, U-Boot, Buildroot, and similar components are fulfilled through release-bound source-compliance assets.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
