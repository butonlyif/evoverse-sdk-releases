EvoVerse SDK in Depth

EvoVerse SDK In Depth

Version: v1.0.0　Last updated: 2026-09-30 Supported platforms: Trae IDE (recommended) / VS Code 1.80+ · Windows

This document is the product-level description of the EvoVerse SDK: what it is, which components it consists of, what it can do, and how its capabilities connect. For step-by-step procedures, use it together with the User Manual, the WS-E1 SD-to-CSI-2 project tutorial, and the two controlled Skill documents.

Design iteration control (2026-09-13)

The SDK uses server-side design iteration as the authorization source for reliability. Trae natural language and Workbench Control read the same project_next current-action envelope; a new conversation restores the revision, the current iteration, the recommended action, user decisions, evidence boundaries, and the receipt from the envelope instead of keeping a separate chat-state copy.

The design, system-integration, and project-generation chains use registrable recovery contracts. Contracts are enforced at service-call time; any non-terminal state must expose a real, plannable completion or quarantine exit. If the control plane detects a managed Intent/Integration that has not terminated but has no executable action, project_next returns a revision-bound descriptor with a single recovery.open; once that descriptor is persisted verbatim, only recovery exits such as recovery.quarantine are exposed while normal business actions stay frozen. Recovery states and attempts are appended to the fact history, and quarantine preserves the trusted baseline, the facts, and the failure evidence—it does not count as success. Natural language only selects the recovery target; the server-side descriptor spells out keep/replace/discard/steps/successChecks. Abandoning the initial system design closes the Intent and the corresponding integration directly, without fabricating a worktree execution.

System integration follows a commit-ahead-of-facts Saga. Every deferred feature merge persists the request, the branch head, and the verification summary before the commit, and binds the exact HEAD/tree after it; the baseline is fully constructed in quarantined staging and published through a single pointer, with the promotion/integration/execution facts committed under one batch marker. If the process is interrupted after the commit, the next state read completes the facts only when the Git and journal identities match exactly—the merge is never repeated; if the facts are committed but the queue is not yet updated, the registry converges automatically.

Free-form development remains available and ordinary Builds are not constrained by reliability gates; as soon as a controlled asset changes, the current iteration shows UNVERIFIED_CHANGES. Bringing the change under management freezes the change set, computes the exact DAG impact, quarantines the candidate, and then requires rtl.task.qualify test-asset qualification, Design Assurance, six-layer simulation, and promotion in that order. Qualification identities and verdicts are held by the Verification Service—the host only submits execution inputs—and the previous baseline is never overwritten; audit receipts are always kept.

Reliable external calls go through MCP only. One transport failure allows exactly one automatic recovery; after that, the required tools must be verified and the iteration/task/state/candidate/spec digests reconciled. Only read-only, idempotent, or confirmed-not-executed requests may be replayed safely. When reconciliation is impossible or the connection drops again, the flow fails closed—there is no CLI business fallback. Automated fixtures, real RTL simulation, Efinity Native Build, programming, and physical hardware each constitute an independent evidence boundary.

Discovery for Icarus/Questa does not conclude availability from "the exe exists / the version string is readable": the same provider command contract runs a minimal compile, execute, and event-parse smoke test. When a selected toolchain fails, a TOOLCHAIN_INVALID stop receipt is written and project_next returns WAITING_FOR_USER with toolchain.reprobe / toolchain.reselect—no silent fallback, and no simulation evidence is produced.

1. What the SDK is

The EvoVerse SDK is an FPGA and SoC development workbench running inside Trae / VS Code. Built around Efinix Titanium FPGAs (WS E1/E3 boards), it provides a complete closed loop from project creation → RTL authoring and simulation → build and reports → timing closure → programming and debug → RISC-V software, and opens the same flow to the command line and AI agents through its CLI and MCP.

It solves three problems:

Pain point How the SDK answers it
Fragmented FPGA toolchains (editor, simulator, vendor IDE, and scripts each going their own way) All day-to-day operations happen in one IDE; vendor tools are invoked only in the background
AI-generated code that "looks right" but cannot be verified Deterministic tool gates: simulation, style checks, builds, and timing diagnostics all produce reproducible evidence
Board materials, IP, and project configuration scattered everywhere A single-source-of-truth Catalog: boards / carriers / reference designs / IP are registered and referenced in one place

2. Design principles

  1. Determinism first. Every critical operation (build, simulate, check, diagnose) invokes real tools and retains evidence (reports, waveforms, diffs); an AI's claim of "done" must be bound to that evidence.
  2. Single source of truth. Board specifications, IP documentation, and reference designs are maintained exactly once (in the Catalog); the documentation portal renders with the delivery package, and board documents sync to the local machine with the Catalog—no copies are spawned.
  3. Core + Adapter layering. The SDK core extension provides the generic shell and shared facilities; each target platform gets one Adapter extension, installed and evolving independently. Platforms you do not use consume no resources and never appear in the UI.
  4. Agent-native. An MCP server, a structured plan channel (generate → preview → confirm → transactional apply), and Skill packages let an LLM operate on the project within controlled boundaries.

3.3 How the core and Adapters relate

  • Adapters register capabilities with the core's AdapterRegistry (build / timing / debug / program / software / ip / designApi / workspace)
  • A user request (such as Build) is routed by the core to the matching Adapter; the Adapter invokes the real toolchain (for example efx_run --flow compile) and posts structured results back to the Workbench for display
  • Each Adapter owns its Workbench tab content; the core handles loading, resource injection, and the unified look-and-feel

6. Typical development loops

6.1 The FPGA mainline (first run)

Set Up → describe the project goal in Trae → confirm the action recommended by Control → write RTL → Simulate (inspect the waveform)
→ Check Code Style → Build (read the report) → Program FPGA (watch the board)

For a complete first-run experience, follow the WS-E1 SD-to-CSI-2 project tutorial: discover materials and freeze the specification first, then generate and verify the RTL, and finally integrate and build. You never leave the IDE.

6.2 The timing-closure loop

Build → Diagnose Timing (the 12 rules report cause and confidence)
→ datapath tracing / pipeline analysis to locate the bottleneck
→ adjust the build strategy or modify the RTL → Build again to verify WNS/TNS

Every step is backed by native report evidence; AI suggestions should carry the current RTL, SDC, and path context, and the WNS/TNS results of a fresh Build are the final verdict.

6.3 The on-chip debug loop (v0.9.0, pure CLI)

  1. Mark signals: right-click in the editor and choose Add Signal to Efinity Debug (writes (* mark_debug *))
  2. Build (auto-instantiation generates the debug cores) → Program FPGA
  3. Scan Device: FTDI/JTAG scan showing the core connections
  4. Configure the trigger (compare / pattern / mask) → Trigger or Immediate Capture
  5. The VCD is generated and opened automatically; VIO supports reads and safe writes (a write requires a confirmation receipt)

Everything is bridged through evoverse_dbg.py to the Efinity efx_dbg API; the Efinity GUI never opens. You can also describe a debug intent in natural language to generate a plan that is applied transactionally after preview and confirmation.

6.4 The RISC-V software loop

Confirm the Sapphire SoC / memory / debug interface → create or refresh the software project in the SW tab → Regen BSP
→ Build Software → download according to what the project actually supports → GDB debugging

6.5 Vibe coding (agent-assisted)

`/evoverse-design-spec` confirm the simulation level and draft the specification within the level budget → approve the specification
→ `/evoverse-rtl` deliver candidate RTL → Design Assurance and level-limited simulation evidence
→ native Efinity Build

On the reliable path, every agent claim of "passed/promoted" is bound by a control-plane action receipt to the scope, the real project diff, Design Assurance, and simulation evidence. The simulation level precedes the specification (the user chooses): once a reliable iteration is established, the simulation level must be confirmed before spec.draft drafts the specification (simulation.profile.select; otherwise the control plane blocks drafting with SIMULATION_PROFILE_REQUIRED). The AI recommends one of the three levels FPGA_FUNCTIONAL / FPGA_INTEGRATION / HIGH_ASSURANCE (or an explicit user CUSTOM) under fixed risk rules; the user makes the choice. Selecting below the recommended minimum requires acceptedRisks to be recorded, and exceeding the level budget requires reconfirmation. The specification is written to the budget of the selected level, and the level is bound to the design iteration. The packagePath submitted by spec.draft must point to a sealed executable-2.0 specification package directory: the server seals it and records a specPackageDigest as its trusted identity, while specification.md is deterministically rendered by the sealing script for human review only. A bare Markdown file is rejected, with the workspace, the input/parsing paths, and the reason returned; legacy Markdown specifications must be re-drafted from the executable package and migrated. candidate.deliver validates the complete HDL/include/module/testbench closure before the manifest and the facts are persisted; a failure forms no authoritative candidate, and it is safe to retry after the fix. verification.simulate derives the candidate, the source closure, the Test IR, and the spec digest from server-side state and runs module/Intent-scope verification in the feature worktree; a local pass only moves the candidate to READY_FOR_INTEGRATION. Compile or elaboration failures are recorded as the repairable CANDIDATE_COMPILE_FAILED; only a missing backend or vendor model is CAPABILITY_UNAVAILABLE. The mainline system-integration Intent then runs composite specification checks, system simulation, and document confirmation, and only when all of them pass is the baseline promoted atomically. A level-limited simulation pass (FPGA_FUNCTIONAL_PASS and the like) does not change the evidence boundary: NATIVE_BUILD_PENDING and BOARD_VALIDATION_REQUIRED are reported independently, automated fixtures are not real Questa evidence, and Efinity Native Build, timing, programming, and on-board results still have to be reported separately (build.native / hardware.program / hardware.validate).

6.6 Multi-Intent worktrees

  • Before a project baseline exists, the first design is itself the INITIAL_DESIGN system-integration Intent, completing the full specification, generation, system simulation, and document confirmation on the mainline; it has no feature worktree. Until it finishes, a second Intent is blocked with BASELINE_INITIALIZATION_IN_PROGRESS.
  • Once the baseline exists, the SDK creates a codex/intent-<id> branch and a dedicated Git worktree per Intent; the active limit is fixed at 4.
  • After verification and commit, a feature Intent only reaches READY_FOR_INTEGRATION and enters a FIFO queue. The mainline creates one worktree-less system-integration Intent at a time, absorbs the branches with merge --no-commit --no-ff, composes the system specification, and runs system simulation and document verification; only on success does it commit, promote the baseline, and clean up the worktree.
  • Conflicts or failed system validation abort the uncommitted merge, restore a clean mainline, and keep the branches/worktrees. The main Workbench shows Feature Intents and System Integration separately; an Intent worktree shows only itself.

6.7 Module candidates and controlled integration (module contracts)

Reliable module iteration freezes one more module contract boundary beneath the specification: qualify the contract first, deliver candidates next, and let controlled system integration promote the single baseline last.

  • The contract and CONTRACT.md: the executable specification package embeds the canonical module contract (the closed RTL/test inventory, the top module, the dependency summary, budgets, and candidate-writable paths) and deterministically renders CONTRACT.md for human review. The document always presents system/internal module relationships, interfaces, clock/reset/state and data structures, algorithm formulas and pseudocode/pipeline stages, budgets, requirements traceability, simulation and evidence definitions (simulation boundaries, clock/reset stimulus, BFM roles, normal/boundary/exception/recovery scenarios, oracles, and coverage), harness scenarios, and risks plus already-decided items. The machine contract is the single source of truth; the document exists only for review approval. Missing sections, stale content, or inconsistencies all block qualification, and approval binds both moduleContractDigest and contractDocumentDigest.
  • Contract qualification: contract.qualify (moduleId + the user-approved approvedDocumentDigest) runs the deterministic qualification engine—structural completeness; requirement/clause/orphan-test traceability; simulation-definition completeness; interface/clock/reset/budget compatibility with the system; and feasibility-contradiction checks. Outstanding engineering trade-offs produce a DecisionRequest for the user to decide; the agent never chooses on their behalf. Qualification includes the Contract Harness: a real simulation provider compiles and elaborates the contract-declared sources in isolation under a frozen ExecutionIdentity, producing only CONTRACT_HARNESS evidence—which proves compilability/elaboratability and nothing more; it is not algorithm, Native Build, programming, or hardware evidence. On success the intent records CONTRACT_QUALIFIED; any change to the contract digest invalidates existing harness runs, candidates, and unpromoted composite evidence, forcing requalification. Without qualification, candidate.deliver is blocked by CONTRACT_QUALIFICATION_REQUIRED; a Discovery Spike produces no reusable PASS.
  • RTL Module vs. Qualification Component: an RTL Module is the single top design unit declared by the contract; the unit of qualification and integration is the Qualification Component, which may consist of multiple genuinely cycle-coupled RTL Modules. Cross-component references into private hierarchies are rejected when the candidate is frozen.
  • Readiness is separated from promotion: after a MODULE candidate is delivered, candidate.promote only reaches READY_FOR_INTEGRATION (the Workbench shows candidate readiness); it does not install a baseline. The system-integration Intent freezes the components, interfaces, and topological composition, completes system simulation and the Native Build gates required by policy, and then the control plane performs the sole promotion to a BASELINE_PROMOTED baseline. The state ladder is QUALIFIED → READY_FOR_INTEGRATION → INTEGRATION_CANDIDATE → BASELINE_PROMOTED. No in-place fixes happen inside integration staging—pre-integration failures and post-promotion defects are both handled through a new candidate, a new composition, and a new baseline, and historical facts are append-only.
  • Evidence boundary (macOS / Efinity): the control plane and the Icarus simulation chain support full development and verification on macOS; until Efinity Native Build, programming, or hardware validation has actually run, honest states such as NATIVE_BUILD_PENDING are kept. Workbench Control presents each intent's evidence state independently as an evidence vector (seven fields: assurance, moduleSimulation, systemSimulation, nativeBuild, programming, hardwareValidation, maturity), and no simulation pass is ever upgraded into a native or hardware conclusion.

7. Project layout and the Catalog

7.1 Project directory (after skeleton generation)

my-project/
├── evoverse-project.json   # Project manifest: board, source files, IP, software applications
├── rtl/                  # RTL sources (the top module lives here)
├── sim/                  # Simulation testbenches and scripts
├── constraints/          # SDC / ISF constraints
└── soc/                  # RISC-V SoC configuration and software applications (optional)

7.2 Catalog layout (single source of truth)

${EVOVERSE_HOME}/catalog/
├── boards/ws-e1/            # E1 core board: specification, datasheet, pinout
│   ├── carriers/ws-e1-base/ # E1 Base carrier: specification and carrier materials
│   └── ...
├── boards/ws-e3/            # E3 board
├── demos/                    # Reference demos fetched via Sync Catalog
└── ips/                      # General-purpose IP fetched via Sync Catalog

The Catalog syncs into the local runtime via EvoVerse: Sync Catalog; board specifications, demos, and IP are traceable material sources. A new project must be generated from a frozen specification—copying an entire reference project as a baseline is not allowed.

9. Upgrades, uninstallation, and FAQ

  • Upgrading: the core and the installed Adapters stay on the same version number (for example, all at 0.9.0); when upgrading the core, upgrade the Adapters at the same time.
  • Uninstalling an Adapter: the core keeps working; the corresponding Workspace tabs disappear and everything else is unaffected.

Q: I only do FPGA development—do I need to install the RK3588 Adapter? No. An uninstalled Adapter consumes no resources and never appears in the UI.

Q: Can both Adapters be installed at the same time? Yes. A Workspace switcher appears at the top of the sidebar, and the System root gives a cross-platform overview.

Q: Does on-chip debug require the Efinity GUI? No. Since v0.9.0 the debug flow is pure CLI throughout and only calls the efx_dbg API in the background.

Q: Do I need to reinstall an Adapter after upgrading Efinity? Adapter versions are independent of the Efinity version; an occasional major Efinity release may require an Adapter update—defer to the Release Notes.
