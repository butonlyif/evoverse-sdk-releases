SDK Function Reference Manual

EvoVerse SDK — User Manual

Version: v1.0.0 Last updated: 2026-09-30 Applies to SDK version: v1.0.0 Supported platforms: Trae IDE / VS Code 1.80+ · Windows · macOS · Linux

Agent Runtime (v0.7.1+): Timing Diagnosis, Build Report, and the native @evoverse share one persistent session. The model can be the host vscode.lm or an OpenAI-compatible endpoint; the model ID must be configured explicitly, remote content can be previewed and confirmed before it is sent, and the API Key is stored only in SecretStorage. Prerequisites: Python 3.11+ (auto-detected), Efinity 2026.1+ (required for builds and programming), Icarus Verilog or QuestaSim (required for simulation)

Design-flow selection (2026-09-30): Trae natural language and Workbench Control share the server-side current-action envelope. Reliable/free mode is stored per design iteration; it is not a project-wide switch. A new conversation restores the current revision, the recommended action, and the evidence boundary from project_next. Free mode does not block ordinary Builds, but controlled changes show UNVERIFIED_CHANGES; at any time you can choose "bring the current changes into the reliable flow" to incrementally re-run the affected gates.

If the reliable flow hits an MCP transport interruption, it recovers automatically at most once and re-checks capabilities and server-side digests before continuing; when the state cannot be reconciled, it stops instead of falling back to running through the CLI. Assurance, simulation, Native Build, programming, and on-board results are reported separately—a PASS at one boundary never substitutes for another.

If design, system integration, or project-file generation is interrupted, simply state in natural language "what to keep, what to replace, what to discard, and where you want to return to". The Agent shows the recovery description the server generated for the current revision; after you confirm, it executes one recovery step at a time and re-reads the state. If project_next returns RECOVERY_REQUIRED with recovery.open, the Agent must submit the action's inputPreview verbatim and must not edit the recovery scope; after the record is persisted, execute the server-provided recovery.quarantine. Quarantine preserves the trusted baseline, the facts, and the failure evidence and releases the affected scope, but it does not count as task success. Do not delete .evoverse state by hand. An initial design can also be safely abandoned and the Intent re-created.

System-integration commits are recoverable transactions: if the IDE, the Agent, or a process is interrupted after the merge, reopening the project or reading the state triggers identity reconciliation. Only when the commit, tree, request, and verification digests all match are the baseline and the completion facts filled in; the system never repeats the merge and never treats half-committed facts or a half-generated baseline as success. On an identity conflict it stops and preserves the scene—do not delete .evoverse or the Git journal by hand.

If the real smoke test, license check, startup, compilation, run, or event parsing of the selected Questa/Icarus fails, the flow stops at WAITING_FOR_USER. After fixing the environment, choose to re-probe, or explicitly reselect the toolchain; the system does not silently switch backends or keep producing PASS.

5. Project management

5.1 Create a project with natural language

State the goal, the board, the carrier, and the Catalog materials you need in Trae Chat. The Agent first calls project_status and project_next and shows only the recommended action, the required user decisions, and the evidence boundary from the server envelope. Only after you confirm does it submit project_execute with the envelope's actionId and expectedRevision.

After execution completes, project_next must be re-read to verify the new revision and the next recommended action. If the response is interrupted, first verify the receipt, then decide whether to retry with the same action identity; never create a new request to guess the state.

Creating a project produces a manifest, constraints, and a minimal RTL/simulation skeleton. When you need a reference design, have the Agent list the available materials from the synced Catalog with their provenance; do not hard-code a fixed Jacket name as an entry point assumed to exist for every customer.

Free-form development can still edit files directly and run ordinary Builds; only after the current iteration opts into reliable mode and the user selects FPGA_FUNCTIONAL, FPGA_INTEGRATION, or HIGH_ASSURANCE via simulation.profile.select do candidates, simulation, and promotion become gated by evidence. Simulation, Native Build, Program, and Hardware Validation are recorded separately; boundaries that have not run explicitly show NOT_RUN / BOARD_VALIDATION_REQUIRED.

5.2 Take over an existing project

Describe the existing project directory and your takeover goal in Trae Chat. The Agent first reads project_status / project_next and submits only after confirming that the server recommends asset.observe, asset.adopt, or another legitimate action; upgrading a native Efinity project is still done by EvoVerse: Adopt Project (upgrade native Efinity).

External project support: even without evoverse-project.md, as long as the directory contains Efinity's <project>.xml file, Build / Report / Diagnose / Program and related operations all work normally.

5.4 Sync project files

Command: Toolchain: Sync HDL Sources to XML

Scans .v/.sv/.vhd files under rtl/, ip/, hdl/, and src/, plus the IP instances under ip/, and syncs them automatically into the project XML's <efx:design_file> and <efx:ip_info> lists. Inside IP directories, only design sources declared by external_source_* are synced; external_example_* are vendor example projects and never enter the user design-file list.

CLI equivalent:

evoverse sync-sources --apply        # scan and write the XML
evoverse sync-sources                 # preview only (dry-run)
evoverse sync-sources --dir rtl --dir my_ip_dir  # specify scan directories

6. Catalog material management

6.1 Catalog structure

The Catalog is the SDK's material hub and uses a five-layer model:

Layer Type Location Description
L1 Board catalog/boards/<id>/ FPGA module with pins and IO constraints
L2 Carrier .../carriers/<carrier-id>/ Base carrier board
L3 Jacket .../carriers/<carrier-id>/jackets/<id>/ Function mezzanine
L4 IP catalog/ips/<id>/ RTL module + register table
L5 Demo .../carriers/<carrier-id>/demos/<id>/ Complete example project

6.2 Sync the Catalog

Command: EvoVerse: Sync Catalog

On first install the Catalog is empty and the CLI, MCP, and UI all clearly return CATALOG_NOT_INSTALLED. The customer must first accept the personal-GitHub-account read-only invitation to the unified private Catalog repository and complete local authentication via Git Credential Manager or the GitHub CLI. The repository URL is visible to VSIX users, but the content remains protected by GitHub authorization; team-shared PATs are forbidden.

Sync pulls the latest official catalog-v* tag from the remote and mirrors the official content over the local catalog/ (for same-named official entries, the remote version wins); a network or permission failure never affects existing local content.

Customers may add their own Boards, IPs, Carriers, Jackets, or Demos under evoverse.home/catalog/; the CLI, MCP, and the workbench discover them all from this single root. Sync never deletes local-only entries—any directory or file at any layer that the official release does not have (for example catalog/boards/customer-board/ or catalog/ips/customer-ip/) is kept as-is. Note: if a customer material has the same name and path as an official entry, the official version overwrites it during sync, so use a separate directory and ID for customer materials.

CLI equivalent:

evoverse sync --json
evoverse catalog status --json

7.3 Build flow details

v0.7.1 behavior change (see Appendix A.A1): the SDK no longer sanitizes the project XML automatically and no longer runs the structural health check automatically before a build; the HDL file watcher no longer auto-runs sync-sources. All source syncing and health checks are now manual (see §5.4 and §10.6). AI diagnosis results are no longer applied automatically; user confirmation is required.

In CLI mode the SDK executes the following steps:

1. Preprocessing (Pre-PT)
   ├─ Parse the project XML
   └─ Convert base.peri.isf → <design>.peri.xml (PT conversion)

2. Synthesis — efx_map
   ├─ Read the design file list (<efx:design_file>)
   ├─ Run Verilog/SystemVerilog synthesis
   └─ Write the mapped netlist to work_syn/

3. Place & Route — efx_pnr
   ├─ Import the mapped netlist
   ├─ Place logic cells
   └─ Route connections

4. Bitstream generation — efx_pgm
   ├─ Generate the .bit file
   └─ Generate the .hex file

5. Post-processing
   ├─ Parse the outflow/ reports
   ├─ Parse into an in-memory BuildSummary and update the report view
   └─ Update the status bar (restored from native reports when the project is reopened)

12.5 Design Assurance and rule management

The style checker in 12.1–12.4 is heuristic, based on the Efinity coding-style documents; the Design Assurance in this section is a separate deterministic rule engine (sdk/design-assurance) that checks RTL structural rules and protocol contracts and reports three states (pass / fail / incomplete—missing evidence is incomplete, not pass). The two do not affect each other.

Command-line check:

# Check a project (RTL sources are auto-discovered by default and the rtl-baseline rule pack runs; testbench-style files are skipped by default)
evoverse assurance check ./my-project

# To also include testbenches (tb_*/sim/) in the analysis
evoverse assurance check ./my-project --include-testbench

# Restrict the analysis to sources under rtl/
evoverse assurance check ./my-project --include-glob 'rtl/*.sv'

# View the rule catalog and switch states
evoverse assurance rules --format text

rtl-baseline@1 analyzes only the synthesizable subset; testbench files (initial/$task/#delay/@event etc.) are out of scope, and auto-discovery skips them by default via **/sim/**, **/testbench/**, **/tb/**, tb_*.*, *_tb.*, sim_*, test_*; internally the scanner skips whole initial ... end blocks as testbench code (recorded as info, not counted as unverified). MCP assurance_check likewise supports the three inputs include_testbench / include_glob / exclude_glob.

Exit codes: 0=pass, 1=fail, 2=incomplete, 64=usage/configuration error. For the detailed contract (request JSON, evidence, exceptions) see docs-en/design-assurance/README.md.

Rule manager (Rule Manager UI)

Entry point: Welcome page → Assure card → Rule Manager (or the command EvoVerse: Assurance Rules).

Manages the switches of all assurance rules and applies to every check (the CLI / MCP are equally affected):

Action Description
Master switch (All checks) When off, all checks are skipped and the report becomes incomplete (it does not masquerade as pass)
Rule-pack switches Enable/disable whole packs: rtl-baseline@1 / amba.axis@1 / custom@1
Single-rule switches Disable one rule at a finer granularity than disabling the pack
Add a custom rule Declarative regex lint: rule id, severity (error/warning/info), description, Python regex pattern; matched lines are reported as violations
Delete a custom rule ✕ in the custom-rule list deletes it
Save / Reload / Reset Saves to the global configuration and validates via an engine read-back; Reset restores the all-enabled default state in one click

The configuration persists in <EVOVERSE_HOME>/assurance-rules.json (the path is shown in the panel header) and can also be edited by hand—see the "Rule management" chapter of docs-en/design-assurance/README.md for the format and constraints.

14.8 Common issues

  • "No native peri.xml exists": the project has never run Pre-PT; click Rebuild to trigger one efx_map run.
  • "GPIO exists" but it is missing from the inspect list: the base ISF and the current peri.xml are out of sync; rebuild peri.xml from base.peri.isf.
  • Apply fails although the ISF is fine: check the Pre-PT log in the EvoVerse output panel; the DesignAPI flow first runs a full PT to generate peri.xml—if the Efinity installation is broken or the license has expired, PT fails.
  • The block-type list is missing the one I want: the doc/pdf/efinity-python-api.pdf in the current Efinity installation is authoritative; the SDK keeps no copy of the properties.

15.7 Specification-driven RISC-V software verification loop (in development on the v0.9.x branch)

Unlike the free-form software development of 15.1–15.6, this loop is driven by a frozen executable specification package: software candidates, BSP binding, host tests, cross-compilation, promotion, and board tests are all receipt-based; any step that cannot be bound to the same specPackageDigest is rejected.

Command chain (source CLI): the expectedStateDigest in the legacy software-chain input is read only as a historical compatibility alias; new control-plane write operations uniformly use expectedRevision.

evoverse verification software-task-start ...     # spec-derived writable/promotable sets
evoverse verification software-task-bind-bsp ...  # adapter inspectBsp; only MATCH may bind
evoverse verification software-task-prepare ...   # writes engine-derived generated files + application sources
evoverse verification software-task-check-interface ...
evoverse verification software-task-test-host ...
evoverse verification software-task-build ...     # validates ELF class/memory regions/unresolved symbols
evoverse verification software-task-promote ...
evoverse verification fpga-milestone ...          # RTL_PROMOTED→INTEGRATION_READY→BUILD_COMPLETE
evoverse verification software-task-board-test ...  # PASS or HARDWARE_UNAVAILABLE

States: BUILD_COMPLETE (next step RUN_PROJECT_REVIEW) → REVIEW_READY (evidence footer hardwareStatus ∈ {NOT_RUN, PASS, FAIL, INCOMPLETE} with evidence covering every recorded milestone).

The "reliable design and evidence" domain is the core capability for reliable code generation: the control plane keeps only 4 stable interfaces—project_status / project_next / project_execute / evoverse_health. project_next returns the current action envelope (recommended action, user decisions, evidence boundary, recovery info, and terminalState); exactly one action advances at a time: read the current revision → verify the envelope's {actionId, intentId, expectedRevision} → submit project_execute → re-read project_next and the new revision. If a response is lost, first verify the receipt, then decide whether to retry with the same identity; advancing from memory is not allowed.

Execution identity is unified as ExecutionIdentity: the UI shows only the abbreviated executionIdentityDigest read-only; users are never asked to fill in component digests such as candidate/spec/Test IR/environment. Providers verify the real tool environment at the prepare → freeze → execute boundaries; status/next/Workbench projections reuse sealed manifests and receipts instead of re-hashing the candidate tree or large images. File bytes are still re-verified at trust boundaries—freeze, execute, promote, install, and release—so what is reduced is redundant computation, not integrity checking.

The simulation profile precedes the specification (user choice): once a reliable iteration exists, and before spec.draft starts drafting, the control plane requires the simulation profile to be confirmed first (otherwise drafting is blocked with SIMULATION_PROFILE_REQUIRED). The AI recommends one based on fixed risk rules, and the user chooses: FPGA_FUNCTIONAL (single-clock simple functions such as a stopwatch or blinking LED—at most 3 core blocking scenarios + 1 key boundary + 1 integration smoke), FPGA_INTEGRATION (protocol/FIFO/CDC/backpressure/cross-line cross-frame state, such as a windowed ISP or DMA), HIGH_ASSURANCE (high-speed complex protocols, memory control, irreversible control, safety-related), or CUSTOM to explicitly divide blocking/deferred obligations. Choosing below the recommended minimum requires recording acceptedRisks; exceeding the profile budget forces a re-confirmation from the control plane. The specification is written within the selected profile's budget; the profile binds to the design iteration, and changing it requires a new iteration. The packagePath submitted by spec.draft must point to a sealed executable 2.0 specification-package directory: the server seals it and records the specPackageDigest as the reliable identity; specification.md is deterministically generated by the sealing script and is for human review only; Markdown files are rejected, and legacy Markdown specifications must be re-drafted and migrated from the executable package. Simulation passes are profile-qualified (FPGA_FUNCTIONAL_PASS etc.), and deferred items never produce fake PASS; NATIVE_BUILD_PENDING / BOARD_VALIDATION_REQUIRED and the simulation status are always reported separately—a functional-level simulation pass does not mean a native-build or hardware pass.

In reliable mode, candidate.deliver only freezes the candidate—it does not promote the baseline—and runs RTL Design Assurance (structure, clocks, reset, CDC, FSM, FIFO, completeness, and protocol contracts); the service first checks the complete HDL/include/module/testbench closure, writes no candidate facts on failure, and can be retried safely after a fix. verification.simulate explicitly selects the iverilog or questa backend; the required identity digests are generated server-side from the frozen state, and it runs layer by layer—elaboration, module-smoke, requirement, module-regression, subsystem, system—stopping at the first failing layer. Only when the current candidate's simulation achieves a valid PASS and satisfies qualification does candidate.promote install the baseline. On DUT_FAIL or CANDIDATE_COMPILE_FAILED, the Agent records the failed requirements and a bounded diagnosis; a single well-evidenced cause may be fixed once in a targeted way, while multiple causes or a still-failing fix call for engineering options (rationale, next checks, cost, and uncertainty) for the engineer to choose from or answer with their own judgment. CAPABILITY_UNAVAILABLE is reported only when a simulator or a vendor model is missing. Human judgment is a hypothesis to be verified; when new evidence conflicts, it must be explicitly fed back and renegotiated—it must never be treated as PASS. An automated fixture passing is not the same as real Questa, Efinity Native Build, programming, or on-board passing—the evidence of build.native, hardware.program, and hardware.validate is mutually independent and must be reported separately.

Module contracts and controlled integration (module candidates): a reliable module iteration freezes one more layer beneath the specification—a module contract. The executable specification package embeds the canonical module contract (closed RTL/test lists, top, dependency digests, budgets, and candidate-writable paths) and deterministically renders the CONTRACT.md for human review: it consistently presents system/internal module relationships, interfaces, clock/reset/state and data structures, algorithm formulas and pseudocode, budgets, requirement traceability, simulation and evidence definitions (simulation boundaries, clock/reset stimuli, BFM roles, normal/boundary/exception/recovery scenarios, oracles and coverage), Harness scenarios, plus risks and decided items; the machine contract is the single truth—missing, stale, or inconsistent document sections block qualification. After the user approves CONTRACT.md, contract.qualify (moduleId + approvedDocumentDigest) completes contract qualification: structural completeness, requirement/clause/orphan-test traceability, simulation-definition completeness, and interface/clock/reset/budget system-compatibility and feasibility checks; unresolved trade-offs produce DecisionRequests decided by the engineer, never auto-chosen by the Agent. Qualification also compiles and elaborates the contract-declared sources in isolation on a real simulation provider via the Contract Harness under the frozen execution identity—that evidence proves only compilability/elaboratability and constitutes no algorithmic-functional, Native Build, programming, or hardware evidence. A contract-digest change invalidates existing Harnesses, candidates, and un-promoted combination evidence and forces re-qualification; without qualification, candidate.deliver is blocked by CONTRACT_QUALIFICATION_REQUIRED, inputs labeled Discovery Spike are rejected at planning time, and no reusable PASS is produced. The RTL Module is the contract's single top design unit; the unit of qualification and integration is the Qualification Component, which may contain multiple cycle-coupled RTL Modules, and cross-component private-hierarchy references are rejected at candidate freeze. After a MODULE candidate is delivered, candidate.promote only reaches READY_FOR_INTEGRATION (the Workbench candidate row shows readiness) and no longer installs the baseline directly; the system-integration Intent freezes components, interfaces, and the topology combination, and after completing the system simulation and the policy-required Native Build gates, the control plane is the only path that promotes the BASELINE_PROMOTED baseline (state ladder QUALIFIED → READY_FOR_INTEGRATION → INTEGRATION_CANDIDATE → BASELINE_PROMOTED). No in-place fixes inside integration staging: pre-integration failures and post-promotion defects are all handled through new candidates, new combinations, and new baselines, with append-only historical facts. A macOS session can fully verify the control plane and the Icarus simulation chain; when Efinity Native Build, programming, and hardware validation have not actually run, honest states such as NATIVE_BUILD_PENDING are kept, and the Workbench evidence vector (the seven fields assurance / moduleSimulation / systemSimulation / nativeBuild / programming / hardwareValidation / maturity) is presented independently with no cross-upgrading.

Q1: No EvoVerse icon after installation?

A: Press Ctrl+Shift+P → type EvoVerse: Set Up → confirm the initialization. If it still does not appear, press Ctrl+Shift+P → Developer: Reload Window.

Q2: The build reports "Efinity not found"?

A: Open Settings (Ctrl/Cmd + ,), search for evoverse.efinityPath, and enter the Efinity installation path, for example: - Windows: C:\Efinity\2026.1 - Linux: /opt/Efinity/2026.1

Q3: Simulation reports "iverilog not found"?

A: Set evoverse.iverilogPath. On Windows, download the precompiled package from the Icarus website or install via scoop install iverilog / choco install iverilog.

Q4: How do I migrate an existing Efinity project to EvoVerse?

A: Open the project directory and run EvoVerse: Adopt Project (upgrade native Efinity). The SDK generates evoverse-project.md automatically and registers it with the IDE. You can also just open it directly—as long as the directory contains <project>.xml, Build/Report/Diagnose/Program all work normally.

Q5: The Workbench IP tab shows "No instances found"?

A: IP instances are discovered in two ways: (1) the <efx:ip_info> tags in the project XML; (2) subdirectories under ip/. If you added an IP but it does not show up, click Sync Project Files.

Q6: The timing diagnosis panel shows "No timing data"?

A: Timing diagnosis requires one complete build first. After the build, the SDK parses the timing report in outflow/. If the build failed or P&R never ran, there is no data to analyze.

Q7: The evoverse CLI command is not found?

A: The CLI is installed to ~/.evoverse/runtime/ during Set Up. Make sure that directory is in your PATH, or use the full path: ~/.evoverse/runtime/evoverse.

Q8: How do I update the SDK to a new version?

A: 1. Obtain the new VSIX file 2. Extensions panel → find EvoVerse SDK → uninstall 3. Install from VSIX... → select the new VSIX 4. Reload Window

Q9: What works on macOS?

A: macOS supports development (code authoring), Icarus simulation, AI collaboration, CLI queries, Catalog management, and document viewing. Icarus iverilog / vvp are executed directly through argument arrays; paths with spaces and non-UTF-8 tool output are handled with macOS/POSIX semantics, with no cmd.exe dependency. The host and deployment are cross-platform (the customer package ships both deploy.ps1 and deploy.sh, and the extensions are the same set of VSIXes); full Efinity build/programming still requires a Windows or Linux environment.

Q10: How does a team sync the Catalog?

A: Do not put the runtime catalog/ directory back under version control in the SDK or customer projects. Each member obtains read-only access to the unified private Catalog with their own GitHub identity, completes local authentication, then runs EvoVerse: Sync Catalog; use evoverse catalog status --json to align the version, commit, and tree digest.

Q11: Can multiple Intents advance at the same time?

A: Yes, but the first design is itself the INITIAL_DESIGN system-integration Intent on the mainline, with no feature worktree; no second Intent may open until it completes the full specification, generation, system simulation, and document confirmation and establishes the first baseline. Afterwards at most 4 feature Intents run concurrently, each with its own branch and worktree; passing local verification only shows "Module verified, waiting for system integration". The mainline Workbench splits into Feature Intents and System Integration: system integration absorbs one branch at a time in FIFO order, and promotes the baseline only after re-confirming the composite specification, system simulation, and documents. A conflict or failed system validation aborts the merge and keeps the branch/worktree; after entering some Intent's worktree, Current Intent still shows only that Intent.

Appendix A: Version evolution history

Records the key behavior changes mentioned in this manual and the versions that introduced them, for reference during upgrades. All "behavior change" notes in the chapters above refer to this appendix.

A1. Build and health-check behavior changes (v0.7.1)

v0.7.1 (main release 2026-07-15, repackaged 2026-07-18) made four major adjustments to the build flow and the project health check, aiming to reduce the SDK's implicit background modifications to user projects:

Change Before v0.7.1 Since v0.7.1
XML sanitize The SDK sanitized the project XML automatically (could modify entries such as <efx:design_file>) No longer sanitized automatically; what you edit is what you get
Structural health check Ran automatically before Build and auto-fixed problems No longer runs before Build; moved to the manual §10.6 command
HDL watcher auto sync-sources HDL file changes were synced to the project XML automatically No longer auto-synced; trigger manually via §5.4
SDC pre-check blocking builds A missing/empty SDC blocked Build directly The check was folded into the health check, manually triggered, and does not block builds

Where it applies: §7.3 Build flow details, §7.5 SDC pre-check, §10.6 Project health check.

A2. AI diagnosis behavior changes (v0.7.1)

Since v0.7.1, AI diagnosis has moved from "auto-fix" to "advisory suggestions only", preventing a background Agent from rewriting RTL without user confirmation:

Change Before v0.7.1 Since v0.7.1
Persistent AI session Timing Diagnosis, Build Report, and @evoverse each used a separate session All three share one persistent session; AI context carries across panels
Auto-applying fixes AI diagnosis could modify RTL directly AI suggestions are advisory only; RTL changes need manual user action or Agent confirmation
Remote content preview No unified rules for API Keys and remote content Remote content can be previewed and confirmed before sending; the API Key is written only to SecretStorage
Model selection The SDK defaulted to the first available model evoverse.model.modelId must be configured explicitly; the host vscode.lm or an OpenAI-compatible endpoint may be chosen

Where it applies: §10.1 Timing diagnosis, §3.3 Configure toolchain paths.

A3. Build parameter panel (introduced in v0.7.1, adjusted in v0.8.0)

v0.7.1 provided a per-run override panel; v0.8.0 turned it into workspace settings on the Workbench Build page, allowing only Map/PNR/PT/PGM name=value options, parallel threads, cumulative timeout, and unified flow. The current version provides no Skip PT/Skip PGM or post-build auto-attach switches.

A4. HDL watcher behavior changes (v0.7.1)

Since v0.7.1, the HDL file watcher no longer calls sync-sources automatically, avoiding background XML mutations. All syncing of source files and IP instances into the project XML must be triggered manually via the §5.4 command.

A5. Interface design paradigm change (new in v0.7.2)

v0.7.2 (2026-07-19) introduced the native DesignAPI integration; the SDK no longer depends on the Efinity GUI to modify interface designs. See §14 Interface design.
