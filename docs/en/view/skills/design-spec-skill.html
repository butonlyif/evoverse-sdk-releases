EvoVerse Design Spec Skill

EvoVerse Design Spec Skill

evoverse-design-spec turns a natural-language intent for an FPGA, or an FPGA plus software, into a design package that is reviewable, implementable, and traceable. Its outputs are specifications and implementation plans — not RTL — and it never creates Efinity projects, constraints, firmware, or build artifacts.

When to use

  • Starting a new system from an empty directory and pinning down the board, IPs, interfaces, clocks, software boundaries, and acceptance criteria first.
  • Extracting facts from the Catalog, Efinity, or other approved Demo/IP material, without treating a reference project as a copy baseline for the new project.
  • Getting the customer to confirm architecture-shaping choices such as RISC-V usage, hard IP models, register interfaces, external interfaces, or the verification Oracle.

It is not the tool for a small, free-form RTL edit — do those directly, or use /evoverse-rtl when controlled evidence is required.

Invoking in Trae

Open a Trae chat in an empty directory of the target project, enter the Skill first, then state the full objective and the material scope. For example:

/evoverse-design-spec
为 WS-E1 的 TJ180A484S 新建一个工程：从 SD 卡读取图像，写入 DDR 帧缓存，再由 MIPI CSI-2 TX 输出到外部桥接器。
只从 Catalog、Efinity IP 和允许使用的其他 Demo 中发现物料；不得复制 sd-ddr-csi2 工程。请生成 design-package，列出每个物料的证据、复用分类、待确认决策和分阶段实施计划。

The Skill first clarifies the handful of questions that would change the architecture or the acceptance criteria. Anything the current material can confirm, it verifies through MCP queries rather than guessing from names or past experience.

Deliverables and evidence

Specifications live in two contexts, but the system always keeps exactly one active specification:

  • The first design is an INITIAL_DESIGN system-integration intent on the mainline. It creates no worktree and owns the complete design package, the initial generation, system simulation, and the first system baseline.
  • Once a baseline exists, each feature intent maintains — inside its own worktree — only a ChangeSet and local verification definitions bound to the current revision/digest. When local verification passes, the status is READY_FOR_INTEGRATION; the system baseline cannot be updated directly.
  • The SDK then starts a worktree-less system-integration intent on the mainline, combining the active specification and a ChangeSet into an immutable candidate system specification. Only after system simulation and document confirmation have all passed does the candidate specification replace the active one.

The Skill creates design-package/ in the current project. A freezable design package contains at least:

design-package/
  materials/<material-id>/...
  material-manifest.json
  evidence-snapshot.json
  design-context.json
  decisions.md
  planning/ip-decisions.json
  specification.md
  implementation-plan.md
  traceability-matrix.md
  generation-manifest.json

materials/ holds byte-for-byte copies of the selected material. material-manifest.json records, for each entry, the original location, timestamp, SHA-256, purpose, and classification:

  • REUSE_UNCHANGED: reusable without changing a single byte.
  • ADAPT_REQUIRED: usable as a starting point, but every change must appear as a concrete task in the implementation plan with a stated verification method.
  • REFERENCE_ONLY: interface, configuration, or behavioral facts only; never brought into the project directly.
  • REJECTED: not allowed for this design, with the reason recorded.

Every fact in evidence-snapshot.json must carry a source ID. Verified conclusions are marked CONFIRMED; design inferences are marked PROPOSED; items that require a customer decision are marked DECISION_REQUIRED. The design package cannot be frozen until that count reaches zero.

Working with MCP

The Skill discovers facts and stores controlled design information through the current EvoVerse MCP. Typical actions include reading the Catalog and knowledge base, checking project/board/IP capabilities, creating or reading specifications, and checking downstream verification status. The Agent should surface the sources, summaries, and open decisions returned by key MCP calls in the conversation, not just hand over the final document.

Material discovery follows the trusted-material-source hierarchy: ① the installed Catalog — the only trusted material library. There are exactly two entry points: the location field returned by the CLI evoverse catalog status --json, which points at the synced Catalog directory (containing catalog/ and catalog-sync-receipt.json); and the workspace pointer file .evoverse/catalog.json, whose catalogRoot field is the material root, refreshed automatically by the SDK on activation, whenever the Welcome page opens, and after every sync. ② Code and examples shipped with the toolchain ($EFINITY_HOME/examples/, the SDK docs/efinity/ knowledge base); ③ existing code in the current workspace (read-only); ④ open-source code from the Internet (untrusted, discovery only — it must be confirmed by simulation and its source recorded before it can be cited). Blanket searches to locate material, or citing development-tree copies, are forbidden.

For Efinity-related conclusions, query the runtime toolchain knowledge and current IP/project capabilities first; static examples or old projects qualify only as sourced material. After the customer confirms, the Skill runs Skills/evoverse-design-spec/scripts/validate_design_package.py design-package to validate the structure, digests, and material adaptation tasks, and to predict locally the GENERATION_NOT_READY findings that server-side spec.draft would reject (decision status, numeric policies, protocol roles, connection directions, and so on), so the package is not bounced after sealing. This check is not RTL simulation, Efinity compilation, timing closure, or hardware verification.

In the reliable workflow, spec.draft submits the sealed executable 2.0 spec-package directory via packagePath: the server seals it and records the specPackageDigest as its trusted identity, and specification.md is deterministically generated by the sealing script for human review only. A Markdown file must never be submitted as packagePath.

IP realization planning (before specification drafting)

Before drafting any specification revision, every functional node must first answer "how is this function implemented": Efinity hard IP, Efinity soft IP, Catalog Verified IP, an existing workspace module, custom RTL, or open-source code. Consideration is mandatory — you may not skip the evaluation and write RTL directly; but the IP itself is not mandatory — the engineer may still choose custom RTL or an existing module, except that when a compatible IP candidate exists, a readable technical rejection rationale must be recorded (interface mismatch, resource cost, licensing, integration coupling, and the like).

The whole planning is driven by the server control plane; the Agent and the UI do not invent facts:

  • Inventory snapshot: ip.inventory.refresh is executed by the server and accepts no caller inputs; it re-inventories the Efinity IP library from the current toolchain and produces an immutable snapshot bound to the current device, package, Efinity version, and inventory digest. Changing the device or tool version invalidates the old snapshot, and every dependent decision must be recomputed.
  • Node decision: ip.plan submits, per node, a nodeId plus one selection (realizationKind / candidateId / a readable engineering reason), and a rejection reason for every relevant unselected candidate. The candidate list, compatibility, risk level, and required gates are all derived by the server from the current snapshot and recorded into planning/ip-decisions.json.
  • Candidates come only from the six closed source kinds: EFINITY_HARD_IP, EFINITY_SOFT_IP, CATALOG_VERIFIED_IP, EXISTING_MODULE, CUSTOM_RTL, OPEN_SOURCE. Unknown availability, an unsupported device or tool version, an unclassifiable risk (UNCLASSIFIED), or selecting an INCOMPATIBLE / UNVERIFIED candidate always blocks — there is no silent fallback to generated RTL.
  • Risk only escalates: the risk level (IP_L1 / IP_L2 / IP_L3 / RTL_L2 / RTL_L3) is derived by the server's closed rule table per concrete IP and configuration; the Agent may only explain the result, never assign, lower, or replace it.

Which source kinds require functional simulation, Native Build, or board validation is fixed and cannot be waived in any conversation:

Source Functional simulation Native Build Board validation
Efinity hard IP / soft IP / Catalog Verified IP not required (as IP qualification) required only when escalated; required for IP_L3
IP_L3 (DDR, MIPI D-PHY, LVDS and similar external high-speed interfaces) not required required, plus bank validation required
Existing module / custom RTL required required when risk requires it
Open-source code required required, plus provenance and license evidence when risk requires it

"Not required" applies only to qualifying the IP itself; it does not waive configuration validation, interface checks, timing constraints, Native Build, or system-level evidence. A Native Build PASS never claims a board validation PASS. A generated wrapper around vendor IP is exempt from simulation only when it is pure direct wiring (DIRECT_WIRE); a wrapper carrying functional behavior must be simulated before it passes.

spec.draft stays blocked until every functional node has a complete decision. After approval, the review specification.md derives two sections deterministically from planning/ip-decisions.json — the "IP selection and reuse matrix" (candidates, compatibility, risk, selection reason, and rejected alternatives for every node) and the "IP integration contracts" (identity, parameters, ports, bank/voltage/pin and constraint requirements, generation method, and acceptance conditions); they are review views, not authority — the executable JSON always is.

Next steps after freezing

Once the customer resolves every DECISION_REQUIRED item in the design package, the frozen generation-manifest.json binds the digests of the material ledger, the evidence snapshot, and the design context. Then use /evoverse-rtl to generate one leaf task of the implementation plan into a controlled candidate directory. That Skill may read materials/, but it must never modify the material copies or write back to the reference baseline. When the feature intent finishes, it waits for system integration; the final specification and the retrospective are confirmed together by the system-integration intent, so branch state never diverges from mainline delivery state.

Before freezing, the verification specification's assurance section must also declare rtl-baseline@1, the selected rule pack, every explicit protocol contract, and each exception with its rule ID, reason, expiry, and precise file/module/interface scope. Video contracts use evoverse.video@1 and must state module, imageWidth, bitsPerPixel, parallelism, and lineBufferDepth explicitly; any omission or ambiguity is a DECISION_REQUIRED and must not be inferred from port names.

Stop conditions

Whenever the external interfaces, register map, clock strategy, CDC, hard IP behavior, the Oracle, security requirements, or the way RISC-V is used are unclear, the Skill must stop and ask the customer to decide. It must not fabricate facts to keep generating, choose on the customer's behalf, or treat a reference design's implementation details as an approved specification.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
