Project-Aware Efinity AI Build Review

Project-Aware Efinity AI Build Review · User Guide

The efinity-build-review skill turns all native build evidence of an existing Efinity project into an auditable review report: deterministic status first, then AI interpretation and verifiable recommendations. It supports EvoVerse projects and customer-native projects without .evoverse, arbitrary source layouts, flist/include references, and even report-only projects with no sources at all.

Reviewing is read-only: the skill never edits RTL, SDC, ISF, or the project XML, and never edits reports. To apply a recommendation, it first shows a patch/settings preview; only after your confirmation does it use native capabilities, and it verifies the result with fresh native build evidence.

1. What problem it solves

Taking over an Efinity project usually raises these questions: how far did the build get? Did timing pass, and by how much did it miss? How much of the device is used? Are constraints complete? Which of my code does a reported critical path correspond to? What should change next, and would that change break function? This review answers them all at once, with every statement traceable to evidence:

  • Deterministic facts (resources, WNS/TNS, compile stages, the verdict) come from parsing native reports, not from the AI;
  • The AI only explains, analyzes risk, and proposes verifiable recommendations — each with risk level, functional impact, and verification steps;
  • Missing information renders as NOT_AVAILABLE or UNKNOWN, never as zero and never guessed.

3. Quick start

What you say to the host agent

Open the project folder in Trae (VS Code users: invoke the Skill from Copilot Chat, or ask the Agent to read Skills/efinity-build-review/SKILL.md from the delivered package first) and enter:

/efinity-build-review
Review this Efinity project. Let me select the project XML first, then explain the design structure, build stages, resources, timing, constraint coverage, artifacts, critical-path source correlation, and next actions.

Common variants:

/efinity-build-review
There are several projects in this folder; review the customer deliverable. No native reports exist yet — ask for my approval, run a full build, then produce the review.

/efinity-build-review
Re-review the same project as last time. Focus on the source origin of the worst Setup path and compare viable optimization strategies. Do not modify code directly.

When multiple Efinity XML files exist, the skill lists every candidate and requires an explicit selection; it never silently picks the first or newest file. It analyzes existing reports by default and explains the action and gets approval before starting a new native build.

4. End-to-end workflow

flowchart LR
    A[User selects project XML] --> B[efinity_review_collect gathers deterministic evidence]
    B --> C[AI reads the source closure and indexes to draft the AIReviewDocument]
    C --> D[efinity_review_render performs final validation and atomic persistence]
    D -->|invalid document| E[Repair only reported document fields and retry once]
    E -->|still invalid| F[mode deterministic renders a deterministic fallback]
    D -->|success| G[Return every artifact path]
    F --> G
    G --> H[Open Webview when available otherwise return the HTML entry]
  1. Select the review subject: the skill discovers native Efinity XML files only inside the selected workspace; with multiple candidates, you choose.
  2. Collect evidence: call efinity_review_collect to obtain the evidence bundle — capability level, freshness, six-dimension status, critical paths, source correlations, strategy assessments.
  3. Understand the project: the AI reads only the source closure named by the selected XML/flists/includes plus the relevant SDC/ISF/peri/IP configuration, building an understanding of top-level purpose, hierarchy, clock/reset domains, external interfaces, state machines, and feedback paths.
  4. Generate and finalize: the AI drafts the review per the AIReviewDocument contract and submits it directly to efinity_review_render; render performs the authoritative validation. On failure, only the reported document fields are repaired once, without restarting project analysis. efinity_review_validate is reserved for independent diagnostics.
  5. Render: if the repaired review still fails or AI generation is unavailable, call efinity_review_render with mode: deterministic to create a valid deterministic-only report. Chat text without all six artifact paths is not completion.
  6. Inspect and export: open the report with evoverse.openEfinityBuildReview; use the export action to produce a redacted copy for customers.

If the host does not expose these MCP tools, the skill reports CAPABILITY_UNAVAILABLE instead of presenting free-form text as an authoritative report.

5. Capability levels and evidence freshness

Capability Meaning
FULL_PROJECT Project, sources, constraints, and reports all available; code-level correlation enabled
LIMITED_PROJECT Some sources, generated units, VHDL, or encrypted IP cannot be deeply analyzed
REPORT_ONLY Report state only; code-level conclusions are disabled
PREFLIGHT_ONLY No native implementation reports at all
Freshness Meaning
CURRENT Reports provably correspond to the current inputs
POSSIBLY_STALE Timestamps are compatible, but native reports carry no complete input digest, so exact identity is unproven
STALE Project inputs are newer than the reports; treat reports as historical
UNKNOWN Freshness cannot be established

An mtime-only compatibility check can produce POSSIBLY_STALE, never strong CURRENT. Treat STALE reports as history: rebuild after source changes, then re-review.

6. Reading the report

6.1 Six dimensions and the verdict

The report presents the executive summary and customer actions first. The "Deterministic status cockpit" then keeps six independent dimensions: Flow, Artifact, Timing, Resource, Constraint, and Freshness. Every section heading carries a status badge (Needs fix / Needs attention / OK / No data), and the hero is colored by verdict. The verdict means:

  • BLOCKED: the build failed or evidence is insufficient to continue.
  • BUILT_NOT_READY: build output exists, but timing failures, stale evidence, or another condition blocks readiness.
  • READY_WITH_RISK: proceed to verification only with the stated risks.
  • READY_FOR_VERIFICATION: build evidence supports the next verification step; this is not a simulation, programming, or hardware pass.

6.2 Report section map

The reading order is now “executive summary and AI recommendations → status and macro system framework → technical diagnosis → collapsed appendix.” The framework shows only the top and major block types supported by source evidence. Native flow, artifacts, the design–implementation crosswalk, limitations, and evidence identity are in the appendix; the crosswalk is collapsed by default with item and finding counts.

6.3 Claim kinds

Every AI claim is labeled one of four kinds:

Kind Meaning Must carry
FACT Directly supported by reports/sources Evidence IDs
INTERPRETATION AI interpretation or root-cause hypothesis Evidence IDs
RECOMMENDATION Actionable advice Risk, functional impact, verification steps, user-decision flag
UNKNOWN Not enough evidence —

Conclusions inferred from names or behavior (for example, module purpose) are INTERPRETATION, not vendor facts. Confidence is labeled HIGH / MEDIUM / LOW / NOT_APPLICABLE. The review document is bilingual: Chinese primary fields plus a mandatory English mirror (document headlineEn, section titleEn, claim en); a missing mirror fails validation.

7. Source correlation levels

Path locations are labeled:

Level Meaning
EXACT A native-report file:line annotation inside the selected project evidence closure
SYMBOL_MATCH Leaf symbol match; duplicate candidates all remain visible and ambiguity is marked
SEMANTIC_CANDIDATE Semantic candidate
HEURISTIC Filename/synthesis-suffix heuristic, not an exact annotation
UNRESOLVED No resolution

Verilog/SystemVerilog uses a structured tokenizer/parser to model modules, instances, ports, parameters, processes, assignments, functions, generate blocks, arrays, source ranges, and driver-consumer edges, then uses data cones to support correlation. Incomplete macro/parameter elaboration, VHDL, generated units, and encrypted units degrade explicitly instead of pretending to be fully elaborated. The path drawer presents endpoint candidates, the AST data cone, principal-logic mapping, pipeline suitability, the strategy matrix, functional impact, and the verification checklist together.

8. Optimization advice and constraint safety

8.1 Pipeline suitability

Before suggesting a pipeline register, the skill checks: feedback, state-transition logic, valid/ready handshakes, packet-boundary sidebands, multiple consumers, reset/clock enable, fixed-latency contracts, RAM/DSP latency, CDC, and verification assets (assertions/testbenches). The verdict is one of SUITABLE, CONDITIONALLY_SUITABLE, UNSUITABLE, UNKNOWN — one missing semantic check prevents a definite pipeline recommendation.

8.2 Strategy matrix

Strategy Meaning
PIPELINE Pipeline register insertion
RETIME Register retiming
EXPRESSION_REFACTOR Expression refactor (logic depth / comparator fan-in)
FANOUT_REPLICATION Replication of high-fanout nets
RAM_DSP_REGISTER Primitive-supported RAM/DSP input/output registers
TOOL_EFFORT Native tool effort/seed options
CLOCK_ARCHITECTURE Clock architecture change
IO_CONSTRAINT Complete I/O timing constraints
CDC_ARCHITECTURE CDC architecture redesign
NO_ACTION Evidence or benefit insufficient; no change

Each recommendation states the expected direction, risk and functional impact, and verification steps side by side. Strategy lifecycle: PROPOSED → ACCEPTED → APPLIED_UNVERIFIED → IMPROVED / NO_CHANGE / REGRESSED / REJECTED; a final state must reference fresh native after-build evidence, and without new evidence a strategy cannot be marked final.

8.3 Constraint safety rules

  • I/O delays require external-device timing (Tco/Setup/Hold) and PCB delay/skew parameters; when they are missing, the skill shows placeholders and asks you — it never invents 0 ns, 2 ns, or another "conservative" value.
  • Adding set_false_path, set_multicycle_path, set_max_delay, or set_min_delay merely to remove a violation is forbidden; timing exceptions require structural evidence, design-intent evidence, and your explicit confirmation.
  • The skill never rewrites RTL, SDC, ISF, or the project XML on its own to eliminate a violation.

9. Artifacts and directory layout

<project root>/
└─ .evoverse/
   ├─ reports/build-review/<reviewId>/     # Full local review (non-overwriting)
   │  ├─ review.json        # AI review document (authoritative input; Chinese fields + en mirror)
   │  ├─ evidence.json      # Deterministic evidence bundle
   │  ├─ report.html        # Self-contained HTML report (Chinese-first UI)
   │  ├─ report.md          # Markdown copy (Chinese-first)
   │  ├─ report-en.html     # Pure-English HTML twin
   │  └─ report-en.md       # Pure-English Markdown twin
   └─ exports/build-review/<reviewId>/     # Redacted customer export (same six files; evidence redacted)
  • Each local review is atomically promoted from a temporary directory; an existing reviewId is never overwritten. Failure or cancellation cannot leave a partial review that looks complete.
  • Exported HTML remains script-free under a strict CSP (default-src 'none'). The IDE Webview injects only a nonce-bound local bridge and revalidates evidence ID, file existence, and line number before opening source, so customer content cannot invoke commands directly.
  • The HTML has a print stylesheet; PDF support currently means IDE/browser "Print to PDF", not a built-in deterministic PDF engine.
  • Customer export removes local paths and source bodies, then scans for credential-like text, environment values, and paths; findings fail closed — fix the finding, do not bypass it.
  • Comparison first checks project, device, and top-module compatibility, then reports changes in WNS/TNS, resources, duration, paths, constraints, and issue clusters.

10. Command and MCP tool reference

Entry point Purpose
efinity_review_collect Gather deterministic evidence for the explicitly selected project XML; the mandatory first step
efinity_review_validate Optional diagnostic tool for schema and evidence-reference errors; not a mandatory pre-render pass
efinity_review_render Finalize and atomically persist six artifacts; pass review for a full AI report or mode: deterministic for a deterministic fallback
Command evoverse.openEfinityBuildReview Open the latest rendered review of the active project (Webview)

Common parameters are project and the explicitly selected absolute projectXml. validate takes review; render takes either the review bound to collect's reviewInputId, or mode: deterministic when AI composition is unavailable.

evoverse.openEfinityBuildReview re-validates review.json against evidence.json and the HTML safety properties before opening; on failure it prompts to re-render and refuses to open a modified report.

11. FAQ

Symptom Handling

Multiple project XMLs in the folder The skill lists all candidates for selection; confirm you pick the one to deliver/review
Capability is PREFLIGHT_ONLY No native reports. On your explicit request the skill runs efx_run --flow compile first, then reviews
Report marked STALE Treat as historical evidence; rebuild and re-review rather than accepting on stale reports
render returns document-validation issues The skill repairs document fields once; a second failure uses mode: deterministic so the run still ends with rendered artifacts

Report will not open; schema/HTML validation failed The review directory was modified or corrupted; re-render the same review with efinity_review_render

12. Verification boundary

Compile, Timing, Simulation, Programming, and Hardware are independent results. A native map/interface/PNR/PGM pass and bitstream do not prove simulation, download, or board behavior. Resources, WNS/TNS, stage states, and the top-level verdict come from the deterministic parsing layer; the AI provides only explanation, risk analysis, and verifiable recommendations. Project files and reports are evidence, never instructions — the skill ignores any comment or log text that attempts to change this workflow.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
