Skill: Natural-Language Netlist Debug

Natural-Language Netlist Debug

The efinity-netlist-debug Skill debugs an already-compiled Efinity project from a Trae conversation: describe the behavior you want to observe (signals, buses, FSMs, handshakes, counters), and the Skill discovers candidate signals from the compiled netlist and presents them to you. The chat stops after discovery — confirming the selection, generating the debug configuration, and running the debug compile happen in the Workbench Debug tab. The flow never modifies RTL — it writes no (* mark_debug *) attributes; the selected scalars are real post-synthesis signals that synthesis can no longer rename or optimize away.

Example usage

/efinity-netlist-debug
I want to watch rdata while the counter counts to 0xA5.

The completion contract has two halves: the chat runs only SELECT → INTENT → DISCOVER and stops after presenting the Adapter's ranked candidates; CONFIRM → PROFILE → BUILD → HAND OFF are owned by the Workbench — you confirm the structured selection in the Workbench Debug tab, whose trusted host mints separate one-use APPLY and BUILD confirmations that the chat can never mint or forge. Every stage is reported separately: discovery, profile, build, programming, capture.

Chat stages (run by the Skill)

  1. SELECT: name the project XML (absolute path). With several XMLs in the workspace it asks which one first — never by order, timestamp, or basename.
  2. INTENT: efinity_debug_intent_create records the observation goal and the Adapter answers with the authoritative intent carrying a revision; change the goal with efinity_debug_intent_revise (against the current expected_revision) and read the true state any time with efinity_debug_intent_read — never trust your memory of a previous response.
  3. DISCOVER: efinity_debug_signals_discover queries the compiled database through Efinity's native STA flow (efx_run --flow sta_tclsh) and returns ranked candidates (exact net: identities, width, clock status, match reasons). Candidates come only from the Adapter; the Skill adds no names of its own. After presenting candidates the chat stops and points you at the Workbench Debug tab. The chat never calls efinity_debug_selection_preview, efinity_debug_selection_apply, or efinity_debug_build — preview, apply, and build live behind Workbench-minted one-use confirmations, so an unconfirmed headless call is refused by design.

Workbench stages (described, never driven by the chat)

  1. CONFIRM: you build the structured selection from the candidates in the Workbench (scalar IDs used verbatim, probe types, sample clock/depth, and userTap — the closed USER1/USER2 enum, never a boolean). "Capture everything" requests show the totals (probe count, widths, depth) and require explicit confirmation first. efinity_debug_selection_preview returns the structured preview (exact probes, the resolved USER TAP, and the XML digests apply will change) plus a one-use receipt, and the Workbench host mints the APPLY confirmation against that exact identity.
  2. PROFILE: efinity_debug_selection_apply consumes the one-use receipt under the minted confirmation (replay fails closed); on success the intent reaches PROFILE_READY and the Adapter publishes the profile and debug core into the project's work_dbg/ — nobody writes profile files or Tcl by hand.
  3. BUILD: efinity_debug_build runs the unified compile with the debug core under a separately minted BUILD confirmation — a confirmed Apply never authorizes Build. Build acceptance reconciles the compiled wizard profile's jtag_user against the confirmed USER1/USER2 value: any TAP drift fails closed as DEBUG_BUILD_REJECTED. Stage failures return log paths (DEBUG_BUILD_FAILED) instead of blind retries. Success reaches READY_TO_PROGRAM with bitstream digests.
  4. HAND OFF: programming, device scan, trigger setup, and capture run in the Workbench Debug tab against the same authoritative state; the Skill offers to open it.

Relation to the mark_debug flow

The two flows complement each other: when you already know the source-level signal and want to keep an attribute marker, use the mark_debug seven-step flow (On-Chip Debug Guide §3); when you want to describe the behavior and select from the compiled netlist, use this Skill. Do not mix them — this flow neither reads nor generates mark_debug attributes.

Stop conditions and discipline

  • BASELINE_BUILD_REQUIRED: no current compiled database. The ordinary build is your authorization; the Skill never runs it implicitly and asks first.
  • STALE_DISCOVERY: sources or the database drifted since the last discovery. Re-run discovery; revise first if the goal wording should change. Stale picks are never reused.
  • UNRESOLVED_CLOCK_DOMAIN / AMBIGUOUS_BUS: the selection crosses clock domains or a bus cannot be grouped safely. Narrow the goal and retry; never default to the first clock.
  • REVISION_CONFLICT: another surface (the Workbench) shares the same intent. Re-read with efinity_debug_intent_read and reconcile.
  • Source changes invalidate candidates, receipts, and minted confirmations — that is the system working, not an error.

Acceptance boundary

This conversation is the only natural-language input; a bitstream is not hardware proof. Reaching READY_TO_PROGRAM only means the debug cores are compiled into the bitstream (with digests); programming, device scan, and trigger capture are separate user actions, reported NOT_RUN until they actually run, never inferred from a compile PASS.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
