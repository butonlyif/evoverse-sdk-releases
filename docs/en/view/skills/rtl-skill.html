EvoVerse RTL Skill

evoverse-rtl drives a single, well-bounded RTL generation or modification task. The natural-language prompt describes the intended behavior, but what may actually be changed, when it passes, and whether it can enter the official baseline are all decided by action receipts from the EvoVerse control plane.

When to use

  • You already have an approved specification and a leaf module or subtask that can be verified on its own.
  • You need delivered RTL to go through both candidate freezing (including RTL Design Assurance) and the simulation gate.
  • You want the existing project kept as a read-only baseline so the Agent cannot drag unrelated RTL, test assets, or constraints into the change.

It does not replace free-form development. Ordinary Agent edits and builds remain available and are never blocked by this Skill; they simply do not automatically earn the candidate, isolation, and promotion evidence this Skill produces.

How to invoke

Trae (recommended host): at activation the SDK installs this Skill into Trae's skill directory (~/.trae-cn/skills for Trae CN, ~/.trae/skills for the international edition); once the host recognizes it, invoke /evoverse-rtl in the chat. Open the project that contains the approved specification, and state in the conversation the single task, the specification source, the target RTL path, the simulation sources, and the read-only dependencies. For example:

/evoverse-rtl
根据 design-package/specification.md 实现视频帧写入控制器。交付到 rtl/frame_writer.sv；
保留 sim/frame_writer_tb.sv 与 sim/models/ 作为验证源；rtl/common/ 必须只读。
请先展示任务范围和控制面回执，再开始生成。

If the interfaces, bit widths, register map, clock/reset domains, Oracle, or hard IP models remain ambiguous, the Skill stops and requires going back to /evoverse-design-spec for a decision or updating the specification first.

VS Code: the SDK does not copy a host-level skill directory into VS Code (unlike Trae); Skills are offered to Copilot Chat through the VSIX chatSkills contribution — loaded on demand in agent mode, and in recent Copilot Chat versions also callable as the /evoverse-rtl slash command (requires the Copilot Chat extension). The equivalent is to ask the Agent to read Skills/evoverse-rtl/SKILL.md from the delivered package and follow it as instructions; the MCP control-plane tools are already wired into the user-level mcp.json by the SDK.

Controlled lifecycle

flowchart TD
    S["project_status read-only check<br/>read revision and active Intent"] --> A["Intent intent.create"]
    A --> B["Simulation level simulation.profile.select<br/>precedes the specification, chosen by the user"]
    B --> C["Specification spec.draft<br/>written to the selected level's budget"]
    C --> D["Contract qualification contract.qualify"]
    D --> E["Candidate delivery candidate.deliver<br/>freeze candidate in staging dir + RTL Design Assurance"]
    E --> F{"Assurance and simulation PASS?"}
    F -- "No: DUT_FAIL" --> G["Diagnosis<br/>candidate.repair one targeted fix in the same round<br/>or diagnostic.options.propose → choice.select"]
    G --> E
    F -- "Yes" --> H["Promotion candidate.promote<br/>module candidate → READY_FOR_INTEGRATION"]
    H --> I["project_status re-check<br/>report unverified boundaries one by one<br/>NATIVE_BUILD_PENDING / BOARD_VALIDATION_REQUIRED"]
    S -. "State off track: RECOVERY_REQUIRED" .-> J["recovery.open → recovery.quarantine<br/>isolated recovery, baseline and failure evidence preserved"]
  1. Read the project, the specification, and the dependencies without modifying any file. Use project_status to read the current revision and the active Intent.
  2. Use project_next to read the currently permitted actions and identify prerequisites such as intent.create (a new increment). Show the customer the scope and the chosen action; once the customer confirms, execute it with project_execute, with expectedRevision equal to the most recently read revision.
  3. The simulation level precedes the specification (the user chooses): in a reliable iteration, the simulation level must be confirmed before spec.draft starts drafting, or the control plane blocks drafting with SIMULATION_PROFILE_REQUIRED. The Agent extracts riskFacts from the user's requirements, the material, and the topology, and submits simulation.profile.select; the control plane recommends a level under fixed risk rules (FPGA_FUNCTIONAL / FPGA_INTEGRATION / HIGH_ASSURANCE), and after the Agent explains it, the user chooses (choosing below the recommended minimum requires recording acceptedRisks). The specification is written to the budget of the selected level; when the budget is exceeded, the control plane demands fresh confirmation of the overrun — never silent trimming or silent scope expansion.
  4. Write the fully declared file set to a local staging directory (never straight into official RTL) and execute candidate.deliver with project_execute: the complete candidate set is submitted in one shot. In reliable mode this step only freezes the candidate and runs RTL Design Assurance; it does not promote the baseline.
  5. Execute verification.simulate with project_execute, explicitly selecting the iverilog or questa backend; the service compiles the candidate RTL together with the retained TB, BFM, and Oracle under the blocking obligations of the selected level, and saves the candidate-bound evidence. Only after the current candidate earns a valid PASS and meets eligibility does executing candidate.promote install the reliable baseline. A level-limited simulation pass (for example FPGA_FUNCTIONAL_PASS) is not a hardware conclusion.
  6. On a DUT_FAIL, keep the failing requirement and the receipt. A cause backed by a single sufficient piece of evidence may be repaired once, in a targeted way, using diagnostic.repair.record and candidate.repair; when the attribution is ambiguous or the repair still fails, use diagnostic.options.propose to present the rationale, the next checks, the cost, and the uncertainty, and wait for the engineer to judge via diagnostic.choice.select. Human judgment must be checked against fresh evidence; on conflict, record it with diagnostic.finding.record and communicate promptly — never treat it as a PASS.
  7. After every action, read the new revision with project_status again and report which boundaries are verified and which are not; list deferred items one by one, reporting NATIVE_BUILD_PENDING and BOARD_VALIDATION_REQUIRED separately.

When the process goes off track or an old state can no longer continue, the Agent must never reset the runtime on its own; it may only explain the server's recovery description and obtain the customer's confirmation:

  • The recovery description deterministically lists what is kept, replaced, and discarded, the steps, and the success checks, and is bound to the current revision; old plans must not be reused across revisions.
  • When the control plane finds a non-terminal state with no genuine exit, project_next returns RECOVERY_REQUIRED with the single recovery.open, whose inputPreview must be submitted verbatim.
  • Once the recovery record is on disk, re-read it and execute only server-exposed safe exits such as recovery.quarantine.
  • Quarantine preserves the trusted baseline, the fact history, and the failure evidence, releasing only the affected scope — it is not a delivery success.
  • Abandoning an INITIAL_DESIGN atomically closes the Intent and the initial system integration, and never fabricates a worktree execution that does not exist.

A simulator counts as "available" only after version probing is followed by a minimal real compile, run, and event parse. If any step of the selected Questa/Icarus setup becomes invalid, the control plane enters WAITING_FOR_USER and accepts only an explicit re-probe or reselection; it never switches backends automatically, nor does it write simulation PASS evidence before success.

project_status, project_next, and project_execute (plus evoverse_health for health checks) are the MCP protocol for this flow; the corresponding control-plane actions come from project_next, including intent.create, simulation.profile.select, candidate.deliver, verification.simulate, candidate.promote, and the diagnostic actions on failure. If the MCP tool snapshot lacks a stable interface, refresh MCP first — generic verification tools or raw CLI commands must not stand in for stage actions.

RTL Design Assurance and the simulation gate

RTL Design Assurance is not an ordinary coding-style check. It inspects the candidate production RTL's structure, clocks, resets, CDC, state machines, FIFOs, data integrity, and protocol contracts; dynamic obligations that static checking cannot prove remain incomplete and are never treated as a PASS. Assurance runs inside candidate.deliver on the service side — without a PASS receipt, the delivery has not succeeded.

The simulation gate must use verification.simulate: the candidate production RTL runs together with the TB/BFM/Oracle, and the test assets themselves must pass qualification. A broken testbench, an ambiguous Oracle, missing models, a timeout, or insufficient coverage cannot be attributed to the DUT, and none of it makes the RTL verified. Temporary compile outputs stay in a staging directory outside the project and never enter the official project; on promotion, the service installs only the declared RTL and the retained sim/ sources.

Results and remaining boundaries

A successful delivery means this one task holds a scope receipt, rule results, and simulation evidence. It does not automatically prove Efinity native compilation, timing, hard IP internal behavior, board-level wiring, or hardware display results — those are evidenced separately by build.native, hardware.program, and hardware.validate. When the Skill finishes, it must list these outstanding steps explicitly and keep the next layer of tasks locked until the current evidence is complete.

Stop conditions

The Skill must stop when the control plane is unavailable, project_execute returns a failure, a receipt is missing, writes go beyond the declared scope, the specification is not approved, or the verification verdict is fail/incomplete. Existing project files are by default a read-only baseline keyed by byte hash; files that depend on compilation do not become writable on that account — problems found there are reported as baseline debt, not silently fixed.

Advanced references are for on-demand lookup; design records, release procedures, audit reports and future plans are not customer entry points.
