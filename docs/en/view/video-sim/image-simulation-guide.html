Image Simulation Guide

evoverse.simIsp User Manual

Applicable SDK version: v1.0.0

1. Overview

evoverse.simIsp is the EVOVERSE SDK command dedicated to ISP (image signal processing) / image-processing IP simulation and verification. It compiles the testbench, RTL, and optional BFMs provided by the project, captures result.hex, then runs image-quality analysis with the Python backend and finally produces an analysis report covering PSNR, sharpness, white balance, histogram, Gamma, and more.

The current v1.0.0 VSIX provides the Video Sim launch entry and the accompanying analysis capabilities, but does not yet ship a generic AXI-Stream BFM. If your project needs a BFM, put it in sim/BFM/ or sim/common/.

Differences from evoverse.sim

Feature evoverse.sim evoverse.simIsp
Applicable scenario generic FPGA simulation ISP / image-processing IPs
Configuration sim.yaml video_sim.yaml
Input data generic stimulus image / video pixel stream (AXI-Stream)
Output artifacts VCD waveform result.png + JSON analysis report
Analysis metrics none PSNR, sharpness, white balance, histogram, Gamma

The two commands are fully independent and share zero code.

Overall data flow

evoverse.simIsp
    ↓
parse sim/video_sim.yaml
    ↓
scan: RTL (rtl/) + testbench (sim/tb_*.v) + BFM (axis_video_source/sink)
    ↓
iverilog -g2012 compile → sim_isp.vvp
    ↓
vvp run the simulation → result.hex
    ↓
gen_output.py: result.hex → result.png
    ↓
analyze.py: golden.png vs result.png → JSON report
    ↓
Webview displays the report

2. Directory structure

When you run evoverse.simIsp, the command looks for the sim/ directory in the project root. The complete directory convention:

project/
├── rtl/                         # user DUT (RTL design files, auto-scanned and included)
│   ├── isp_denoise.v
│   └── color_space.v
└── sim/
    ├── video_sim.yaml           # [required] ISP simulation configuration file
    ├── BFM/                     # project-supplied BFMs (optional)
    │   └── axis_video_*.v
    ├── common/                  # local shared BFMs (optional)
    │   └── axis_video_*.v
    ├── tests/                   # testbench test cases
    │   └── tb_isp.v
    ├── tb_*.v / tb_*.sv         # testbenches may also sit directly in the sim/ root
    ├── testdata/                # test data
    │   ├── stimulus.hex         # input stimulus (read by axis_video_source)
    │   ├── golden.png           # golden reference image
    │   └── result.hex           # [simulation output] written by axis_video_sink
    └── output/                  # [created automatically] analysis output
        ├── images/
        │   └── result.png       # image restored from result.hex
        └── reports/
            └── sim_isp_<timestamp>.json  # analysis report

Directory notes

Directory / file Required Description
sim/video_sim.yaml ✅ yes configuration file; the command activates by detecting this file
rtl/ no Verilog/SystemVerilog files of the user DUT, scanned recursively
sim/BFM/ no user-defined BFMs; the current version ships no generic BFM
sim/common/ no user-defined shared BFMs
sim/tests/ no testbench directory, scanned recursively for tb_*.v / tb_*.sv
sim/tb_*.v ✅ yes at least one testbench file is required
sim/testdata/ recommended holds golden.png, stimulus.hex, and other test data
sim/output/ automatic created automatically at run time; holds images and reports

File scanning rules

  • BFM files: scans sim/BFM/ and sim/common/. The runner also retains the ability to scan bundled/video_sim/sim/common/, but the current v0.9.0 package does not ship generic BFM files.
  • Testbenches: scans tb_*.v/tb_*.sv in the sim/ root plus testbench files found recursively under sim/tests/
  • RTL files: scans rtl/ recursively for all .v, .sv, and .vh files

3. Configuration file video_sim.yaml

The configuration file must sit at sim/video_sim.yaml.

Complete form

adapter: video_sim

params:
  width: 1920
  height: 1080
  frames: 1
  pixel_format: RGB888

  golden: sim/testdata/golden.png
  result: sim/testdata/result.hex

metrics:
  - psnr
  - sharpness
  - white_balance
  - histogram
  - gamma

Field reference

Top level

Field Type Required Description
adapter string ✅ yes fixed value video_sim; distinguishes the simIsp command from sim
params object ✅ yes simulation parameters
metrics string[] no analysis metrics to enable; all are enabled by default

params parameters

Field Type Default Description
width number 1920 image width (pixels)
height number 1080 image height (pixels)
frames number 1 frame count (set to 1 for a single-frame image)
pixel_format string RGB888 pixel format, see the table below
golden string - golden reference image path (relative to the project root, or absolute)
result string - simulation output result.hex path (relative to the project root, or absolute)

Supported pixel formats

Format Width tdata width Channels Description
RGB888 24 bit 3 bytes 3 standard RGB 8-8-8; the format verified by the current tutorials
BGR888 24 bit 3 bytes 3 BGR byte order
RGBA8888 32 bit 4 bytes 4 RGBA byte order
BGRA8888 32 bit 4 bytes 4 BGRA byte order
RGB565 16 bit 2 bytes 3 input is two little-endian bytes, converted to RGB888

result.hex currently uses a one byte per line format. For example, a red RGB888 pixel is written as three consecutive lines ff, 00, 00. RAW/YUV formats have not completed end-to-end verification and are not promised by the v0.9.0 tutorials.

4. Quick start

Prerequisites

  • Python: 3.10+, with Pillow and numpy installed
  • Icarus Verilog: iverilog + vvp; configure evoverse.iverilogPath in VS Code
  • EVOVERSE SDK: the extension is installed

Step 1: Create the project structure

Create the sim/ and rtl/ directories under the project root:

mkdir sim                    # PowerShell
mkdir sim\testdata
mkdir sim\tests
mkdir rtl

Step 2: Write the DUT (RTL)

Place the Verilog/SystemVerilog code of your image-processing IP under rtl/. The DUT must follow the AXI-Stream video interface convention—receive the pixel stream from axis_video_source, process it, and output it to axis_video_sink.

Step 3: Write the testbench

Create the testbench file under sim/tests/ (or the sim/ root); the name must start with tb_, e.g. tb_my_isp.v.

The testbench must instantiate: - axis_video_source — reads pixels from stimulus.hex and streams them over AXI-Stream - your DUT - axis_video_sink — receives the DUT's output pixel stream and writes result.hex

Step 4: Prepare the test data

  1. Prepare the input stimulus per your project's BFM convention. The SDK's result.hex converter uses one byte per line; if input and output share the format, stimulus.hex should use the same convention.
  2. Put the golden reference image golden.png into sim/testdata/

Step 5: Create the configuration file

Create video_sim.yaml under sim/:

adapter: video_sim

params:
  width: 64
  height: 48
  frames: 1
  pixel_format: RGB888

  golden: sim/testdata/golden.png
  result: sim/testdata/result.hex

metrics:
  - psnr
  - sharpness
  - white_balance
  - histogram
  - gamma

Step 6: Configure the iverilog path

Configure the Icarus Verilog installation path in the VS Code settings:

{
    "evoverse.iverilogPath": "C:/iverilog/bin"
}

Step 7: Run the command

In VS Code press Ctrl+Shift+P, type evoverse.simIsp, and execute it.

The command automatically: 1. Parses video_sim.yaml 2. Scans and compiles all source files 3. Runs the simulation 4. Generates result.png 5. Runs the image-quality analysis 6. Shows the analysis report in a Webview

All output logs appear in VS Code's "Output" panel (select the "Sim ISP" channel).

5. BFM notes

A BFM (Bus Functional Model) is a non-synthesizable model that emulates bus behavior during simulation. A project may supply its own BFMs following the interface responsibilities below; the files in the table are currently not part of the v0.9.0 VSIX bundle:

axis_video_source — video source

Reads pixel data from stimulus.hex and outputs it pixel by pixel over the AXI-Stream interface.

How it works: 1. At the start of the simulation, $readmemh loads all of stimulus.hex into an internal array 2. Pixels are sent one by one per the AXI-Stream ready/valid handshake 3. tuser marks the first pixel of each frame (SOF); tlast marks the last pixel of each line (EOL) 4. Supports a multi-frame replay mode and a flush mechanism (for IPs with pipeline latency)

axis_video_sink — video sink

Receives the AXI-Stream pixel stream and writes result.hex.

How it works: 1. Opens the result.hex file at the start of the simulation 2. Whenever tvalid & tready are both high, writes tdata to the file in 8-bit hexadecimal form 3. Protocol-compliance-checks tuser and tlast, and reports an error on violation 4. After receiving WIDTH × HEIGHT × FRAMES pixels, sets frame_done and flushes the file 5. Configurable backpressure mode (C_READY_MODE / C_READY_RATE) emulates downstream throughput limits

Other BFMs

BFM Function
reg_config.v register-configuration model; sends register read/write requests to the DUT
ddr_model.v DDR memory behavioral model
axi_frame_buffer.v AXI frame buffer model, for frame-buffer reads and writes

BFM lookup order

The command looks for BFM files in the following priority order (high to low): 1. sim/BFM/ — project-local BFMs 2. sim/common/ — project-local shared BFMs 3. bundled/video_sim/sim/common/ — reserved extension BFM directory; empty in the current v0.9.0 package

For files with the same name, the higher priority wins.

6. Analysis metrics

6.1 PSNR (Peak Signal-to-Noise Ratio)

Measures how similar the output image is to the golden reference. The higher the value, the smaller the distortion.

PSNR value Grade Meaning
> 40 dB Excellent virtually no distortion; the difference is invisible to the eye
> 30 dB Good slight distortion, usually acceptable
> 20 dB Fair obvious distortion; optimization needed
≤ 20 dB Poor severe distortion; the DUT may have a bug

The analysis result includes: overall PSNR (dB), per-channel PSNR (B/G/R), and MSE.

⚠ PSNR requires a golden reference image and an output image.

6.2 Sharpness

Measures image clarity and edge-detail retention. Rated by combining Laplacian variance and Tenengrad.

Laplacian variance Grade Meaning
≥ 2000 Outstanding ample sharpness, crisp edges
≥ 800 Excellent good sharpness, complete detail
≥ 200 Good moderate sharpness, generally acceptable
≥ 50 Fair soft; some detail is lost
< 50 Blurry severely blurred; the DUT may over-denoise/filter

The analysis result includes: Laplacian variance, mean Sobel gradient, and Tenengrad value.

6.3 White Balance

Analyzes the image's color balance based on the gray-world assumption. Ideally the R, G, and B channel means should be equal.

The analysis result includes: - r_gain / g_gain / b_gain — per-channel gain coefficients - bias — color-temperature tendency: - Cool (bluish): R/B ratio < 0.85, the image leans blue - Neutral: R/B ratio between 0.85 and 1.15, colors balanced - Warm (yellowish): R/B ratio > 1.15, the image leans yellow - white_point — the RGB value of the white point in the brightest region

6.4 Histogram

Statistics of the RGB channel brightness distributions plus the brightness change of the output relative to the input.

The analysis result includes: - Per-channel mean, standard deviation, median, min/max, and P5/P95 percentiles - shift — the direction and magnitude of the overall brightness shift, e.g. "brightness +12.3 (mean change)"

6.5 Gamma

Measures the deviation of the DUT's Gamma curve from the target (2.2 by default), fitted by sampling a 17-step grayscale ramp.

Deviation (Δ) Grade Meaning
< 0.05 Excellent the Gamma curve almost perfectly matches the target
< 0.1 Good slight deviation, practically imperceptible in real use
< 0.3 Fair perceptible deviation; check the Gamma-correction logic
≥ 0.3 Large deviation severe deviation; the Gamma-correction module may be faulty

The analysis result includes: measured Gamma, target Gamma, deviation, and the number of valid sample points.

⚠ Gamma analysis requires a golden reference image (rich in gray levels) and an output image.

7. FAQ

Q: It says "iverilog not found"

Cause: the Icarus Verilog path is not configured, or is incorrect.

Fix: 1. Confirm Icarus Verilog is installed (download: http://bleyer.org/icarus/) 2. Configure evoverse.iverilogPath in the VS Code settings: - Windows example: C:/iverilog/bin - Linux example: /usr/bin 3. Make sure the directory contains iverilog.exe (or iverilog) and vvp.exe (or vvp)

Q: It says "No testbench found"

Cause: no testbench file was found under sim/.

Fix: make sure the testbench file matches one of the following: - placed in the sim/ root, with a filename starting with tb_ and the extension .v or .sv - placed under sim/tests/, with a filename starting with tb_

Q: It says "result.hex not found"

Cause: result.hex was not generated after the simulation.

Possible cases: 1. The testbench does not instantiate axis_video_sink, or instantiates it but wires it incorrectly 2. The DUT did not output the pixel stream correctly, so the sink received no data 3. The simulation exited abnormally before result.hex was written

Troubleshooting: check the simulation log (VS Code Output panel → "Sim ISP") for ERROR entries. Check that the axis_video_sink instantiation in the testbench is correct.

Q: A Python script fails with "No module named 'PIL'" or "No module named 'numpy'"

Cause: the Pillow or numpy dependency is missing.

Fix:

pip install Pillow numpy

If you use a specific Python environment, configure it in the VS Code settings:

{
    "evoverse.pythonPath": "C:/path/to/python.exe"
}

When unset, Windows defaults to py and Linux/macOS defaults to python3.

Q: The analysis report says an "--output comparison image is required"

Cause: some analyses (PSNR, Gamma) require both golden.png and result.png to exist. If the simulation produced no result.hex or result.png, those analyses are skipped automatically.

Fix: confirm the simulation completed normally and produced result.hex, and that gen_output.py successfully converted it to result.png.

Q: Image size mismatch warning

Cause: golden.png and result.png resolutions do not match.

Fix: analyze.py automatically scales result.png to the size of golden.png. For an exact comparison, make sure width/height in video_sim.yaml match golden.png.

Q: How to generate stimulus.hex

The current conversion convention is one 8-bit hexadecimal byte per line. RGB888 writes three consecutive lines—R, G, B—per pixel. You can generate it from an image with a Python script:

from PIL import Image

img = Image.open("input.png").convert("RGB")
with open("stimulus.hex", "w") as f:
    for r, g, b in img.getdata():
        f.write(f"{r:02x}\n{g:02x}\n{b:02x}\n")

Or refer to the hex-parsing logic in the SDK's built-in products/video-sim/scripts/gen_output.py.

Q: Can multiple DUTs be analyzed at once

Each project can have only one sim/video_sim.yaml. To test multiple DUTs, instantiate different DUTs in the testbench and select among them through register configuration, or create a separate project directory per DUT.

Q: How to view detailed logs

Open the "Output" panel in VS Code (Ctrl+Shift+U) and select the "Sim ISP" channel from the dropdown. Logs from every compile, simulation, and analysis step are printed there.
