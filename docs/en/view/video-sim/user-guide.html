1. Product introduction

The VIP simulation and verification platform is an end-to-end video IP simulation environment, delivered as a Trae / VS Code extension with two entry points: a graphical console and the command line. Core capabilities:

  • Image/video → simulation stimulus: real images are converted automatically into hex stimulus readable by Verilog $readmemh
  • One-click simulation: iverilog compile + run + result collection, fully automatic
  • Result restoration: simulation output hex is restored automatically to an image/video, so the effect is directly visible
  • Golden-reference comparison: a Python reference model reproduces the RTL fixed-point arithmetic bit for bit and declares PASS/FAIL automatically
  • Multi-dimensional quality analysis: sharpness, white balance, PSNR, histogram, Gamma curve, each in a pop-up panel of its own

In one sentence: feed an image in, get an image out, with your IP in between—and be told how well the processing worked.

2. Installation and environment setup

2.1 Installing the extension

Install the EvoVerse SDK core extension (evoverse-sdk-<version>.vsix, Video Sim included):

code --install-extension evoverse-sdk-<version>.vsix

After installation, reload the Trae / VS Code window (Cmd+Shift+P → Developer: Reload Window).

3.1 Data bridging

Python and Verilog are bridged through hex text files:

File Direction Content
stimulus.hex Python → simulation 32-bit hex pixel data
header.hex Python → simulation resolution, format, frame-count metadata
regcfg.hex Python → simulation sequence of register addresses and written values
result.hex simulation → Python 32-bit hex output pixel data
expected.hex Python → simulation golden expected output (used for comparison)
*_report.json Python → console quality analysis reports (data source for the panels)

3.2 Supported pixel formats

Format ID Name Bits per pixel Corresponding tdata arrangement in Verilog
3 RGB888 24 bit {8'd0, R[7:0], G[7:0], B[7:0]}

RGB888 is currently the primary supported format. RAW8/10/12 and YUV422/444 are defined in the Python toolchain, but on the Verilog BFM side RGB888 is the workhorse format.

4. Using the Trae extension (recommended entry)

4.1 One unified entry: the simulation console

Remember a single entry point — Ctrl+Shift+P (Windows) / Cmd+Shift+P (Mac) → VIP Sim: 打开仿真控制台. The console switches between two shapes depending on the current workspace:

  • Already a simulation project → the console loads directly and auto-detects the project's IP / registers / inputs and outputs (no manual import). When you open a simulation project folder, the console pops up automatically as well.
  • Not a simulation project (or no folder open) → the console shows a "Get Started" landing page; click ➕ New Simulation Project to create a project in the same view—no separate command needed.

  E --> F[Open the project] --> C

When you create a project, the extension automatically: 1. Copies the complete simulation environment to the new directory (Python scripts / Verilog BFMs / Makefile / example DUT) 2. Creates the in-project Python virtual environment .venv and installs opencv/numpy/pillow 3. Opens the project (the console then loads automatically)

The VIP Sim: 新建仿真项目 command still exists and is equivalent to the landing page's "New" button; day to day, "Open the simulation console" is the only entry point you need.

4.4 GUI operation notes

Import image: opens a file dialog to pick a PNG/BMP/JPG, copies it automatically to sim/testdata/, and sets it as the stimulus source.

Generate pattern: pops up 9 built-in test patterns: - Grayscale ramp (tests Gamma / contrast) - Color bars (tests color-space conversion) - Low-contrast chart (tests contrast enhancement) - Checkerboard (tests boundary alignment) - Gray card · 6500K / 3000K / 8500K (tests white balance) - Noise injection + dead-pixel injection (based on the current image)

Preprocessing: applies an operator to the input image before the simulation: Gaussian noise / dead-pixel injection / Gaussian blur / combination / custom (AI-generated)

Register editing: the console reads rtl/<IP>/regdef.json automatically; RW registers appear as editable input fields and RO registers show their default values grayed out. When you click Run, regcfg.hex is generated from the current values and written into the simulation.

Register read/write self-check: the simulation does not just "write the form values and call it done". Before the video stream starts, the reg_config BFM first writes every register, then reads each one back and compares, exercising the register read/write timing on the real logic. It prints REGCHK PASS/FAIL to the output panel (a mismatch reports the @addr/wrote/read detail), and only after the IP's register interface is confirmed correct is the pixel data released.

Run simulation: chains, in one click, gen_stimulus → gen_header → iverilog compile → vvp run (register configuration + self-check first, then the video stream) → gen_output → analyze.

Analysis panels: each of the 6 buttons opens its own Webview panel; multiple panels can be opened side by side for comparison.

5. Typical usage scenarios

Scenario 0: Import an existing project into simulation (the most common entry)

When to use: you already have an RTL project (code handed over by a team, an IP you wrote earlier) and want to bring it onto the simulation platform quickly to verify the image results.

Steps

  1. Ctrl+Shift+P / Cmd+Shift+P → VIP Sim: 导入已有工程 (or click "📥 Import existing project" on the console landing page)
  2. Select the root directory of the existing RTL project (the folder containing the .v/.sv files)
  3. The extension then does all of the following:
Step What happens
① Create the simulation workspace Creates a standalone <project>_vipsim/ directory next to the project; the original project is never modified
② Set up the Python environment Creates .venv and installs opencv / numpy / pillow
③ Scan and identify IPs Walks every .v/.sv; modules whose top level has both s_axis_* and m_axis_* ports are recognized as video IPs
④ Copy the RTL IP top level → rtl/<ip>/, shared submodules → rtl/_imported_common/ (deduplicated globally)
⑤ Generate the testbench Generates sim/tests/tb_<ip>.v from the DUT's real port names
⑥ Generate the register description Detects cfg_* buses → generates a rtl/<ip>/regdef.json skeleton
  1. Choose to open the workspace in a new window or the current one
  2. The console loads automatically; the recognized IPs appear in the IP dropdown
  3. Import an image → set the resolution → ▶ Run simulation

Recognition rules

Conditions for recognizing an AXI-Stream video IP:
  the module's top-level ports include both s_axis_tdata and m_axis_tdata
  (signal-name variants tolerated: tvalid/tready/tlast/tuser are all optional)
  • Missing tuser/tlast → the TB rebuilds frame/line boundaries from the pixel index
  • Missing s_axis_tready → the source pushes the stream freely (no backpressure)
  • cfg_* bus present → wired to the reg_config BFM automatically, and the register form is generated
  • Data files referenced by $readmemh → copied automatically; if missing, you are prompted to add them manually

Command-line equivalent

# Option 1: through the extension command (recommended)
# Ctrl+Shift+P → VIP Sim: 导入已有工程

# Option 2: run manually
python scripts/import_project.py --src /path/to/your/project --json

The original project changed? Run the import command again to refresh the workspace (you will be asked whether to overwrite and rebuild).

Scenario 1: Single-frame image simulation (most common)

Applicable IPs: color-space conversion, Gamma correction, dead-pixel correction, denoise, sharpening, contrast enhancement

Steps:

  1. Import a test image in the console (640×480 recommended; use small resolutions for everyday debugging)
  2. Select the target IP and set the resolution
  3. Edit register values (e.g. Gamma coefficient 0x04=0x00000003 for bypass mode)
  4. Click ▶ Run simulation
  5. When it finishes, check the output thumbnail → click the analysis buttons for the metrics

Console output example (when the golden reference passes):

🔧 Register self-check  REGCHK PASS  2/2 readbacks match (write-then-read compare)
📋 Golden reference  PASS  bit-exact, 0 mismatched pixels
📊 Quality analysis  PSNR 42.3 dB · 640×480

Command-line equivalent:

make all IP=gamma_corr WIDTH=640 HEIGHT=480 INPUT_IMG=sim/testdata/input.png

Scenario 2: Developing a new IP from scratch (vibe coding flow)

When to use: you have the project but no IP code at hand and will generate it with AI.

Recommended — spec-driven (RTL and golden model generated together, consistent by construction):

  1. Tell the AI: "Implement a 3-tap sharpening filter with coefficients [1,-2,1] and a bypass" (or a more specific spec)
  2. The AI writes .ip_spec.yaml per .trae/rules/project_rules.md and calls gen_ip_spec.py
  3. The toolchain produces 4 files in one shot:
File Purpose
rtl/<ip>/<ip>.v Verilog RTL—usable as-is, or modify the datapath
rtl/<ip>/regdef.json data source for the console's register form
sim/tests/tb_<ip>.v testbench skeleton
scripts/golden.py golden-model function (appended to MODELS/CONFIG)
  1. Refresh the console; the new IP appears in the IP dropdown automatically
  2. Run make verify IP=<ip> to verify (golden comparison runs automatically)

Traditional — follow the assignment doc (the 7 existing assignments):

  1. Read the spec for the assignment in docs/IP开发课题说明书.md
  2. Tell the AI: "Implement assignment 2, the Gamma correction IP, placing files per the project rules"
  3. The AI generates RTL + TB + regdef (the golden model must be added manually—see below)
  4. Refresh the console → import an image → run the simulation

The development iteration loop:

flowchart LR
    A["Describe the requirement to the AI"] --> B["gen_ip_spec.py generates\nRTL + TB + regdef + golden"]
    B --> C["make verify IP=&lt;ip&gt;"]
    C --> D{"Golden reference PASS?"}
    D -- No --> E["Fix the RTL / golden.py<br/>inspect analysis panels / waveforms"]
    E --> C
    D -- Yes --> F["Verify on a large image / run the regression"]

About fixing the golden model: the auto-generated golden model is an algorithm template; RTL details (fixed-point widths, truncation points, saturation logic) need manual review. How to check:

# Compare the RTL fixed-point arithmetic against golden.py's Python arithmetic
make verify IP=my_filter WIDTH=64 HEIGHT=48

# On FAIL, find where the mismatches are
# open output/reports/result_<ip>.json and look at mismatch_pixels
# decide whether it is fixed-point truncation error (tune CONFIG['tol']) or a logic bug (fix golden.py)

Scenario 3: Golden-reference comparison

Applicable IPs: all 7 IPs

Principle: every IP has a Python reference model (scripts/golden.py) that reproduces the processing result with integer/fixed-point arithmetic exactly matching the RTL; the simulation output is compared word by word.

How to run: - The comparison runs automatically when you click ▶ Run simulation in the console; the result is shown in the UI - Command line: make verify IP=gamma_corr WIDTH=640 HEIGHT=480

Reading the result:

Display Meaning
Golden PASS Bit-exact, 0 mismatched pixels. The algorithm is correct.
Golden FAIL Mismatched pixels exist; the count and the first mismatch coordinate are shown. The RTL needs checking.
No reference model No golden model registered for this IP yet; only image-quality analysis runs
Video mode · no per-frame bitwise comparison In video mode there is no word-by-word comparison; temporal analysis evaluates instead

Scenario 4: Multi-frame video simulation

Applicable IPs: denoise (temporal), auto white balance (inter-frame statistics), contrast enhancement (inter-frame statistics)

Steps:

  1. Click 🎬 Import video in the console
  2. Pick an MP4; the extension detects the frame count automatically
  3. Set the number of frames to simulate (2–30 recommended; iverilog is not fast)
  4. Click ▶ Run simulation
  5. When the frames finish: drag the slider to preview frame by frame → click "Temporal analysis" to watch the metrics evolve across frames

Important: statistics-based IPs (AWB, contrast enhancement) must be simulated over multiple frames. The gain is computed on frame N and takes effect on frame N+1; a single-frame simulation outputs the input unchanged.

Command line:

make video IP=denoise INPUT_VIDEO=sim/testdata/test.mp4 FRAMES=30

Scenario 5: Regression testing (CI batch verification)

Purpose: after changing a shared module, quickly verify that none of the IPs broke.

make regression

For every registered IP the command runs: single-frame passthrough → golden comparison → randomized backpressure test, and summarizes PASS/FAIL.

Scenario 6: Debugging with waveforms

Steps: 1. Click 📈 View waveform in the console (the VCD is generated and opened automatically) 2. Or from the command line: make sim WAVE=1 IP=gamma_corr 3. In the waveform viewer check: - reset-release timing from aresetn to s_axis_tvalid - SOF/EOL alignment of tuser/tlast (are frame start / line end correct?) - glitches on tdata during the tready handshake - pipeline latency: the number of clock cycles from input pixel to output pixel

Scenario 7: Defect injection and robustness verification

Operation: console ⚔ Preprocess → pick an injection → run the simulation

Injection What it tests
Gaussian noise σ=15 noise suppression capability of the denoise IP
Dead-pixel injection 200/frame whether the dead-pixel-correction IP can detect and repair them
Gaussian blur 5×5 whether the sharpening IP can restore clarity
Noise + dead pixels (combined) the cascade effect of chained processing (denoise → dead-pixel correction)

6. Image-quality analysis in depth

After every simulation, 5 analyses run automatically. Click the corresponding button in the console to open its standalone panel.

6.1 Image comparison

Shows the input image and the output image side by side to confirm the visual effect. Good for a quick "did anything happen at all" check.

6.2 Difference heatmap

Pseudo-color rendering of |output − input|. Red areas = large changes, blue = unchanged. Locate where the IP acts at a glance.

6.3 Sharpness analysis

Metric Algorithm Reading
Laplacian variance cv2.Laplacian().var() Overall sharpness. Higher is sharper.
Tenengrad value sum of squared Sobel gradients A classic focus-measure function. Stronger edges give a higher value.
Grade automatic verdict Blurry / Fair / Good / Excellent / Outstanding

Typical uses:

  • Sharpening IP development: feed a blurred test pattern; the Laplacian variance of the output should rise significantly
  • Denoise IP development: feed a noisy image; the output should not lose much sharpness (the Laplacian variance should not drop noticeably)

6.4 White-balance analysis

Metric Algorithm Reading
R/G/B gains gray-world assumption ideal values are 1.0 / 1.0 / 1.0
Color-temperature tendency estimated from the R/B ratio warm (yellowish) / neutral / cool (bluish)

Typical use: AWB IP development — feed a 3000K gray card (warm); the output gains should approach 1.0 / 1.0 / 1.0 and the color-temperature tendency should become "neutral".

6.5 Histogram

Metric Description
R/G/B means average brightness of the three channels
Brightness change shift from the input mean to the output mean
Quantile statistics P5/P50/P95 percentiles

Typical uses:

  • Gamma correction: the output mean should rise, lifting the shadows
  • Contrast enhancement: the histogram should spread more evenly

6.6 PSNR

Peak signal-to-noise ratio; measures how much the output differs from the input.

PSNR range Grade Meaning
> 40 dB Excellent Differences are tiny and invisible to the eye
30–40 dB Good Slight differences
20–30 dB Fair Noticeable differences (the IP is working; the processing is strong)
< 20 dB Poor Large differences (possibly an algorithm or parameter problem)

Note: A high PSNR is not necessarily good, and a low one is not necessarily bad. A sharpening IP naturally has a low PSNR (it deliberately changes pixel values). Judge PSNR together with the other metrics.

6.7 Gamma analysis

Measured Gamma curve vs. target Gamma curve. Samples a 16-step grayscale ramp and least-squares-fits the effective Gamma value.

Typical uses: Gamma-correction IP (target 2.2, deviation < 0.05 is excellent), color-space-conversion IP (target 1.0, passthrough).

9. FAQ

Q: The IP dropdown is empty after creating a project

A: A new project has only the passthrough example IP. After generating or hand-writing IP code, make sure a .v file exists under rtl/<ip_name>/, then refresh the console.

Q: The simulation says "no results yet" after running

A: Check the log in the VIP Sim output panel. Common causes: the iverilog compile failed (syntax error), stimulus.hex was not generated, or a pixel-count mismatch in the DUT hung the sink.

Q: Statistics-based IPs (AWB / contrast enhancement) show no effect in single-frame simulation

A: That is expected. Statistics-based IPs compute their gains/parameters on frame N and apply them on frame N+1. You must set frames ≥ 2 in the console; the analysis tool takes the last frame's result by default.

Q: 4K simulation is slow

A: iverilog is an interpreted simulator; one 4K frame has 8.3 million pixels and can take tens of minutes. Use a reduced resolution for everyday debugging (e.g. 64×64 or 256×144)—the algorithm logic is identical to full resolution. Run full resolution only once or twice at milestone verification.

Q: How to add a golden model for a new IP

A: Edit scripts/golden.py: 1. Add '<ip>': m_<ip> to the MODELS dict 2. Implement m_<ip>(pixels, regs, width, height) → return the expected pixel list 3. Register the comparison parameters (frame count, tolerance, allowed mismatch ratio) in the CONFIG dict 4. Run make verify IP=<ip> to check

Q: The simulation log shows ERROR: simulation timeout

A: The DUT did not output enough pixels and the sink kept waiting. Check: - whether the DUT passes tuser/tlast through correctly - whether pipeline depth delays the output (the timeout guard is generously large unless the pixel count is badly mismatched) - whether the statistics-based IP is in bypass mode

Q: PSNR is 100 dB but the golden reference FAILs

A: The golden reference checks consistency between the RTL fixed-point result and the Python reference model (bit-exact); PSNR measures the difference between output and input. The two are independent—a high PSNR only says the output is close to the input, not that the algorithm is correct.

Q: The output image looks purple/green-shifted

A: Check that the byte arrangement of tdata in the RTL is {8'd0, R[7:0], G[7:0], B[7:0]}. Common mistakes are reversing the RGB order or truncating the width.
