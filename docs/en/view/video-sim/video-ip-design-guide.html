Video IP Design Guide

EvoVerse VIP/IP Design Guide and Assurance Contract v1.1

Document version: v1.1 Updated: 2026-09-01

0. Document relationships

  • The single authoritative spec source for customer video IP design
  • Kept in sync with the frozen-spec Assurance contract (see §0.5)
  • Does not replace the Efinity toolchain reference or the IPM library guide

0.5 SDK Assurance contract statement

This guide defines the design requirements for video IPs; a project's frozen specification writes each instance's explicit values into assurance.contracts and validates candidate RTL with evoverse.video@1.

RTL may be written freely by the designer or an Agent, but its video intent must not be inferred from module names or port names. When module, imageWidth, bitsPerPixel, parallelism, or lineBufferDepth is missing, the spec must be marked DECISION_REQUIRED and must not enter freezing or controlled Assurance.

SDK implementation points:

  1. Rules: sdk/design-assurance/evoverse_assurance/protocols/video.py
  2. Spec: the frozen ModuleSpec/SystemSpec assurance.contracts
  3. Execution entry: evoverse assurance or MCP assurance_check
  4. Project harness: evoverse new-project copies this guide to <project>/docs/VIP-IP-DESIGN-GUIDE.md and drops a project-level instruction (applyTo: **/*.{v,sv}); any in-project change to video_* code must follow it. Single source: this file (docs/video-sim/视频IP设计指南.md); the bundle (build-vsix.ps1 vendor) and the in-project VIP-IP-DESIGN-GUIDE.md are both generated from this file—do not edit them directly.

Sync principle: changes to this guide, the spec template, and the evoverse.video@1 rules must be reviewed together. Any change on either side must leave a trace in DAYLOG/.

1. Scope and terminology

  • VIP: Video IP—any AXI-Stream video-processing core
  • Generic register interface (cfg_*)
  • AXI-Stream streaming interface (s_axis_/m_axis_)
  • BRAM line buffer
  • Synchronous reset (aresetn, active-low)

2. Common specification (contract body)

2.1 System parameters

Parameter Default Description
MAX_WIDTH 3840 maximum pixel width
MAX_HEIGHT 2160 maximum pixel height
DATA_WIDTH 24 default pixel width (RGB888)
PARALLEL 1 pixels per clock
CLK_FREQ_MHZ 125 operating clock frequency

2.2 Clock architecture

  • Single clock aclk + active-low synchronous reset aresetn
  • Synchronized reset release (rst_sync_r two-stage flip-flop chain)
  • Multiple clock domains must flag CDC explicitly in §4

2.3 AXI-Stream video interface standard (contract)

Signal set (compatible with Xilinx AXI-Stream Video): | Signal | Direction | Width | Description | |---|---|---|---| | aclk | in | 1 | clock | | aresetn | in | 1 | asynchronous active-low reset | | s_axis_tvalid | in | 1 | source data valid | | s_axis_tready | out | 1 | sink ready | | s_axis_tdata | in | DATA_WIDTH | pixel data | | s_axis_tuser | in | 1 | SOF, start of frame | | s_axis_tlast | in | 1 | EOL, end of line | | m_axis_* | out | as above | mirrored output set |

Conventions: - SOF (tuser=1) is asserted for exactly 1 cycle on the first pixel of each frame - EOL (tlast=1) is asserted for exactly 1 cycle on the last pixel of each line - Frame/line counters are maintained inside the IP and never exposed

2.4 Register interface standard (contract)

Signal set: | Signal | Direction | Width | Description | |---|---|---|---| | cfg_clk | in | 1 | register-interface clock (needs CDC when asynchronous to aclk) | | cfg_addr | in | 8 | byte address | | cfg_wdata | in | 32 | write data | | cfg_wen | in | 1 | write enable | | cfg_ren | in | 1 | read enable | | cfg_rdata | out | 32 | read data | | cfg_rdy | out | 1 | ready |

Register map template: - 0x00 IP_VERSION (RO) - 0x04 IP_CTRL (RW): [0] enable, [1] bypass - 0x08 IP_STATUS (RO): [0] running, [1] error - 0x0C IP_RESET (WO): write 1 for a soft reset - 0x10 IMG_WIDTH (RW, 16 bit) - 0x14 IMG_HEIGHT (RW, 16 bit) - 0x18 IMG_FORMAT (RW, 3 bit: 0=RAW8/1=RAW10/2=RAW12/3=RGB888/4=YUV422) - 0x1C-0x3C IP_PARAM_* (RW, algorithm parameters, defined per IP)

2.5 Basic IP structure (contract: top-level template)

module <ip_name> #(
    parameter C_DATA_WIDTH = 24,
    parameter C_MAX_WIDTH  = 3840,
    parameter C_MAX_HEIGHT = 2160
) (
    // System interface (fixed order)
    input  wire        aclk,
    input  wire        aresetn,

    // Register interface
    input  wire        cfg_clk,
    input  wire [7:0]  cfg_addr,
    input  wire [31:0] cfg_wdata,
    input  wire        cfg_wen,
    input  wire        cfg_ren,
    output wire [31:0] cfg_rdata,
    output wire        cfg_rdy,

    // AXI-Stream input
    input  wire        s_axis_tvalid,
    output wire        s_axis_tready,
    input  wire [C_DATA_WIDTH-1:0] s_axis_tdata,
    input  wire        s_axis_tuser,
    input  wire        s_axis_tlast,

    // AXI-Stream output
    output wire        m_axis_tvalid,
    input  wire        m_axis_tready,
    output wire [C_DATA_WIDTH-1:0] m_axis_tdata,
    output wire        m_axis_tuser,
    output wire        m_axis_tlast
);

Port-order contract: ① system (aclk/aresetn) → ② registers (cfg_) → ③ input stream (s_axis_) → ④ output stream (m_axis_*). Any reordering counts as an implementation defect.

2.6 BRAM line-buffer contract

Resource estimation formula (used for the synthesis resource budget in §4):

Per-line data volume (bits) = IMG_WIDTH × BPP × PARALLEL
Required BRAM blocks = ceil(per-line data volume / 10240) × number of lines

TJ180 limit: a single IP ≤ 16 BRAM blocks; line-buffer depth ≤ 4 lines.

2.7 Performance contract

Metric Requirement
Maximum resolution 3840×2160
Maximum frame rate 60 fps @ 1080p
Pipeline depth ≤ 16 stages
End-to-end latency ≤ 1 line (with BYPASS)

3. RTL coding and naming conventions

3.1 Naming conventions

Element Rule Example
Module name lower_snake_case video_register_slice
Parameter UPPER_SNAKE_CASE with C_ prefix C_DATA_WIDTH
Register address UPPER_SNAKE_CASE with REG_ prefix REG_IP_CTRL
Port lower_snake_case with direction suffix s_axis_tvalid, cfg_wdata
Internal signal lower_snake_case pixel_cnt

3.2 Coding style (aligned with the common SDK template)

  • timescale 1ns / 1ps
  • default_nettype none (restore wire at the end of the file)
  • Synchronous reset aresetn, active-low
  • Synchronized reset release (two flip-flop stages)
  • Port suffixes: _i (input), _o (output), _io (bidirectional)
  • Chinese inline comments

3.3 Simulation test requirements

  • Every IP must include a self-checking _tb.v testbench
  • Must cover: basic function, boundaries (minimum/maximum resolution), back-to-back frames, reset recovery

3.4 Synthesis constraint template

create_clock -name aclk -period 8.0 [get_ports aclk]
set_input_delay -clock aclk -max 2.0 [all_inputs]
set_output_delay -clock aclk -max 2.0 [all_outputs]
set_false_path -from [get_ports {aresetn}]
set_false_path -from [get_ports {cfg_clk}]   # asynchronous register clock

4. Multiple clock domains and CDC

4.1 Single-clock IP (default)

  • All signals live in the aclk domain
  • Register interface cfg_clk = aclk (synchronous register interface)

4.2 Asynchronous register interface

  • When cfg_clk is asynchronous to aclk, a two-stage synchronizer is required
  • CDC must be flagged in RTL comments
  • The checker verifies the presence of // CDC: comments

5. Assurance contract (SDK implementation points)

5.1 The frozen spec must declare

assurance:
  rulePacks: [rtl-baseline@1, evoverse.video@1]
  contracts:
    - id: camera_pipe
      protocol: evoverse.video
      module: video_pipe
      imageWidth: 1920
      bitsPerPixel: 24
      parallelism: 1
      lineBufferDepth: 2

5.2 Rule coverage

  1. §2.3 signal set completeness (6 each of s_axis_ / m_axis_)
  2. §2.4 register signal set completeness (7 cfg_*)
  3. §2.5 port order (system → registers → input stream → output stream)
  4. §2.6 BRAM line-buffer budget

5.3 How it runs

A controlled RTL task reads the contract from the frozen spec and keeps the candidate binding receipt. Free-form development can run evoverse assurance directly to check explicitly declared requests; without dynamic evidence the result is incomplete, not PASS.

6. Out of scope for this guide

  • The ISP algorithms themselves (demosaic/AWB/denoise, etc.): implemented by customers on top of the templates
  • regmap.h C-header generation: to be included in v1.1
  • Cross-language bindings: to be included in v1.1
