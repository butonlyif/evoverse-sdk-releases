Design Assurance 规则与证据

EvoVerse Design Assurance

零依赖、vendor 无关的设计保证（Design Assurance）引擎：对 RTL 项目运行确定性规则与协议契约检查，用同一套证据（evidence）与例外（exception）机制产出可复现的 JSON 报告。

  • 代码：sdk/design-assurance/（纯 Python 3 标准库，无第三方依赖）
  • 契约：sdk/design-assurance/schema/ 下的 JSON Schema 是语言无关的公共契约
  • 测试：python -m unittest discover -s sdk/design-assurance/tests -v

状态语义：三态而非两态

status 含义
pass 所有启用的规则均通过或被有效例外覆盖
fail 存在至少一条结构可证伪的 violation
incomplete 存在缺少证据的行为属性（unverified）

缺少证据是 unverified，不是 pass（missing evidence is unverified, not pass）。 时序性属性（如握手 payload 稳定）无法由结构扫描证明，必须提交 property-run 证据；没有证据时报告状态为 incomplete，绝不静默放行。

规则包

规则包 内容
rtl-baseline@1 18 条确定性 RTL 基线规则：结构 9 条（latch、组合环、组合阻塞赋值、位宽截断、派生时钟、case 完备、复位极性、default_nettype、多驱动）+ 域 9 条（复位同步释放、复位已知值、CDC 同步属性、CDC 最少级数、CDC 总线禁逐位同步、FSM default 恢复、握手 payload 稳定、FIFO 溢出保护、FIFO 下溢保护）
amba.axis@1 AXI4-Stream 契约：6 条静态规则（binding 校验、信号存在、信号方向、TDATA/TKEEP 位宽、旁带位宽）+ 5 条行为规则（valid-stable、payload-stable、handshake=至少完成一次 beat 的死锁检测、reset-valid、beat-fields），并生成可直接 bind 的 SVA 断言/覆盖资产
custom@1 用户自定义正则规则（经规则管理器添加，存于 assurance-rules.json）——声明式 lint：对每个源文件全文 re.finditer，命中即报违规（带行号）。无内置规则

规则管理（Rule Manager）

所有规则开关集中在一个全局配置文件：<EVOVERSE_HOME>/assurance-rules.json（契约见 sdk/design-assurance/schema/rule-config.schema.json）。它对每一次 assurance 检查生效（CLI / MCP / 规则管理 UI 读取同一份）。

{
  "version": 1,
  "enabled": true,
  "packs": { "rtl-baseline@1": true, "amba.axis@1": false },
  "disabledRules": ["rtl.comb.blocking"],
  "customRules": [
    {
      "id": "myteam.no-tabs",
      "description": "tabs are not allowed in RTL sources",
      "severity": "warning",
      "pattern": "\t"
    }
  ]
}
字段 语义
enabled 总开关。false 时跳过全部规则——fail-closed：报告产出 engine.no-rule-packs unverified，状态 incomplete，绝不冒充 pass
packs 每个规则包的开关；缺省视为启用
disabledRules 逐条规则禁用（比关包更细粒度）
customRules 用户自定义正则规则，注册为 custom@1 包，随 packs["custom@1"] 开关

自定义规则约束：id 匹配 ^[a-z][a-z0-9.-]*$ 且不得与 disabledRules 中的条目重名；severity ∈ {error,warning,info}；pattern 必须是可编译的 Python 正则。非法配置会被引擎拒绝（CLI exit 64），不会静默降级。

UI：Welcome → Assure → Rule Manager

evoverse.assuranceRules 命令（Welcome 页 Assure 卡片）打开规则管理面板：

  • 总开关 + 每包开关 + 每条规则开关（含 severity 徽标与规则描述）
  • 自定义规则的添加（id / severity / description / pattern，客户端预校验）与删除
  • Save 写入 assurance-rules.json 后回读引擎校验——引擎拒绝的错误（如非法正则）会以引擎自身的错误消息回显；Reset 可一键恢复全启用默认态
  • 配置文件路径显示在面板头部

与请求级 disabledRules 的关系

请求 JSON 的 disabledRules（见 request.schema.json）是单次运行级的临时禁用；全局配置在 CLI/MCP 入口处经 apply_rule_config 并入请求（全局禁用 ∪ 请求禁用）。引擎内部对二者一视同仁。

请求（Assurance Request）

请求是一个 JSON 文档，契约见 sdk/design-assurance/schema/request.schema.json。可复制模板：

{
  "projectRoot": ".",
  "sources": ["rtl/axis_source.sv"],
  "rulePacks": ["amba.axis@1"],
  "interfaces": [
    {
      "id": "m_axis",
      "protocol": "amba.axis",
      "role": "master",
      "module": "axis_source",
      "clock": "clk_i",
      "reset": "rst_n_i",
      "resetPolarity": "active-low",
      "signals": {
        "tvalid": "m_axis_tvalid_o",
        "tready": "m_axis_tready_i",
        "tdata": "m_axis_tdata_o",
        "tlast": "m_axis_tlast_o",
        "tkeep": "m_axis_tkeep_o"
      },
      "widths": { "tdata": 32, "tkeep": 4 }
    }
  ],
  "evidence": [
    {
      "id": "sim-pass-1",
      "kind": "property-run",
      "status": "pass",
      "executor": "evoverse-sim",
      "executorVersion": "1.0.0",
      "artifact": "sim/m_axis.log",
      "propertyId": "evoverse_axis_m_axis_payload_stable"
    }
  ],
  "exceptions": [
    {
      "ruleId": "rtl.cdc.min-stages",
      "scope": { "module": "slow_sync" },
      "reason": "single-flop is acceptable for this debounce path",
      "expiresOn": "2026-12-31"
    }
  ]
}

要点：

  • sources 必须是 projectRoot 内的相对路径，禁止越界
  • interfaces 显式绑定协议信号到模块端口名——引擎不靠端口名猜测
  • 属性命名：evoverse_axis_<接口id sanitized>_<suffix>（如 evoverse_axis_m_axis_valid_stable）

例外（Exception）到期形式

每条例外必须恰好提供一种到期形式，防止例外变成永久豁免：

  • expiresOn：ISO 日期（YYYY-MM-DD），过期自动失效
  • untilRulePack：如 "rtl-baseline@2"，规则包升级后自动失效

例外必须给出精确 scope（file / module / interface 三选一，禁止通配符）与理由。

证据（Evidence）

  • status：pass | fail | error
  • kind 必须形如 property-run / lint-run 等小写 *-run 族；只有 property-run 能关闭行为属性
  • pass 证据清除对应的 unverified 行为规则；fail 证据把行为规则升级为 violation，引用 executor / artifact / counterexample
  • 无任何证据 → unverified，报告 incomplete
  • 作用域：propertyId 为规则 id（如 rtl.handshake.payload-stable）时只在整个项目恰好一个候选模块时生效；多模块项目需按模块限定 propertyId=<规则id>@<模块名>，一条证据不能同时关闭多个模块
  • 声明了 interfaces 却未启用对应协议包（如 amba.axis@1）时，报告产出 engine.uncovered-interface unverified（fail-closed），不会静默通过

CLI

evoverse assurance check <project>
    [--request FILE] [--config FILE] [--format text|json]
    [--include-testbench] [--include-glob PATTERN] [--exclude-glob PATTERN]
evoverse assurance rules [--config FILE] [--format text|json]
  • check 的 --request 缺省时依次查找 <project>/.evoverse/assurance.json，再退化为自动发现 .v/.sv/.vh/.svh 源 + rtl-baseline@1
  • --config 缺省为 <EVOVERSE_HOME>/assurance-rules.json（存在才读；不存在视为全启用）
  • rules 输出规则目录（全部包 + 每条规则的开关状态/severity/description，custom 规则另含 pattern）——规则管理 UI 的数据源；--format text 为人读格式
  • JSON 仅写 stdout，诊断仅写 stderr

自动发现时跳过 testbench（默认）

rtl-baseline@1 只分析可综合子集；testbench（initial/$task/#delay/@event）属域外。自动发现按默认清单跳过 testbench 风格的文件：

跳过形态 说明
子树 sim/、testbench/、tb/
基名 tb_*.*、*_tb.*、sim_*、test_*

跳过只是源收集层，引擎本身仍可分析；--include-testbench 可重新开启；--include-glob PATTERN 仅保留匹配文件（隐式关闭默认 testbench 跳过）；--exclude-glob PATTERN 在默认清单之上再叠加排除。scanner 对 initial ... end 整块作 testbench 跳过（记录 info，不入 unverified）。

退出码契约

退出码 含义
0 pass（rules 子命令正常输出）
1 fail
2 incomplete
64 invalid request / usage（请求非法、项目目录缺失、无源文件、规则配置非法）
70 engine failure（引擎内部异常，绝不静默崩溃）

示例：

# 检查一个工程（读取全局规则开关）
sdk/cli/evoverse assurance check my-project --request my-project/assurance.json --format json

# 查看规则目录与开关状态
sdk/cli/evoverse assurance rules --format text

# 用指定的配置文件检查（不动全局配置）
sdk/cli/evoverse assurance check my-project --config team-rules.json

MCP

MCP 工具 assurance_check 是 CLI 的薄适配器（不复制引擎逻辑）：

  • 入参：project（必填）、request（可选）、include_testbench（可选，默认 false）、include_glob（可选，fnmatch 模式数组）、exclude_glob（可选，fnmatch 模式数组）、format 固定为 JSON
  • 退出码 1（fail）与 2（incomplete）仍返回完整 JSON 报告；仅 64/70 映射为 MCP error
  • testbench 跳过规则与 CLI --include-testbench / --include-glob / --exclude-glob 完全一致
  • 旧工具 check_rtl_code_style 保留原有字段（violations / fileCount / totalLines / severity summary），内部经 legacy_style_report 适配共享引擎，unverified 永不作为 violation 暴露

报告

报告是确定性的：同请求产出同 digest。顶层字段：status / engineVersion / rulePacks / timestamp / digest / projectRoot / sourceCount / summary（errors/warnings/infos/unverified）/ violations / unverified / exceptions / evidence。契约见 schema/report.schema.json。

架构定位

Design Assurance 是设计原则规则的可执行归属地（single source of truth）：规则、证据、例外都由它统一定义与裁决；Adapter 与 Catalog 职责不变。详见 sdk/docs/SDK-ARCHITECTURE-VISION.md。

编辑器中的旧“代码检查”命令和 MCP 的 check_rtl_code_style 仅是兼容入口，不再拥有规则实现。Vibe Coding 生成前绑定 rule-pack/config/interface digest，候选 RTL 先做静态 Assurance；incomplete 中可执行的行为属性进入 Test IR，由 Icarus、Questa 或 Video Sim 产生合格 property evidence 后再次交给本引擎裁决。功能仿真与 Assurance 必须同时为 PASS，父级模块才会解锁。

视频 IP 合规

视频 IP 不依赖模板生成入口。冻结规格声明 evoverse.video@1 契约后，Design Assurance 独立验证寄存器接口、端口组顺序和 TJ180 BRAM 行缓冲预算；缺少资源输入时报告 incomplete，不会推断通过。

动态属性（payload 稳定性、AXIS handshake 活性）在测试层允许 unverified——按设计需仿真证据（property-run）闭环。

高级参考用于按需查询；设计记录、发布流程、审计报告和未来规划不属于客户操作入口。
