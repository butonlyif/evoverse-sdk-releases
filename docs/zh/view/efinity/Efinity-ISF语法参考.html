Efinity ISF 语法参考

适用版本：Efinity 2026.1（C:\Efinity\2026.1） 更新日期：2026-09-25 证据基准：本文所有论断均直接取自 Efinity 2026.1 安装目录内的 Python 源码、官方 examples/helloworld-unified 示例，以及 EvoVerse SDK 自带的 sdk/cli/import_gpio.* 自检工具。每条论断后以 （路径:行号） 形式标注证据出处。

0. 文档定位

项目 内容

一句话结论（先记住这个）： ISF 是被 Python exec() 逐行执行的源码，执行上下文中 design 变量绑定 Efinity DesignAPI 实例；它分为一次性 bootstrap（含 create_*）与重放安全（仅 set/assign）两种合法用法，工程 XML 只允许引用重放安全的 ISF。

1. ISF 本质：被 exec 执行的 Python API 源码

1.1 执行模型

ISF 文件的每一行都会被取出并交给 Python exec() 执行：

环节 证据
逐行 exec(code) isf_importer.py:236
执行前注入 design = self.design_api（绑定 DesignAPI 实例） isf_importer.py:217
模块化执行路径同样注入：setattr(module, "design", self.design_api) isf_importer.py:287
导出侧写出的行同样以 design. 开头（design_api_handle="design"） isf_exporter.py:94

因此在 ISF 里能写的，就是 DesignAPI 暴露的 Python 方法调用（第 2 章全集），外加 Python 语言本身允许的注释与空行。不存在任何"ISF 专用语法"——所谓 ISF 语法就是 DesignAPI 方法签名的文本序列化格式。

1.2 预过滤规则

导入器在 exec 之前对每行做预判断（isf_importer.py）：

规则 行为 证据
空行或整行 # 注释 直接跳过，不执行 isf_importer.py:227（code == "" or code.startswith("#")）
--skip-resasg 启用时，以 design.assign 开头的行 跳过（用于消费 .auto_asg.isf 时只要属性、不要分配） isf_importer.py:231-233
其余行 交给 exec() isf_importer.py:236

推论：注释必须写成 Python 注释（#），行尾注释作为合法 Python 也能执行；但为了与导出器产出一致（见 §5.5），建议只使用整行注释。

1.3 错误分级与终止行为（决定"一个坏行毁掉整个文件"的范围）

导入器按异常类型分级处理（isf_importer.py）：

异常 级别 是否继续处理后续行 证据
PTException（Efinity 语义错误，如实例不存在） warning 继续 importer 异常分支
AttributeError（方法名不存在 → 打错字） error 继续 importer 异常分支
SyntaxError / UnicodeError / TypeError / 其他 Exception fatal break，终止整次导入 importer 异常分支

关键语义：import_isf 只要 issue 注册表非空（哪怕全是 warning 级）就返回 False（isf_importer.py:191 附近）。也就是说——

warning ≠ 通过。任何一条 issue 都会导致该次 import 判定失败，统一流程随即 abort（§7.2）。

导入完成后还有后处理：重算 PLL 频率 + 运行 APIPropertyChecker 设计检查（isf_importer.py:414-431），检查产生的问题同样计入 issue。

1.4 ISF 不是 XML、也不是引脚表格

格式 本质 消费者
.isf（ISF） Python API 源码，design.create_input_gpio(...) 等 efx_run_pt_unified.py / DesignAPI.import_design()
<design>.peri.xml efxpt:design_db 命名空间的工程源文件（数据库），只能由 Efinity PT 工具产出 PT 工具 / GUI
3 列 GPIO .csv 仅引脚清单，走 ImportGPIODesign 后端（GUI 向导同款） import_gpio_cli.py:154

不要在 .isf 后缀里写 <efx:gpio> 之类 XML；不要手写 <design>.peri.xml（namespace 是 efxpt:design_db，schema 为 peri_design_db.xsd，官方 helloworld.peri.xml 头部可证）。历史上 SDK 曾产出过 46 KB 的 <EFX_PERI_INTERFACE> XML 命名为 *.peri.isf，被 ISF 导入器以 "invalid syntax" 直接拒绝——这个教训已固化为强制自检（§6）。

1.5 ISF 与 peri.xml 的关系（理解重放的前提）

统一流程（unified flow）中：

  1. <design>.peri.xml 是持久化的工程源文件（官方 unified 示例全部自带），构建时被加载；
  2. 工程 XML 引用的每个 .isf 会被重放（import）到这份已存在的数据库上；
  3. design_api.save() 把合并结果写回 peri.xml（efx_run_pt_unified.py:281）。

所以 ISF 的每一条命令都跑在"数据库已存在"的前提下——这就是 §3 重放安全契约的根源。

2.2 创建族（一次性 bootstrap）

2.2.1 create_block

# design.py:192
def create_block(self, name: str, block_type: str, **kwargs)
  • block_type 常用：PLL、OSC、DDR、LVDS_RX、LVDS_TX、MIPI_RX、MIPI_TX、JTAG、SPI_FLASH 等（完整合法集合见 §5.2 导出器支持表）。
  • kwargs 支持创建期参数：mode / conn_type / tx_mode / rx_conn_type（design.py:192 签名）。
  • 序列化格式（isf_command.py:102-108）：
design.create_block("pll_inst1","PLL")
design.create_block("inst","TYPE",mode="X")     # 带 kwargs 时

2.2.2 14 个 create_*_gpio

方法 design.py 行号 用途 典型使用场景
create_input_gpio 1072 普通输入 RTL 顶层输入端口（通常由综合自动推断，ISF 中一般不需要）
create_output_gpio 1098 普通输出 同上
create_inout_gpio 1124 双向 顶层双向 IO（如 sda_io）
create_open_drain_output_gpio 1150 开漏输出 I2C 类开漏驱动
create_vref_gpio 1170 VREF 参考电压 SSTL 等需要 VREF 的接口
create_input_clock_gpio 1188 单端输入时钟 普通时钟输入引脚
create_regional_input_clock_gpio 1207 区域时钟输入 Regional clock 网络
create_pll_input_clock_gpio 1226 PLL 参考时钟输入 PLL 必备（见 §4.2 实录第 15 行）
create_pll_ext_fb_gpio 1245 PLL 外部反馈 EXTERNAL_FEEDBACK 模式
create_mipi_input_clock_gpio 1265 MIPI 输入时钟 MIPI RX 参考
create_pcie_perstn_gpio 1285 PCIe 复位 PERSTn 引脚

create_global_control_gpio 1324 全局控制 全局控制网络
create_unused_gpio 1343 显式未用 声明保留/悬空脚

总线判定规则（design.py:1088-1091，以 create_input_gpio 为代表，其余 create 同构）：

# msb == lsb → 标量 GPIO；msb != lsb → GPIO 总线（gpio_bus）
if msb == lsb:
    gpio = ...
else:
    gpio_bus = ...

序列化格式（isf_command.py:45-48）：

design.create_input_gpio("rstn")            # 标量
design.create_input_gpio("data_in", 3, 0)   # 总线，msb=3, lsb=0

陷阱：普通 GPIO（RTL 顶层端口）不要在 ISF 里重新创建。Unified Flow 下综合工具会从 RTL 端口自动推断 GPIO；ISF 里重复 create 同名实例会在重放时触发 already exists（§3.4、§8.2）。ISF 的 create_ 只应服务于硬 IP 与其专用 GPIO*（PLL/DDR/LVDS/OSC/MIPI 及 PLL_CLKIN 类）。

2.3 属性族（可重放）

set_property（design.py:507）

def set_property(self, inst, prop_name: Union[str, Dict[str, str]], prop_value=None, block_type: str="GPIO")
  • 四参形式是 ISF 序列化的唯一形态：序列化器恒输出 4 个位置参数（isf_command.py:147）：
design.set_property("pll_inst1","REFCLK_FREQ","25.0","PLL")
design.set_property("reverse","PULL_OPTION","WEAK_PULLUP")     # block_type 省略时为 GPIO
  • ⚠️ set_property 的 docstring 明确警告：不要用它设置资源和引脚——那是 assign_resource / assign_pkg_pin 的职责（design.py:507 docstring）。
  • prop_name 可传 dict 批量设置（Python 调用层能力；文本 ISF 一行一条属性）。
  • from_str 解析正则只给 prop_value 开了空格与方括号：[\w\s\.\[\]]*（isf_command.py:130）——含逗号/引号的值在文本 ISF 中不可表达。

set_device_property（design.py:559）

def set_device_property(self, inst: str, prop_name, prop_value=None, devset_type: str="IOBANK")

器件级设置入口。devset_type 的合法集合恰好 5 类（int_device_setting.py:79-108，is_setting_supported 判定）：

devset_type 支持条件
IOBANK 恒支持
SEU 仅 Tesseract 家族
RU 器件存在 ctrl_reg
EXT_FLASH 器件存在 ext_flash_reg
CLKMUX 仅 Tesseract（源码注释：Trion clkmux has no configuration）

set_iobank_voltage（design.py:639）

def set_iobank_voltage(self, bank_name: Union[str, Dict[str, str]], voltage=None)

它就是 set_device_property(bank, "VOLTAGE", volt, "IOBANK") 的语法糖（design.py:639 实现）——因此天然幂等、可重放：

design.set_iobank_voltage("TL","3.3")

硬约束（违反 → Design Check io_bank_rule_voltage_assignment）：同一 bank 所有 IO 必须同电压标准；MIPI bank 必须 1.2V 且不得与 LVDS 共 bank；HSIO bank 内 GPIO/LVDS/MIPI 之间须留至少一对未分配 IO 做隔离；Ti60ES 不支持 2.5V。

set_gpio_unused_state（design.py:1360）

全局未用引脚电平设置。序列化（isf_command.py:92）：

design.set_gpio_unused_state("value")

set_mode_sel_name（design.py:754）

def set_mode_sel_name(self, bank_name, value, bonded_bank=None)

设置 bank 的 mode_sel 名称；bonded_bank 处理非满 bonded 封装的 bank 对应关系。per-IO 电压标准（iostd）与 mode_sel_name 最终都落在 peri.xml 的 efxpt:iobank 元素上（helloworld.peri.xml 可证）。

lock_property（design.py:1936）

def lock_property(self, inst, prop, value, btype, checksum)

把属性登记进 netlist_config（由外围网表 checksum 锁定）。注意：inst 未知时静默返回 None，不报错（design.py:1936 实现）——ISF 里写错实例名的 lock 行不会立即暴露，排查时务必先确认实例存在。序列化（isf_command.py:175）：

design.lock_property("inst","PROP","VALUE","TYPE","checksum")

2.4 资源与引脚（可重放）

assign_resource（design.py:790）

def assign_resource(self, inst, res_name, block_type="GPIO", override=True)

把实例放到具体硬资源（如 PLL → PLL_TL0）。序列化恒 3 位置参数（isf_command.py:156）：

design.assign_resource("pll_inst1","PLL_TL0","PLL")

assign_pkg_pin（design.py:837）

def assign_pkg_pin(self, inst, pin_name, override=True)

引脚分配。总线成员写 "bus[N]" 格式。序列化恒 2 位置参数（isf_command.py:164）：

design.assign_pkg_pin("rstn","J13")
design.assign_pkg_pin("led[0]","K14")

GPIO 一律用 assign_pkg_pin 而非 assign_resource 分配引脚——导出器对 GPIO 的引脚导出通道就是 assign_pkg_pin（isf_exporter.py:837-853）。

2.5 删除族（API-only，无 ISF 序列化——这是"ISF 无 delete"的证据）

方法 行号 说明
delete_block 255 API 层可删 block
delete_gpio 302 API 层可删 GPIO

API 里存在这些删除能力，但 isf_exporter.py 全部 46 个类（§5）与 isf_command.py 全部命令类里没有任何一个能把它们序列化成 ISF 文本。结论：ISF 命令集没有 delete/clear，也不允许发明。清库的唯一合法途径是删除 peri.xml 后重新 bootstrap（由工具/工程生命周期决定，脚本不得擅自删 peri.xml）。

3. 重放安全契约（本仓库 ISF 验收的第一判据）

3.1 为什么存在这个契约

Unified build 的固定行为：加载已持久化的 <design>.peri.xml → 逐个 import 工程 XML 引用的 ISF → save() 写回。每次编译都会重放（§1.5、efx_run_pt_unified.py）。因此 ISF 里的每条命令都必须能对"实例已存在"的数据库重复执行。

3.2 幂等命令白名单

工程引用的 ISF 只允许出现这些命令（重复执行结果不变）：

命令 幂等性依据
design.set_property(...) 属性覆写，design.py:507
design.assign_pkg_pin(...) 带 override=True 重分配，design.py:837
design.assign_resource(...) 带 override=True 重分配，design.py:790
design.set_device_property(...) 器件设置覆写，design.py:559
design.set_iobank_voltage(...) set_device_property 的糖，design.py:639
design.set_gpio_unused_state(...) / set_mode_sel_name(...) 覆写型，design.py:1360 / 754

lock_property 亦为登记型（design.py:1936），但通常由工具在部分设计流程中生成，手写 ISF 不需要。

3.3 一次性 bootstrap：create_*

create_block 与全部 create_*_gpio 是"创建实例"语义（isf_command.py:177-181 的 is_creation_command 正是以它们判定创建类命令）。对已含同名实例的 peri.xml 重放 → 触发 already exists。所以：

  • create_* 只能在 peri.xml 尚不存在（或清库重建）时执行一次；
  • 之后必须从会被重放的 ISF 中移除（注释掉）。

3.4 already exists 报错链（二次编译必失败的机制）

重放含 create_* 的 ISF 时，底层查重失败抛错，出处：

抛错点 文件:行号
数据库项查重 pt\bin\design\db_item.py:792
设计导出/导入层 pt\bin\design\design_export_import.py:2015
服务层 pt\bin\design\service.py:635

报错形如 GPIO/PLL ... exists。这是 PTException（warning 级、继续执行），但如 §1.3 所述——任何 issue 都使 import 判定失败，统一流程随即 abort。表现为"第一次编译 PASS、第二次必失败"。

3.5 工程侧契约（SDK 三条铁律）

  1. 工程 XML 只引用重放安全的 ISF（官方即如此：§4.4）。
  2. 任何构建路径（SDK / adapter / 脚本）不得删除 <design>.peri.xml——它是工程源文件，删了重生成是 workaround 不是修复。
  3. ISF 与 peri.xml 一起纳入版本管理；ISF 变更必须过 import_gpio.bat --dry-run 自检（§6）。

4.5 Bootstrap ritual（SDK 标准引导流程）

新工程 / 新基线的固定动作（依据：§3 + §4）：

  1. 写好全部 set_property / assign_* 行，临时启用 create_* 行；
  2. 编译一次（PT 生成 <design>.peri.xml）→ 立即注释掉全部 create_*，旁注一行说明（何时启用）；

6. 自检流程：import_gpio.bat --dry-run

6.1 工具链

  • --dry-run：只解析、出报告，不写回 peri.xml（import_gpio_cli.py:243-245）；
  • 非 dry-run：写回前先备份为 <name>.bak_pre_import（import_gpio_cli.py:216-217）。

6.5 CI 要求（强制）

  • 每份 constraints/*.isf 提交前必须通过 --dry-run（exit 0）；
  • CI 在每次 constraints/*.isf 变更时自动运行；
  • 但 --dry-run 只验证"语法与导入合法性"，不能替代 §4.5 的"引导 + 重放两连 PASS"重放验证（dry-run 无法发现 already exists 的时序前提——它不模拟完整构建）。

8. 已知陷阱（按新证据修订）

8.1 把 ISF 写成 XML / 自创标签 → "invalid syntax"

ISF 是 Python API 源码。<efx:gpio>、<EFX_PERI_INTERFACE> 之类 XML 进 .isf 会被当作 Python 解析，首行即 SyntaxError → 整文件终止（§1.3）。历史教训：46 KB 的 XML 改名 .peri.isf 被导入器当场拒绝，且该缺陷潜伏数月无人发现——原因就是没有任何环节真正 import 过它。对策即 §6 的强制自检。

8.2 重放含 create_* 的 ISF → GPIO/PLL ... exists，二次编译必失败

机制链：create 语义 + 每次构建重放（§3.1）→ 查重失败（db_item.py:792、design_export_import.py:2015、service.py:635）→ PTException（warning 级继续）→ issue 非空即 import 失败（§1.3）→ 统一流程 abort。对策：§4.5 bootstrap ritual（引导后立即注释 create_*，重放编译必须再 PASS）。

8.3 用 set_property 设资源或引脚

set_property docstring 明确禁止（design.py:507）。资源和引脚有专用通道 assign_resource / assign_pkg_pin；走错通道的属性可能被 Design Check 或后续分配覆盖。

8.4 总线 vs 标量混淆

  • msb == lsb 是标量、否则是总线（design.py:1088-1091）；
  • 总线 GPIO 用 create_output_gpio("led", 5, 0) 创建——不要拆成 create_output_gpio("led[0]", 0, 0) 逐位创建；
  • 引脚分配成员用 "led[N]" 格式：design.assign_pkg_pin("led[0]","K14")（§4.3 实录）；
  • 文本序列化层面：标量 create 行无 msb/lsb，总线 create 行带两个数字（§5.8）。

8.5 ISF 实例名与 RTL 端口名不一致

Unified Flow 的 GPIO 实例名来自 RTL 顶层端口（经 .unified.isf 重建，§7.2）。ISF 里 set/assign 用的名字对不上端口名时，set_property 对未知实例会挂到错误对象或无效对象上，lock_property 甚至静默返回 None（design.py:1936）——错误可能延迟到 Design Check 才暴露。

8.6 "warning 级 issue 也算失败"

PTException 在 importer 中是 warning 且继续执行，但 import_isf 只看 issue 计数（§1.3）。不要把日志里有 warning 的导入当作成功；退出码/流程状态才是准绳。

8.7 create_regional_control_gpio 不存在

导出器映射表里 gpio_reg_ctrl 条目被注释（isf_exporter.py:695-712），对应 API 从未提供。写它 = AttributeError（error 级 issue，§1.3）→ 导入失败。

8.8 文本 ISF 的值表达能力有限

from_str 只允许 prop_value 含字母/数字/下划线/空白/点/方括号（isf_command.py:130）。含逗号、引号等复杂值无法用文本行表达；空字符串值是合法的（§4.2 实录中 LOCKED_PIN","","PLL"）。

8.9 手写/手改 .peri.xml

efxpt:design_db 是工具私有数据库，只有 PT 工具/GUI 能产出（§7.4）。任何构建路径删除或重生成 peri.xml 都是违规 workaround；SDK 三条铁律见 §3.5。

8.10 Bank 电压与 IO 标准匹配（保留自旧版，Ti180 实测证据）

  • 同一 bank 的所有 IO 必须同电压标准；bank 电压用 design.set_iobank_voltage("TL","3.3") 声明（§2.3）；
  • MIPI bank 必须 1.2V，且 MIPI 与 LVDS 不能共存同 bank（电压要求不同）→ 违反报 io_bank_rule_voltage_assignment；
  • HSIO bank 内 GPIO/LVDS/MIPI 之间必须留至少一对未分配 IO 做隔离；
  • Ti60ES（工程样片）不支持 2.5V，仅量产版支持；
  • 实测基线：Ti180 器件 catalog 工程工程 XML（opx_333x642_b40_d20_tj180a484s.xml）中 bank 电压声明与上述规则一致。

8.11 PLL 只能在 ISF 创建（配合 §4.2 模板）

RTL 只声明端口（pll_clk_out / pll_locked），PLL 实例与参数全部经 ISF create_block("pll_inst1","PLL") + set_property 表达，资源用 assign_resource("pll_inst1","PLL_TL0","PLL")。PLL 输出分频器只能是 2 的幂次，相位仅 45° 步进（详见《Efinity优化设计.md》）。
