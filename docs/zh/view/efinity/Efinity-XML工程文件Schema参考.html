1. 定位、命名空间与布局规则

1.1 工程文件是什么

<工程名>.xml 是 Efinity 工程的唯一入口文件：GUI 打开工程、efx_run --flow compile 编排编译、各工具二进制（map/pnr/pgm）读取各自配置段，全部从它开始。它由 enf_proj.xsd 定义，targetNamespace 为：

xmlns:efx="http://www.efinixinc.com/enf_proj"

证据：c:\Efinity\2026.1\bin\enf_proj.xsd L1-L7；c:\Efinity\2026.1\scripts\efx_run_common.py L10（EFX_PRJ_XML_NAMESPACES = {'efx': 'http://www.efinixinc.com/enf_proj'}——编排脚本按此前缀解析，写错命名空间等于所有 efx: 元素都不存在）。

1.2 布局硬规则（违反即失败）

规则 说明 证据
工程 XML 放工程根目录 官方示例全部如此；不要发明 efinity_project/ 之类子目录 C:\Efinity\2026.1\examples\helloworld-unified\helloworld.xml 位于示例根目录
所有相对路径以 XML 文件所在目录 为基准解析 SDC、RTL、ISF、flist 全部如此 本文 §1.3
namespace 必须精确 工具按前缀→URI 映射解析 efx_run_common.py L10
<efx:inter_file name=""> 空值 见本文 §13 专项裁定；生成器不应写出 工作区硬约束 §2 + 官方示例 L15

1.3 相对路径解析基准

EvoVerse 侧校验逻辑与 Efinity 工具行为一致——引用路径一律相对工程 XML 父目录解析：

  • EvoVerse 工程引用校验：c:\work\awesomsdk\sdk\cli\evoverse L1562-1570（相对 project_xml 父目录 os.path.exists 检查）。
  • XSD 中 file_type 注明 name "must include relative path"（enf_proj.xsd L123-126）。

因此：工程 XML 在根目录时，<efx:sdc_file name="constraint/timing.sdc"/> 指向 <工程根>/constraint/timing.sdc。

2. 根元素 <efx:project>：属性与子元素顺序

2.1 子元素出现顺序（xs:sequence，严格有序）

XSD 以 xs:sequence 定义子元素（enf_proj.xsd L9-43），顺序不可打乱，出现次数如下：

# 元素 出现次数 说明
1 device_info 1 器件与 timing model
2 design_info 1 顶层模块与源文件
3 package_info 0..1 待废弃（XSD 注释 "will be deprecated"）
4 interface_info 0..1 接口设计器（peri 文件）
5 constraint_info 1 SDC / inter / ISF 约束
6 isf_info 0..1 ISF 脚本（新位置，官方示例未用，见 §6.4）
7 sim_info 0..1 仿真
8 misc_info 0..1 保留段（官方示例未用）
9 ooc_info 0..1 Out-of-Context 编译
10 ip_info 0..1 IP 实例
11 synthesis 0..1 综合选项
12 place_and_route 0..1 布局布线选项
13 bitstream_generation 0..1 比特流选项
14 debugger 0..1 调试器选项
15 security 0..1 加密/签名

顺序敏感的实证：<efx:design_file> 必须出现在 top_vhdl_arch 之前——EvoVerse adapter 注释明确记录违反顺序会让 Efinity 在下次原生加载时拒绝工程 XML（c:\work\awesomsdk\products\efinity-adapter\extension\src\capabilities\ip.ts L92-95）。

2.2 根元素属性表（enf_proj.xsd L44-59）

属性 必填 默认 语义
name ✅ — 工程名
description — 空 描述
sw_version ✅ — 生成该工程的 Efinity 版本（官方示例为 2025.2.276）
last_change — 空 最后修改者
last_change_date — 空 保留的向后兼容属性
location — 空 工程路径
last_run_state — 空 枚举 pass/fail/crash/空——GUI 状态展示，不影响编译
last_run_flow — 空 上次运行的 flow 名
last_run_tool — 空 上次运行的工具
config_result_in_sync — 空 GUI 工程与配置同步标记
design_ood / place_ood / route_ood — 空 枚举 sync/new/change/空——GUI 的「过期」标记
last_run_timing — 空 枚举 core_only/unified_timing/unknown/空

这些 last_run_* / *_ood 属性是 GUI 书签：工具运行后回写。EvoVerse 生成器直接固定 last_run_state="pass" 等 Neutral 值即可（sdk\cli\evoverse L1868-1954 即如此做）。

3. <efx:device_info> — 器件与 Timing Model

Schema（enf_proj.xsd L63-85）：

子元素 次数 默认 类型 语义
family 1 Quantum non_empty_string 器件族：Titanium / Trion / Quantum / Topaz
device 1 Q10 non_empty_string 具体型号，如 Ti60F225、T120F576
timing_model 0..1 op1 字符串 时序模型速度等级

工程 XML ↔ peri.xml 一致性：unified PT 阶段会校验工程 XML 的 device/timing_model 与 peri 设计数据库一致，不一致即报错（c:\Efinity\2026.1\scripts\efx_run_pt_unified.py L226-231）。换器件必须连同 peri.xml 一起处理，不能只改工程 XML。

工作区规则关联：Ti35/Ti60 的 timing model I4/I4L 已废弃，必须用 C4 或 C5（工作区硬约束 §13）。三个官方示例均使用 C4。

4. <efx:design_info> — 顶层模块与源文件

4.1 属性（enf_proj.xsd L88-103）

属性 必填 默认 语义
top_module ✅ — 综合顶层模块名（→ map 命令行 root=<name>）
top_vhdl_arch — 空 VHDL 顶层 architecture 名（→ arch=<name>）
unified_flow — false 是否启用 unified flow（interface designer 融合流程）
partition_interface_allowed_off_perimeter — true 分区接口允许离周边

⚠️ unified_flow 的 XSD 默认值是 false（enf_proj.xsd L101）。不写这个属性 = 标准双流程；要 unified flow 必须显式写 unified_flow="true"。官方 helloworld-unified 示例显式写了；helloworld-dbg/helloworld-ru 未写（即 false）。

4.2 子元素顺序与两类文件元素

design_info 内部同样是 xs:sequence：先全部 design_file（0..N），最后可选 top_vhdl_arch。design_file 必须全部在 top_vhdl_arch 之前（见 §2.1 顺序敏感实证）。

4.3 <efx:design_file> — version 三态语义（核心）

Schema（enf_proj.xsd L123-136）：name（必填，含相对路径）、version（可选）、library（可选，VHDL 库名）。

efx_run.py 对 version 的处理有三种状态（c:\Efinity\2026.1\scripts\efx_run.py L703-715）：

version 取值 解析结果 map 二进制实际收到
缺省（属性不写） 加入 extra_files 列表 -v <file>（Verilog include 语义）
"na" 加入 flist 列表 --flist <file> → map 二进制 --f
其他任何值（如 "v1.2"） extra_files + ,t:<version> 后缀 -v <file>,t:v1.2（带版本编译单元）

证据链：efx_run.py L703-715（三态分派）；--flist 到 map 二进制的二次映射在 c:\Efinity\2026.1\scripts\efx_run_map.py L44、L144（--flist → map --f）。

实践含义：

<!-- 普通 RTL 源：什么都不写 -->
<efx:design_file name="rtl/top.v"/>

<!-- flist 清单：version="na"，文件内容是一行行其他文件路径 -->
<efx:design_file name="src/files.f" version="na"/>

<!-- 带版本的编译单元（罕见） -->
<efx:design_file name="rtl/legacy.v" version="1995"/>

5. <efx:interface_info> — 接口设计器文件

Schema（enf_proj.xsd L106-113）：

子元素 次数 语义
peri_file 1 接口设计器数据库文件（<design>.peri.xml）
interface_script_file 0..N 接口脚本（与 constraint_info 下 isf_file 同义，见 §6.4）

⚠️ Schema 与编排脚本的位置不一致（实践警告）：XSD 把 peri_file 定义在 interface_info 段（enf_proj.xsd L110-111），但 efx_run.py 的 parse_project_file 实际从 constraint_info 段下读取 peri_file（efx_run.py L983-990）。工程能工作是因为 GUI 写出的工程两个位置语义兼容、且各工具经 --prj 自读 XML 时走 projectdb 层（db.py L283 将 inter_file 映射为 interface_constraint_file，peri 由接口数据库体系管理）。结论：照抄官方示例的写法（peri 文件不手写、由 PT 工具产出），不要自创只在其中一个位置合法的布局。

<design>.peri.xml 本身是 PT 工具产出的 efxpt:design_db 命名空间工程源文件，不是本文 enf_proj 体系的一部分——用户与 SDK 都不应手写（工作区硬约束 §1、§15）。

6. <efx:constraint_info> 与 <efx:isf_info> — 约束文件

6.1 constraint_info 子元素（enf_proj.xsd L152-183，xs:sequence 有序）

# 元素 次数 状态 消费者
1 sdc_file 0..N 有效 efx_pnr（时序约束）
2 unified_sdc_file 0..N 有效 unified timing 分析（efx_run_pnr.py L224-241：多个 unified SDC 组成 filelist）
3 io_place_file 0..1 已废弃 旧引脚分配（映射为 user_io_assignment）
4 core_place_file 0..1 已废弃 旧核布局（映射为 fix_pins）
5 inter_file 0..1 有效 → efx_pnr 的 sync_file（仅 name 非空时，见 §13）
6 interface_script_file 0..N 有效（旧名） 加载时迁移为 isf_file
7 isf_file 0..N 有效 PT 的 design_api.import_design() 输入

6.2 efx_run.py 的 constraint → CLI 映射表

efx_run.py L720-733 中的映射字典（原文）：

{'sdc_file': 'sdc_file',
 'unified_sdc_file': 'unified_sdc_file',
 'io_place_file': 'user_io_assignment',
 'core_place_file': 'fix_pins',
 'inter_file': 'sync_file'}

关键细节：L726 用 elem.get('name') 做真值检查——name 为空字符串或缺失的条目被静默跳过。这直接影响 §13 的裁定。

6.3 SDC 的消费方式

  • PNR 包装器 efx_run_pnr.py L174 将 --prj <xml> 直传 efx_pnr 二进制，二进制自行从 XML 读 SDC 列表。
  • use_unified_timing 模式下多个 SDC 组成 filelist（efx_run_pnr.py L224-241）。
  • 无 sync_file 时的兜底：Trion/Titanium/Topaz 器件下，包装器会自动寻找 .interface.csv 作为同步文件（efx_run_pnr.py L203-206）。

6.4 interface_script_file 与 isf_file 同义迁移

工程数据库加载层显式做迁移（c:\Efinity\2026.1\python311\Lib\site-packages\projectdb\db.py）：

  • L283：interface_constraint_file = inter_file
  • L284：interface_script_file_list = isf_file
  • L731-737：加载时把 interface_script_file 元素迁移为 isf_file（源码注释原文："because of some genius define two element type for same information"）。

实践：新工程一律写 isf_file；读旧工程时两者等价。

6.5 isf_file 与 unified PT 的关系（重放机制）

unified flow 下（c:\Efinity\2026.1\scripts\efx_run_pt_unified.py L233-267）：

  1. 网表接口提取产出 <design>.unified.isf，插入 peri_scripts 列表首位；
  2. 逐个对列表中的 ISF 执行 design_api.import_design(script)，任何一个失败整体失败。

这就是工作区硬约束 §15「ISF 必须重放安全（只 set_property/assign_pkg_pin 等；create_* 只做一次性 bootstrap）」的工具链根源：每次 unified build 都会把工程 XML 引用的全部 ISF 重放到已持久化的 peri.xml 上。

6.6 空 <efx:isf_file name=""/> 的实证拒绝

EvoVerse 生成器注释记录：空的 <efx:isf_file name=""/> 条目会让 PT 拒绝携带 peri.xml 的工程（c:\work\awesomsdk\sdk\cli\evoverse L1884-1887，注释原文 "an <efx:isf_file name=""/> entry makes PT reject projects that carry a peri.xml instead of an ISF"）。因此生成器在 isf 文件名为空时整行省略而非写空值。

7. <efx:sim_info> / <efx:misc_info> / <efx:ooc_info>

7.1 sim_info（enf_proj.xsd L199-211）

项 类别 默认 说明
top_module 属性 "sim" 仿真顶层（⚠️ 旧版本文档误写为子元素，实为属性）
pt_sim_top_module 属性 "ptsim" PT 仿真顶层
sim_file 子元素 0..N — 仿真源文件；存在且后缀为 .v/.sv/.vhd 时被 efx_run.py 转为 --tb（efx_run.py L666-673）
defmacro 子元素 0..N — 仿真宏定义（→ verilog-macros=） 
<efx:sim_info top_module="tb_top" pt_sim_top_module="ptsim">
    <efx:sim_file name="sim/tb_top.v"/>
</efx:sim_info>

7.2 misc_info / ooc_info

  • misc_info（L213-219）：保留段，官方三示例均未使用。
  • ooc_info（L221-243）：Out-of-Context 编译配置，仅分层次编译流程使用，常规工程不写。

8. <efx:ip_info> — IP 实例

8.1 Schema 定义（enf_proj.xsd L245-263）

ip_info 下为 0..N 个 ip 元素（ip_type）：

项 类别 必填 默认 语义
instance_name 属性 ✅ — IP 实例名
path 属性 ✅ — 指向 IP 的 settings.json（含路径）
ooc 属性 — false 是否 Out-of-Context 编译
ip_src_file 子元素 0..N — — IP 附加源文件（相对 IP 根解析）
ip_postmap_module 子元素 0..1 — — post-map 替换模块名

8.2 完整合法示例

<efx:ip_info>
    <efx:ip instance_name="ddr_ctrl" path="ip/ddr_ctrl/settings.json" ooc="false">
        <efx:ip_src_file name="ip/ddr_ctrl/synthesis/edn/ddr_ctrl_wrapper.v"/>
    </efx:ip>
</efx:ip_info>

8.3 <efx:ip> 在编排层的真实行为（关键认知）

efx_run.py L676-683：每个 <efx:ip path="ip/<m>/settings.json"> 被转换为把 ip/<m>（settings.json 的父目录）加入 source_dir → map 命令行 --dir ip/<m>——即对该目录做源码全量扫描。同时 --project_xml 也会传给工具内核，内核自行消费 ip_src_file（相对 IP 根解析——若 IP 根下不存在对应文件则解析失败）。

8.4 EvoVerse 的实证决策：不写 <efx:ip>

c:\work\awesomsdk\products\efinity-adapter\extension\src\capabilities\ip.ts L100-106 注释（原文要点）：

  • efx_run 把每个 <efx:ip path="ip/<m>/settings.json"> 变成 --dir ip/<m> 源扫描；
  • 这会把已经是 design_file 的同一文件二次编译 → VERI-1206 duplicate module 错误；
  • ip_src_file 相对 IP 根解析，而 SoC netlist 在 IP 根下并不存在。

因此 EvoVerse adapter 的 publishGeneratedIp（ip.ts L73-108）只把 IP 生成源以 design_file 注册，刻意不写 <efx:ip_info>/<efx:ip>；selectGeneratedSources（L136-160）同时过滤掉 sim/、testbench/、template/、devkit/、source_<simulator>/ 目录，避免把非综合源扫进工程。

结论：<efx:ip> 是「IP 集成工具链（IP 生成器管理）」的元素；手工/生成器管理源码清单的流程用 design_file 更可控。

9. 编译选项段：synthesis / place_and_route / bitstream_generation / debugger / security

五段结构同构（enf_proj.xsd 中各 tool section 定义）：内容由 0..N 个 <efx:param name="..." value="..."/> 组成。

9.1 <efx:param> 通用结构

<efx:param name="param_name" value="param_value"/>
  • name/value 均为必填字符串；value 的解释权在各消费层（§10）。
  • 各段参数集合由 GUI 的选项数据库（tool_options 全局元素，enf_proj.xsd L372-394）定义，XSD 本身不校验 param 名——写错参数名不会报 schema 错，只会被工具静默忽略或报选项不存在。

9.2 synthesis（efx_run.py L738-795）

param → 命令行 / 行为
work_dir work-dir=<dir>，并强制生效（DEVINFRA-1142：work_dir 从 XML 优先，CLI 覆盖被抑制）
def_veri_version / def_vhdl_version veri_options=verilog_mode=<v> / vhdl_mode=<v>（如 verilog_2k）
include I=<path>（可多个）
opt_mode syn_options=mode=<v>（如 speed/area）
peri-syn-instantiation / peri-syn-inference 仅 unified flow（un_flow）时下发，官方 unified 示例为 1
dynparam top-params=<k>=<v>（下发两次，map 与 syn 各一次）
defmacro verilog-macros=...

unified_flow="true" 且 CLI 未显式给 --un_flow 时，efx_run.py 从该属性推导 un_flow=True（L738-795 内）。

9.3 place_and_route（efx_run.py L797-840 + efx_run_pnr.py L168-182）

编排器只处理两类 param：

  1. work_dir → PNR 工作目录；
  2. 以 qp_options= 为前缀的 param（剔除 anneal_random_seed）→ 拼入 vpr 选项。

其余 pnr param 不由 efx_run.py 转 CLI——efx_run_pnr.py L168-182 解析 XML pnr param 仅用于 option_exists 去重校验，随后 L174 把 --prj <xml> 直传 efx_pnr 二进制，由二进制自行解析 <efx:place_and_route> 段。这是「双通道」模型（§11.2）的典型体现：不要指望给 XML 里加一个 pnr param 就一定能在命令行上看到它。

常用 pnr param（官方示例实证）：active_capture_clk_edge（Titanium 必须保持默认 negedge）、retiming、oscillator_clock_divider、beneficial_skew 等。

9.4 bitstream_generation（efx_run.py L842-867）

param 行为
mode / width 官方示例中既有 e_option 也有 e_string 写法（§12 对照表），均被读取
cascade / cold_boot / randomize_iv_value / iv_value 编排器忽略（二进制经 --prj 自读）
jtag_usercode 正则 ^0x[a-fA-F0-9]{8}$ 校验；不匹配则强制 0xFFFFFFFF 并回写工程 XML（副作用：XML 被工具改写）
bitstream_compression / four_byte_addressing 有效参数（dbg 示例 compression=on；four_byte_addressing 仅部分示例有）

9.5 debugger（efx_run.py L962-981）

work_dir、auto_instantiation（on → True，控制 build 时自动实例化 debug core）、profile（NONE → 空串）。官方 dbg 示例携带 debug core 配置。

9.6 security（efx_run.py L877-960）

比特流加密/签名：encrypt → --encrypt、sign → --sign、keypair → --keypair=，以及 sc_* 系列（secure chip）；IV 类值要求长度 24（12 字节 hex）。

10. param_value_type 深度解析：XML 值类型与消费链

10.1 五种枚举（enf_proj.xsd L325-333）

<xs:simpleType name="param_value_type">
    <xs:restriction base="xs:string">
        <xs:enumeration value="e_string"/>
        <xs:enumeration value="e_bool"/>
        <xs:enumeration value="e_option"/>
        <xs:enumeration value="e_integer"/>
        <xs:enumeration value="e_noarg"/>
    </xs:restriction>
</xs:simpleType>
枚举 语义 XML 中 value 的典型取值
e_string 自由字符串 任意文本（路径、名字、数值均可）
e_bool 布尔 on / off（不是 true/false！）
e_option 下拉枚举 预定义选项之一（如 e_option 的 pgm mode=active）
e_integer 整数 十进制整数字符串
e_noarg 「无参数」开关 存储层与 e_bool 同为 on/off，语义是「该选项存在即生效，不接值」

10.2 XML → 命令行映射举例

XML 消费后
<efx:param name="opt_mode" value="speed" value_type="e_option"/> syn_options=mode=speed（值原样进选项串）
<efx:param name="auto_instantiation" value="on" value_type="e_bool"/> 编排层判定 on → Python True（efx_run.py L962-981）
<efx:param name="retiming" value="2" value_type="e_integer"/> 经 --prj 由 pnr 内核读取，数值 2
e_noarg 型开关（value=on） 内核读 XML 时视作「选项开启、无关联值」；编排层不为其生成带值参数

10.3 谁真正消费 value_type？（重要澄清）

  • Python 编排层基本不消费：efx_run.py 全文仅 L803 读取一次 value_type 且未使用。编排层把 value 当纯字符串搬运。
  • GUI 渲染层消费：efinity_plugin/OptionSchema.py L29-49（e_bool/e_noarg → boolean 控件，e_option → 逗号分隔枚举下拉）、efinity_plugin/ProjectMeta.py L1111-1159（e_bool/e_noarg 序列化为 'on'/''）、aoe/core/common.py L43-49（EFX_VT 枚举无 noarg 的历史差异）、projectdb/defines.py L79-88（ParameterType 含 NOARG）。
  • 工具二进制：经 --prj 自读 XML 时按各自 section 的参数语义解释值。

实践含义：手写工程 XML 时，value_type 写错通常不会让编译失败（编排层不看它），但会让 GUI 显示/编辑行为异常；布尔语义值必须是 on/off 才被可靠识别。

11.2 「双通道」模型：编排器 CLI 转换 ≠ 全部参数传递

efx_run.py 有两条参数通道，理解这一点才能解释 §9.3 的现象：

  1. CLI 通道：编排器解析 XML，把部分参数翻译成子工具命令行参数（§11.1 总表）。
  2. XML 直读通道：以 --prj <工程.xml> 传递 XML，各工具内核自行解析自己关心的 section：
  3. 综合：--prj 时同时传 --project_xml（efx_run.py L1200-1266）；
  4. PNR：--prj <xml> 直传（efx_run.py L1273-1341 → efx_run_pnr.py L174）；
  5. PT/unified：--un_flow + --peri_netlist，并加载工程数据库取 interface_script_file_list 逐个 --peri_scripts（efx_run.py L1420-1495）。

推论：XML 里写了但编排器不转的参数，依然可能通过 XML 直读通道生效——「命令行上看不到」不等于「没生效」；反之，想确认某个参数的真实效果，要以工具报告/日志为准。

13. 【证据张力裁定】空 <efx:inter_file name=""/>

13.1 冲突

  • 事实 A（官方示例）：三个 2025.2.276 官方工程 XML 的 L15 均为 <efx:inter_file name=""/>，且根属性 last_run_state="pass"（上轮构建通过）。
  • 事实 B（工作区规则）：本仓库硬约束（rules-efinity-hard.md §2 / AGENTS.md §2）称「空的 <efx:inter_file name="" /> 会导致 build 失败」，并要求发现即删除。

13.2 双方证据的进一步实读

证据 内容 指向
efx_run.py L726 对 inter_file 做 elem.get('name') 真值检查，空 name 静默跳过 编排层对空 inter_file 无害
efx_run_pnr.py L203-206 无 sync_file 时自动找 .interface.csv 兜底 空/缺失 inter_file 在 PNR 侧有兜底
sdk\cli\evoverse L1884-1887 空 <efx:isf_file name=""/> 实证让 PT 拒绝带 peri.xml 的工程（同族「空 name 引用」失败模式） 失败可能发生在 PT/内核层而非编排层
官方示例 sw_version 2025.2.276（旧于工具 2026.1） 存在版本差异假说空间

13.3 裁定

  1. 两层事实并不直接矛盾：编排器（efx_run.py）确实跳过空 inter_file；但 build 全链还包括 PT import_design、projectdb 加载、efx_pnr 内核对 XML 的直读——失败可能发生在这些层，或仅发生在特定版本组合（官方示例配 2025.2 时代构建通过，不代表所有版本安全）。
  2. 同族失败模式已实证：空 isf_file 让 PT 拒绝工程是 EvoVerse 侧实测结论；「空 name 引用元素不安全」是跨元素的合理归纳。
  3. 安全实践（本仓库执行口径）：
  4. 生成器不写 <efx:inter_file>（XSD minOccurs=0，不写完全合法）——EvoVerse _build_native_project_xml 即不产出该元素；
  5. 遇到 GUI 历史工程带空 inter_file 且构建通过：不必恐慌删除，但升级工具版本后必须重验；
  6. 绝不给空 inter_file 填非空乱值来「修复」——那会真的产生一个坏的 sync_file 引用；
  7. 本仓库规则仍按工作区硬约束执行：生成路径不允许出现 <efx:inter_file name=""/>。
