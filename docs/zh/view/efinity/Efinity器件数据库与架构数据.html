1. 器件家族与 JTAG IDCODE 总表

1.1 数据来源与结构

Efinity 2026.1 的 programmer 侧器件数据库实际位于 pgm\bin\ 目录（不是 pgm\ 根目录，这是常见路径误解）：

证据：C:\Efinity\2026.1\pgm\bin\device_db.xml

该 XML 为 programmer 识别 JTAG 链上器件的数据源，核心结构为逐器件条目，关键字段：

字段 含义
name 器件名（如 Ti60、Ti180、Tz175）
idcode JTAG IDCODE（32 位十六进制）
family 家族（Trion / Titanium / Topaz）
sec_disp_name 安全显示名（security 脚本引用的规范名）

同一物理器件可能存在多个条目：ES（工程样片，Engineering Sample）与 MP（量产，Mass Production）的 IDCODE 不同；此外还有测试板、MUT 等内部变体条目。JTAG 链识别到哪个 IDCODE，programmer 就按哪个条目处理——ES 片必须用 ES 条目对应的位流。

1.5 ES vs MP：与官方文档的对照

官方 Titanium IDCODE 文档只列 MP 值：

证据：C:\Efinity\2026.1\pgm\doc\topics\jtag-device-ids-ti.html（第 175-260 行，FPGA / Package / JTAG Device ID 三列表，文档版本 HLP-EFN-PGM-v2.0）

对比项 device_db.xml 官方 jtag-device-ids-ti.html
Ti60 0x00360A79（ES）+ 0x10660A79（MP，条目名 Ti60_MP） 仅 0x10660A79（标注 "All" 封装）
ES 变体 显式存在（Ti60 ES、Ti135ES 等） 不列 ES 值
用途 programmer 运行时识别 人工查表

结论：手上若为 ES 片（如 Ti60 ES），JTAG 读回 0x00360A79，programmer 按 ES 条目处理；官方文档查到的 0x10660A79 是量产值。两者都"正确"，但位流不通用——详见 §3.3。

2.2 die 代号与器件对照

arch 数据以 die 代号 + 几何规格命名，与市场器件名的对应关系（实测锚点）：

die 数据名 对应器件 证据线索
opx_218x322_b16_d10 Ti60 存在 _es 变体目录，与 Ti60ES 器件存在对应
opx_268x484_b24_d12 Ti180 主力 die
opx_333x642_b40_d20 Ti375 最大 Titanium die
opx_334x484 Ti240

die 代号族：oph / opu / opx / opy / ssn / tz。命名规律：<die>_<宽>x<高>_b<bank数>_d<规模档>（b/d 后缀仅部分 die 可见）。

2.3 文件格式判定表

arch 目录内的扩展名全部是工具私有格式，判定依据来自加载它们的 DLL：

扩展名 格式判定 证据
.xdb libdevicedb.dll 私有容器（非明文 XML） C:\Efinity\2026.1\bin\libdevicedb.dll 加载；用文本编辑器打开无明文结构
.zst / .delaym.zst Zstandard 压缩 安装目录含 libzstd.dll
.blk / .btm / .clib libchipper.dll + libprotobuf.dll 消费的块/时序/单元库数据 C:\Efinity\2026.1\bin\ 下两 DLL 共存
.oc 速度等级（operating condition）文件 arch\oc\ 下按 C2/C3/I4 等命名
.flrpln floorplan 数据 arch\flrpln\
.tmv2 pt_route 时序模型 v2 arch\pt_route\，仅 Titanium 新 die 使用
.tenc / .pt_device Interface Designer 侧器件数据 pt 目录配套

2.4 只读守则（重要）

arch 目录是工具内部数据，只读勿编。 理由：

  1. 全部为私有二进制/压缩格式（§2.3），无公开 schema，手工编辑必然损坏；
  2. SDK / adapter / 脚本的任何构建路径都不应写入、删除或重生成 arch 内容——这属于 §7「不为工具行为建 workaround」的范畴；
  3. 需要查询器件能力时，正确入口是工程 XML（enf_proj.xsd，见《Efinity-XML工程文件Schema参考.md》）与 ISF API（见《Efinity-ISF语法参考.md》），不是 arch 二进制。

2.5 速度等级全景与 I4/I4L 证据边界

证据：C:\Efinity\2026.1\arch\oc\ 与 arch\pt_route\ 实测目录清单

数据集 实测速度等级
opx（Titanium 新 die） C2 / C3 / C3L / C4 / C4L / I2 / I3 / I3L / I4 / I4L / Q3
pt_trion / oph C2 / C3 / C4 / I2 / I4 / I4L / Q4 / t28hpc+typ
Ti125 的 tmv2 仅 C3 / C3L / C4 / C4L / I3 / I3L（无 I4/I4L）
C5 全安装目录不存在

I4/I4L 废弃断言的证据边界（如实呈现）：

  • 工作区规则断言：Ti35/Ti60 timing model I4/I4L 已废弃，必须用 C4 或 C5。
  • 安装目录内证据：矛盾现象——arch\oc\ 下仍存在 I4.oc / I4L.oc；Ti125 tmv2 却不含 I4/I4L；全目录无任何 C5 数据。
  • 结论："I4/I4L 废弃"在安装目录内无法用单一文件直接证实，只能给出两条硬实测事实：(a) 新 die（Ti125 tmv2）的速度等级集合不含 I4/I4L；(b) 旧等级文件仍留在 oc 目录（可能仅为兼容旧工程）。工程选型时以工作区规则（C4/C5）为准，本卷不做超出证据的扩写。

3. flash loader 位流与 IDCODE 对应表

证据：C:\Efinity\2026.1\pgm\fli\ 实测目录清单（fli = flash loader images） 参数细节与 ftdi_program.py 用法见《Efinity辅助工具与脚本参考.md》；烧录操作流程见《Efinity编程与烧录指南.md》。本卷只给 IDCODE ↔ 位流命名的对应关系。

3.1 位流命名规则

flash loader 位流文件名格式：u<IDCODE>[_<die>].bit，其中 <IDCODE> 为 §1 表中对应器件条目的 8 位十六进制（无 0x 前缀）。

3.2 三家族位流清单概览

家族目录 .bit 数量 命名示例
pgm\fli\titanium\ 21 u10660A79.bit（Ti60 MP）、u00680A79.bit（Ti180）
pgm\fli\topaz\ 14 按 Topaz IDCODE 命名
pgm\fli\trion\ 11 带 die 后缀：u00210A79_t20.bit（T20/T13/T8 共 IDCODE，靠 die 后缀区分）

要点：

  1. Trion 位流必须带 _<die> 后缀——因为 Trion 多个器件共用同一 IDCODE（§1.2），loader 靠后缀选对 die；
  2. Titanium / Topaz 位流为纯 u<IDCODE>.bit，无后缀。

3.3 Ti60ES 专项：无 flash loader 位流

证据：C:\Efinity\2026.1\pgm\fli\titanium\ 清单中不存在 u00360A79.bit（Ti60 ES 的 IDCODE），仅存在 u10660A79.bit（MP）。

Ti60ES 三重限制（本卷汇总，出处各异）：

# 限制 证据
1 无 flash loader 位流（u00360A79.bit 不存在） pgm\fli\titanium\ 实测
2 安全特性排除（AES/RSA 签名脚本明确 "excluding Ti60ES devices"） C:\Efinity\2026.1\security\bin\AddSecurityTitanium.py 第 31 行
3 不支持 2.5V IO 电压标准（仅量产版支持） 工作区规则（rules-efinity-hard.md §3），安装目录内无直接文件证据

工程含义：ES 片只能做功能验证，不能做安全量产烧录方案的目标器件；量产设计必须切到 MP 片（IDCODE 0x10660A79）。

5. lpf.xsd 勘误专节：peri_device_db 真身

5.1 常见误解

C:\Efinity\2026.1\pt\bin\schema\lpf.xsd 文件名带 "lpf"，容易被误认为与 LPF 约束文件、SDC 约束或 peri.xml（efxpt:design_db）相关。全部错误。

5.2 实测事实

证据：C:\Efinity\2026.1\pt\bin\schema\lpf.xsd

行号 实测内容 含义
第 2 行 targetNamespace="http://www.efinixinc.com/peri_device_db" 命名空间是 peri_device_db（器件数据库），不是约束、也不是 peri.xml 的 efxpt:design_db
第 5 行 前缀 efxpt 与 peri.xml 同用 efxpt 前缀，但 URI 不同
第 8 行 import 了 peri_util.xsd 依赖同一 schema 目录下的公共类型

根元素结构：periphery → sequence / block_def（含 bitsize、paramsize 属性）/ instance。

5.3 结论

问题 答案
lpf.xsd 描述什么？ peri_device_db 器件数据库的 bit 级块定义（bank/IO 块的位宽模型），供 PT 内部消费
与 SDC/LPF 约束有关吗？ 无关。约束格式只有 ISF 与 SDC 两种（工作区规则 §1）
与 peri.xml 有关吗？ 无直接关系。peri.xml 的命名空间是 http://www.efinixinc.com/peri_design_db（design_db），lpf.xsd 是 peri_device_db（device_db），两个不同 URI
XSD 实际位置？ 工程格式 XSD 在 C:\Efinity\2026.1\bin\（如 enf_proj.xsd）；lpf.xsd 在 C:\Efinity\2026.1\pt\bin\schema\——两处 schema 目录不同，勿混
