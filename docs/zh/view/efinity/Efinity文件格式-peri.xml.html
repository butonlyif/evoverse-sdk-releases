Efinity 文件格式：peri.xml

Efinity 文件格式参考 —— <project>.peri.xml（PT 设计库）

适用版本：Efinity 2026.1（C:\Efinity\2026.1） 调查日期：2026-09-25 证据方法：全部结论来自对 Efinity 2026.1 安装目录下真实文件的一手实读（XSD schema、Python 源码、官方示例、官方 HTML 词汇表），证据路径在正文逐条标注。不含任何推测或外部来源内容。

1. 定位与生命周期：工程源文件，不是生成物

1.1 官方定义（词汇表原文）

官方词汇表对 <project>.peri.xml 的定义（证据：C:\Efinity\2026.1\doc\topics\gloss-peri.xml.html L168-197）：

  • 标题（L168）：<project>.peri.xml
  • 文件系统位置（L177-178）：<project>（即工程根目录下，与工程 XML 同名）
  • Created by（L181-183）："Interface Designer when you create an interface"
  • Design source? Yes（L185-186）——这是 PT 关联产物中唯一被官方标记为 design source 的文件（SDC 报告卷 §5 曾对比：报告类产物均为 "Design source? No"）
  • 内容（L190-193，原文照录）：

"The Interface Designer creates this file when you create a new interface for your project. This file contains all of the settings that you specified in the Interface Designer for I/O banks, GPIO, LVDS, PLLs, MIPI, DDR, etc. You should not edit this file directly!"

两条关键官方结论： 1. Design source? Yes → peri.xml 是工程源文件，与 .v、.sdc、.isf 平级，构建后必须存活，必须纳入版本管理。 2. You should not edit this file directly! → 官方明令禁止直接编辑。所有修改必须通过 Interface Designer（GUI）或 ISF/DesignAPI（脚本）。

1.2 三重身份

peri.xml 同时是三样东西，理解任何一条都不能丢掉另外两条：

# 身份 含义 证据
① 工程源文件 存放你在 Interface Designer 中指定的全部 periphery 设置（IO bank、GPIO、PLL、MIPI、DDR……），与工程 XML 一起构成工程 gloss-peri.xml.html L185-193
② PT 工具独占产物 只能由 PT 工具 / Interface Designer 产出（XSD schema 是 efxpt:design_db，内部结构复杂且随版本演进） §2、§3
③ 每次 unified build 的重放目标 每次 unified 编译都会加载已持久化的 peri.xml，并把工程 XML 引用的 ISF 重放上去；所以 ISF 必须重放安全 efx_run_pt_unified.py L180-184、L252；ISF 卷 §3

1.3 生命周期与 unified 流程中的位置

efx_run_pt_unified.py（证据：C:\Efinity\2026.1\pt\bin\efx_run_pt_unified.py）中 peri.xml 相关的关键行：

行号 代码/注释（摘录） 含义

unified 九步流程全景（详细步骤表见 ISF 卷 §7.1，此处只标注 peri.xml 相关环节）：

工程 XML (.xml)
   │ 引用
   ▼
ISF 约束 (*.isf) ──重放──▶ <design>.peri.xml（已持久化的设计库，内存中演化）
                              │

1.4 bootstrap / 重放两阶段契约（与 ISF 的分工）

peri.xml 的存在直接决定了 ISF 的写法约束（完整契约见 ISF 卷 §3 与硬约束 rules-efinity-hard.md §15，此处从 peri.xml 视角复述要点）：

阶段 条件 ISF 允许的命令 对 peri.xml 的效果
bootstrap（引导） peri.xml 尚不存在（新工程/新基线） create_*_gpio / create_block / create_pll_input_clock_gpio 等 create 类 + set/assign 类 创建实例并设置属性，落盘生成第一个 peri.xml
重放（replay） peri.xml 已存在（每次后续 build） 只有幂等命令：set_property / assign_pkg_pin / assign_resource / set_device_property / set_iobank_voltage 在已有实例上重设属性；create_* 会因实例已存在而报 GPIO/PLL ... exists → 第二次编译失败
  • ISF 命令集没有 delete/clear——PT 原生 API 对不存在的实例会 raise，不存在可写进 ISF 的幂等删除（不要试图发明）。
  • 因此标准引导仪式是：create_ 临时启用 → 编译一次生成 peri.xml → 立即注释掉 create_** → 重放编译必须再次全 PASS（两连 PASS 才算验收）。

2. 命名空间与根元素

2.1 命名空间三足鼎立

Efinity PT 的 XML 世界由三个 targetNamespace 构成，前缀习惯与职责泾渭分明（证据：各 XSD 头部 targetNamespace 声明，C:\Efinity\2026.1\pt\bin\schema\）：

命名空间 URI 惯用前缀 职责 代表文件
http://www.efinixinc.com/peri_design_db efxpt 设计库：你工程中的 periphery 实例（GPIO/PLL/iobank…） peri_design_db.xsd + 24 个设计类子 schema
http://www.efinixinc.com/peri_device_db （器件库） 器件库：芯片出厂数据（die/package/timing model/bit 级块定义） peri_device_db.xsd、lpf.xsd、die_definition.xsd 等 9 个
http://www.efinixinc.com/peri_tool （工具类型） 公共简单类型（非空串、坐标串等） peri_util.xsd

⚠️ peri.xml 与工程 XML（enf_proj 命名空间 http://www.efinixinc.com/enf_proj）完全不同——工程 XML 由用户/SDK 编写，peri.xml 由 PT 编写，二者靠工程 XML 的 <efx:inter_file name="*.isf"> 引用间接协作。

2.2 根元素与六个根属性

peri.xml 的根元素是 design_db（证据：C:\Efinity\2026.1\pt\bin\schema\peri_design_db.xsd L36 <xs:element name="design_db" type="design_db_type"/>）。

根属性定义（peri_design_db.xsd L175-222）：

属性 必填 类型 含义 helloworld 实测值
@name ✅ string 设计名 = 工程名（与 {design}.peri.xml 的 {design} 一致） helloworld
@device_def ✅ string 器件定义名（须与工程 XML 器件一致，加载时三重校验，见 §1.3） Ti60F225
@version ❌ string 产出该文件的工具版本 2025.2.276
@db_version ❌ string 设计库 schema 版本号，8 位数字形如 20252006（不是点分版本） 20252006
@last_change_date ❌ string 最后修改时间（PT 写出时的人类可读时间戳） Wed Oct 29 10:27:16 2025
@location ❌ string 文件路径（PT 写出时的位置记录） —

@db_version 语义：值形如 20252006 的 8 位整数，是 PT 内部 design_db 格式的代际标记，PT 用它判断旧文件是否需要迁移。不要手工改动它——值与工具版本强绑定。

2.3 最小片段示例（结构示意，非手工模板）

以下片段摘自官方示例（C:\Efinity\2026.1\examples\helloworld-unified\helloworld.peri.xml L1-4 + L105-108，展示根元素、iobank 与空容器），仅用于理解格式：

<?xml version="1.0" encoding="UTF-8"?>
<efxpt:design_db name="helloworld" device_def="Ti60F225" version="2025.2.276"
    db_version="20252006" last_change_date="Wed Oct 29 10:27:16 2025"
    xmlns:efxpt="http://www.efinixinc.com/peri_design_db"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance">
  <efxpt:iobank name="1A" iostd="1.8 V LVCMOS" is_dyn_voltage="false"/>
  <!-- ... 其余 11 个 iobank，见 §6.2 ... -->
  <efxpt:osc_info/>
  <efxpt:lvds_info/>
  <efxpt:jtag_info/>
  <efxpt:mipi_dphy_info/>
</efxpt:design_db>

要点： - 所有元素挂在 efxpt: 前缀下（声明于根元素 xmlns:efxpt="http://www.efinixinc.com/peri_design_db"）。 - 未使用的域也会写出空容器（如 <efxpt:osc_info/>）——这是 DesignWriterXml 的固定行为，不代表缺内容（见 §5）。

3. Schema 结构地图

3.1 聚合机制

peri.xml 的全部类型定义由 peri_design_db.xsd 聚合（证据：C:\Efinity\2026.1\pt\bin\schema\peri_design_db.xsd，共 256 行）：

  • L3-4：targetNamespace="http://www.efinixinc.com/peri_design_db"，xmlns:efxpt 前缀声明；
  • 24 个 <xs:include> + 1 个 <xs:import>（import 的是 peri_tool 命名空间的 peri_util.xsd）；
  • 勘误点：ext_flash_design.xsd 在 L8 与 L26 被 include 了两次——同一文件重复聚合，XSD 处理器容忍这种情况（幂等），属于官方 schema 自身的小瑕疵，解析自定义校验器时按去重处理即可。

4. 核心域属性全表

本节逐域列出 XML 属性：属性名 / 类型 / 含义 / 示例值。类型均取自 XSD 声明；「含义」以 XSD 内嵌 <xs:documentation> 原文（或忠实翻译）为准。来源文件均在 C:\Efinity\2026.1\pt\bin\schema\ 下。

4.1 iobank 域（iobank_design.xsd，75 行）

iobank_config_type：

属性 必填 类型 含义 示例值
@name ✅ string IO Bank 名（"IO Bank name as per device"） TL
@iostd ✅ string 该 Bank 设定的 IO 标准。XSD 原文（L36-39）："IO Standard set for this IOBank. This is not just the voltage since the decision to display voltage was rather late in the game." ——@iostd 是完整 IO 标准（含电压+电平族），不只是电压 "1.8 V LVCMOS" / "3.3 V LVCMOS"
@is_dyn_voltage ❌ bool 动态电压使能（PT-1225 引入） false
@mode_sel_name ❌ string Bank 模式选择信号名 TL_MODE_SEL

子元素 mode_sel_name（0..*）：bank_name + value 对，记录模式选择的合法组合。

ISF 对应关系：design.set_iobank_voltage("TL", "3.3") 写入的其实是 @iostd（ISF 卷 §3）。SDK 硬约束「MIPI bank 必须 1.2V、MIPI 与 LVDS 不共 bank」最终都落在这一域上。

4.2 gpio 域（gpio_design.xsd，690 行）

双形态：Trion 系用普通 gpio，Titanium 系用 comp_gpio（complex GPIO，属性更多）。gpio_info_type（L47-51）内容：

子元素 出现次数 说明
gpio 0..* 普通 GPIO（gpio_config_type）
comp_gpio 0..* 复杂 GPIO（comp_gpio_config_type，Titanium）
global_unused_config 恰 1 次 全局未用引脚默认状态
bus 0..* 总线 GPIO（bus_config_type）

⚠️ 遗留属性：gpio_info 上的 @device_def 标注 "no longer needed ... backward compatibility"（L47-51）——旧文件可能有，新文件靠根元素 @device_def。

5. DesignWriterXml 写出逻辑

本节只做概述 + 指针；调用链逐行剖析（DesignAPI.save → IntDesignAPI.save → DesignService.save_design → DesignWriterXml.write 的 L3484→L3526→L3596-3713 行号详解）见兄弟卷 《Efinity-DesignAPI方法参考.md》第 5 节「DesignWriterXml 写出模型」，两卷行号证据一致（C:\Efinity\2026.1\pt\bin\design\service.py）。

5.1 何时写出 peri.xml

场景 触发点 证据（service.py）
用户在 Interface Designer 点保存 / DesignAPI.save() DesignService.save_design（L720-732）遍历调用各块服务的 save_design service.py L3696-3697
unified 编译过程（ISF 重放后） 重放完成后对内存中演化的 design 执行整树写出 efx_run_pt_unified.py L252 之后流程

最终落盘动作（service.py L3711-3713）：open(design_file, mode='wb') ——二进制写、UTF-8 XML、整文件重写（非增量）。

5.2 19 类块的固定写出顺序

service.py L3596 有源码注释：# Blocks must be written in correct order。随后 L3597-3695 以 19 个 if/elif 槽位决定块服务追加顺序，即 XML 中块的出现顺序：

①GPIO（GPIODesignService 或 GPIODesignServiceComplex，二选一）
②PLL（5 变体 if/elif 链：普通/复杂/高级等）
③OSC（3 变体）            ④LVDS（3 变体）          ⑤MIPI（2 变体）
⑥JTAG                      ⑦DDR（2 变体）            ⑧H264
⑨MIPI DPHY（2 变体）       ⑩SPI Flash                ⑪HyperRAM
⑫PLL SSC                   ⑬CommonQuad               ⑭QuadPCIe
⑮Lane10G                   ⑯Lane1G                   ⑰RawSerdes
⑱SOC                       ⑲CM（cm_v1）

顺序为什么重要：块之间存在引用（如 GPIO 引用 iobank、PLL 输出引用 GPIO），先写被引用者。工具按此顺序写，解析器/校验器也应按此顺序读。每块写出后再逐个 save_design（L3696-3697）；L3699-3703 写出 partial_design 元素（局部设计模式标记，常规工程为空）。

5.3 空容器行为

即使某域完全未使用，DesignWriterXml 也会写出空容器元素（如 helloworld 的 <efxpt:osc_info/>，L105-108）。这与 design_db_type 全部子元素 minOccurs=0（§3.3）一致：空容器 ≠ 缺失，都是合法状态；做差异比较时不要把空容器当作「内容变化」。

7. 易混淆格式勘误：lpf.xsd 名不副实

7.1 问题：lpf 这个名字极具误导性

schema 目录中存在 C:\Efinity\2026.1\pt\bin\schema\lpf.xsd（167 行）。文件名 lpf 极易让人联想到 "Logic Preference File" / "LPF 约束文件"（某些 FPGA 厂商的物理约束格式），进而误以为 Efinity 也存在某种 LPF 约束。

7.2 事实：它是 peri_device_db 命名空间的器件数据库

实读证据（lpf.xsd）：

行号 内容 结论
L2 targetNamespace="http://www.efinixinc.com/peri_device_db" 属于器件库命名空间，不是 peri_design_db（设计库）；与 peri.xml（efxpt）毫无聚合关系（见 §3.2 清单，lpf.xsd 不在其中）
全文 根元素 periphery（periphery_type：@device / @design / @checksum） 描述某颗器件的 periphery 块数据，带 checksum 的数据库快照
— 子元素 sequence / block_def（@name / @bitsize / @paramsize）/ instance（@id / @type + parameter + 二进制 value） bit 级块定义：每个块（block_def）的位宽、参数布局、实例的二进制映像
— parameter_value 的 setting 类型是 binary_string_type（pattern ([01])+） 参数值是 01 比特串
— parameter_int_type 带 @min / @max / @endianness（little/big）/ @format（binary/hex） 整数参数的比特编码规则

7.3 结论

常见误读 事实
「lpf.xsd 定义了 Efinity 的 LPF 约束文件格式」 ❌ Efinity 没有 LPF 约束格式；约束只有 ISF（给 PT）和 SDC（给 pnr）两种（硬约束 §1）
「peri.xml 会引用 lpf」 ❌ lpf.xsd 属于 peri_device_db（器件库），peri.xml 属于 peri_design_db（设计库），二者命名空间不同、无 include/import 关系（§2.1、§3.2）
「lpf 是 SDC 的变体」 ❌ 与 SDC 毫无关系；SDC 由 efx_pnr 消费，lpf.xsd 描述的是 PT 器件数据库里的 bit 级块定义

用途定位：lpf.xsd 服务于 PT 内部把设计库数据（peri.xml）与器件出厂 bit 级定义对表/校验的场景（block_def 的 bitsize/paramsize + instance 二进制值）。做 SDK 级工具时不需要解析它；任何把「lpf」当约束格式的代码都是被文件名误导的 bug。

同类命名空间勘误可对照 DesignAPI 卷第 0.1 节「三条勘误」与 SDC 卷对报告产物命名空间的分析。

8. 工程守则与兄弟卷交叉引用

8.1 peri.xml 工程守则（清单式）

  1. 绝不手工编写/编辑 peri.xml。官方原话 "You should not edit this file directly!"（gloss-peri.xml.html L190-193）。修改入口只有两条：Interface Designer（GUI）或 ISF/DesignAPI（脚本）。
  2. peri.xml 是工程源文件：与 ISF 一起纳入版本管理；任何构建路径（SDK / adapter / 脚本）不得在构建前删除它——删除重生成是 workaround，不是修复（硬约束 §15）。
  3. 自检 gate：每次变更约束后，先让 ISF 过 cli/import_gpio.bat --dry-run，再跑一次重放编译确认 peri.xml 加载正常（ISF 卷 §4；硬约束 §16）。
  4. bootstrap 一次性：create_* 只在 peri.xml 不存在时跑一次，之后必须注释（ISF 卷 §3；本卷 §1.4）。
  5. 不要写解析/生成 peri.xml 的自研工具：格式由 24 个子 schema 组成且随 db_version 演进（§3、@db_version §2.2），正确姿势是走 DesignAPI（DesignAPI 卷）。唯一合理的程序化接触面是 DesignAPI 读接口（如做工作台 UI 展示）。
  6. 差异比较的注意点：空容器 ≠ 内容变化（§5.3）；@last_change_date 每次保存必变，diff 时忽略。
  7. 器件三重一致性：peri.xml 的 @device_def 必须与工程 XML 器件信息匹配，否则 unified 流程 L224-230 直接 ERROR（§1.3）——复制别的工程当模板时第一件事就是换器件。
  8. SDC 时钟名对齐：peri.xml 中 PLL comp_output_clock/@name 就是 RTL 时钟名，SDC create_clock 必须与之精确匹配（§6.7；SDC 卷硬约束 §7）。
