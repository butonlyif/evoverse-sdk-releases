1. 时序分析基础概念

1.1 核心术语

术语 含义
Setup Time 数据必须在时钟沿到达前稳定的最小时间。违例 = 数据太慢
Hold Time 数据必须在时钟沿到达后保持稳定的最小时间。违例 = 数据太快
Slack 时序余量。正值 = 满足，负值 = 违例。是 Required Time − Arrival Time
WNS (Worst Negative Slack) 最差负 slack，整个设计中最严重违例的 slack 值
TNS (Total Negative Slack) 所有违例路径 slack 的总和，反映违例总量
Tlogic 组合逻辑延迟（LUT、MUX、加法器等 cell 延迟之和）
Tnet 布线延迟（net 上信号的传播延迟）
Tclk_skew 时钟偏斜（同一时钟到达不同寄存器的延迟差）
Critical Path 关键路径：slack 最小（最差）的时序路径，是优化的首要目标

1.2 时序路径模型

启动寄存器 CK→Q → [Tlogic] → [Tnet] → 捕获寄存器 D 端
                                                ↑
                                             Setup/Hold window

Data Arrival Time = Tclk_launch + Tcko + Tlogic + Tnet
Data Required Time = Tclk_capture + Tperiod − Tsetup − Tuncertainty

Slack = Required Time − Arrival Time
  • setup slack < 0：数据到得太晚，没赶上下一个时钟沿采样
  • hold slack < 0：数据到得太早，覆盖了当前时钟沿采样的上一个数据

1.3 Efinix 架构对时序的影响

  • LUT4 架构：每个 LUT 只能实现 4 输入函数，深逻辑链（≥3 LUT 无寄存器打断）容易出现 setup 违例
  • Quantum 架构的 IO Block：有专用的输入/输出寄存器，不占用核心逻辑，延迟更短
  • 全局时钟网络：Efinix 用全局时钟 spine，时钟偏斜通常很小（<0.1ns）
  • DSP/RAM 内置寄存器：这些硬块的输出寄存器是"免费"的，不用则形成长组合路径

2. SDC 约束编写

2.1 基本约束模板

# ========== 时钟定义 ==========
create_clock -period 10.0 -name sys_clk  [get_ports clk_i]
create_clock -period 6.734 -name video_clk [get_ports video_clk_i]

# ========== 异步时钟域 ==========
set_clock_groups -asynchronous \
    -group [get_clocks sys_clk] \
    -group [get_clocks video_clk]

# ========== 生成时钟（PLL 输出）==========
# 如果 PLL 在 Interface Designer 中配置，Efinity 会自动推导
# 手动场景：
create_generated_clock -name pll_clk_200m \
    -source [get_ports clk_i] -multiply_by 4 \
    [get_pins PLL_inst/clk_out]

# ========== I/O 延迟 ==========
# 输入：外部器件 clock-to-out + 板级走线 = 3ns max
set_input_delay -clock sys_clk -max 3.0 [get_ports {data_in[*]}]
set_input_delay -clock sys_clk -min 1.5 [get_ports {data_in[*]}]

# 输出：板级走线 + 外部器件 setup = 2.5ns max
set_output_delay -clock sys_clk -max 2.5 [get_ports {data_out[*]}]
set_output_delay -clock sys_clk -min 1.0 [get_ports {data_out[*]}]

# ========== 伪路径（确认异步才加）==========
# 不要在整个 CDC 路径上加 false_path！
# 正确做法：set_clock_groups 切断时钟域间分析，
# 然后只在同步链前两级（不确定数据处）加 false_path
set_false_path -from [get_cells sync_ff_reg[0]] -to [get_cells sync_ff_reg[1]]

2.2 常见错误

错误 后果 正确做法
忘记 set_clock_groups -asynchronous 工具尝试满足异步时钟间的同步关系，布局被扰乱 确认异步后立即加上
set_false_path 覆盖整条 CDC 掩盖真正的违例，可能漏掉缺失同步器的信号 只覆盖同步链本身
I/O delay 全用 0 工具不知道外部条件，可能把关键资源错配给不重要的 I/O 给合理的保守值
时钟 period 设错 工具按错误频率优化 → 重新编译 用示波器/器件手册确认
多条 create_clock 用同一个 port 覆盖前一条定义 每个时钟 port 只定义一次

2.3 SDC 放置位置

<project>/
  constraints/
    top.sdc          ← 主约束文件，在 Efinity 项目 XML 中引用

EvoVerse SDK 在每次 Build 前会自动检查 SDC 文件是否存在。如果缺失，会弹出警告。

3. Build Report 解读

3.1 触发方式

在 VS Code 中打开 EvoVerse 项目后：

  • 命令面板 → EvoVerse: Build（或快捷键）
  • 或者在 MCP Server 中调用 build_project

编译完成后，如果设置了 "evoverse.build.autoOpenReport": true，会自动打开 Build Report。

3.2 Report 面板 Tab 说明

Build Report 包含以下 Tab：

Tab 内容
Overview 编译概览：器件、Top Module、耗时、时序状态（All Met / N violations）
Resources 资源占用饼图：LUT、FF、RAM、DSP、PLL 使用率
Timing 按时钟域分组的 WNS/TNS/违例路径数，每个时钟域一条
Critical Paths 每条违例路径的 hop-by-hop 延迟列表（按 slack 排序）
Tcl Console 交互式 STA 查询
Optimization 编译策略优化建议（由 BuildStrategyAdvisor 生成）

3.3 从 Overview 快速判断

  • All Met, 利用率 50% 以下：设计轻松收敛，关注资源效率即可
  • All Met, 利用率 80%+：设计稳定，但后续加功能可能触发违例
  • N violations, N ≤ 5：数量少，优先诊断单条路径
  • N violations, N ≥ 10 且集中在一个时钟域：可能存在系统性架构问题（频率过高？长路径模式？

3.4 从 Timing Tab 快速定位

Timing Tab 按时钟域列出。优先关注： 1. WNS 最负的时钟域 2. TNS 最大的时钟域（违例总量最大） 3. 违例路径数最多的时钟域（普遍性问题）

4. 时序诊断：自动根因分析

4.1 触发方式

Build 完成后若有违例，会弹出通知：

Build 完成但有 3 条时序违例（WNS=−1.2ns）。是否运行时序诊断？

点击 "诊断时序"，或通过命令面板 → EvoVerse: Diagnose Timing 手动触发。

4.2 诊断引擎工作流程

CriticalPath[] → extractFeatures() → classify() → queryByCategory() → scoreFingerprint() → Diagnosis[]

第一步：特征提取 对每条违例路径计算： - cell 数量和比例（logicRatio） - route 数量和比例（netRatio） - 是否跨时钟域（crossClock） - 是否起始于 IO port（startsAtPort） - 是否经过 RAM/DSP（throughBlock）

第二步：分类 按优先级匹配 7 大类：

类别 判定条件 置信度
CDC start/end 的时钟名不同 0.7
I/O startsAtPort 或 endsAtPort 0.8
资源瓶颈 经过 RAM 或 DSP 0.8～0.85
长组合逻辑 ≥3 个 cell + logic 占比 > 0.5 0.85
高扇出 net 占比 > 0.4 0.6
时钟架构 同一时钟域 ≥3 条违例 自动升级
未知 不满足以上任何条件 0.3

第三步：知识库召回 按类别查找内建的 14 条知识库条目，每条都带 fingerprint 匹配打分。

第四步：生成建议 按匹配分排序，返回最优的根因诊断和修复方案。

4.3 诊断结果界面

诊断 Webview 包含三个 Tab：

Tab 内容
诊断结果 根因分析 + 修复建议（含示例代码）+ 证据展示
数据路径 Mermaid 路径拓扑图 + 延迟火焰图 + 延迟分解
Pipeline 分析 三阶段冗余打拍分析报告

左上角可以切换违例路径（按 slack 排序的下拉选择器）。

右下角有 "Ask LLM" 按钮，将当前路径的诊断上下文 + RTL 片段 + SDC 发送给 LLM 获取更深层的分析。

5. 数据路径分析与可视化

5.1 DataPathTracer 输出

DataPathTracer 将一条 timing report 中的 hop 序列重新组织为结构化的数据流：

Hop 序列:
  cam_top/cap_reg[3]/CK→Q  ← 启动寄存器
  LUT4: cam_top/cap_next[3]  ← 组合逻辑
  NET: cap_next[3]           ← 布线
  LUT4: cam_top/fifo_wr      ← 组合逻辑 (跨模块!)
  NET: fifo_wr                ← 布线
  u_fifo/wr_ptr[0]/SETUP     ← 捕获寄存器

结构化为：

模块 cam_top 内部:
  register → logic(LUT4) → route → logic(LUT4) ───跨模块边界──→ 模块 u_fifo:
                                                                  route → register

5.2 延迟分解

组成部分 含义 优化方向
logicNs 组合逻辑延迟 减少 LUT 层数、插入流水线
routeNs 布线延迟 检查高扇出、逻辑复制、Floorplan
registerNs 寄存器 CK→Q + Setup 无法优化（工艺固定）
clockOverheadNs 时钟余量（skew + uncertainty） 减少时钟不确定性设置，或调整 PLL

5.3 Mermaid 拓扑图

DataPathTracer 自动生成 Mermaid 流程图，展示数据通路的结构：

  • 绿色节点：延迟占比 < 12%
  • 黄色节点：延迟占比 12%～25%
  • 红色节点：延迟占比 ≥ 25%（瓶颈！）
  • 模块边界用虚线标注

6. Pipeline 深度分析：冗余打拍检测

6.1 不是简单的"找到寄存器就去掉"

这是最复杂的分析模块。去掉一个寄存器会牵动整个数据通路的时序契约——伴生的控制信号、计数器、帧标记、初始化序列都可能不同步。

6.2 三阶段分析

阶段一（时序可行性）    阶段二（信号依赖）        阶段三（等效性）
    ↓                      ↓                        ↓
findCandidateRegisters() → analyzeSignalDep()  → checkEquivalence()
    ↓                      ↓                        ↓
候选寄存器列表            依赖分析报告              最终建议
(slack 预估值)           (7 类检查)              (actionable? 风险等级)

阶段一：时序可行性（纯数量计算）

找到路径上相邻的两个寄存器（跨模块边界最常见），预估去掉一个后的 slack： - slack > 0 → 继续分析 - slack ≤ 0 → 标记为"去掉后仍违例"，不进入阶段二

阶段二：信号依赖分析（7 项检查）

检查项 判断逻辑
握手协议 候选寄存器是否与 valid/ready 在同一个 always 块中
帧标记 是否伴生 last/sof/eof 信号
计数器 数据延迟改变后，帧计数/行计数是否还能对齐
反馈环路 去掉一拍后是否破坏了闭环逻辑（如积分器）
多消费者 该寄存器输出是否被多个下游模块消费
初始化时序 复位/初始化序列是否依赖当前的延迟拍数
SVA 仿真验证中的 ##N 延迟断言是否受影响

阶段三：等效性

生成前后时序契约对比，标注所有不一致点。不确定时宁可保守——标注"需要人工确认"，不给操作按钮。

6.3 硬约束

  • 永不给"只去掉单个寄存器"的建议：识别到伴生信号后，必须整组处理
  • 所有伴生信号都会被标注：即使看似无关的 debug 计数器也要检查
  • actionable = false 时不给操作按钮：仅展示分析结论，等待人工判断

6.4 仿真回归

Pipeline 分析建议修改 RTL 后，需要验证等效性。EvoVerse SDK 提供一键仿真回归：

  • 命令面板 → EvoVerse: Run Simulation Regression
  • 自动调用 iverilog / vvp 对比修改前后测试向量的输出
  • 差异报告直接嵌入诊断 Webview

7. 编译策略优化

7.1 BuildStrategyAdvisor

编译完成后自动分析 BuildSummary，在 Build Report 的 Optimization Tab 中给出策略建议。每条建议都有：

  • 触发原因：引用具体报告数据
  • 预期效果：量化预估
  • 风险等级：low / medium / high
  • 操作按钮（仅 auto 类型）：一键应用 + Rebuild

7.2 策略类型

策略 触发条件 类型
AOE 面积优化 资源利用率高（≥80%）+ 时序宽松 auto
AOE 关闭 资源利用率低（<60%）+ 时序紧张 auto
Retiming 路径上寄存器分布不均 manual
PNR Effort High WNS 很近（−0.1～−0.5ns） auto
Seed Sweep 布局结果波动大 manual
DSP Packing 乘法器未被映射到 DSP 块 manual
BRAM Output Register RAM 读路径出现违例 manual

7.3 AOE 决策矩阵

资源利用率 时序状态 建议
≥80% All Met 保持 AOE，面积优先级正确
≥80% 违例 放松 AOE：允许面积增大换取时序
<60% All Met 开启 AOE：面积可优化
<60% 违例 关闭 AOE：有空间就优先保时序
60-80% 违例 视具体资源瓶颈而定，优先关闭受影响模块的 AOE

9. 典型优化流程

9.1 标准工作流

Step 1: 编写 SDC
  ↓
Step 2: Build（Ctrl+Shift+B 或 EvoVerse: Build）
  ↓
Step 3: 查看 Build Report → Timing Tab
  ├─ All Met? → 完成 ✓
  └─ 有违例 →
       ↓
Step 4: 诊断时序（Diagnose Timing）
  ↓
Step 5: 查看诊断建议
  ├─ 先试低风险工具选项（Optimization Tab）
  │   · Effort Level High
  │   · Seed Sweep
  │   · Retiming → Rebuild → 回到 Step 2
  ↓
Step 6: 若工具选项不足 → 查看 RTL 级建议
  ├─ 长组合链 → 插入流水线
  ├─ 高扇出 → (* max_fanout = N *)
  ├─ CDC → 补同步器 + 改约束
  ├─ I/O → 配置 IO register + IO delay
  └─ 资源瓶颈 → 打开 RAM/DSP 输出寄存器
  ↓
Step 7: 改 RTL → Rebuild → 回到 Step 2
  ↓
Step 8 (高级): 若仍有困难路径
  ├─ 打开 "数据路径分析" Tab → 找到瓶颈 hop
  ├─ 打开 "Pipeline 分析" Tab → 检查跨模块冗余打拍
  └─ "Ask LLM" → 将完整上下文给 LLM 分析

9.2 优先级原则

  1. 先约束、后 RTL：SDC 错误/遗漏是最常见的根本原因
  2. 先选项、后手改：Effort Level / Retiming 是无痛优化
  3. 先局部、后架构：尽量不降频，除非多条路径普遍违例
  4. 先慢路径、后快路径：setup 违例 > hold 违例（hold 通常工具能自动修）

10. 常见违例模式与解法

10.1 模式 A：长组合逻辑链

症状：Tlogic 占比 > 60%，连续 3+ 个 LUT/MUX 无寄存器

根因：assign data_o = f(g(h(data_i))) 这种"一句话算完"

解法：

// ❌ assign result = stage3(stage2(stage1(data_i)));
// ✅
reg [W-1:0] pipe1, pipe2;
always @(posedge clk) pipe1 <= stage1(data_i);
always @(posedge clk) pipe2 <= stage2(pipe1);
assign result = stage3(pipe2);

代价：多 2 拍延迟

10.2 模式 B：高扇出

症状：Tnet 占比 > 40%，一个信号驱动几百个 sink

解法：

(* max_fanout = 100 *) reg shared_enable;

10.3 模式 C：CDC 违例

症状：路径 start 和 end 在不同时钟域

解法：

# 第一步：切断跨时钟域同步分析
set_clock_groups -asynchronous \
    -group [get_clocks clk_a] \
    -group [get_clocks clk_b]

// 第二步：确保有同步器
(* ASYNC_REG = "TRUE" *) reg [2:0] sync_ff;
always @(posedge clk_dst)
    sync_ff <= {sync_ff[1:0], src_signal};

10.4 模式 D：I/O 路径

症状：经过 IO port 的路径违例

解法： 1. 补 set_input_delay / set_output_delay 2. 在 Interface Designer 中勾选 pin 的 "Register" 3. 在 RTL 中：输入第一拍就打拍，输出最后一拍是寄存器

10.5 模式 E：时钟架构问题

症状：同一时钟域 ≥3 条违例，单点优化无法收敛

解法： - 频率是否太高？（TJ180 LUT4 深逻辑的实用上限约 100-150MHz） - 考虑用 PLL 降低该时钟域频率 - 或拆分数据通路：慢域做控制，快域做数据处理

10.6 模式 F：资源瓶颈

症状：经过 BRAM/DSP 的路径违例

解法：

// BRAM: 打开输出寄存器（免费！）
(* ram_style = "block" *) reg [W-1:0] mem [0:D-1];
reg [W-1:0] mem_rd;
always @(posedge clk) begin
    if (wr_en) mem[wr_addr] <= wr_data;
    mem_rd <= mem[rd_addr];  // ← 这个寄存器存在 BRAM 内部，不占用逻辑
end

// DSP: 寄存输入和输出
(* use_dsp = "yes" *)
reg [17:0] a_r, b_r, p_r;
always @(posedge clk) begin
    a_r <= a; b_r <= b;  // 输入寄存器
    p_r <= a_r * b_r;     // 输出寄存器
end

10.7 跨模块冗余打拍

症状：两个模块各自在接口处打了寄存器

模块 A: always @(posedge clk) data_o <= data_next;  // 打了一拍
模块 B: always @(posedge clk) data_r <= data_i;     // 又打了一拍

解法：通过 Pipeline 深度分析确定是否可以去掉某一侧的寄存器（详见第 6 章）
