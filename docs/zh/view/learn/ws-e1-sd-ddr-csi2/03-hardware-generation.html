03 生成 IP 与受控 RTL

阶段 03 · 生成 RTL 并交付候选（三轮增量）

规格与等级决策方式已就绪，本阶段用三轮增量把 SD card -> DDR frame buffer -> MIPI CSI-2 TX 全链路建立起来。每一轮都走同一个循环：intent.create 声明增量 → simulation.profile.select 决策等级 → spec.draft 起草差量规格 → 生成候选 → candidate.deliver 冻结候选 → verification.simulate 独立取证 → candidate.promote 晋级。上一轮晋级产生的新基线，就是下一轮的父基线。

候选语义（可靠设计的核心）：Agent 绝不直接写正式 RTL 目录。candidate.deliver 只负责冻结候选并执行 Design Assurance——基线保持不变；只有仿真 PASS 且资格满足后，candidate.promote 才把候选与父基线合并安装为新基线。生成的一切最终都服务于 TJ180A484S 上的显示链路。

两条贯穿三轮的规则：

  1. 父基线快照：intent.create 会把本轮父基线的资产快照进 IntentRecord.baseBaselineFiles（第一轮 = Stage0 初始基线；第二、三轮 = 上一轮晋级基线）。差量规格的对照、候选校验、晋级合并都以这份快照为准。
  2. expectedRevision 是并发提示值：控制面始终按最新 revision 追加事实；提交时的 revision 冲突只会得到对账动作，不会造成覆盖。它是协作提示，不是安全边界——真正的边界是回执与资格检查。

把这个循环画出来。每一轮都走一遍；仿真 FAIL 不丢弃候选——修复后重新冻结、重新仿真：

你对 Trae 说什么

第一步，完成第一轮增量（SD 输入）的完整循环：

用 intent.create 为本工程声明第一轮增量意图：实现 SD 主机控制器与帧缓冲写控制器，
作用域限定 rtl/ 下两个叶子模块及其 sim/ 验证源。基线中已有的 DDR wrapper 与 CSI-2 TX
例化保持只读，用 asset.adopt 纳入意图作用域；展示 project_next 里这两个动作的
inputSchema 与前置条件后再执行。

接着用 simulation.profile.select 做等级决策：展示服务端推荐等级与理由，
我确认选择；如果低于推荐，列出 acceptedRisks 让我逐条确认。

再用 spec.draft 起草本轮差量规格：只写新增两个模块及其与父基线的顶层连接，
对照父基线文件账本标注复用 / 新增 / 修改，给我预览确认后冻结。

然后用 /evoverse-rtl 按已批准差量规格生成上述两个模块，候选只写到候选区路径；
完成后用 candidate.deliver 提交完整候选文件集（files 或 filesRoot，origin 为 generated），
再用 verification.simulate 按所选等级记录仿真证据。
仿真 PASS 且资格满足后用 candidate.promote 晋级，把候选与父基线合并安装为新基线。
全程展示每一步的 MCP 回执。未冻结规格或回执缺失时立即停止。

第二步，以晋级后的基线为父基线，重复完成第二、三轮：

第一轮已晋级，当前基线包含 SD 输入。请按同样的循环完成第二轮增量：
用 intent.create 声明 DDR 缓冲增量，父基线是 SD 晋级后的基线；
simulation.profile.select 重新决策等级（不继承上一轮的选择与 acceptedRisks），
spec.draft 起草差量规格，candidate.deliver 冻结候选，
verification.simulate 独立仿真，PASS 后 candidate.promote 晋级。

第三轮同理：用 intent.create 声明 CSI-2 输出增量，父基线是 DDR 晋级后的基线，
走完等级决策、差量规格、候选交付、独立仿真与晋级。
每轮都展示 baseBaselineFiles 快照回执与晋级回执；任何一轮仿真未 PASS 就停下等我决策。

Trae 会帮你做什么

  1. project_status 确认 Stage0 基线就绪；project_next 确认 intent.create 可用并展示其 inputSchema。
  2. 提交 intent.create：控制面把本轮父基线（第一轮为 Stage0 初始基线）的资产快照进 IntentRecord.baseBaselineFiles，回执里能看到这份清单——它是后面"复用 / 新增 / 修改"记账的锚点。
  3. simulation.profile.select 两阶段决策：服务端按 riskFacts 给出推荐等级，你确认选择；低于推荐时 acceptedRisks 逐条落账。等级绑定在本轮迭代上，不继承、不外溢。
  4. spec.draft 起草差量规格并冻结：只描述本轮增量及其与父基线的顶层连接，复用项对照 baseBaselineFiles 快照标注。
  5. 调用 /evoverse-rtl 按规格生成候选 RTL 与测试平台到候选区路径，遵守 RTL 编码规范（异步复位同步释放、CDC 同步器、无分频时钟、组合块默认值）。
  6. 候选就绪后提交 candidate.deliver（files 或暂存目录 filesRoot，origin=generated）：控制面冻结候选、执行 Design Assurance、记录候选摘要——基线保持不变；verification.simulate 按所选等级对已冻结候选独立取证，incomplete 不会被当作 PASS。
  7. 仿真 PASS 且资格满足后提交 candidate.promote：控制面把候选与父基线合并安装为新基线，晋级回执记录新基线摘要——它就是下一轮的父基线。
  8. 每个动作后重新 project_status，报告新 revision 与证据区变化；重复第 2–7 步完成 DDR 缓冲与 CSI-2 输出两轮。

你需要确认什么

  • 未冻结规格不能开始生成：如果 /evoverse-rtl 发现接口、位宽、时钟域或 Oracle 有歧义，它会停在规格决策上——这是正常保护，回到阶段 02 补决策，不要绕过。
  • 父基线对不上就停：每一轮 intent.create 的快照回执都要和你认知的父基线一致——第一轮是 Stage0 初始基线，第二、三轮是上一轮晋级基线。对不上说明有未对账的推进，停下来处理，不要在错误的基线上继续。
  • acceptedRisks 是显式决策：simulation.profile.select 低于推荐等级时，每条风险都要你逐条确认；降级不是省钱，是把"没验证什么"写进账本。
  • 候选改一行，重新交付重新仿真：仿真证据绑定的是已冻结候选的摘要；candidate.deliver 之后候选不可变，任何改动都意味着新一轮交付与仿真。
  • expectedRevision 冲突不是事故：它只是并发提示值，冲突时控制面给出对账动作；不要为了"保险"教 Agent 依赖过期 revision。

通过条件

  • 三轮增量共 12 张回执在 project_status 可见：每轮的 intent.create、candidate.deliver、verification.simulate、candidate.promote 各一张。
  • 三轮的 baseBaselineFiles 快照逐一可查：Stage0 初始基线 → SD 晋级基线 → DDR 晋级基线，父基线链条完整。
  • 当前基线包含 SD card -> DDR frame buffer -> MIPI CSI-2 TX 全链路模块，且每轮候选都有规格指纹与独立仿真证据绑定。
  • 任何一轮仿真未 PASS 的候选都不会出现在当前基线里；incomplete 从未被当作 PASS。
  • 生成的 RTL 与测试平台通过资格审查：测试平台损坏、Oracle 含糊、覆盖不足时不会得到 PASS。
  • 三轮晋级完成后，工程离 efx_run --flow compile 的原生编译只差集成阶段（阶段 05）。
