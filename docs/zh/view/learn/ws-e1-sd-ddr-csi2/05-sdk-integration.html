05 SDK 集成

阶段 05 · SDK 集成

三轮增量晋级后的基线与固件已就绪，本阶段把它们与 Efinity 工程文件（XML / ISF / SDC）对齐：检查工程合同、同步设计源、验证设计一致性。所有变更都走"预览 → 确认 → 应用"。

工程合同（project contract）定义了控制面看到的工程结构与 Efinity 工具链看到的工程文件之间的对应关系。SD card -> DDR frame buffer -> MIPI CSI-2 TX 的引脚、时钟、bank 电压都在这一步落到 TJ180A484S 的物理约束上。

三类验证在此分界：verification.simulate 的 PASS 只证明候选在所选等级的仿真场景下正确，不证明原生编译收敛，更不证明板上运转——后者分别由阶段 06 的 build.native 与 hardware.validate 取证。

本阶段的所有检查都围绕工程合同展开，目标是让三视图指向同一套文件：

flowchart TD
    A["控制面资产清单<br>project_status"] --- B{"工程合同<br>project contract"}
    C["Efinity 工程 XML<br>设计源清单"] --- B
    D["ISF / SDC 约束"] --- B
    B --> E["同步设计源<br>预览 → 确认 → 应用"]
    E --> F["设计验证<br>引脚 / bank 电压 / 时钟"]
    F --> G{"三视图一致？"}
    G -->|是| H["revision 更新<br>满足编译输入条件"]
    G -->|否| E

你对 Trae 说什么

帮我做一次集成检查：控制面里的资产清单、Efinity 工程文件和 ISF/SDC 约束
是不是指向同一套文件？把发现的不一致整理成预览清单给我确认，
确认后再同步修正。完成后告诉我新的 revision。

Trae 会帮你做什么

  1. project_status 读取当前 Baseline 与资产清单，展示工程合同：顶层模块、设计文件、约束文件、器件 TJ180A484S。
  2. 检查设计源与工程 XML 的对应关系：新增的候选 RTL 是否已进入源清单，被移除的文件是否还挂在 XML 里。
  3. 同步设计源到 Efinity 工程（新增 <efx:design_file> 条目、更新 flist 引用），同步前给你完整预览。
  4. 运行设计验证：引脚分配、bank 电压、时钟定义与规格物理节逐项比对；MIPI bank 必须 1.2V、与 LVDS 不共 bank、PLL 在 ISF 中创建。
  5. 应用确认后的变更，重新 project_status 报告 revision 变化。
  6. 任何验证失败都会原样报告——集成阶段只修"工程文件与候选不一致"，不静默改你的 RTL。

你需要确认什么

  • 预览清单里的每一条变更：同步工具只改必要部分，ISF/SDC 不做"顺手美化"。
  • 管脚策略：改功能不改 pin；新增功能从板卡 pinout 选空闲管脚且同 bank 电压一致。
  • 工程 XML 不手动编辑：结构变更都通过同步能力完成，避免空的 <efx:inter_file> 之类手写错误。
  • 验证报告中与规格物理节冲突的条目：要么改工程文件，要么回到阶段 02 修订规格——两边不能各说各话。

如果不顺利

现象 怎么处理
验证报告与规格物理节冲突 二选一：改工程文件适配规格，或回到阶段 02 修订规格——两边不能各说各话。
Trae 想顺手优化约束文件 拒绝。集成阶段只修"工程文件与候选不一致"，不做"顺手美化"。
预览清单太长看不完 至少逐条确认引脚分配、bank 电压和时钟定义三处——它们直接影响 efx_run --flow compile 能否收敛。

通过条件

  • 工程合同三视图一致：控制面资产、Efinity 工程 XML、ISF/SDC 约束指向同一套文件。
  • 设计验证零冲突，或剩余冲突都有明确的处理决定记录。
  • SDC 为每个时钟端口提供 create_clock，异步域声明 set_clock_groups -asynchronous。
  • 工程已满足 efx_run --flow compile 的全部输入条件：源清单完整、约束合法、器件与速度等级正确。

完成后进入 阶段 06：编译与硬件验证。
