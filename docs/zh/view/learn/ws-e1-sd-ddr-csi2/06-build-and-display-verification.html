06 编译与显示验证

阶段 06 · 编译与硬件验证

前五个阶段都在准备证据，本阶段产生实物证据：build.native 记录一次原生编译，hardware.program 把 bitstream 烧进 TJ180A484S，hardware.validate 按 scenario 逐条确认 SD card -> DDR frame buffer -> MIPI CSI-2 TX 在板上真实运转。

三类证据互不替代：编译通过 ≠ 时序收敛，时序收敛 ≠ 功能正确，烧录成功 ≠ 板上验证通过。没有硬件时，本阶段允许停在编译证据上，并把集成状态如实标记为 INTEGRATION_PENDING_HARDWARE——这与阶段 04 固件章节的边界一致。

基线状态决定本阶段的入口。基线就绪但从未原生编译时，工程停在 NATIVE_BUILD_PENDING；编译通过但未上板时，停在 BOARD_VALIDATION_REQUIRED。若受控基线资产被自由模式改动过，状态会显示 UNVERIFIED_CHANGES——此时不得把旧基线的 PASS 证据贴到自由改动上，先回到可靠流程重新交付与晋级，或明确接受自由改动并重新编译取证。反过来，可靠仿真也不是通用前置：自由模式普通 Build 始终可用。

这几个状态的流转关系如下：

stateDiagram-v2
    [*] --> NATIVE_BUILD_PENDING: 基线就绪，尚未原生编译
    NATIVE_BUILD_PENDING --> BOARD_VALIDATION_REQUIRED: build.native 编译通过
    BOARD_VALIDATION_REQUIRED --> [*]: hardware.program + hardware.validate
    NATIVE_BUILD_PENDING --> UNVERIFIED_CHANGES: 自由模式改动基线资产
    BOARD_VALIDATION_REQUIRED --> UNVERIFIED_CHANGES: 自由模式改动基线资产
    UNVERIFIED_CHANGES --> NATIVE_BUILD_PENDING: 重新交付晋级后恢复

你对 Trae 说什么

对工程做一次原生编译，把资源占用、时钟域和时序摘要给我看。
编译通过后，如果我已经接好 WS-E1 核心板和 JTAG 调试器，引导我烧录：
烧录前跟我确认板卡和器件编号；烧录后按场景逐条验证显示链路——
SD 卡初始化、DDR 帧缓冲读回校验、读端所有权交接、CSI-2 TX 输出、
接收端图像轮换。没接硬件就停在编译证据，如实标记待硬件验证。

Trae 会帮你做什么

  1. 先 project_status 检查基线状态：NATIVE_BUILD_PENDING / BOARD_VALIDATION_REQUIRED / UNVERIFIED_CHANGES 各自决定本阶段从哪一步开始；基线被自由改动过时不继承旧 PASS。
  2. build.native（mode: free 或 reliable）触发 Efinity Adapter 调用原生 efx_run --flow compile 统一流程：map → PT → pnr → pgm 一步到底，不拆步骤拼接。
  3. 解析编译报告：资源利用率、I/O 与时钟域、WNS/TNS；把报告路径和摘要作为构建证据登记到控制面。
  4. 时序违例不会静默放过——WNS < 0 时提示先回到阶段 05 检查约束，或用时序诊断定位根因，而不是反复重编译碰运气。
  5. 硬件就绪时走 hardware.program：adapterId / boardId / deviceId 必填，器件编号写 ANY 或 AUTO 会被控制面以 AMBIGUOUS_DEVICE 拒绝；confirmedBy 记录是谁确认了这次烧录。
  6. hardware.validate 按你声明的 scenarios 逐条验证部署后的固件与 RTL：每条场景独立判定，部分通过就是部分通过。
  7. 没有硬件时：只登记 build.native 证据，集成状态标记 INTEGRATION_PENDING_HARDWARE，不会把"找到 JTAG 入口"写成"板上验证通过"。

你需要确认什么

  • 烧录目标：板卡与器件编号由你显式确认，工具不会替你猜；插着多块板时尤其如此。
  • 观察顺序：串口先出现 DDR 读回校验通过，再开始 CSI-2 输出；调试采样（扫描器件、采集关键信号等观测能力）能看到读端与 TX 的活动。
  • 接收端显示：图像轮换是你亲眼确认的现象，不是从日志推断的结论。
  • 证据边界：编译证据、时序报告、板上场景证据分别保存；任何一项缺失都要在报告里点名。

如果不顺利

现象 怎么处理
编译超过十几分钟 正常。Titanium 器件的原生编译是长任务，中途取消重跑只会更久；问"现在跑到 map、pnr 还是 pgm"即可。
时序违例（WNS < 0） 不要反复重编译碰运气。让 Trae 用时序诊断定位根因，或回到阶段 05 检查约束。
烧录找不到器件 先查 USB 线、JTAG 连接和驱动；插着多块板时确认烧的是哪一块，不要让工具替你猜。
板上现象和预期不符 让 Trae 按场景逐条给你看证据：串口 DDR 读回校验、CSI-2 输出、接收端图像，一环一环排，不要笼统说"链路不通"。
没接硬件 INTEGRATION_PENDING_HARDWARE 是合法终态，停在编译证据即可，不要伪造板上结论。

通过条件

  • efx_run --flow compile 成功，构建与时序报告已作为 build.native 证据登记。
  • 有硬件时：hardware.program 有烧录回执（含 deviceId 与 confirmedBy），hardware.validate 的全部声明场景通过并留有逐条证据。
  • 无硬件时：项目如实停留在"编译通过 + INTEGRATION_PENDING_HARDWARE"，不留含糊的空间。
  • SD card -> DDR frame buffer -> MIPI CSI-2 TX 链路在 TJ180A484S 上被接收端实际观察到——这一条只有在有硬件的场景下才能勾选。
