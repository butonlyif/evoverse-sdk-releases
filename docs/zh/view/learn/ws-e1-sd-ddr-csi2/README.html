WS-E1 SD 到 CSI-2 总览

WS-E1 SD 到 CSI-2 工程教程（复杂单 FPGA）

适用 EvoVerse SDK v1.0.1 · 2026-11-28

适用版本：v1.0.1　目标器件：TJ180A484S（Titanium Ti60，C4 timing model）　默认宿主：Trae

本教程只讲一个意图：在 TJ180A484S 上做一条 SD card -> DDR frame buffer -> MIPI CSI-2 TX 显示链路。复杂单 FPGA 不等于必须由客户拆成十几个步骤；Agent 会把一个意图拆成若干模块切片，让每个模块按自己的契约独立收敛，最后在同一次芯片内 composition 中合成。

先讲清一条红线：不得把目标 sd-ddr-csi2 工程的 RTL、约束或工程文件复制为新工程基线。目标工程只用于物料分析和结论比对；你要得到的是由你自己的规格、自己的候选 RTL 和自己的证据链支撑的工程。

一个意图，三个决策

整条旅程只要求你做三个决策，其余由控制面连续推进：

  1. 确认方案与可执行规格——Agent 先给出模块拆分（sd_host、frame_buffer_writer、csi2_tx 加时钟/复位）、每个模块的 ModuleSpec 与接口契约、仿真等级与验收场景。你一次确认后，规格冻结；生成前不会再反复打断你。
  2. 按需确认高成本或设备写入——只有烧录、部署或高成本构建需要你显式授权；只读检查、生成、仿真和低成本构建不打扰你。
  3. 查看证据边界并最终验收——技术完成时查看证据摘要与未运行等级；确认后给出接受回执。技术完成不等于已接受。

模块拆分与接口契约

一个意图拆成三个模块切片，各自独立收敛，再合成一条链路：

模块 负责 接口契约 独立证据
sd_host SD 卡初始化、命令/数据握手 对 frame_buffer_writer 输出带 valid/ready 的样本流，位宽与节拍由 ModuleSpec 固定 协议场景、超时与重试策略的仿真
frame_buffer_writer 把样本写入 DDR 帧缓冲，管理写端口背压 读端所有权交接、写地址生成、满/空语义 背压、边界地址与读回一致性的仿真
csi2_tx 从帧缓冲读出并按 CSI-2 TX 时序输出 行/场同步、lane 数、像素节拍 输出时序与协议场景的仿真

接口契约先于实现：每个模块的 ModuleSpec 写明端口、位宽、时钟域、复位语义和验收 Oracle；模块之间只通过契约握手，不靠“顶层连线时再说”。这就是模块可以独立生成、独立仿真、独立修复的原因。

芯片内 composition：三个模块各自通过契约与仿真后，Agent 在同一次 composition 中把它们和只读的 DDR wrapper、CSI-2 TX 硬核连到 TJ180A484S 的顶层，再做整链集成检查。composition 不是客户要背的第四步，而是 Agent 在“集成与实现”阶段完成的动作。

后台如何推进

后台五阶段只用于解释系统，不构成你必须记忆的 action 清单：

  1. Intent — 把你的自然语言目标落成受管意图，快照当前基线。
  2. Plan & Approve — 给出模块拆分、模块契约、仿真等级与验收场景，等你一次确认。
  3. Generate & Converge — 各模块并行生成候选、做 Design Assurance、独立仿真；失败只影响该模块。
  4. Integrate & Realize — 芯片内 composition、工程合同检查、原生编译与烧录。
  5. Accept — 汇总证据边界，等你给出接受或拒绝回执。

证据终态

BUILT（有构建产物）→ PACKAGED（已打包）→ PROGRAMMED（已写入设备）→ HARDWARE_VERIFIED（实板观察）→ SYSTEM_VERIFIED（系统级证据完整）→ READY_FOR_ACCEPTANCE（技术完成）→ ACCEPTED（客户接受回执）；未实际执行的级别保持 NOT_RUN。仿真 PASS 不等于编译通过，编译通过不等于烧录成功，烧录成功不等于板上验证。 没有硬件时，硬件与系统级证据保持 NOT_RUN。

失败恢复

仿真 FAIL 是证据，不是事故：候选被冻结后不可变，修复必须重新生成候选并重新仿真；基线不会因为一次失败被污染，其他模块的既有证据也不失效。若失败暴露的是契约歧义（例如“SD 初始化超时后重试几次”没有定义），Agent 会回到规格决策，而不是在 RTL 里私自加逻辑。

规格升级

规格升级只让受影响的证据失效。例如把 DDR 缓冲深度从 2 行改为 4 行：

  • frame_buffer_writer 的规格与仿真证据失效，需要重新生成、重新仿真；
  • sd_host 与 csi2_tx 的契约没有变化，它们的既有证据继续有效；
  • composition 的整链集成证据需要重跑一次，因为顶层连接与缓冲行为变了。

所以正确做法是只重跑受影响节点，而不是把整条教程从头再来；也不会因为一次规格升级把无关模块的 PASS 作废。

开始前

环境准备按顺序走一遍，全程约 10 分钟：

  1. 安装三个 VSIX（同版本 1.0.1）：evoverse-sdk、evoverse-efinity-adapter、evoverse-rk3588-adapter。在 Extensions 视图选 "Install from VSIX…" 逐个安装，步骤见 Trae 安装指南。
  2. 重启 IDE，让三个扩展全部激活。
  3. 首次引导：重启后弹窗 "Set up EvoVerse SDK?"，确认工作区位置（默认 ~/evoverse-sdk）。
  4. Welcome 页自动打开。点 Sync Catalog 同步板卡目录，等同步完成——后面的 ws-e1 / ws-e1-base 板卡选择就来自这份目录。
  5. 打开一个空目录作为工程根，在 Chat 里直接描述意图：Trae：输入 @evoverse 后描述目标；VS Code：在原生 Chat 的 Agent 模式直接描述同一目标，无需 @evoverse，先确认 EvoVerse MCP 为 Running。Workbench（Project Control 下拉，命令 evoverse.selectDesignFlow）是图形入口，但不会替 Agent 继续对话。

再确认两项：

  • Efinity 2026.1+ 可用；功能仿真需要 Icarus Verilog（或 QuestaSim）。
  • 有一块 WS-E1 核心模组（TJ180A484S）加底板更佳；没有硬件也能完成到编译为止的全部阶段，硬件验证阶段会如实标记为待执行。

你将得到什么

  • 一个受管工程：工程身份、冻结规格、候选与证据都在控制面状态里可追溯。
  • 一条从模块契约到硬件的证据链：每一步要么有 PASS 回执，要么明确标记 incomplete / fail——incomplete 永远不会被当作 PASS。
  • 最终 bitstream 由 Efinity 原生统一流程 efx_run --flow compile 产生；MIPI CSI-2 输出用真实接收端或片上调试核验证。

遇到问题怎么办

教程里的提示词刻意只说意图，不带控制面动作名和流程步骤——推进流程、选动作、核对回执是 Agent 的工作。以下章节的“你对 Trae 说什么”保留为 Trae 主线；在 VS Code 中把同一提示词直接发给原生 Agent，去掉开头的 @evoverse 即可。生成与仿真本身有随机性，遇到不顺利的情况按三条原则处理：

  1. 只说目标，不背流程。 描述你想要什么（“把 SD 卡数据写进 DDR”），而不是命令步骤。Agent 的做法若与教程描述的机制不一致，直接问它“你打算怎么推进”，听它解释后再决定。
  2. 等得久先问进度，别催也别重来。 生成、仿真、原生编译都是分钟级到几十分钟级的任务，中途叠加新指令只会打乱节奏。觉得太慢就问“现在到哪一步了、还差什么”，而不是重发一遍提示词。
  3. 结果不符合预期，先说期望再说问题。 把“我期望看到什么、实际看到了什么”讲清楚，让 Agent 回到对应的证据或规格重新走流程。

准备就绪后，从 阶段 00：环境与 Harness 自检 开始。
