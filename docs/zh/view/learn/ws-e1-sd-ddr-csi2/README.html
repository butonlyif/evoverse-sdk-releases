WS-E1 SD 到 CSI-2 总览

WS-E1 SD 到 CSI-2 工程教程

适用版本：v1.0.0　目标器件：TJ180A484S（Titanium Ti60，C4 timing model）　默认宿主：Trae

本教程带你从空目录开始，在 EvoVerse SDK 的可靠设计流程中重建一个完整工程：SD card -> DDR frame buffer -> MIPI CSI-2 TX。你用自然语言描述目标，由 Project Control Plane 决定每一步是否允许推进；每一段结论都有证据回执。

先讲清一条红线：不得把目标 sd-ddr-csi2 工程的 RTL、约束或工程文件复制为新工程的基线——目标工程只用于物料分析和结论比对。你要得到的是一个由你自己的规格、你自己的候选 RTL 和你自己的证据链支撑的工程，不是参考设计的副本。

开始前

环境准备按顺序走一遍，全程约 10 分钟：

  1. 安装三个 VSIX（同版本 1.0.0）：evoverse-sdk、evoverse-efinity-adapter、evoverse-rk3588-adapter。在 Extensions 视图选 "Install from VSIX…" 逐个安装，步骤见 Trae 安装指南。
  2. 重启 IDE，让三个扩展全部激活。
  3. 首次引导：重启后弹窗 "Set up EvoVerse SDK?"，确认工作区位置（默认 ~/evoverse-sdk）。
  4. Welcome 页自动打开。点 Sync Catalog 同步板卡目录，等同步完成——后面的 ws-e1 / ws-e1-base 板卡选择就来自这份目录。
  5. 开始对话：在 Trae 聊天框输入 @evoverse，用自然语言驱动 SDK；Workbench（Project Control 下拉，命令 evoverse.selectDesignFlow）是同一个控制面的图形入口。

再确认两项：

  • Efinity 2026.1+ 可用；功能仿真需要 Icarus Verilog（或 QuestaSim）。
  • 有一块 WS-E1 核心模组（TJ180A484S）加底板更佳；没有硬件也能完成到编译为止的全部阶段，硬件验证阶段会如实标记为待执行。

可靠设计流程：五步控制循环

v1.0.0 中，SDK 的所有可靠能力都由一个控制面（Project Control Plane）统一裁决。Agent、Workbench、CLI 都通过同一组接口推进：

  1. 读状态 — 调用 project_status，得到当前 revision、Baseline、活动 Intent、证据与候选。
  2. 读动作 — 调用 project_next，得到服务端允许的 ActionDescriptor 列表（含前置条件与阻塞原因）。
  3. 解释并选择 — 让 Agent 向你解释每个动作的 effect、preconditions、blockedReasons；不确定就先问。
  4. 执行 — 你确认后，用 project_execute 提交 {actionId, expectedRevision, inputs}。
  5. 处理决策并重读 revision — 遇到结构化决策（DecisionRequest）时由你选择；动作完成后重新 project_status，绝不复用旧 revision。

每一次状态推进都产生证据（规格摘要、候选摘要、仿真回执、构建回执、硬件回执）。证据绑定在工程状态里，对话口头伪造不了。

八个阶段

阶段 文档 控制面动作
00 建立工程 Harness project.initialize
01 物料分析 asset.observe
02 冻结规格 spec.draft → spec.approve（差量规格，机制讲解）
03 生成 RTL 并交付候选 三轮增量，每轮：intent.create → simulation.profile.select → spec.draft → candidate.deliver → verification.simulate → candidate.promote
04 Sapphire 固件 candidate.deliver（软件候选）
05 SDK 集成 合同检查与源同步
06 编译与硬件验证 build.native → hardware.program → hardware.validate
07 Skills 与 MCP 速查 工具与动作索引
08 整理工程并交付 证据归档与复编译

阶段之间有依赖：规格未批准时无法交付候选；候选未冻结时无法记录仿真证据；仿真未 PASS 时无法晋级；上一轮未晋级，下一轮增量就没有新父基线。构建证据与硬件证据相互独立，不互相替代。每一阶段结束后控制面会暂停，等你确认再继续。

三轮增量：每一轮都以晋级收尾

教程主线不是"一次生成全链路"，而是三轮增量迭代：

Stage0 基线 → SD 输入增量 → 晋级 → DDR 缓冲增量 → 晋级 → CSI-2 输出增量 → 晋级 → Efinity 原生编译 → 实板验证

每一轮增量走同一个循环：

  1. intent.create 声明意图时，控制面把当时的基线资产快照进 IntentRecord.baseBaselineFiles——这就是本轮的父基线。
  2. candidate.deliver 只冻结候选并执行 Design Assurance，基线保持不变。
  3. verification.simulate 对已冻结候选独立取证。
  4. 仿真 PASS 且晋级资格满足后，candidate.promote 把候选与父基线合并安装为新基线——它就是下一轮增量的父基线。

对应到教程阶段：

  S["Stage0 工程初始化"] --> M["物料分析"]
  M --> P["系统规格<br>等级先于规格"]
  P --> G["硬件生成<br>候选 仿真 晋级"]

提交动作时携带的 expectedRevision 只是并发提示值：控制面始终按最新 revision 追加事实，过期 revision 不会变成安全边界。

你将得到什么

  • 一个受管工程：工程身份、规格、候选、证据都在控制面状态里可追溯。
  • 一条从规格到硬件的证据链：每一步要么有 PASS 回执，要么明确标记 incomplete / fail——incomplete 永远不会被当作 PASS。
  • 最终 bitstream 由 Efinity 原生统一流程 efx_run --flow compile 产生；MIPI CSI-2 输出用真实接收端或片上调试核验证。

遇到问题怎么办

教程里的提示词刻意只说意图，不带控制面动作名和流程步骤——推进流程、选动作、核对回执是 Trae 的工作，你不需要背。生成与仿真本身有随机性，遇到不顺利的情况按三条原则处理：

  1. 只说目标，不背流程。 描述你想要什么（"把 SD 卡数据写进 DDR"），而不是命令步骤。Trae 的做法若与教程描述的机制不一致，直接问它"你打算怎么推进"，听它解释后再决定。
  2. 等得久先问进度，别催也别重来。 生成、仿真、原生编译都是分钟级到几十分钟级的任务，中途叠加新指令只会打乱节奏。觉得太慢就问"现在到哪一步了、还差什么"，而不是重发一遍提示词。
  3. 结果不符合预期，先说期望再说问题。 把"我期望看到什么、实际看到了什么"讲清楚，让 Trae 回到对应的证据或规格重新走流程。仿真 FAIL 不是事故，是证据——修复后重新交付、重新仿真即可，基线不会被污染。

准备就绪后，从 阶段 00：建立工程 Harness 开始。
