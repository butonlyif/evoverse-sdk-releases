FPGA + RK3588 系统意图教程（WS-E2 双芯片）

FPGA + RK3588 系统意图教程（WS-E2 双芯片）

适用 EvoVerse SDK v1.0.1 · 2026-11-28

适用版本：v1.0.1　目标器件：TJ180A484S（Titanium Ti60） + RK3588J　默认宿主：Trae

本教程只讲一个系统意图：在 WS-E2 上跑一个必须由 FPGA 与 RK3588 协同完成的应用——FPGA 负责实时采集与像素预处理，RK3588 负责 Linux 用户态应用与网络/存储。系统意图不是把两份单芯片教程粘在一起，而是先按功能分配芯片，冻结一份接口契约，再分别实现、最后做系统级 composition。

整条旅程仍然只有三个用户决策节点：确认方案与可执行规格（含芯片分配）、按需确认高成本或设备写入、查看证据边界并最终验收。

1. 一个系统意图，先谈功能再谈芯片

用一句自然语言把系统目标讲清楚，不要一上来就指定“哪些代码放 FPGA、哪些放 RK3588”：

我要在 WS-E2 上做一个双芯片视频通路：FPGA 采集相机原始数据并做去马赛克与缩放，RK3588 运行 Linux 应用接收处理后画面、叠加 UI 并通过网络推流。请先给出功能拆分和芯片分配建议，说明每个功能的职责、数据量、实时性要求和候选板间接口，等我确认后再动手。

Agent 需要返回的是功能清单，不是文件清单：采集、预处理、帧缓冲、显示/推流、控制面配置。功能粒度以“能否独立验证”为准，不以目录结构为准。

2. 芯片分配与接口契约（第一个决策节点）

按功能把职责分配到两颗芯片，并给出理由。典型分配如下，具体以你的目标与 Catalog 材料为准：

功能 芯片 职责 独立证据
相机采集与像素预处理 FPGA 实时流水线、确定性延迟、硬核 CSI-2 / DDR 接口 时序仿真 + 芯片内 composition
帧缓冲与显示/推流 RK3588 Linux 驱动、用户态应用、网络与存储 内核/用户态构建 + 启动检查
控制面配置 两侧 FPGA 寄存器映射、RK3588 设备树与驱动绑定 接口契约一致性检查
板间数据通道 两侧 按带宽/延迟/引脚约束选择 PCIe、MIPI、RGMII 或 GPIO 链路自检与错误计数

职责必须互斥：同一个功能不能两边都“顺便做一点”，否则系统级证据无法归因。

接口契约先于实现，至少冻结这些字段：

  • 方向与拓扑（谁发起、谁应答、点对点还是共享总线）；
  • 数据格式（位宽、字节序、对齐、打包方式）；
  • 带宽与时钟域（峰值/均值、跨域同步方式）；
  • 延迟与缓冲（最大允许延迟、队列深度、满/空语义）；
  • 错误处理（超时、重试、错误计数与上报路径）；
  • 版本与兼容（契约有 revision，任一侧改动都形成新 revision）。

芯片分配和接口契约一起构成方案决策。你在这一节点一次确认后，规格冻结；生成前不会因为“再选一次实现方式”反复打断你。

3. 两芯片并行实现

分配确认后，FPGA 侧与 RK3588 侧的实现可以并行推进：两侧各自有自己的工程、规格、构建链路与证据，互不阻塞。

  • FPGA 侧按 WS-E1 的模块切片方式收敛（复杂单芯片路径：ModuleSpec、接口契约、独立仿真、芯片内 composition）。
  • RK3588 侧按 WS-E2 的 atomic 路径收敛（一个意图、方案/规格确认、连续生成与四阶段构建）。

两侧的构建细节由各自的 Adapter 负责，执行命令与参数以 Adapter 参考为准，本文不复述厂商原生命令，避免与参考文档形成第二份真值。你只需要在每侧技术完成时查看证据摘要。

4. CHIP composition 与 SYSTEM composition

两个词不能混用：

  • CHIP composition：在一颗芯片内，把多个子模块或子意图合成一个可交付结果。例如 FPGA 侧把采集、预处理、DDR 写回合成一条完整流水线。
  • SYSTEM composition：跨两颗芯片，把各自的 CHIP 结果、接口契约与系统级连接合成为系统证据。

系统 composition 检查的是“拼起来还对不对”：接口契约 revision 是否两侧一致、带宽与延迟是否满足、控制面寄存器与设备树是否对齐、错误上报链路是否闭环。它不会替任何一侧修复实现，也不会把两侧各自的 PASS 自动升格为系统 PASS。

5. 证据终态

BUILT（有产物）→ PACKAGED（已打包）→ PROGRAMMED（已写入设备）→ HARDWARE_VERIFIED（实板观察）→ SYSTEM_VERIFIED（系统级证据完整）→ READY_FOR_ACCEPTANCE（技术完成）→ ACCEPTED（客户接受回执）；未实际执行的级别保持 NOT_RUN。

  • 两侧都 BUILD_READY 不等于系统可运行，更不等于 SYSTEM_VERIFIED；
  • READY_FOR_ACCEPTANCE 只表示技术完成，不等于 ACCEPTED；
  • 技术完成时你可以查看证据摘要后给出接受回执，也可以拒绝并把问题退回规格。

6. 部分失败：一侧就绪，系统仍未就绪

系统旅程最常见的状态是部分失败：FPGA 侧已经 BUILD_READY，RK3588 侧仍在构建；或一侧 PROGRAMMED 而另一侧尚未上电；或两侧都能跑但板间链路错误计数持续增长。

此时正确报告是：系统仍未就绪，已完成的芯片证据保留但其边界不外推。不允许用“FPGA 编译过了”替代系统级结论，也不允许把一侧的 PASS 写成 SYSTEM_VERIFIED。

系统验收提示词：

验收当前双芯片系统意图。分别读取两侧的 CHIP 证据与系统 composition 记录，列出各自的证据终态、接口契约 revision、未运行等级与阻塞原因。如果只有一侧完成，明确写出系统仍未就绪以及还差哪一项，不要给出 SYSTEM_VERIFIED。

7. 失败恢复与规格升级

失败恢复只动失败的那一侧：

诊断当前系统失败。只分析本次系统 composition 与失败侧对应的证据，判断问题属于 FPGA 实现、RK3588 实现、接口契约歧义还是硬件未验证四类之一。先给根因与最小修复方案，等我确认后再改；不要创建绕过厂商原生链路的脚本或 wrapper（workaround）。

规格升级只让受影响的证据失效。例如把板间通道从 RGMII 改为 PCIe：

  • 接口契约 revision 变化，两侧与链路相关的证据失效；
  • 未使用该通道的 FPGA 像素流水线证据继续有效；
  • 系统 composition 需要重跑，因为连接与带宽假设变了。

反过来，只改 RK3588 侧用户态应用逻辑时，FPGA 侧证据不应失效。正确做法是只重跑受影响节点，而不是把整个系统旅程从头再来。

8. 当前能力边界

  • 已实现：三个决策节点、CHIP composition、SYSTEM composition、以及“生成 ≠ 编译 ≠ 打包 ≠ 烧录 ≠ 硬件验证 ≠ 系统验证 ≠ 接受”的证据分层。
  • 计划中（planned）：一次系统意图下的全自动双芯片并行调度编排。若你的版本尚未暴露系统级入口，就按芯片级分别推进，两侧都技术完成后再触发系统 composition。
  • 保持 NOT_RUN：实板 PCIe/MIPI/RGMII 链路验证、跨芯片时序联调、长时间稳定性与系统级硬件证据。没有实板时这些一律写 NOT_RUN，不得用文档、包结构或单侧 PASS 替代。

9. 完成检查表

  • [ ] 用一句话描述了一个系统意图，而不是先指定代码归属
  • [ ] 功能拆分清单可独立验证，没有为形式完整而过度拆分
  • [ ] 芯片分配与职责互斥，且经用户确认
  • [ ] 接口契约冻结：方向、格式、带宽/时钟、延迟/缓冲、错误处理、revision
  • [ ] 两芯片实现已并行推进，未互相阻塞
  • [ ] FPGA 侧完成 CHIP composition，RK3588 侧完成自身构建证据
  • [ ] 系统 composition 跑过并留有记录
  • [ ] 部分失败时如实报告系统仍未就绪
  • [ ] 技术完成（READY_FOR_ACCEPTANCE）与 ACCEPTED 已区分
  • [ ] 未实际执行的硬件与系统级证据保持 NOT_RUN
