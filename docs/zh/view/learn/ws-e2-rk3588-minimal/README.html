WS-E2 RK3588J 最小系统自然语言教程

WS-E2 RK3588J 最小系统自然语言教程

适用 EvoVerse SDK v1.0.1 · 2026-11-28

本教程是一条 atomic（原子）旅程：用 一个意图 从安装 EvoVerse 走到包含 U-Boot、Linux kernel、设备树、最小 rootfs 和固件包的 WS-E2 RK3588J 工程。除了安装 VSIX、Docker Desktop 等工具，其余操作全部用自然语言生成和执行。

原子意图默认 不强制拆分。WS-E2 最小系统本身就是一个可交付单元，不需要为了流程完整而拆成子意图、子模块或多次“小步确认”；拆分只在意图确实复杂到无法一次收敛时才发生。

整条旅程只有三个用户决策节点：

  1. 确认方案与可执行规格；
  2. 按需确认许可、材料部署、高成本动作或设备写入；
  3. 查看证据边界并最终验收。

背景五阶段（Intent → Plan & Approve → Generate & Converge → Integrate & Realize → Accept）用于解释系统，不需要用户记忆逐条 action 清单。

本教程完成软件构建闭环。烧录、启动、DDR/eMMC 压力测试以及 FPGA↔RK3588 实板接口验证保持 硬件验证：NOT_RUN。BUILD_READY 不等于硬件验证。

每节都给出一条可以直接复制的“自然语言提示词”。需要许可、材料选择或风险确认时，Agent 必须停下来等你明确同意。

0. 安装三个 VSIX 并准备 Docker

这是全教程唯一需要手工操作的部分：

  1. Windows 10/11 x64，目标磁盘至少 9 GiB 可用空间；
  2. Trae CN 或兼容的 VS Code 宿主；
  3. 在 Extensions 视图选择“Install from VSIX…”，依次安装 evoverse-sdk-1.0.1.vsix、evoverse-efinity-adapter-1.0.1.vsix、evoverse-rk3588-adapter-1.0.1.vsix；
  4. 重启 IDE；
  5. 安装并启动 Docker Desktop，确认运行 Linux containers；
  6. 准备 EvoVerse 提供的两个 .evopkg 离线包，不要解压、改名或重新压缩。

自然语言提示词 1：安装与准备自检

检查当前 EvoVerse SDK、Efinity Adapter 和 RK3588 Adapter 是否正确安装并激活，同时检查 Docker CLI、Docker daemon 和 Linux container 模式；再同步 EvoVerse Catalog（默认公开仓库，无需 GitHub 账号），确认 ws-e2 板卡、rk3588j-evm 载板和 RK3588 最小系统材料可用。只做只读检查，不要修改工程。如果缺少工具，请准确告诉我需要手工安装什么。

回答中应出现 ws-e2、rk3588j-evm、BSP b8f5dda5、工具链 2026.09 和两个离线包文件名。工具安装必须由你完成；不要让 Agent 下载来源不明的安装程序。板卡与 Demo 清单以 Catalog 声明为准，本节写出的 BSP 号与工具链版本是写作时的快照，若同步结果不同，以 Catalog 为准。

1. 环境与材料（按需出现的第二个决策节点）

这一节属于第二个决策节点：只有在你需要部署离线材料、接受许可或支付高成本动作时才出现。环境已经 READY 或使用在线材料时，可以直接跳到第 2 节。

自然语言提示词 2：检查 RK3588 开发环境

检查 RK3588 开发环境。使用 Adapter 的环境体检能力检查 Docker、磁盘空间、WS-E2 BSP、工具链离线包、安装回执和已安装文件身份。解释 PACKAGE_REQUIRED、REPAIRABLE、USER_ACTION_REQUIRED 或 READY，并只给出当前合法的下一步。

对应 MCP 能力：rk3588_environment_status（只读，不产生安装收据或 staging 目录）。首次通常得到 PACKAGE_REQUIRED，表示需要离线材料。

许可与高成本确认（按需，不是所有用户都必经）

把两个原始 evopkg 文件复制到固定目录 <EVOVERSE_HOME>\downloads\rk3588\（EVOVERSE_HOME 默认为 %USERPROFILE%\evoverse-sdk），然后：

重新检查两个 RK3588 离线包，核对 Catalog 声明、字节数、外层 SHA-256、内部 manifest 和逐文件 checksum。通过后展示许可确认内容和预计磁盘占用，等我明确确认后再部署。结束后重新运行完整健康检查，只有最终状态为 READY 才能报告成功。

对应 MCP 能力：先用 rk3588_environment_prepare 获取一次性 inspectionToken，再以 acceptedLicenses: true 调用 rk3588_environment_deploy。token 只对检查时刻的字节有效；包内容变化后必须重新检查，重放旧 token 会被拒绝。

阅读许可后由你明确回复：“我接受离线包中的许可条款并确认部署。”部署取消或失败时，本次新增目录、回执和镜像应回滚，部署前已有镜像不删除。导入 Docker 镜像、重建 BSP Git 树和逐文件校验加起来可能要十几分钟，期间让 Agent 保持等待，不要叠加新指令；它会在结束后重新跑完整健康检查，只有 READY 才算成功。

2. 一个意图：WS-E2 RK3588J 最小系统

打开一个空目录作为项目目录，然后用一句话描述目标。工程身份来自当前 Catalog、BSP qualification 和生成链路，不需要你手工拼接 Profile。

自然语言提示词 3：创建 WS-E2 RK3588J 最小系统

在当前空目录创建一个名为 ws-e2-rk3588j-minimal 的 EvoVerse 工程。板卡选择 ws-e2，载板选择 rk3588j-evm，开发目标选择 rk3588。基于当前 Catalog 和已经 READY 的离线环境生成最小 Linux 系统，推荐 eMMC 启动、UART2 日志和 Buildroot minimal rootfs。不要手工拼接 Profile，不要猜测 loader、分区、DDR 或 DTS；身份必须来自当前 Catalog、BSP qualification 和生成链路。生成前展示推荐与替代选择，等我确认。

Agent 应说明：核心板已包含 PMIC、LPDDR4X、eMMC 和基准时钟；这仍不是实板验证结论。

对应 MCP 能力：rk3588_project_generate（目标只允许 ws-e2 / rk3588j-evm / minimal-linux 组合，工程目录必须是绝对路径；成功后工程为 PROFILE_READY，不代表可构建）。原子单意图不产生集成记录，生命周期直接复用 COMPLETED。

3. 方案与可执行规格确认（第一个决策节点）

生成前把方案固定成可执行规格：BSP 与工具链身份、启动介质、串口、rootfs、loader、分区表和 DTS 来源。规格是升级门禁——以后任何需求变化都必须先改规格再重跑，不能绕过硬编码。

自然语言提示词 4：确认方案与规格

我确认采用推荐方案：固定当前 BSP 与工具链身份，eMMC 启动，UART2 日志，Buildroot minimal rootfs。请完成受控生成，但不要构建。检查生成 manifest 的文件所有权，并确认再生成不会覆盖 applications 下的客户内容。

预期生成 Profile、DTS/DTSI、generation manifest、客户应用目录和输出目录骨架。此时正确状态是 PROFILE_READY，不能冒充 BUILD_READY。

4. 连续生成、预检与构建

确认规格后不需要逐条发提示词。让 Agent 连续执行 preflight 与四阶段构建，过程细节由 Adapter 原生链路负责，你只需要观察结果。

自然语言提示词 5：连续执行 preflight 与四阶段构建

对当前 RK3588 工程连续执行：先跑 preflight，重新资格化 BSP，检查 root commit、四个 submodule、loader、分区表、容器 digest、工具链、DTS manifest、输出目录和四阶段能力；再使用 RK3588 Adapter 依次构建 U-Boot、kernel/DTB、rootfs、package。每阶段报告退出码、当次必要产物、SHA-256 和诊断；任何阶段失败都停止，不要使用旧产物冒充成功。preflight 发现阻塞时给出稳定错误码、证据和最小修复建议，不要自动修改 BSP 源码。结束后重新计算 Build Identity 和 readiness。

对应 MCP 能力：rk3588_project_preflight（只读资格化检查，timeout 300 秒）与 rk3588_project_build（headless 构建只接受完整四阶段顺序 uboot → kernel → rootfs → package，不接受部分阶段）。

常见 preflight 阻塞：

  • BSP_BINDING_REQUIRED：用当前已部署材料重新绑定；
  • BSP_SOURCE_DIRTY：备份并恢复声明版本，不能绕过；
  • BSP_QUALIFICATION_STALE：重新核对当前身份，不能继承旧 PASS。
阶段 预期产物
U-Boot uboot.img
Kernel Image、rk3588j-evoverse.dtb
Rootfs rootfs.ext2
Package ws-e2-rk3588j-minimal-firmware.tar.gz

每阶段的命令、退出码和 SHA-256 证据统一归属于工程目录下 .evoverse/output/build-report.json，最终状态以该文件为权威，聊天回复只是它的摘要。四阶段是长任务，机器性能一般时半小时以上很常见；期间让 Agent 保持等待，不要叠加新任务。

5. 证据复核与验收（第三个决策节点）

自然语言提示词 6：验收证据

验收当前 WS-E2 RK3588J 最小系统。读取 build-report、build-manifest、四阶段 receipts 和固件包，不要只看文件是否存在。用表格列出阶段状态、产物摘要和 Build Identity，判断是否为 BUILD_READY，并单独列出所有 NOT_RUN 项。

对应 MCP 能力：rk3588_project_status（读取 .evoverse/output/build-report.json 与 readiness 汇总，只读，不重跑构建、不刷新证据）。

验收要求：四阶段属于当前 Build Identity、error diagnostics 为 0、固件包含 U-Boot/Image/DTB/rootfs、工程状态为 BUILD_READY；同时明确 硬件验证：NOT_RUN。烧录、启动和实板接口都属于 HARDWARE_VERIFIED 范畴，不能由 BUILD_READY 冒充。

6. 失败恢复与规格升级

失败恢复始终留在原生链路：先读本次 runId 的日志、receipt、diagnostics 和 Profile，区分环境、材料绑定、BSP qualification、原生工具错误和硬件未验证五类问题；不要创建绕过原生工具链的脚本、wrapper 或环境变量 hack（workaround）。

诊断当前 RK3588 操作失败。只分析本次 runId 对应的证据，不继承旧 PASS。先给根因与最小修复方案，等我确认后再修改。

规格升级是另一个受控动作：例如把启动介质从 eMMC 改为 SD，或把 rootfs 从 Buildroot minimal 改为更大集合。先更新方案与可执行规格，再重新生成并重跑 preflight 与四阶段构建；只有受影响节点的证据失效，未受影响的历史产物可以保留但不能被当成新证据。

7. 下一步选择

准备烧录，但暂不执行

基于当前 WS-E2 Profile 和固件证据给出烧录前检查清单，只说明 loader、分区、设备识别、备份和回滚要求，不执行烧录，保持硬件状态 NOT_RUN。

加入 FPGA 协同

在不修改现有 RK3588 BUILD_READY 基线的前提下，规划 WS-E2 FPGA + RK3588 系统旅程：按功能分配芯片、冻结接口契约、两芯片可并行实现，最后做芯片级与系统级 composition。不要把板间连接器作为独立真值，不执行硬件验证。

开始板端应用

基于当前最小 rootfs 规划第一个 AArch64 用户态应用。应用代码放在客户目录，说明交叉编译、打包和运行时依赖，不修改受管理的 BSP 或生成文件。
