WS-E2 RK3588J 最小系统自然语言教程

本教程从安装 EvoVerse 开始，最终得到包含 U-Boot、Linux kernel、设备树、最小 rootfs 和固件包的 WS-E2 RK3588J 工程。除了安装 VSIX、Docker Desktop 等工具，其余操作全部用自然语言生成和执行。

本教程完成软件构建闭环。烧录、启动、DDR/eMMC 压力测试以及 FPGA↔RK3588 实板接口验证保持 硬件验证：NOT_RUN。

flowchart LR
  A[安装三个 VSIX + Docker] --> B[Catalog + 环境 READY]
  B --> C[自然语言创建工程]
  C --> D[PROFILE_READY]
  D --> E[Preflight]
  E --> F[四阶段构建]
  F --> G[BUILD_READY]
  G --> H[固件 + 回执 + 日志]
  H --> I[硬件验证：NOT_RUN]

每节都提供可以直接复制的“自然语言提示词”。涉及许可、材料选择或风险边界时，Agent 必须等待用户确认。

0. 准备清单

  • Windows 10/11 x64，目标磁盘至少 9 GiB 可用空间；
  • Trae CN 或兼容的 VS Code 宿主；
  • Docker Desktop，运行 Linux containers；
  • 三个 EvoVerse VSIX；
  • EvoVerse 提供的两个 .evopkg 离线包。

不要解压、改名或重新压缩 .evopkg。

1. 安装三个 VSIX

这是需要手工操作的工具安装步骤：

  1. 在 Extensions 视图选择“Install from VSIX…”；
  2. 安装 evoverse-sdk-1.0.0.vsix；
  3. 安装 evoverse-efinity-adapter-1.0.0.vsix；
  4. 安装 evoverse-rk3588-adapter-1.0.0.vsix；
  5. 重启 IDE；
  6. 安装并启动 Docker Desktop，确认使用 Linux containers。

自然语言提示词 1：检查安装

检查当前 EvoVerse SDK、Efinity Adapter 和 RK3588 Adapter 是否正确安装并激活，同时检查 Docker CLI、Docker daemon 和 Linux container 模式。只做只读检查，不要修改工程。如果缺少工具，请准确告诉我需要手工安装什么。

工具安装必须由用户完成；不要让 Agent 下载来源不明的安装程序。

2. 同步 Catalog 并确认 WS-E2

自然语言提示词 2：同步板卡材料

请同步 EvoVerse Catalog（默认公开仓库，无需 GitHub 账号），然后检查 ws-e2 板卡、rk3588j-evm 载板和 RK3588 最小系统材料是否可用。报告 Catalog 版本、开发目标、离线包声明和证据边界，不要创建工程。

回答中应出现 ws-e2、rk3588j-evm、BSP b8f5dda5、工具链 2026.09 和两个离线包文件名。如果 Catalog 不可用，先修复同步，不能凭记忆伪造材料。

具体板卡、载板与 Demo 清单以 Catalog 声明为准：本节写出的 BSP 号与工具链版本是写作时的快照，Catalog 更新后可能变化。若同步结果与本节不一致，以 Catalog 为准，让 Agent 如实报告差异，不要按教程旧值硬套。

3. 检查 RK3588 开发环境

自然语言提示词 3：环境体检

检查 RK3588 开发环境。使用 Adapter 的环境体检能力检查 Docker、磁盘空间、WS-E2 BSP、工具链离线包、安装回执和已安装文件身份。解释 PACKAGE_REQUIRED、REPAIRABLE、USER_ACTION_REQUIRED 或 READY，并只给出当前合法的下一步。

对应 MCP 能力：rk3588_environment_status（只读，不产生安装收据或 staging 目录）。

首次通常得到 PACKAGE_REQUIRED，表示需要离线材料。

4. 获取和部署双离线包

向 EvoVerse 获取：

  • rk3588-toolchain-2026.09.evopkg
  • ws-e2-rk3588-bsp-b8f5dda5.evopkg

两个离线包存放在固定目录 <EVOVERSE_HOME>\downloads\rk3588\（EVOVERSE_HOME 默认为 %USERPROFILE%\evoverse-sdk）。提示词 4 让 Agent 打开的正是这个目录：把两个原始 evopkg 文件复制进去，再执行提示词 5。

自然语言提示词 4：打开收件箱

请打开 RK3588 离线包固定目录，不要开始部署。我会把 EvoVerse 提供的两个原始 evopkg 文件复制进去。打开后告诉我完整路径。

复制完两个文件后：

自然语言提示词 5：检查并部署

重新检查两个 RK3588 离线包，核对 Catalog 声明、字节数、外层 SHA-256、内部 manifest 和逐文件 checksum。通过后展示许可确认内容和预计磁盘占用，等我明确确认后再一键部署。结束后必须重新运行完整健康检查，只有最终状态为 READY 才能报告成功。

对应 MCP 能力：先用 rk3588_environment_prepare 获取一次性 inspectionToken，再以 acceptedLicenses: true 调用 rk3588_environment_deploy。token 只对检查时刻的字节有效，包内容变化后必须重新检查；重放旧 token 会被拒绝。

阅读许可后明确回复：“我接受离线包中的许可条款并确认部署。”部署取消或失败时，本次新增目录、回执和镜像应回滚，部署前已有镜像不删除。

5. 确认环境 READY

自然语言提示词 6：解释环境证据

再次检查 RK3588 开发环境，逐项解释 READY 的证据：Catalog 包身份、内部 manifest、安装回执、逐文件与额外文件检查、BSP qualification、Docker image digest 和最低 Adapter 版本。最后明确说明哪些事情仍未验证。

此时正确边界是环境 READY，但当前工程尚未达到 BUILD_READY，烧录和硬件验证仍是 NOT_RUN。

6. 创建 WS-E2 RK3588J 最小系统

打开一个空目录作为项目目录。

自然语言提示词 7：创建工程

在当前空目录创建名为 ws-e2-rk3588j-minimal 的 EvoVerse 工程。板卡选择 ws-e2，载板选择 rk3588j-evm，开发目标选择 rk3588。基于当前 Catalog 和已经 READY 的离线环境生成最小 Linux 系统，推荐 eMMC 启动、UART2 日志和 Buildroot minimal rootfs。不要手工拼接 Profile，不要猜测 loader、分区、DDR 或 DTS；身份必须来自当前 Catalog、BSP qualification 和生成链路。生成前展示推荐与替代选择，等我确认。

Agent 应说明：核心板已包含 PMIC、LPDDR4X、eMMC 和基准时钟；这仍不是实板验证结论。

自然语言提示词 8：确认推荐

我确认采用推荐方案：固定当前 BSP 与工具链身份，eMMC 启动，UART2 日志，Buildroot minimal rootfs。请完成受控生成，但不要构建。检查生成 manifest 的文件所有权，并确认再生成不会覆盖 applications 下的客户内容。

预期生成 Profile、DTS/DTSI、generation manifest、客户应用目录和输出目录骨架。此时可以是 PROFILE_READY，但不能冒充 BUILD_READY。

对应 MCP 能力：rk3588_project_generate（目标只允许 ws-e2 / rk3588j-evm / minimal-linux 组合，工程目录必须是绝对路径；成功后工程为 PROFILE_READY，不代表可构建）。

7. 运行工程 Preflight

自然语言提示词 9：预检

对当前 RK3588 工程运行 preflight。重新资格化 BSP，检查 root commit、四个 submodule、loader、分区表、容器 digest、工具链、DTS manifest、输出目录和四阶段能力。不要自动修改 BSP 源码；如有阻塞，给出稳定错误码、证据和最小修复建议。

  • BSP_BINDING_REQUIRED：用当前已部署材料重新绑定；
  • BSP_SOURCE_DIRTY：备份并恢复声明版本，不能绕过；
  • BSP_QUALIFICATION_STALE：重新核对当前身份，不能继承旧 PASS。

对应 MCP 能力：rk3588_project_preflight（只读资格化检查，timeout 300 秒；任何修复动作都必须经用户确认后单独执行，不随 preflight 自动发生）。

8. 自然语言完成四阶段构建

自然语言提示词 10：构建

使用 RK3588 Adapter 构建当前工程，依次执行 U-Boot、kernel/DTB、rootfs、package。每阶段报告退出码、当次必要产物、SHA-256 和诊断；任何阶段失败都停止，不要使用旧产物冒充成功。结束后重新计算 Build Identity 和 readiness。

阶段 预期产物
U-Boot uboot.img
Kernel Image、rk3588j-evoverse.dtb
Rootfs rootfs.ext2
Package ws-e2-rk3588j-minimal-firmware.tar.gz

对应 MCP 能力：rk3588_project_build（headless 构建只接受完整的四阶段顺序 uboot → kernel → rootfs → package，不接受部分阶段）。每阶段的命令、退出码和 SHA-256 证据统一归属于工程目录下 .evoverse/output/build-report.json，最终状态以该文件为权威，聊天回复只是它的摘要。

9. 验收最小系统

自然语言提示词 11：验收证据

验收当前 WS-E2 RK3588J 最小系统。读取 build-report、build-manifest、四阶段 receipts 和固件包，不要只看文件是否存在。用表格列出阶段状态、产物摘要和 Build Identity，判断是否为 BUILD_READY，并单独列出所有 NOT_RUN 项。

验收要求：四阶段属于当前 Build Identity、error diagnostics 为 0、固件包含 U-Boot/Image/DTB/rootfs、工程状态为 BUILD_READY，同时明确 硬件验证：NOT_RUN。

对应 MCP 能力：rk3588_project_status（读取 .evoverse/output/build-report.json 与 readiness 汇总，只读，不重跑构建、不刷新证据）。

10. 下一步选择

准备烧录，但暂不执行

基于当前 WS-E2 Profile 和固件证据给出烧录前检查清单，只说明 loader、分区、设备识别、备份和回滚要求，不执行烧录，保持硬件状态 NOT_RUN。

加入 FPGA 协同

在不修改现有 RK3588 BUILD_READY 基线的前提下规划 WS-E2 FPGA + RK3588 system 工程。读取最终器件映射和接口契约，推荐 PCIe、MIPI、RGMII 或 GPIO；不要把板间连接器作为独立真值，不执行硬件验证。

开始板端应用

基于当前最小 rootfs 规划第一个 AArch64 用户态应用。应用代码放在客户目录，说明交叉编译、打包和运行时依赖，不修改受管理的 BSP 或生成文件。

11. 故障诊断提示词

诊断当前 RK3588 操作失败。读取本次 runId 对应的日志、receipt、diagnostics 和 Profile，只分析本次证据。区分环境、材料绑定、BSP qualification、原生工具错误和硬件未验证五类问题。不要继承旧 PASS，不要创建绕过原生工具链的脚本；先给根因与最小修复方案，等我确认后再修改。
