EvoVerse 与 RK3588：从自然语言意图到板端应用

EvoVerse 与 RK3588：从自然语言意图到板端应用

适用 EvoVerse SDK v1.0.1 · 2026-11-26

适用基线：EvoVerse SDK / RK3588 Adapter v1.0.1 当前验证基线：WS-E2 / RK3588J / rk3588j-evm / minimal-linux
文档性质：知识总结，不是已冻结的产品设计或实施排期
更新日期：2026-10-31

这份文档回答五个问题：

  1. EvoVerse 整体是什么，Core、Adapter、Catalog、工具链和目标板怎样配合？
  2. 用户说出一个应用意图后，系统怎样把它变成工程、模型、应用和板端证据？
  3. 当前仓库已经实现到哪一步，哪些能力还只是目标状态？
  4. SDK 之外还需要准备什么环境，在 Windows、macOS 和 Linux 上分别怎样部署？
  5. 要把它完善成可扩展到更多 CPU、GPU、NPU、XPU 的平台，还需要补什么？

1. 一页读懂：它是什么、现在在哪里

1.1 EvoVerse 不是另一套芯片工具链

EvoVerse 位于自然语言和原生开发工具之间。它不替代 Rockchip BSP、Buildroot、Linux、RKNN 或烧录工具，而是把这些能力组织成可理解、可确认、可执行、可追踪的工程流程。

用户意图
   ↓
EvoVerse Core：理解目标、管理状态、确认、证据和下一步
   ↓
具体 Adapter：把通用动作翻译成厂商/器件动作
   ↓
Catalog + 原生工具链：提供受控事实并真正生成二进制
   ↓
目标设备：部署、启动、运行和验证

最重要的边界是：

Core 管理“怎样安全地完成一项工程任务”；Adapter 管理“某个厂商和器件具体怎样完成”。

Core 不保存 CPU、GPU、NPU、XPU 固定枚举。它只理解开放的 capability、产物关系、执行状态、风险、确认和证据。Rockchip、RK3588、RKNN、DTS、Buildroot、Maskrom 等概念属于 RK3588 Adapter 及其 Catalog。

1.2 当前已经能做到什么

截至本文基线，当前系统已经能够：

  • 安装 EvoVerse Core、Efinity Adapter 和 RK3588 Adapter；
  • 发现并调用 RK3588 Adapter 的结构化 headless 能力；
  • 同步受版本控制的 Catalog；
  • 检查并部署 RK3588 双离线环境包；
  • 从 WS-E2 / RK3588J / minimal-linux 基线生成平台工程；
  • 基于真实 BSP symbol 生成受管 DTS/DTSI 候选；
  • 完成 preflight；
  • 在固定 Linux 容器中执行 U-Boot、Kernel、Rootfs、Package 四阶段构建；
  • 生成 Build Identity、产物摘要、报告和 BUILD_READY 证据。

1.3 当前还不能声称什么

当前系统还不能声称已经实现：

  • 从任意自然语言意图自动生成完整 RK3588 应用；
  • 自动完成 ONNX→RKNN、精度对照、应用集成和板端 benchmark；
  • 由 Adapter 原生完成设备发现、固件 Flash、回读与回滚；
  • 自动完成 UART、ADB、SSH 或启动失败诊断；
  • 在 macOS/Windows 前端与远程 Linux builder 之间形成完整受控执行面；
  • 以统一控制面支持任意 CPU/GPU/NPU/XPU 厂商流程。

因此，当前真实能力可以概括为：

已经具备“自然语言驱动的 RK3588 平台工程生成与可复现构建底座”，尚未形成“从意图到经过实机验证的 NPU 应用”的完整闭环。

2.1 SDK 内部负责什么

层次 核心职责 不应该承担的职责
自然语言交互 理解目标、发现缺失信息、解释结果 猜工具版本、BSP label 或分区表
EvoVerse Core Intent、规格、计划、状态、确认、路由、产物身份和证据 理解 RKNN、DTS、CUDA 等厂商私有字段
Adapter 厂商能力翻译、安全门禁、原生工具调用、结果归一化 自行推进 Core 生命周期或伪造成功状态
Catalog 板卡、基线、版本、策略、已验证组合 执行构建或替代原生工具
Workbench/MCP/CLI 给人和 Agent 提供统一入口 各自复制一套业务实现

2.2 SDK 外部负责什么

外部组成 作用 为什么不能简单打进 VSIX
Docker/远程 Linux 提供一致的 Linux 执行环境 体积、平台架构、运行权限不同
Rockchip BSP U-Boot、Kernel、rkbin、Buildroot、分区与固件材料 体积大、版本绑定、许可与源码身份复杂
交叉工具链 生成 AArch64 目标程序和系统组件 需要与 BSP、libc、sysroot 配套
RKNN 工具链 模型检查、转换、量化和报告 Python/native 依赖与版本矩阵复杂
设备连接工具 Flash、串口、ADB、SSH、回读 依赖主机驱动、USB 权限和物理设备状态
目标板 runtime 驱动、RKNPU runtime、应用服务 必须与固件和模型版本匹配

SDK 安装完成，只代表“控制软件可用”；并不代表 BSP、工具链、模型环境和目标板都已准备好。

3. Core 如何兼容未来的 CPU、GPU、NPU、XPU

3.1 Core 只保存跨平台仍然成立的概念

Core 概念 作用
Intent / Specification / Revision 描述目标、确认理解、防止旧请求覆盖新请求
Adapter identity / API range 发现并路由到能力提供者
Capability Plan / Dependency 表达动作及其依赖，不规定厂商步骤
Artifact / Manifest / Digest / Lineage 管理产物身份、来源、缓存和组合关系
Execution / Progress / Cancellation 管理长任务生命周期
Risk / Permission / Confirmation 控制文件修改、部署和设备写入
Evidence / Metric / Blocker / Remediation 保存事实，支持完成、纠错和回滚
Device identity / Deployment receipt 记录部署目标、内容和恢复点

capability id 和 artifact role 必须是开放标识符，而不是 Core 维护的封闭枚举。Core 可以校验命名、版本、依赖、摘要和状态，但不应规定所有 Adapter 只能使用一份 CPU/GPU/NPU 功能清单。

3.2 厂商和器件语义必须留在 Adapter

Adapter 私有内容 RK3588 示例
厂商与器件 Rockchip、RK3588J、具体板卡与载板
工具链与 runtime RKNN-Toolkit2、RKNPU2、BSP、Buildroot
工程私有字段 DTS label、defconfig、kernel fragment、loader
私有产物 .rknn、固件镜像、厂商报告
设备协议 Maskrom、Loader、分区烧录、回读
性能解释 NPU 利用率、厂商 profiler、转换精度报告
兼容矩阵 driver/runtime/toolkit/firmware 配套关系

一个实用判断方法是：

如果明天接入一种从未出现过的计算单元，这个字段是否仍有相同含义和控制作用？

如果答案是“是”，例如 digest、dependency、risk、receipt，它可以属于 Core；如果答案依赖某个厂商、器件、runtime 或文件格式，它就应属于 Adapter。

3.3 多 Adapter 的长期结构

flowchart LR
    C[EvoVerse Core<br/>开放能力 + 通用治理]
    C --> R[Rockchip Adapter<br/>RK3588 / RKNN / BSP]
    C --> G[GPU Adapter<br/>厂商 SDK / Runtime]
    C --> Q[NPU Adapter<br/>厂商模型与设备工具]
    C --> L[CPU/Linux Adapter<br/>Compiler / OS / Package]
    C --> F[未来 XPU / DSP / FPGA Adapter]

这些 Adapter 可以声明完全不同的计划。Core 不根据“它是 GPU 还是 NPU”选择流程，而根据 Adapter 返回的能力、依赖、风险和证据决定合法下一步。

4. 从一句自然语言到板端应用，完整流程是什么

用户可能只说：

在 WS-E2 上做一个摄像头目标检测应用，使用 RK3588 NPU，启动后自动运行，并给出 FPS 和延迟。

系统内部不能直接把这句话变成一组 shell 命令。完整闭环应分为十个阶段。

4.1 意图与应用规格

自然语言首先生成的是可确认的应用规格，而不是代码。规格至少应描述：

  • 目标设备与系统基线；
  • 输入源、格式、尺寸和帧率；
  • 模型任务、来源、许可与精度目标；
  • 预处理、后处理和业务逻辑；
  • 输出方式，例如屏幕、文件、网络或 GPIO；
  • 运行方式，例如 systemd 服务、容器或命令行；
  • 性能、资源和功能验收条件；
  • 部署模式与可接受风险。

用户确认规格后，后续计划和候选都应绑定同一个 specDigest。

4.2 Adapter 计划

RK3588 Adapter 根据规格和当前环境给出依赖图，而不是一串写死的全局步骤：

flowchart TD
    S[Approved Application Spec] --> P[Adapter Plan]
    P --> PF[平台工程生成/预检]
    P --> MI[模型检查]
    P --> AG[应用源码生成]
    PF --> PB[平台或固件构建]
    MI --> MC[ONNX → RKNN]
    MC --> MV[模型语义/精度验证]
    AG --> AB[AArch64 应用构建]
    PB --> PKG[Application Package]
    MV --> PKG
    AB --> PKG
    PKG --> DP[部署计划与确认]
    DP --> DEV[目标设备]
    DEV --> RV[功能与性能验证]

只修改应用逻辑时可以跳过模型转换；只更换模型时不必重建整个 BSP；只有发布固件或改变系统组件时才需要进入完整固件构建和 Flash。

4.3 平台工程生成

当前已实现的 RK3588 生成链主要覆盖这一阶段：

  1. 从 Catalog 读取 runtime-project.json 和 health-policy.json；
  2. 找到已部署 BSP 与工具链；
  3. 校验 BSP root commit、组件、loader、分区和环境身份；
  4. 根据平台契约生成 DTS/DTSI 候选；
  5. 生成 evoverse-rk3588-profile.json；
  6. 通过受管文件和原子写入安装候选；
  7. 写入 generation manifest 和文件摘要；
  8. 执行 preflight。

DTS 不能由大模型自由发挥。它必须来自真实 BSP symbol、Catalog 约束和可验证的变换规则，否则 label、时钟、regulator、pinmux 和驱动兼容性无法保证。

4.4 模型资格与转换

模型不能因为“扩展名是 ONNX”就直接交给 NPU。模型资格至少需要回答：

  • 模型来源、版本、许可和 SHA-256 是什么；
  • opset、算子和动态 shape 是否受支持；
  • 输入颜色空间、layout、尺寸、dtype、归一化和量化参数是什么；
  • 输出 tensor 怎样解释；
  • 量化数据集是否代表实际输入；
  • 转换工具、目标平台和配置是什么；
  • RKNN 与源模型输出偏差是否在规格允许范围内。

合理的链路是：

源模型 → inspect → 资格判断 → 量化/转换 → .rknn
      → 源模型/RKNN 样本对照 → 模型包与转换报告

模型身份不能只记录 .rknn 摘要，还要绑定源模型、转换工具、配置、量化数据摘要和输入输出契约。

4.5 应用生成与构建

应用应由可组合部件生成，而不是一次输出一个不可维护的大文件：

  • 输入适配器：Camera/V4L2、文件、RTSP、共享内存；
  • 预处理：resize、crop、颜色转换、归一化、layout；
  • 推理封装：模型加载、tensor 绑定、执行和错误处理；
  • 后处理：检测框、分类、分割、关键点等；
  • 业务逻辑：告警、跟踪、记录、协议输出；
  • 生命周期：配置、日志、健康检查、systemd/容器；
  • 验收探针：样本结果、FPS、延迟、内存和温度。

构建必须使用与目标 rootfs 匹配的 sysroot、编译器和 runtime，而不是开发机上的任意本地库。

4.6 Application Package

平台、模型和应用最后应汇入一个可追踪的应用包：

Application Package
├── application binary / libraries
├── model.rknn
├── preprocessing + postprocessing config
├── service or container definition
├── install / health / rollback metadata
└── manifest + digests + compatibility requirements

同一个应用包可以有两种交付方式：

  • 固件集成：加入 rootfs 后重建固件，适合发布与量产；
  • 增量部署：通过 SSH、ADB 或受控设备通道更新，适合开发和现场升级。

4.7 设备部署与验证

部署完成不是流程终点。至少需要分别记录：

  1. 设备身份与当前系统版本；
  2. 部署前后应用、模型和 runtime 摘要；
  3. 安装/Flash 回执与回滚点；
  4. 服务启动和健康检查；
  5. 功能样本结果；
  6. FPS、延迟、内存、温度和长稳结果。

只有具备这些证据，才能说“应用在这块板上达到了什么状态”。

5. 各层具体有什么、怎样发挥作用

5.1 EvoVerse Core

Core 是控制面，主要包含：

组件 作用
Workbench Shell 承载多个 Adapter 工作区和 System 总览
Adapter Registry 注册、卸载、API 协商和能力发现
Project Control 管理 Intent、规格、修订、确认和状态推进
Catalog Sync/Pointer 定位可信 Catalog，而不是扫描任意同名目录
MCP/CLI 为 Agent 提供结构化调用入口
Artifact/Evidence 管理 manifest、digest、blocker、receipt 和证据引用

Core 的价值不是“替大模型包一层 API”，而是把不稳定的生成过程变成可审阅、可重放、可恢复的工程事务。

5.2 RK3588 Adapter

Adapter 是语义翻译器、安全门禁和结果归一化器。目前声明的 headless 能力包括：

能力 当前作用
environment.status 查看 Docker、包、BSP、工具链和空间状态
environment.prepare Adapter 直连 Manager 读取 catalog 并生成 planDigest 绑定的安装计划
environment.deploy Workbench 完成许可确认后，Adapter 以单次 token 调用 Manager 安装并验证
project.generate 从 Catalog 基线生成工程
project.preflight 检查工程、BSP、工具链和身份一致性
project.build 运行 U-Boot、Kernel、Rootfs、Package 四阶段
project.status 读取报告并判断 readiness

未来模型、应用、设备和 runtime 能力也应由 Adapter 提供，但不应把 RKNN 私有字段放进 Core。

5.3 Catalog

Catalog 不是普通模板目录。它保存：

  • 板卡、载板和 SoC 身份；
  • 支持的参考工程；
  • BSP、工具链和容器版本；
  • loader、分区、启动材料和构建入口；
  • 健康策略、许可策略和验收策略；
  • 已验证模型、应用组件和性能基线（未来应补）。

可信位置以：

evoverse catalog status --json

返回的 location 为准。工作区的 .evoverse/catalog.json 是一跳指针；开发 checkout 或扩展 bundled 目录不能冒充已同步的可信 Catalog。

5.4 原生工具层

真正产生二进制的是原生工具：

  • Rockchip BSP 产生 bootloader、kernel、rootfs 和固件；
  • 交叉编译器产生 AArch64 应用；
  • RKNN-Toolkit2 产生 .rknn；
  • RKNPU2/runtime 在目标板加载和执行模型；
  • 厂商 Flash/USB 工具写入设备。

EvoVerse 应调用它们的原生流程并保存证据，不应通过额外脚本绕过错误配置。

6. 当前实现状态：不要把“已有”和“目标”混在一起

能力域 当前状态 当前边界
Core/Adapter 注册与 API 协商 已有 可发现 RK3588 Adapter
Catalog 同步与可信定位 已有 使用 receipt/location/pointer
双离线环境包检查与部署 已有 固定 BSP 与工具链版本
WS-E2 minimal-linux 工程生成 已有 当前只支持这一组工程身份
BSP qualification 与 DTS 候选 已有 绑定真实 BSP symbol
Preflight 与四阶段构建 已有 到 BUILD_READY
通用 Adapter Action 契约 契约基础已有 尚未贯通 ProjectState、Reducer、dispatch 和 next-action
任意自然语言→完整应用规格 部分基础 尚无完整 RK3588 应用 schema 与稳定路由
ONNX→RKNN 转换与验证 未形成闭环 无模型资格、转换和对照证据链
应用组件生成与 Application Package 未形成闭环 无统一应用包契约
Adapter 原生设备发现与 Flash 未实现 当前 descriptor 中 flash/debug 不支持
增量部署、回滚、板端 benchmark 未形成闭环 缺设备通道与运行证据模型
远程 Linux builder 未实现完整控制面 macOS/团队重构建仍需外部组织
多 CPU/GPU/NPU/XPU Adapter 通用流 架构方向已明确 仍需将开放计划与产物图接入生命周期

当前状态的关键判断是：BUILD_READY 只说明本次受控构建产生了可交付固件；它不等于已经烧录、成功启动或通过 NPU 应用验收。

7. SDK 外部环境到底要部署什么

7.1 四类安装必须分开

安装/下载 内容 默认位置或结果 作用
EvoVerse 客户包 VSIX、文档、部署脚本 Trae/VS Code 扩展目录 安装控制面与 Adapter
Catalog Sync 板卡、基线、策略、版本指针 Catalog status 返回的 location 决定允许生成什么
RK3588 双离线包 BSP 和固定工具链镜像 <EVOVERSE_HOME>/downloads/rk3588/ 提供大型原生环境
目标设备部署 固件或 Application Package eMMC/SD/目标 rootfs 让产物真正运行

把它们都叫“下载 SDK”会导致最常见的误解：装完 VSIX 后认为已经拥有 BSP，或者构建完成后认为应用已经在板上运行。

7.2 当前双离线包

当前基线要求：

  • rk3588-toolchain-2026.09.evopkg
  • ws-e2-rk3588-bsp-b8f5dda5.evopkg

放入：

<EVOVERSE_HOME>/downloads/rk3588/

Adapter 会验证包大小、SHA-256、manifest、逐文件 checksum、许可确认和环境身份，然后部署到：

<EVOVERSE_HOME>/bsp/ws-e2/b8f5dda5/
<EVOVERSE_HOME>/toolchains/rk3588/2026.09/
<EVOVERSE_HOME>/receipts/rk3588/
<EVOVERSE_HOME>/staging/rk3588/<operation-id>/

7.3 模型环境还需要补什么

要支持 NPU 应用，SDK 外部还需要一个受版本锁定的模型转换环境：

  • Linux/Python 基线；
  • RKNN-Toolkit2 与 native dependency；
  • 支持矩阵和目标平台配置；
  • 量化数据集或数据集摘要；
  • ONNX reference runtime；
  • 转换、对照和 benchmark 工具；
  • 与板端 RKNPU driver/runtime 的兼容关系。

它更适合进入固定 Linux 容器或远程 Linux builder，而不是散装安装到每台 Windows/macOS 主机。

7.4 设备环境还需要什么

板端部署至少涉及：

  • 可识别的设备 ID、板卡型号和当前系统版本；
  • USB Maskrom/Loader 或 SD/eMMC 制作工具；
  • 串口驱动和日志采集；
  • ADB/SSH 等增量部署通道；
  • 写入前检查、分区计划、确认、回读与回滚；
  • runtime、驱动、模型和应用版本记录。

这些能力当前不能由 EvoVerse 自动保证，应在外部烧录站或经过验证的实验室流程中完成，并把摘要与日志带回工程证据目录。

8. Windows、macOS、Linux 应该怎样分工和部署

8.1 Windows：当前最完整的客户主机

主机准备：

  • Windows 10/11 64 位；
  • Python 3.11+、Git；
  • Trae 或 VS Code；
  • Docker Desktop，使用 Linux containers；
  • 当前离线环境至少约 9 GiB 空间，实际项目应预留更多；
  • 若承担烧录，安装经过验证的 USB、串口和厂商设备驱动。

安装 EvoVerse：

# Trae
python deploy.py --host trae

# 或 VS Code
python deploy.py --host vscode

安装后按顺序执行：

  1. 重启 IDE 并完成首次 Setup；
  2. EvoVerse: Sync Catalog；
  3. 验证 Catalog location/version/commit；
  4. 放置两个 .evopkg；
  5. Workbench 执行环境检查（2026-11-01 起（P3）为只读事实展示，附 LEGACY_ENVIRONMENT 弃用说明，部署入口停用）；
  6. 环境部署改由 Linux Environment Manager（P4）承接——Adapter 不再直接执行环境部署；
  7. 等 Environment READY（P3 起该状态由 Environment Manager 报告）；
  8. 生成工程、preflight、构建；
  9. 将固件交给当前受控烧录流程。

8.2 macOS：适合作为前端，不应假设具备全部设备工具

macOS 可以完成：

  • Trae/VS Code、Core 和 Adapter 安装；
  • CLI/MCP、Catalog 同步；
  • 意图、规格、工程和代码生成；
  • Docker Desktop Linux VM 中的 BSP/应用/模型任务；
  • 报告与证据查看。

安装命令：

# Trae
python deploy.py --host trae

# 或 VS Code
python deploy.py --host vscode

主要限制：

  • 大型 BSP 通过 bind mount 时 I/O 可能较慢；
  • ARM Mac 与 x86_64 Linux image 可能触发仿真；
  • USB Maskrom、串口和厂商烧录工具未必原生可用；
  • 当前 Adapter 尚无 flash/debug，不能自动弥补这些差异。

推荐拓扑：

macOS IDE
  ├─ 自然语言、规格、代码、Catalog、结果查看
  └─ 发起受控任务
            ↓
Linux builder（Docker Desktop 或远程 Linux）
  ├─ BSP build
  ├─ ONNX → RKNN
  └─ AArch64 application build
            ↓
Windows/Linux 烧录与验证站
  ├─ Flash / UART / ADB / SSH
  └─ 板端功能与性能证据

8.3 Linux：最适合重构建、模型转换和设备自动化

Linux 原生主机或受管 builder 更适合：

  • 保存大型 BSP 和构建缓存；
  • 运行固定容器；
  • 执行 RKNN 转换和交叉编译；
  • 接入 USB、串口和设备权限；
  • 执行 CI/批量构建与板端实验室自动化。

一个完整远程 builder 还需要：

  • 身份认证和项目隔离；
  • 输入 manifest 与摘要校验；
  • 固定容器镜像和缓存策略；
  • 进度、日志、取消和断线重连；
  • 产物与证据回传；
  • 禁止未确认的设备写入。

当前仓库尚未形成这套完整远程执行控制面，因此它属于完善方向，不是已交付能力。

9. 构建、部署和证据怎样判断成功

9.1 当前四阶段平台构建

U-Boot → Kernel/DTB → Rootfs → Package

每一阶段都应绑定本次输入、工具身份、日志和产物。旧产物存在不能证明本次构建成功。

9.2 不同 readiness 不能混用

状态 能说明什么 不能说明什么
Environment READY BSP/工具链环境可用 工程或应用已生成
PROFILE_READY 平台工程与受管文件已生成 原生构建成功
BUILD_READY 四阶段构建成功且固件摘要存在 已烧录或成功启动
DEPLOYED 指定内容已写入指定设备 功能和性能合格
RUNTIME_VALIDATED 指定应用在指定设备达到验收条件 所有硬件场景都长期稳定

9.3 NPU 应用需要多维证据

  • 生成证据：规格、计划、候选、manifest 和 digest；
  • 平台证据：Profile、BSP、工具链、构建报告和固件摘要；
  • 模型证据：源模型、转换配置、量化数据、转换日志和输出对照；
  • 应用证据：编译、依赖闭包、应用包和安装检查；
  • 部署证据：设备身份、部署模式、前后版本、回执和回滚点；
  • 运行证据：功能样本、FPS、延迟、内存、温度和稳定性。

这些证据是依赖图，不是一个单一等级。例如“模型验证通过但应用未部署”和“应用已部署但性能不合格”必须保留为两个不同事实。

9.4 风险和确认

动作 风险 应有控制
规格/计划生成 低 只预览，不写设备
工程、模型、应用构建 低到中 固定环境；只写受管输出
应用增量部署 中 绑定设备；展示替换内容；保留回滚包
固件生成 中 只产生镜像，不自动 Flash
Firmware Flash 高 单独能力、显式确认、分区计划、回读摘要
runtime benchmark 中 限制资源和时长；记录设备负载和温度

失败只能产生 blocker、remediation 或 correction intent，不能自动扩大权限。例如，应用部署失败不能自动升级成完整固件烧录。

10. 现有控制面是否足够

10.1 可以直接复用的基础

  • Intent identity 和 expectedRevision；
  • Specification draft/approve；
  • digest、manifest 和 lineage；
  • 受管文件、stage/install 和原子写入；
  • Adapter 的不透明 payload 边界；
  • PASS/FAIL/INCOMPLETE/NOT_RUN、blocker 和 remediation；
  • 多 Intent、system integration、reconnect 与 committed observation。

这些机制与芯片无关，适合成为异构计算 Core。

10.2 当前不足

当前动作信封仍以：

intent → spec → candidate → simulation → native build
       → hardware program → hardware validate → integration

为主。这条链明显偏向 HDL/FPGA，不能完整表达平台固件、模型转换、应用包、增量部署和 runtime benchmark。

仓库已经出现 AdapterActionRequest、AdapterActionResult、AdapterPlanRef 和 CandidateManifestV2，它们建立了正确的通用边界，但目前仍主要是契约层：尚未完整接入 ProjectState/facts、Reducer、动作注册、provider dispatch 和当前动作计算。

10.3 应怎样补，而不是怎样重写

不需要建立 RK3588 专用 Core，也不应把 rknnModelPath、DTS、BSP 或 Buildroot 字段加入 Core。更合适的是：

  1. 把通用 Adapter Action 契约接入状态、Reducer、dispatch 和 next-action；
  2. 让 Adapter Plan 提供动作依赖图；
  3. 让 CandidateManifestV2 支持领域中立产物；
  4. 引入开放 artifact role、依赖边和多维 evidence；
  5. 先让现有 RK3588 project.generate/preflight/build/status 走通通用流；
  6. 再增加模型、应用、设备和 runtime 能力；
  7. 保留现有 FPGA Adapter 的仿真、Build、Program 和 Validate 计划。

这样 Core 只理解“计划身份、合法动作、产物关系、风险、确认和证据”，各 Adapter 自己定义厂商流程。

11. 还需要做什么才能完善

下面按依赖关系排列，不代表已经确定的版本排期。

11.1 第一层：完成通用控制面

  • 将通用 Adapter Action 契约接入完整生命周期；
  • 将固定 FPGA 动作排序改为 Adapter plan 驱动；
  • 建立开放 artifact/evidence 模型；
  • 保持 Core 不出现 CPU/GPU/NPU/XPU 固定枚举和厂商字段。

11.2 第二层：扩大可信平台基线

  • 增加更多板卡、载板和系统基线；
  • 完善 Catalog qualification、版本和兼容矩阵；
  • 建立缓存、升级和基线迁移规则；
  • 保留当前 WS-E2 minimal-linux 作为可重放样板。

11.3 第三层：补齐 NPU 模型与应用链

  • 定义 AI Application Spec；
  • 建立模型资格、RKNN 转换和样本对照；
  • 建立应用组件库与 AArch64 构建；
  • 定义 Application Package；
  • 用摄像头目标检测等代表性应用贯通全链。

11.4 第四层：建设外部执行环境

  • 固定 RKNN/应用构建容器；
  • 建设远程 Linux builder；
  • 实现日志、进度、取消、缓存和证据回传；
  • 明确 Windows/macOS/Linux 的支持矩阵。

11.5 第五层：设备部署与硬件验收

  • 先实现只读设备发现和部署计划预览；
  • 增加应用增量部署、健康检查和回滚；
  • 再增加高风险 Firmware Flash、回读和恢复；
  • 接入 UART、ADB、SSH 和启动诊断；
  • 建立功能、性能、温度和长稳证据。

11.6 第六层：验证多厂商可扩展性

选择至少一个与 RK3588 明显不同的 Adapter，例如通用 CPU/Linux 或 GPU runtime，验证：

  • Core 无需增加器件类别枚举；
  • 同一 Intent/Plan/Artifact/Evidence 机制可以复用；
  • Adapter 可以声明不同动作图和私有 schema；
  • Workbench 能呈现不同流程而不复制 Core 状态机。

只有经过第二种平台验证，才能真正证明 Core 是异构计算控制面，而不只是抽象过的 RK3588 控制器。

15. 最后的判断

EvoVerse 对 RK3588 的价值，不是生成更多脚本，而是把自然语言、平台事实、厂商工具、应用产物和硬件证据连成一条受控链。

当前最扎实的部分是平台工程与可复现构建底座；最明显的缺口是模型、应用、设备部署和板端验收；最重要的长期原则是保持 Core 领域中立，让 Adapter 承担具体厂商和器件语义。

完善后的目标不是“输入一句话，AI 神奇地烧出一块板”，而是：

用户用自然语言表达目标，系统形成可确认规格；Adapter 使用可信材料生成、构建和部署；每一步都有身份、摘要、风险边界和证据；新的 CPU、GPU、NPU、XPU 平台可以通过新 Adapter 接入，而不需要重写 Core。

高级参考用于按需查询；设计记录、发布流程、审计报告和未来规划不属于客户操作入口。
