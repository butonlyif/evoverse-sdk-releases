1. RK3588 简介

1.1 芯片定位

Rockchip RK3588 是瑞芯微电子的高性能 ARM SoC，定位高端物联网、智能座舱、边缘计算、AIoT 领域。它采用 4× Cortex-A76 + 4× Cortex-A55 异构 CPU 架构与 8nm 工艺；具体频率、媒体能力和可用接口仍受芯片变体、封装、板级设计及 BSP 限制。

1.2 主要特性

类别 规格 说明
CPU 4x Cortex-A76 + 4x Cortex-A55 ARM big.LITTLE 架构，大核主频最高 2.4GHz
GPU Mali-G610 MP4 支持 OpenGL ES 1.1/2.0/3.2, Vulkan 1.2
NPU 6TOPS 支持 INT4/INT8/INT16/FP16，算力强劲
VPU 8K@30fps 编解码 支持 H.265/H.264/VP9/AV1
ISP 最大 48MP 支持双 ISP 通道
内存 LPDDR4/LPDDR4X/LPDDR5 最大支持 32GB
存储 eMMC 5.1, UFS 2.1, PCIe 3.0, SATA 3.0 多存储接口支持
接口 USB 3.0, USB 2.0, PCIe, HDMI 2.1, MIPI-CSI/DSI 丰富外设接口
工艺 8nm FinFET 低功耗高性能

1.3 应用场景

  • 智能座舱: IVI、数字仪表、HUD
  • 边缘计算: AI 推理、机器视觉
  • 智能家居: 智能音箱、智能显示
  • 工业控制: 工业平板、机器视觉
  • ARM 开发板: 面向开发者的评估板（如 Rockchip EVB、第三方开发板）

2. 开发环境技术栈

2.1 交叉编译工具链

RK3588 采用 ARM64 (AArch64) 架构，需要使用交叉编译工具链：

工具链 说明 获取方式
GCC AArch64 主流选择，GCC 10+ apt install gcc-aarch64-linux-gnu
Linaro GCC 长期支持版本，稳定可靠 developer.arm.com
Rockchip 配套工具链 官方 BSP 配套 SDK 内部自带

典型工具链前缀: aarch64-linux-gnu-

2.2 SDK 类型

Rockchip 提供多种 SDK 选择：

SDK 类型 适用场景 构建系统 特点
Rockchip Linux SDK Linux 开发 Buildroot / Yocto 完整 BSP，包含 U-Boot、Kernel、Rootfs
Rockchip Android SDK Android 开发 AOSP 完整 Android 系统
Debian/Ubuntu Rootfs 快速验证 预编译镜像 可直接烧录使用

3.4 SDK 编译流程

3.4.1 Linux SDK 完整编译

cd rockchip-linux-sdk

# 1. 按当前 BSP release note 选择板级配置（命令名称因 BSP 而异）
./build.sh lunch
# 必须选择目标板卡 profile，不要只按 SoC 名称猜测 defconfig

# 2. 完整编译 (包含 u-boot, kernel, rootfs)
./build.sh

# 3. 产物位置
ls rockdev/
# update.img - 完整固件包

3.4.2 单独编译各组件

# 编译 U-Boot
cd u-boot
make distclean
make rockchip/rk3588_defconfig
make CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)

# 编译 Kernel
cd ../kernel-6.1
make ARCH=arm64 rockchip_linux_defconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- -j$(nproc)

# 编译设备树
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- dtbs

4. 常见开发场景

4.1 Linux 开发

4.1.1 内核驱动开发

# 1. 获取内核源码
cd kernel-6.1

make ARCH=arm64 menuconfig  # 配置内核选项

# 2. 编写驱动 (示例: hello_world.c)
cat > drivers/misc/hello_rk3588.c << 'EOF'
#include <linux/module.h>
#include <linux/kernel.h>

static int __init hello_init(void) {
    pr_info("Hello RK3588!\n");
    return 0;
}

static void __exit hello_exit(void) {
    pr_info("Goodbye RK3588!\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_AUTHOR("Developer");
MODULE_DESCRIPTION("Hello RK3588 Driver");
EOF

# 3. 编译模块
make ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- M=drivers/misc modules

8. 深度调研结论与工程基线

8.1 最重要的结论

  1. RK3588 不是一个可独立构建的“通用目标”。真正的构建目标是 SoC + 封装/内存拓扑 + PMIC + 存储 + Carrier + BSP 发布版。同为 RK3588 的 EVB、Rock 5、Firefly 等板卡，其 DDR 初始化、U-Boot defconfig、DTS、分区表和烧录 loader 均可能不同。
  2. BSP 是版本闭包，不是组件清单。U-Boot + rkbin/DDR blob + TF-A/OP-TEE + Kernel + DT + Rootfs + 打包工具 必须按厂商验证过的组合锁定。单独把内核或 U-Boot 升级到“较新版本”不构成可复现方案。
  3. 开发与部署分离。编译应在固定 Linux 容器/VM 中完成；串口、ADB/SSH 和烧录可在宿主机执行。macOS Docker Desktop 的 Linux VM 不能默认直通 Maskrom USB，烧录建议使用原生 Linux/Windows 工位或经验证的 USB 转发方案。
  4. 先做板级 bring-up，再做自动化。Adapter 的首个支持对象必须是一块明确板卡和一个明确 BSP 版本，不能从 SoC 数据手册直接推导出可启动固件。

8.2 推荐的可复现环境契约

每次构建必须生成 build-manifest.json，至少记录：

{
  "boardProfile": "vendor-board-revision",
  "bspManifestCommit": "<sha>",
  "components": {"uboot": "<sha>", "kernel": "<sha>", "rkbin": "<sha>"},
  "toolchain": {"triple": "aarch64-linux-gnu", "version": "<exact>", "sha256": "<sha256>"},
  "containerImage": "<registry/image@sha256:digest>",
  "configHashes": {"uboot": "<sha256>", "kernel": "<sha256>", "rootfs": "<sha256>"},
  "sourceDateEpoch": 0
}

宿主机建议基线：Linux x86_64、磁盘预留不少于 250 GB（Android 构建需更高）、内存至少 16 GB（大型并行构建建议 32 GB）、Git LFS 与 repo 可用。具体容量以 BSP release note 为准。容器镜像必须使用 digest 固定；源码、下载缓存和输出目录分卷挂载，避免因容器删除丢失产物。

8.3 三条经过校正的工作流

工作流 输入 输出 适用范围
BSP 全量构建 厂商 manifest、board profile、锁定容器 可烧录镜像与 manifest 发布/CI，最可信
内核/DT 增量 同一 BSP 的 .config、DTS、Module.symvers Image、DTB、modules 驱动开发；必须保持 ABI 一致
应用/NPU sysroot、交叉工具链、RKNN 兼容矩阵 ELF/包、.rknn、验证报告 不触碰启动链，迭代最快

8.4 烧录安全门禁

  • 执行写操作前必须记录 USB VID/PID、芯片信息、设备模式、板卡 profile 和目标存储介质；多设备连接时拒绝自动选择。
  • loader 必须来自当前板卡/BSP，禁止仅凭“RK3588”复用；DDR 参数不匹配可能导致下载失败或不稳定。
  • 禁止把示例 0x4000 当作通用分区地址。偏移单位、GPT/parameter 布局和镜像类型必须由 profile 明确给出。
  • 默认先读取并保存 GPT/parameter；擦除、写 bootloader、写全盘镜像属于高风险操作，必须显式确认。
  • 写入后至少校验镜像哈希/回读、启动串口关键阶段、内核版本、DT model/compatible 与 rootfs 版本。

8.5 验收清单

环境调研只有在以下证据齐全时才算完成：同一 clean checkout 连续构建两次成功；产物及配置可追溯；冷启动/热重启/掉电启动通过；串口保留完整 BootROM→loader→U-Boot→Kernel→userspace 日志；PCIe、GMAC、MIPI、GPIO 逐项以板卡原理图和运行时探测验证；NPU 记录 Toolkit2、模型格式、runtime 与驱动版本，并用固定输入做精度/性能回归。

8.6 资料可信度与待确认项

优先级为：板卡 BSP release note/manifest 与原理图 > Rockchip 芯片文档及官方仓库 > Linux 内核文档 > 开发板社区资料。公开资料无法替代受控 datasheet/TRM、板级原理图和实际 BSP。

在选定首块目标板前，以下内容保持“待确认”：具体 PCIe/Combo PHY 复用关系、MIPI DPHY 路由、GPIO 可用性、调试 UART 波特率、分区布局、loader 文件、DT 节点 label、内核分支及 RKNN 兼容组合。EvoVerse Adapter 必须把这些作为 profile 输入，不能硬编码。
