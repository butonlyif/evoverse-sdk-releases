EvoVerse SDK 详细说明

EvoVerse SDK 详细说明

版本：v1.0.0　更新日期：2026-09-30 适用平台：Trae IDE（推荐）/ VS Code 1.80+ · Windows

本文是 EvoVerse SDK 的产品级说明：它是什么、由哪些组件构成、能做哪些事、各能力之间如何衔接。操作步骤请配合用户使用手册、WS-E1 SD 到 CSI-2 工程教程和两篇受控 Skill 文档使用。

1. SDK 是什么

EvoVerse SDK 是一套运行在 Trae / VS Code 内的 FPGA 与 SoC 开发工作台，围绕 Efinix Titanium FPGA（WS E1/E3 板卡）提供从工程创建 → RTL 编写与仿真 → 编译与报告 → 时序收敛 → 烧录调试 → RISC-V 软件的完整闭环，并通过 CLI 与 MCP 把同一套流程开放给命令行和 AI Agent。

它解决三个问题：

痛点 SDK 的回答
FPGA 工具链碎片化（编辑器、仿真器、厂商 IDE、脚本各自为政） 一个 IDE 内完成全部日常操作，厂商工具只在后台被调用
AI 生成代码"看起来对"但无法验证 确定性工具门禁：仿真、风格检查、编译、时序诊断全部给出可复现证据
板卡资料、IP、工程配置散落各处 单一事实源 Catalog：板卡 / 底板 / 参考设计 / IP 统一入库、统一引用

2. 设计原则

  1. 确定性优先。所有关键操作（编译、仿真、检查、诊断）调用真实工具并保留证据（报告、波形、diff），AI 的"完成"声明必须绑定到这些证据上。
  2. 单一事实源。板卡规格、IP 文档、参考设计只维护一份（Catalog），文档门户随交付包渲染，板卡文档随 Catalog 同步到本地，不产生副本。
  3. 核心 + Adapter 分层。SDK 核心扩展提供通用外壳与共享设施；每个目标平台一个 Adapter 扩展，独立安装、独立演进。不用的平台不占资源、不出现在界面中。
  4. Agent 原生。MCP Server、结构化计划通道（生成 → 预览 → 确认 → 事务应用）和 Skill 技能包让 LLM 在受控边界内操作工程。

3.3 核心与 Adapter 的关系

  • Adapter 向核心的 AdapterRegistry 注册能力（build / timing / debug / program / software / ip / designApi / workspace）
  • 用户请求（如 Build）由核心路由到对应 Adapter，Adapter 调用真实工具链（如 efx_run --flow compile），结构化结果回传 Workbench 展示
  • Adapter 拥有自己的 Workbench Tab 内容；核心负责加载、资源注入与统一外观
flowchart LR
    WD[workspaceDocument<br>HTML 解析与资源注入] --> WB["Workbench 外壳<br>（六 Tab / System 根）"]
    WB -->|能力请求| AR[AdapterRegistry]
    AR <-->|headless adapter 协议| EF[efinity-adapter]
    AR <-->|headless adapter 协议| RK[rk3588-adapter]
    EF -->|build / timing / debug / program<br>software / IP / designApi| RUN["efx_run --flow compile"]
    RK --> BSP["BSP Profile 校验<br>四阶段交叉编译"]

4. 能力总览

能力 入口 说明
工程创建与接管 Trae 自然语言 / Workbench Control（evoverse.selectDesignFlow，EvoVerse: Select Design Flow） 由 project_next envelope 给出当前唯一推荐动作；每次执行后重新读取 revision，也可接管已有文件夹或归档
板卡向导 evoverse.newBoard（EvoVerse: New Board…） 从原理图 PDF / pinout 数据创建新板卡定义并入库
Catalog 物料 evoverse.syncCatalog（EvoVerse: Sync Catalog） 从官方公开发布 Catalog 同步板卡 / 底板 / Jacket / IP；教程中的物料只能作为带证据的来源，不能替代新工程规格
RTL 编辑 原生编辑器 Verilog / SystemVerilog 语法、代码片段、(* mark_debug *) 右键标记（efinity.debug.addSelectedSignal，Add Signal to Efinity Debug）
仿真 evoverse.sim（Toolchain: Simulate） Icarus Verilog / QuestaSim 一键运行，VCD 波形自动打开；ISP 图像仿真用 evoverse.simIsp（Toolchain: Simulate ISP (Video Sim)）

构建报告 Build Tab / evoverse.openReport（Toolchain: Open Build Report） 资源占用、时钟域、I/O、时序摘要结构化展示
时序诊断 evoverse.diagnoseTiming（Toolchain: Diagnose Timing Violations） 六类指纹根因分类引擎逐违例端点给出原因与置信度；数据路径追踪、流水线深度分析、Tcl 控制台
片上调试 Debug Tab 纯 CLI 六步闭环（见 §6.3），不启动 Efinity GUI
烧录 evoverse.program（Toolchain: Program FPGA） efx_pgm 调用，FTDI/JTAG 下载 bitstream
RISC-V 软件 SW Tab / evoverse.newRiscvProject（EvoVerse: New RISC-V Project…） Sapphire SoC 应用创建、BSP 生成（evoverse.generateBsp，Software: Generate BSP Headers）、构建、下载、GDB 调试
IP 管理 IP Tab 简单 IP 表单配置；复杂 IP（DDR/MIPI）经 Efinity IP Manager 配置后同步回工程
接口设计（DesignAPI） evoverse.openDesign（Efinity: Open Native Design） 事务式修改 ISF 接口约束：预览 → 确认 → 应用 → DRC
知识库 evoverse.knowledgeBase（EvoVerse: Show Knowledge Base） 沉淀验证过的工具链现象与解法，供人和 Agent 查询
AI 辅助 Timing Tab "Ask AI" 等 把 RTL + SDC + 路径分析打包成上下文交给 LLM；结构化计划需确认后才落盘
规格驱动设计 /evoverse-design-spec 把意图和运行时证据整理为可冻结的 design-package/；不直接生成 RTL
受控 RTL /evoverse-rtl 对一个封闭 RTL 任务执行候选、Assurance、仿真、隔离和提升；普通 Build 与自由开发路径不受门禁阻塞
CLI evoverse 命令行 终端复用同一套工程、Catalog 和验证流程；与 MCP 使用同一份本地 SDK 运行时。逐命令说明见文档门户「CLI 参考」页
MCP MCP Server Agent 的工程控制面入口；公开工具共 11 个：project_status / project_next / project_execute + evoverse_health + 7 个 rk3588_*（环境 status / prepare / deploy，工程 generate / preflight / build / status）

受控 Agent 路径的详细输入、输出、停止条件和 MCP 回执见 EvoVerse Design Spec Skill 与 EvoVerse RTL Skill。

5. Workbench 工作台

Workbench 是侧边栏工作台：核心提供外壳与 System 根（跨平台总览），Efinity Adapter 提供 FPGA 开发的六个 Tab。

Tab 功能
Home 工程仪表盘：Build 按钮、板卡信息、工具链动作、健康检查
Build 编译选项（Map / PNR / PT / PGM）、实时输出流、取消、结果摘要
Timing 时序报告、六类指纹根因诊断、数据路径与 Pipeline 分析、Tcl 控制台
Debug 纯 CLI 调试闭环六步（§6.3）
SW RISC-V 应用列表、BSP 重新生成、新建软件工程
IP 浏览 / 添加 IP、跳转 Efinity IP Manager、同步回工程

6. 典型开发闭环

6.1 FPGA 主线（第一次跑通）

Set Up → 在 Trae 描述工程目标 → 确认 Control 推荐动作 → 写 RTL → Simulate（看波形）
→ Check Code Style → Build（读报告）→ Program FPGA（上板看现象）

首次完整体验使用 WS-E1 SD 到 CSI-2 工程教程：先发现物料、冻结规格，再生成并验证 RTL，最后集成和编译。全程无需离开 IDE。

6.2 时序收敛闭环

Build → Diagnose Timing（六类指纹根因分类引擎给出原因与置信度）
→ 数据路径追踪 / Pipeline 分析定位瓶颈
→ 调整编译策略或修改 RTL → 重新 Build 验证 WNS/TNS

每一步都有原生报告证据；AI 建议应携带当前 RTL、SDC 和路径上下文，并以重新 Build 的 WNS/TNS 结果为准。

6.3 片上调试闭环（v0.9.0，纯 CLI）

  1. 标记信号：编辑器右键 Add Signal to Efinity Debug（写入 (* mark_debug *)）
  2. Build（auto-instantiation 自动生成 debug cores）→ Program FPGA
  3. Scan Device：FTDI/JTAG 扫描，显示 core 连接
  4. 配置触发（compare / pattern / mask）→ Trigger 或 Immediate Capture
  5. VCD 自动生成并打开；VIO 可读 / 安全写（写入需确认回执）

全程经 evoverse_dbg.py 桥接 Efinity efx_dbg API，不打开 Efinity GUI。也支持自然语言描述调试意图生成计划，预览确认后事务性应用。

6.4 RISC-V 软件闭环

确认 Sapphire SoC / 存储 / 调试接口 → SW Tab 创建或刷新软件工程 → Regen BSP
→ Build Software → 按工程实际能力下载 → GDB 调试

6.5 Vibe Coding（Agent 辅助）

`/evoverse-design-spec` 确认仿真等级并按等级预算起草规格 → 批准规格
→ `/evoverse-rtl` 交付候选 RTL → Design Assurance 与等级限定仿真证据
→ 原生 Efinity Build

可靠路径中，Agent 的每个"通过/晋升"声明由控制面动作回执绑定到范围、真实工程 diff、Design Assurance 和仿真证据。仿真等级先于规格（用户选择）：可靠迭代建立后、spec.draft 起草规格前必须先确认仿真等级（simulation.profile.select，否则控制面以 SIMULATION_PROFILE_REQUIRED 阻塞起草）；AI 依据固定风险规则推荐 FPGA_FUNCTIONAL / FPGA_INTEGRATION / HIGH_ASSURANCE 三档等级（或用户显式 CUSTOM），由用户选择，低于推荐最低等级必须记录 acceptedRisks，超出等级预算必须重新确认；规格按所选等级的预算编写，等级绑定设计迭代。spec.draft 提交的 packagePath 必须指向密封的可执行 2.0 规格包目录：服务端密封并记录 specPackageDigest 作为可靠身份，specification.md 由密封脚本确定性生成、仅供人工评审；Markdown 文件会被拒绝，并返回 workspace、输入/解析路径及原因，旧 Markdown 规格需从可执行包重新起草迁移。candidate.deliver 在 manifest 和事实落盘前校验 HDL/include/module/testbench 完整闭包；失败不形成权威候选，修正后可安全重试。verification.simulate 从服务端状态派生 candidate、source closure、Test IR 与 spec 摘要，在 feature 工作树执行模块/Intent 范围验证，本地通过只进入 READY_FOR_INTEGRATION；编译/展开失败记录为可修复的 CANDIDATE_COMPILE_FAILED，缺少后端或 vendor model 才是 CAPABILITY_UNAVAILABLE。主线系统集成 Intent 再执行组合规格校验、系统仿真与文档确认，全部通过后才原子晋升基线。等级限定的仿真通过（FPGA_FUNCTIONAL_PASS 等）不改变证据边界：NATIVE_BUILD_PENDING 与 BOARD_VALIDATION_REQUIRED 独立报告，自动化夹具不是实际 Questa 证据，Efinity Native Build、时序、烧录与实板结果仍需分别报告（build.native / hardware.program / hardware.validate）。

6.6 多 Intent 工作树

  • 尚无工程基线时，第一个设计就是 INITIAL_DESIGN 系统集成 Intent，在主线完成完整规格、生成、系统仿真和文档确认；它没有 feature worktree。完成前第二个 Intent 以 BASELINE_INITIALIZATION_IN_PROGRESS 阻塞。
  • 基线建立后，SDK 为每个 Intent 创建 codex/intent-<id> 分支和独立 Git worktree；活动上限固定为 4。
  • Feature Intent 验证并提交后只到 READY_FOR_INTEGRATION 并进入 FIFO 队列。主线一次创建一个无工作树的系统集成 Intent，以 merge --no-commit --no-ff 吸收分支，组合系统规格并执行系统仿真和文档验证；成功后才提交、晋升基线并清理 worktree。
  • 冲突或系统验证失败会 abort 未提交合并，恢复干净主线并保留分支/worktree。主 Workbench 分开显示 Feature Intents 与 System Integration；Intent worktree 只显示自身。

6.7 模块候选与受控集成（模块契约）

可靠模块迭代在规格之下再冻结一层模块契约边界：先资格化契约，再交付候选，最后由受控的系统集成晋升唯一基线。

  • 契约与 CONTRACT.md：可执行规格包内嵌 canonical 模块契约（闭合的 RTL/测试清单、top 模块、依赖摘要、预算与候选可写路径），并确定性渲染出人工评审用的 CONTRACT.md，固定呈现系统/内部模块关系、接口、时钟/复位/状态与数据结构、算法公式与伪代码/流水级、预算、需求追踪、仿真与证据定义（仿真边界、时钟/复位刺激、BFM 角色、正常/边界/异常/恢复场景、oracle 与覆盖率）、Harness 场景以及风险与已决策事项。机器契约是唯一真值，文档仅供评审批准；缺节、过期或不一致都会阻塞资格化，审批同时绑定 moduleContractDigest 与 contractDocumentDigest。
  • 契约资格化：contract.qualify（moduleId + 用户批准的 approvedDocumentDigest）执行确定性资格化引擎——结构完整性、需求/子句/孤测试追踪、仿真定义完整性、接口/时钟/复位/预算与系统兼容、可行性矛盾检查；未决工程权衡产出 DecisionRequest 交用户决策，不由 Agent 代选。资格化包含 Contract Harness：真实仿真 provider 以冻结 ExecutionIdentity 隔离编译并 elaborate 契约声明源，只产生 CONTRACT_HARNESS 证据——仅证明可编译/可展开，不构成算法、Native Build、编程或硬件证据。通过后 intent 记录 CONTRACT_QUALIFIED；契约 digest 变化会使既有 Harness、候选与未晋升组合证据失效，必须重新资格化。未资格化时 candidate.deliver 被 CONTRACT_QUALIFICATION_REQUIRED 阻塞；Discovery Spike 不产生可复用 PASS。
  • RTL Module 与 Qualification Component：RTL Module 是契约声明的单一 top 设计单元；资格化与集成的单位是 Qualification Component，可由多个真实周期耦合的 RTL Module 组成，跨组件私有层次引用在候选冻结时被拒绝。
  • readiness 与晋升分离：MODULE 候选交付后 candidate.promote 只到达 READY_FOR_INTEGRATION（Workbench 显示候选 readiness），不安装基线；系统集成 Intent 冻结组件、接口与拓扑组合（composition），完成系统仿真与策略要求的 Native Build 门后，由控制面唯一晋升 BASELINE_PROMOTED 基线。状态阶梯：QUALIFIED → READY_FOR_INTEGRATION → INTEGRATION_CANDIDATE → BASELINE_PROMOTED。集成暂存内不做原地修复——集成前失败与晋升后缺陷都通过新候选、新组合、新基线处理，历史事实 append-only。
  • 证据边界（macOS / Efinity）：控制面与 Icarus 仿真链可在 macOS 完整开发与验证；Efinity Native Build、编程与硬件验证未实际执行时保持 NATIVE_BUILD_PENDING 等诚实状态。Workbench Control 以证据向量（assurance、moduleSimulation、systemSimulation、nativeBuild、programming、hardwareValidation、maturity 七字段）独立呈现每个 intent 的证据状态，任何仿真通过都不会升格为原生或硬件结论。

7. 工程结构与 Catalog

7.1 工程目录（骨架工程生成后）

my-project/
├── evoverse-project.json   # 工程清单：板卡、源文件、IP、软件应用
├── rtl/                  # RTL 源码（top 模块在此）
├── sim/                  # 仿真测试台与脚本
├── constraints/          # SDC / ISF 约束
└── soc/                  # RISC-V SoC 配置与软件应用（可选）

7.2 Catalog 布局（单一事实源）

${EVOVERSE_HOME}/catalog/
├── boards/ws-e1/            # E1 核心板：规格、datasheet、pinout
│   ├── carriers/ws-e1-base/ # E1 Base 底板：规格与载板物料
│   └── ...
├── boards/ws-e3/            # E3 板卡
├── demos/                    # 通过 Sync Catalog 获取的参考 Demo
└── ips/                      # 通过 Sync Catalog 获取的通用 IP

Catalog 通过 EvoVerse: Sync Catalog 同步到本地运行时；板卡规格、Demo 和 IP 是可追溯材料来源。新工程必须由已冻结规格生成，不能把参考工程整体复制为基线。

9. 升级、卸载与常见问题

  • 升级：核心与已安装 Adapter 保持同版本号（如均为 1.0.0）；升级核心时建议同步升级 Adapter。
  • 卸载 Adapter：核心仍可用；对应 Workspace Tab 消失，其余功能不受影响。

Q：只做 FPGA 开发，需要装 RK3588 Adapter 吗？ 不需要。未安装的 Adapter 不占用资源，也不出现在界面中。

Q：两个 Adapter 能同时装吗？ 可以。侧边栏顶部出现 Workspace 切换器，System 根提供跨平台总览。

Q：片上调试需要打开 Efinity GUI 吗？ 不需要。v0.9.0 起调试全程纯 CLI，只在后台调用 efx_dbg API。

Q：Efinity 升级后 Adapter 要重装吗？ Adapter 版本与 Efinity 版本独立；个别 Efinity 大版本变化可能需要 Adapter 更新，以 Release Notes 为准。
