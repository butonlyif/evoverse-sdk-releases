EvoVerse SDK — 用户使用手册

版本：v1.0.0 更新日期：2026-09-30 适用 SDK 版本: v1.0.0 适用平台：Trae IDE / VS Code 1.80+ · Windows · macOS · Linux

Agent Runtime（v0.7.1+）：Timing Diagnosis、Build Report 和原生 @evoverse 使用同一持久化会话。模型可选择宿主 vscode.lm 或 OpenAI-compatible 端点；模型 ID 必须显式配置，远程内容发送前可预览并确认，API Key 仅保存在 SecretStorage。 前置要求：Python 3.11+（自动检测），Efinity 2026.1+（编译/烧录时需要），Icarus Verilog 或 QuestaSim（仿真时需要）

设计流程选择（2026-09-30）：Trae 自然语言与 Workbench Control 共用服务端 current-action envelope。可靠/自由模式按设计迭代保存，不是工程全局开关；新对话从 project_next 恢复当前 revision、推荐动作与证据边界。自由模式不阻止普通 Build，但受控修改显示 UNVERIFIED_CHANGES，可随时选择“将当前修改纳入可靠流程”增量重走受影响门禁。

可靠流程遇到 MCP 传输中断只自动恢复一次，并在继续前重新检查能力和服务端摘要；状态不能对账时停止，不会切换到 CLI 代跑。Assurance、仿真、Native Build、烧录和实板结果分别报告，任一边界的 PASS 不替代其他边界。

如果设计、系统集成或工程文件生成中断，直接用自然语言说明“保留什么、替换什么、丢弃什么、希望回到哪里”。Agent 会展示服务端按当前 revision 生成的恢复描述；确认后一次只执行一个恢复步骤并重新读取状态。若 project_next 返回 RECOVERY_REQUIRED 和 recovery.open，Agent 必须原样提交动作中的 inputPreview，不能编辑恢复范围；记录落盘后再执行服务端提供的 recovery.quarantine。隔离会保留可信 baseline、事实和失败证据并释放受影响范围，但不表示任务成功。不要手工删除 .evoverse 状态。初始设计也可安全放弃后重新创建 Intent。

系统集成提交采用可恢复事务：若 IDE、Agent 或进程在 merge 后中断，重新打开工程或读取状态即可触发身份对账。只有 commit、tree、请求和验证摘要全部匹配时才补齐 baseline 与完成事实，系统不会重复 merge，也不会把半批事实或半生成 baseline 当作成功。出现身份冲突时会停止并保留现场，不要手工删除 .evoverse 或 Git journal。

如果已选 Questa/Icarus 的真实 smoke、许可、启动、编译、运行或事件解析失败，流程会停在 WAITING_FOR_USER。修好环境后选择重新探测，或明确重选工具链；系统不会自动换后端或继续产生 PASS。

3. 安装与配置

3.1 安装扩展

  1. 获取 3 个 v1.0.0 VSIX：evoverse-sdk-1.0.0.vsix、evoverse-efinity-adapter-1.0.0.vsix、evoverse-rk3588-adapter-1.0.0.vsix
  2. Trae IDE 或 Visual Studio Code → 左侧 Extensions 图标 → 右上角 ... → Install from VSIX...
  3. 按顺序安装：先 evoverse-sdk，再装两个 Adapter（使用交付包时可运行 scripts/deploy.ps1 一键安装，见 部署指南）
  4. Reload Window（弹窗提示时点击）

Trae、标准 VS Code 和其他 VS Code fork 使用同一组 VSIX，无需分别编译。扩展激活后才检测宿主并选择对应集成方式。

3.1.1 Workbench Adapter 插件（v0.8.0+）

从 v0.8.0 起，EvoVerse SDK 采用核心 + 可选 Adapter的插件架构：

VSIX 扩展 ID 说明
evoverse-sdk-*.vsix evoverse-hw.evoverse-sdk 核心扩展（必须安装），提供 Workbench Shell、Catalog、CLI、MCP
evoverse-efinity-adapter-*.vsix evoverse-hw.evoverse-efinity-adapter Efinity Adapter（可选），提供 Efinity Workspace（6 Tab）
evoverse-rk3588-adapter-*.vsix evoverse-hw.evoverse-rk3588-adapter RK3588 Adapter（可选），提供 RK3588 Workspace（8 Tab）

安装组合： - 仅 Core：显示安装 Adapter 的引导，不显示虚假的厂商 Workspace - Core + Efinity：隐藏切换器，直接进入 Efinity Workspace - Core + RK3588：隐藏切换器，直接进入 RK3588 Workspace - Core + 两个 Adapter：显示 Workspace 切换器和 System Workspace，首次进入 System

Adapter 必须在 Core 之后安装（extensionDependencies 自动处理依赖关系）。

各 Adapter 的功能边界与使用方法见： - SDK 详细说明 - Efinity Adapter 使用指南 - RK3588 Adapter 使用指南

3.2 首次初始化（Set Up）

安装后首次打开自动弹出引导对话框（按钮 Yes, set up / Later）：

┌─────────────────────────────────────────────────────────────┐
│  Set up EvoVerse SDK?                                        │
│                                                              │
│  This will create ~/evoverse-sdk for your catalog and        │
│  integrate the EvoVerse Agent with supported host features.  │
│  No system files are modified.                               │
│                                                              │
│  [Yes, set up]  [Later]                                      │
└─────────────────────────────────────────────────────────────┘

点击 Yes, set up 后自动完成（Output 面板输出 === EvoVerse SDK bootstrap ===）： - 创建 ~/evoverse-sdk：Catalog、projects、CLI、MCP Server、verification runtime 共用这一根目录（运行时以链接方式指向扩展自带副本） - Trae：写入 ~/.trae/mcp.json 注册 MCP Server，并部署 ~/.trae/user_rules/ 下的通用 + RTL Agent 规则 - 标准 VS Code：合并用户级 mcp.json 的 servers.evoverse；其他宿主安全降级，不写宿主私有配置 - 检测 Python 版本（需 3.11+） - 完成后输出 === EvoVerse SDK ready ===

引导未自动弹出或需要重跑时：Ctrl+Shift+P → EvoVerse: Set Up (re-run bootstrap)

Catalog 不随 Set Up 部署。 首次打开 Welcome 时 Catalog 为空（状态 CATALOG_NOT_INSTALLED），运行 EvoVerse: Sync Catalog 从公开发布仓库同步板卡物料（无需 GitHub 账号），见第 6 章。

3.3 配置工具链路径

Ctrl/Cmd + , 打开设置，搜索 evoverse：

配置项 必填 说明 示例值
evoverse.efinityPath 是（编译时） Efinity 安装路径 C:\Efinity\2026.1
evoverse.simulator 是（仿真时） 普通 RTL 仿真后端：iverilog 或 questa iverilog
evoverse.iverilogPath 选择 Icarus 时 包含 iverilog/vvp 的目录 C:\iverilog\bin
evoverse.questaPath 选择 Questa 时 包含 vlib/vlog/vsim 的目录 C:\questasim64_2024.1\win64
evoverse.pythonPath 否 Python 解释器（留空自动检测） —
evoverse.home 否 SDK 工作根目录（默认 ~/evoverse-sdk） —
evoverse.model.provider AI 可选 vscode-lm 或 openai-compatible vscode-lm
evoverse.model.modelId AI 必填 显式模型 ID；不会默认选择第一个模型 由宿主/端点提供
evoverse.model.baseUrl OpenAI-compatible 必填 HTTPS API 根地址 https://api.openai.com/v1/

OpenAI-compatible API Key 通过命令 EvoVerse: Set OpenAI-compatible API Key 写入 SecretStorage，不要写入 settings.json。

其他可选配置见 第 21 章。

5. 工程管理

5.1 用自然语言建立工程

在 Trae Chat 中说明目标、板卡、载板和需要的 Catalog 物料。Agent 先调用 project_status 与 project_next，只展示服务端 envelope 中的推荐动作、所需用户选择和证据边界。你确认后，Agent 才以 envelope 的 actionId 与 expectedRevision 提交 project_execute。

执行完成后必须重新读取 project_next，核对新 revision 和下一推荐动作。若响应中断，先核对 receipt，再决定是否用同一 action identity 重试；不得创建新请求来猜测状态。

工程创建后会产生 manifest、约束与最小 RTL/仿真骨架。需要参考设计时，让 Agent 从已同步 Catalog 中列出可用物料并说明来源；不要把某个固定 Jacket 名称写成所有客户都存在的入口。

自由开发仍可直接编辑并运行普通 Build；只有当前迭代选择 reliable 后，用户通过 simulation.profile.select 选择 FPGA_FUNCTIONAL、FPGA_INTEGRATION 或 HIGH_ASSURANCE，候选、仿真与 promotion 才受证据门禁。仿真、Native Build、Program 和 Hardware Validation 分别记录，未运行的边界明确显示 NOT_RUN / BOARD_VALIDATION_REQUIRED。

5.2 接管已有工程

在 Trae Chat 中说明已有工程目录和接管目标。Agent 先读取 project_status / project_next，确认服务端推荐 asset.observe、asset.adopt 或其他合法动作后再提交；原生 Efinity 工程升级仍由 EvoVerse: Adopt Project (upgrade native Efinity) 执行。

外部工程支持：即使没有 evoverse-project.md，只要目录中有 Efinity 的 <project>.xml 文件，Build / Report / Diagnose / Program 等操作均可正常工作。

7.3 编译流程详解

SDK 不自动 sanitize 工程 XML，不在 build 前自动运行结构健康检查；HDL 文件监视器不自动 sync-sources。源文件同步与健康检查均手动触发（见 §5.4 与 §10.6）。AI 诊断结果不自动应用，需用户确认。（历史变更见 附录 A.A1）

CLI 模式下，Build 请求由 SDK 路由到 efinity-adapter，adapter 通过 build.compile 能力执行 efx_run --flow compile（Efinity 原生统一流程）：

1. 工程定位
   └─ 定位工程 XML，收集流程选项（§7.6 参数面板）

2. 统一流程 — efx_run --flow compile
   ├─ map — Verilog/SystemVerilog 综合（efx_map）
   ├─ PT  — 接口约束导入（把工程引用的 ISF 重放到持久化的 <design>.peri.xml）
   ├─ pnr — 布局布线（efx_pnr）
   └─ pgm — 比特流生成（efx_pgm）

3. 报告解析
   ├─ 解析 outflow/ 报告
   ├─ 生成 BuildSummary 并更新报告视图
   └─ 更新状态栏（重新打开工程时从原生报告恢复）

7.4 并行编译

默认构建不覆盖 Efinity 工程参数。只有显式启用 evoverse.build.parallelJobs 时，SDK 才通过命令行覆盖综合/PNR 的并行线程数。

7.5 SDC 预检

  • sdc-missing-or-empty（SDC 缺失/为空）
  • sdc-clock-coverage（时钟约束覆盖）

12.5 设计保证与规则管理（Design Assurance）

12.1–12.4 的风格检查器基于 Efinity 编码风格文档的启发式规则；本节的 Design Assurance 是独立的确定性规则引擎（sdk/design-assurance），检查 RTL 结构规则与协议契约，报告为三态（pass / fail / incomplete，缺证据是 incomplete 而非 pass）。两者互不影响。

命令行检查：

# 检查工程（默认自动发现 RTL 源，跑 rtl-baseline 规则包；testbench 风格文件默认跳过）
evoverse assurance check ./my-project

# 需要把 testbench（tb_*/sim/）也纳入分析
evoverse assurance check ./my-project --include-testbench

# 限定只分析 rtl/ 下的源文件
evoverse assurance check ./my-project --include-glob 'rtl/*.sv'

# 查看规则目录与开关状态
evoverse assurance rules --format text

rtl-baseline@1 只分析可综合子集；testbench 文件（initial/$task/#delay/@event 等）属域外，自动发现默认按 **/sim/**、**/testbench/**、**/tb/**、tb_*.*、*_tb.*、sim_*、test_* 跳过；scanner 内部把 initial ... end 整块当 testbench 跳过（记 info，不入 unverified）。MCP assurance_check 同步支持 include_testbench / include_glob / exclude_glob 三个入参。

退出码：0=pass、1=fail、2=incomplete、64=用法/配置错误。详细契约（请求 JSON、证据、例外）见 docs/design-assurance/README.md。

规则管理器（Rule Manager UI）

入口：Welcome 页 → Assure 卡片 → Rule Manager（或命令 EvoVerse: Open Assurance Rules）。

管理所有 assurance 规则的开关，作用于每一次检查（CLI / MCP 同样生效）：

操作 说明
总开关（All checks） 关闭后所有检查跳过，报告为 incomplete（不冒充 pass）
规则包开关 rtl-baseline@1 / amba.axis@1 / custom@1 整包启停
单条规则开关 比关包更细粒度地禁用某一条规则
添加自定义规则 声明式正则 lint：规则 id、severity（error/warning/info）、描述、Python 正则 pattern，命中行即报违规
删除自定义规则 自定义规则列表中 ✕ 删除
Save / Reload / Reset 保存到全局配置并经引擎回读校验；Reset 一键恢复全启用默认态

配置持久化在 <EVOVERSE_HOME>/assurance-rules.json（面板头部显示路径），也可手工编辑——格式与约束见 docs/design-assurance/README.md 的"规则管理"章节。

14.8 常见问题

  • "No native peri.xml exists"：工程从未跑过 Pre-PT，点 Rebuild 触发一次 efx_map。
  • "GPIO exists" 但 inspect 列表里看不到：基础 ISF 与当前 peri.xml 不一致，从 base.peri.isf 重建 peri.xml。
  • Apply 失败但 ISF 没问题：检查 EvoVerse 输出面板的 Pre-PT 日志；DesignAPI 流程会先跑一次完整 PT 生成 peri.xml，若 Efinity 安装损坏或 license 过期，PT 会失败。
  • block type 列表没有我想要的：以当前 Efinity 安装目录的 doc/pdf/efinity-python-api.pdf 为准；SDK 不维护属性副本。

MCP Server 实际暴露 97 个工具，按域分组：Catalog 与知识库 / 可靠设计与证据 / 工程与代码生成 / 构建、软件与 IP / 调试、烧录与时序等。完整清单与逐工具必填/可选参数见文档门户「MCP 工具参考」页。new_riscv_project、ip list、ip add、sync_sources 是 CLI 子命令，不是 MCP 工具。

其中「可靠设计与证据」域是可靠代码生成的重点能力：控制面只保留 4 个稳定接口——project_status / project_next / project_execute / evoverse_health。project_next 返回当前 action envelope（推荐动作、用户决策、证据边界、恢复信息与 terminalState）；每次只推进一个动作：读当前 revision → 核对 envelope 的 {actionId, intentId, expectedRevision} → 提交 project_execute → 重新读取 project_next 与新 revision。响应丢失时先核对 receipt，再决定是否以同一 identity 重试；不允许凭记忆推进。

执行身份统一为 ExecutionIdentity：界面只读显示缩写后的 executionIdentityDigest，不会要求用户填写 candidate/spec/Test IR/environment 等组件 digest。Provider 在 prepare → freeze → execute 边界核对真实工具环境；status/next/Workbench 投影复用已封存 manifest 和 receipt，不重复哈希候选树或大镜像。文件字节仍会在冻结、执行、晋升、安装与发布等信任边界重新校验，因此减少的是重复计算，不是完整性检查。

仿真等级先于规格（用户选择）：可靠迭代建立后、spec.draft 起草规格前，控制面要求先确认仿真等级（否则以 SIMULATION_PROFILE_REQUIRED 阻塞起草）。AI 依据固定风险规则给出推荐，由用户选择：FPGA_FUNCTIONAL（单时钟简单功能，如秒表、流水灯——最多 3 个核心阻塞场景 + 1 个关键边界 + 1 个集成冒烟）、FPGA_INTEGRATION（协议/FIFO/CDC/背压/跨行跨帧状态，如窗口化 ISP、DMA）、HIGH_ASSURANCE（高速复杂协议、存储控制、不可逆控制、安全相关），也可用 CUSTOM 显式划分阻塞/延期义务。选择低于推荐最低等级时必须记录 acceptedRisks；超出等级预算时控制面要求重新确认。规格按所选等级的预算编写；等级绑定设计迭代，改变等级需要新的迭代。spec.draft 提交的 packagePath 必须指向密封的可执行 2.0 规格包目录：服务端密封并记录 specPackageDigest 作为可靠身份，specification.md 由密封脚本确定性生成、仅供人工评审；Markdown 文件会被拒绝，旧 Markdown 规格需从可执行包重新起草迁移。仿真通过带等级限定（FPGA_FUNCTIONAL_PASS 等），延期事项不产生伪 PASS；NATIVE_BUILD_PENDING / BOARD_VALIDATION_REQUIRED 与仿真状态始终分开报告，功能级仿真通过不代表原生构建或硬件通过。

candidate.deliver 在可靠模式只冻结候选，不晋级基线，并执行 RTL Design Assurance（结构、时钟、复位、CDC、FSM、FIFO、完整性与协议契约）；服务会先检查 HDL/include/module/testbench 完整闭包，失败不写候选事实，修正后可安全重试。verification.simulate 显式选择 iverilog 或 questa 后端，所需身份摘要由服务端从冻结状态生成，按 elaboration、module-smoke、requirement、module-regression、subsystem、system 逐层运行并在首个失败层停止。只有当前候选仿真取得有效 PASS 且满足资格，candidate.promote 才安装基线。出现 DUT_FAIL 或 CANDIDATE_COMPILE_FAILED 时，Agent 记录失败需求和有界诊断；单一证据充分的原因可定向修复一次，多种原因或修复仍失败时提出工程选项（依据、下一步检查、代价和不确定性），由工程师选择或填写自己的判断。缺少仿真器或 vendor model 才报告 CAPABILITY_UNAVAILABLE。人工判断是待验证假设；新证据冲突时须明确反馈并重新沟通，不得将其视为 PASS。自动化夹具通过不等于实际 Questa、Efinity Native Build、烧录或实板通过——build.native、hardware.program、hardware.validate 的证据相互独立，必须分别报告。

模块契约与受控集成（模块候选）：可靠模块迭代在规格之下再冻结一层模块契约。可执行规格包内嵌 canonical 模块契约（闭合的 RTL/测试清单、top、依赖摘要、预算与候选可写路径），并确定性渲染出人工评审用的 CONTRACT.md：固定呈现系统/内部模块关系、接口、时钟/复位/状态与数据结构、算法公式与伪代码、预算、需求追踪、仿真与证据定义（仿真边界、时钟/复位刺激、BFM 角色、正常/边界/异常/恢复场景、oracle 与覆盖率）、Harness 场景以及风险与已决策事项；机器契约是唯一真值，文档缺节、过期或不一致都会阻塞资格化。用户批准 CONTRACT.md 后用 contract.qualify（moduleId + approvedDocumentDigest）完成契约资格化：结构完整性、需求/子句/孤测试追踪、仿真定义完整性、接口/时钟/复位/预算系统兼容与可行性检查，未决权衡产出 DecisionRequest 由工程师决策而非 Agent 代选；资格化还通过 Contract Harness 在真实仿真 provider 上以冻结执行身份隔离编译并 elaborate 契约声明源——该证据仅证明可编译/可展开，不构成算法功能、Native Build、编程或硬件证据。契约 digest 变化会使既有 Harness、候选与未晋升组合证据失效，必须重新资格化；未资格化时 candidate.deliver 被 CONTRACT_QUALIFICATION_REQUIRED 阻塞，Discovery Spike 标签的输入在规划阶段即被拒绝，不产生可复用 PASS。RTL Module 是契约的单一 top 设计单元；资格化与集成的单位是 Qualification Component，可包含多个周期耦合的 RTL Module，跨组件私有层次引用在候选冻结时被拒绝。MODULE 候选交付后 candidate.promote 只到达 READY_FOR_INTEGRATION（Workbench 候选行显示 readiness），不再直接安装基线；系统集成 Intent 冻结组件、接口与拓扑组合，完成系统仿真与策略要求的 Native Build 门后由控制面唯一晋升 BASELINE_PROMOTED 基线（状态阶梯 QUALIFIED → READY_FOR_INTEGRATION → INTEGRATION_CANDIDATE → BASELINE_PROMOTED）。集成暂存内不做原地修复：集成前失败与晋升后缺陷都通过新候选、新组合、新基线处理，历史事实 append-only。macOS 会话可完整验证控制面与 Icarus 仿真链；Efinity Native Build、烧录与硬件验证未实际执行时保持 NATIVE_BUILD_PENDING 等诚实状态，Workbench 证据向量（assurance / moduleSimulation / systemSimulation / nativeBuild / programming / hardwareValidation / maturity 七字段）独立呈现、互不升格。

22. 常见问题

Q1: 安装后看不到 EvoVerse 图标？

A: 点击 Ctrl+Shift+P → 输入 EvoVerse: Set Up (re-run bootstrap) → 确认初始化。如果仍不显示，按 Ctrl+Shift+P → Developer: Reload Window。

Q2: 编译报 "Efinity not found"？

A: 打开设置（Ctrl/Cmd + ,），搜索 evoverse.efinityPath，填入 Efinity 的安装路径，如： - Windows: C:\Efinity\2026.1 - Linux: /opt/Efinity/2026.1

Q3: 仿真报 "iverilog not found"？

A: 设置 evoverse.iverilogPath。Windows 上推荐从 Icarus 官网 下载预编译包，或通过 scoop install iverilog / choco install iverilog 安装。

Q4: 如何将已有 Efinity 工程迁移到 EvoVerse？

A: 打开工程目录后，执行 EvoVerse: Adopt Project (upgrade native Efinity)。SDK 会自动生成 evoverse-project.md 并注册到 IDE。也可以直接打开——只要目录中有 <project>.xml，Build/Report/Diagnose/Program 均可正常工作。

Q5: Workbench 的 IP Tab 显示 "No instances found"？

A: IP 实例通过两种方式发现：(1) 工程 XML 中的 <efx:ip_info> 标签；(2) ip/ 目录下的子目录。如果添加了 IP 但未显示，点击 Sync Project Files 按钮。

Q6: 时序诊断面板显示 "No timing data"？

A: 时序诊断需要先完成一次完整编译（Build）。编译后 SDK 会解析 outflow/ 中的时序报告。如果编译失败或未运行过 P&R，则无数据可分析。

Q7: CLI 命令 evoverse 找不到？

A: CLI 在 Set Up 时安装到 ~/.evoverse/runtime/。确保该目录在系统 PATH 中，或使用完整路径：~/.evoverse/runtime/evoverse。

Q8: 如何更新 SDK 到新版本？

A: 1. 获取新版本 VSIX 文件 2. Extensions 面板 → 找到 EvoVerse SDK → 卸载 3. Install from VSIX... → 选择新版本 vsix 4. Reload Window

Q9: macOS 上能做什么？

A: macOS 支持开发（代码编写）、Icarus 仿真、AI 协作、CLI 查询、Catalog 管理、文档查看。Icarus 的 iverilog / vvp 通过参数数组直接执行；带空格路径和非 UTF-8 工具输出均按 macOS/POSIX 语义处理，不依赖 cmd.exe。宿主与部署已跨平台（客户包同时提供 deploy.ps1 与 deploy.sh，扩展为同一组 VSIX）；完整 Efinity 编译/烧录仍需 Windows 或 Linux 环境。

Q10: 多人协作如何同步 Catalog？

A: 不要把运行时 catalog/ 目录重新纳入 SDK 或客户工程版本管理。每位成员执行 EvoVerse: Sync Catalog 即可从官方公开发布仓库同步（无需 GitHub 账号）；用 evoverse catalog status --json 对齐版本、commit 与 tree digest。

Q11: 可以同时推进多个 Intent 吗？

A: 可以，但第一次设计本身是主线上的 INITIAL_DESIGN 系统集成 Intent，没有 feature worktree；它完成完整规格、生成、系统仿真和文档确认并建立首个基线前，不允许开启第二个 Intent。之后最多同时有 4 个 feature Intent，每个使用独立分支和 worktree，本地验证通过只显示“Module verified, waiting for system integration”。主线 Workbench 分为 Feature Intents 与 System Integration：系统集成按 FIFO 一次吸收一个分支，重新确认组合规格、系统仿真和文档后才晋升基线。冲突或系统验证失败会 abort 合并并保留分支/worktree；进入某个 Intent worktree 后，Current Intent 仍只显示该 Intent。

v0.7.1 起，AI 诊断从"自动修复"改为"建议仅供参考"，避免后台 Agent 在用户未确认时改写 RTL：

远程内容预览 API Key 与远程内容处理无统一规范 远程内容发送前可预览确认；API Key 仅写入 SecretStorage
模型选择 SDK 默认选用第一个可用模型 需显式配置 evoverse.model.modelId；可选宿主 vscode.lm 或 OpenAI-compatible 端点

v0.7.1 起，HDL 文件监视器不再自动调用 sync-sources，避免后台 XML 突变。所有源文件与 IP 实例到工程 XML 的同步须通过 §5.4 命令手动触发。

A5. 接口设计范式变更（v0.7.2 新增）

v0.7.2（2026-07-19）引入原生 DesignAPI 集成，SDK 不再依赖 Efinity GUI 修改接口设计。详见 §14 接口设计。
