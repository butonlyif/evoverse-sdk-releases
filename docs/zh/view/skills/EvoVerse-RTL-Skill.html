EvoVerse RTL Skill

EvoVerse RTL Skill

evoverse-rtl 用于一个边界明确的 RTL 生成或修改任务。自然语言描述所需行为，但真正允许修改什么、何时通过、能否进入正式基线，均由 EvoVerse 控制面的动作回执决定。

何时使用

  • 已有批准规格和一个可独立验证的叶子模块或子任务。
  • 需要对交付 RTL 同时执行候选冻结（含 RTL Design Assurance）和仿真门禁。
  • 希望保留已有工程作为只读基线，防止 Agent 把无关 RTL、测试资产或约束一起改掉。

它不替代自由开发。普通 Agent 编辑和 Build 仍然可用，不会被本 Skill 阻塞；但它们不自动获得本 Skill 的候选、隔离和晋升证据。

在 Trae 中调用

打开包含批准规格的工程，在对话中明确唯一任务、规格来源、目标 RTL 路径、仿真源和只读依赖。例如：

/evoverse-rtl
根据 design-package/specification.md 实现视频帧写入控制器。交付到 rtl/frame_writer.sv；
保留 sim/frame_writer_tb.sv 与 sim/models/ 作为验证源；rtl/common/ 必须只读。
请先展示任务范围和控制面回执，再开始生成。

如果接口、位宽、寄存器图、时钟/复位域、Oracle 或硬 IP 模型仍有歧义，Skill 会停止并要求先回到 /evoverse-design-spec 决策或更新规格。

受控生命周期

  1. 读取工程、规格和依赖，不修改任何文件。用 project_status 读取当前 revision 与活动 Intent。
  2. 用 project_next 读取当前允许的动作，确定 intent.create（新增量）等前置动作；向客户展示范围与选定动作，客户确认后用 project_execute 执行，expectedRevision 必须等于最近一次读到的 revision。
  3. 仿真等级先于规格（用户选择）：可靠迭代在 spec.draft 起草规格前必须先确认仿真等级，否则控制面以 SIMULATION_PROFILE_REQUIRED 阻塞起草。Agent 从用户需求、材料与拓扑提取 riskFacts 提交 simulation.profile.select；控制面按固定风险规则给出推荐（FPGA_FUNCTIONAL / FPGA_INTEGRATION / HIGH_ASSURANCE），向客户解释后由用户选择（低于推荐最低等级必须记录 acceptedRisks）。规格按所选等级的预算编写；超出预算时控制面要求超出预算重新确认，不得静默裁剪或扩大范围。
  4. 把完整声明的文件集写到本地暂存目录（绝不直接写正式 RTL），用 project_execute 执行 candidate.deliver：一次提交完整候选集。可靠模式在这一步只冻结候选并执行 RTL Design Assurance，不晋级基线。
  5. 用 project_execute 执行 verification.simulate，显式选择 iverilog 或 questa 后端；服务按所选等级的阻塞义务编译候选 RTL 与保留的 TB、BFM、Oracle，并保存候选绑定证据。当前候选取得有效 PASS 且满足资格后，执行 candidate.promote 才安装可靠基线。等级限定的仿真通过（如 FPGA_FUNCTIONAL_PASS）不是硬件结论。
  6. 若出现 DUT_FAIL，保留失败需求与回执。单一证据充分的原因可用 diagnostic.repair.record 和 candidate.repair 定向修复一次；归因有歧义或修复仍失败时，用 diagnostic.options.propose 呈现依据、下一步检查、代价和不确定性，等待工程师通过 diagnostic.choice.select 判断。人的判断需要新证据核查；冲突时记录 diagnostic.finding.record 并及时沟通，不得当作 PASS。
  7. 每次动作后重新 project_status 读取新 revision，并报告已验证与尚未验证的边界；延期事项逐项列出，NATIVE_BUILD_PENDING 与 BOARD_VALIDATION_REQUIRED 独立报告。

流程走歪或旧状态无法继续时，Agent 只能解释服务端恢复描述并让客户确认，不能自行重置运行时。恢复描述固定列出保留、替换、丢弃、步骤与成功检查，并绑定当前 revision；旧计划不能跨 revision 使用。控制面发现非终态没有真实出口时，project_next 返回 RECOVERY_REQUIRED 和唯一的 recovery.open，其 inputPreview 必须原样提交；恢复记录落盘后重新读取，只执行服务端暴露的 recovery.quarantine 等安全出口。Quarantine 保留可信 baseline、事实历史和失败证据，只释放受影响范围，不等于交付成功。INITIAL_DESIGN 放弃会原子关闭 Intent 和初始系统集成，不创建不存在的 worktree execution。

仿真器“可用”要求版本探测后完成最小真实编译、运行和事件解析。已选 Questa/Icarus 任一步失效时，控制面进入 WAITING_FOR_USER，只接受显式 re-probe 或 reselection；不会自动切换后端，失败前也不会写仿真 PASS 证据。

project_status、project_next、project_execute（另有 evoverse_health 健康检查）是这条流程的 MCP 协议；对应控制面动作由 project_next 给出，包括 intent.create、simulation.profile.select、candidate.deliver、verification.simulate、candidate.promote 和失败时的诊断动作。MCP 工具快照缺少稳定接口时，必须先刷新 MCP，不能用通用验证工具或直接 CLI 命令替代阶段动作。

RTL Design Assurance 与仿真门禁

RTL Design Assurance 不是普通 Coding Style Check。它检查候选生产 RTL 的结构、时钟、复位、CDC、状态机、FIFO、数据完整性和协议契约；不能由静态检查证明的动态义务保持 incomplete，不会被当作 PASS。Assurance 在 candidate.deliver 内由服务执行，不回执 PASS 就不算交付成功。

仿真门禁必须使用 verification.simulate：候选生产 RTL 与 TB/BFM/Oracle 一起运行，且测试资产本身也要通过资格审查。测试平台损坏、Oracle 含糊、模型缺失、超时或覆盖不足都不能归因给 DUT，更不能把 RTL 视为已验证。临时编译输出留在项目外暂存目录，不进入正式工程；晋级时服务只安装已声明的 RTL 与保留的 sim/ 源。

结果和剩余边界

交付成功说明这一个任务拥有范围回执、规则结果和仿真证据。它不自动证明 Efinity 原生编译、时序、硬 IP 内部行为、板级连接或硬件显示结果——这些分别由 build.native、hardware.program、hardware.validate 独立取证。Skill 完成时应明确列出这些尚需执行的步骤，并将下一层任务保持锁定，直到当前证据完整。

停止条件

控制面不可用、project_execute 返回失败、回执缺失、写入超出声明范围、规格未批准或验证结论为 fail/incomplete 时，Skill 必须停止。已有工程文件默认按字节哈希作为只读基线；依赖于编译的文件不因此变成可写文件，发现问题应报告为基线债务而非静默修复。

高级参考用于按需查询；设计记录、发布流程、审计报告和未来规划不属于客户操作入口。
